# 指令：线上问题定位与热修

## 热修与普通修复的唯一区别

**热修牺牲设计质量，不能牺牲可追溯性。**

| 项 | 普通修复 | 热修 |
|---|---|---|
| 设计完备性 | 要求 | **可以妥协**（先止血） |
| 故障单号 | 建议 | **强制** |
| 先写复现用例 | 建议 | **强制** |
| 提交信息带 FN | 强制 | **强制** |
| 补测试用例 | 视情况 | **24 小时内强制补** |

妥协的是"修得漂亮"，不妥协的是"事后能查清"。

## 四道强制工序

### 1. 有故障单号

无单号的热修，事后无法回答：谁发现的、影响谁、什么时候开始的、影响面多大。
**没单号就先建单**，不要"先修了再说"。

### 2. 先写复现用例

顺序不能反：

| 顺序 | 用例的作用 |
|---|---|
| 先写用例 → 再修复 | ✅ 证明"问题确实存在过" |
| 先修复 → 再补用例 | ❌ 只能证明"实现现在是这样" |

**先写的用例，修复前必须是失败的。** 跑一遍确认——这步是验证用例真的复现了问题，
而不是写了个恒过的用例走形式。

### 3. 提交信息带 FN 编号

```
fix(FN-CORE-045): 修正导出并发写入导致的缓存不一致
```

与常规开发同等要求。热修不走快车道豁免追溯链。

### 4. 24 小时内补测试用例

热修常跳过单测（时间压力下合理）。但**必须补上**，并登记待办。

补的不是"证明修复正确"的用例，而是**防止同类问题复发**的用例——
所以它应该照着重现触发条件来设计，而不是照着修复后的实现来写。

## 先定位根因，不要猜着改

线上压力下最诱人的做法是"先改改看会不会好"。**不要这样做。**

猜着改有三个后果：

1. 故障时长可能因引入新问题而延长
2. 即使"好了"，你也不知道为什么好了——同类问题必然复发
3. 掩盖了根因，后续排查者面对的是被改乱的现场

**定位不了根因时**：停止修改，输出已排除的可能与下一步排查方向（要看哪段日志、哪个时间点、
哪个指标）。这是有价值的输出，比"改改看"强。

## 复现用例的写法

```java
@Test
void should_not_leak_cache_when_concurrent_write_within_1s() {
    // 触发条件：同一项目 1 秒内两次写入
    ...
    // 修复前：第二次写入后读取到旧值（此用例失败）
    // 修复后：读到新值（此用例通过）
    assertEquals(newValue, readAfterSecondWrite);
}
```

用例名里直接写上**触发条件**，它同时也是给未来读代码的人的说明。

## 最小修复，不顺手重构

热修期间改无关代码 = 在故障恢复过程中引入新的不确定性。

如果发现旁边有该重构的地方：**记下来**（进 `ai-daily-03-techdebt` 或台账），
**但不要在热修时动它**。

## 需要改契约或表结构时

**拒绝热修。**

即使线上紧急，契约变更影响前端与外部调用方、表结构变更影响存量数据——
这两类不能靠"先改了再说"处理。

紧急情况下正确的做法是**止血而非变更**：

| 止血手段 | 说明 |
|---|---|
| 功能降级开关 | 关掉出问题的能力，先恢复可用性 |
| 回滚到上一版本 | 如果回滚代价小于修复代价 |
| 数据修正脚本 | 仅修正数据，不改结构 |

止血之后，变更本身仍走完整流程。

## 复盘要写「触发条件」

| 项 | 回答 | 用途 |
|---|---|---|
| 根因 | 为什么出错 | 修复 |
| **触发条件** | **什么情况下会出错** | **预防** |

只记根因的复盘，下次还会出——没人知道该在什么条件下警惕它。

例：

- 根因：缓存未失效
- **触发条件：同一项目在 1 秒内被两次写入**

后者才能变成一条可检查的规则或一条回归用例。

## 完成后

1. 登记故障复盘到 `09_资产库/故障案例库/线上问题复盘.md`
2. 登记 24 小时内补测试用例的待办
3. 提示：若本次故障暴露了结构性问题，应一并记入 `ai-daily-03-techdebt`

## 你绝对不要做的事

- 不要在无故障单号时开工
- 不要先修复再补用例（顺序反了用例就没意义了）
- 不要在根因未定位时"改改看"
- 不要顺手重构
- 不要接受需要改契约或表结构的热修（止血可以，变更不行）
- 不要执行 git 操作

## 输出格式

```
故障单号：INC-20261020-003
现象：列表页偶发显示旧数据，11:20 起，影响 3 个租户
定位过程：
  排除：数据库写入正常（查了 binlog）
  排除：缓存服务健康（指标正常）
  确认：并发写入时缓存失效消息丢失
根因：缓存失效走异步消息，同一项目 1 秒内两次写入时后一条消息被覆盖
触发条件：同一项目在 1 秒内被两次写入

复现用例：should_not_leak_cache_when_concurrent_write_within_1s（修复前确认失败）
修复：改为携带版本号的失效消息，提交 fix(FN-CORE-045)
补测试待办：24 小时内（已登记）

需变更契约/表结构：否
后续技术债：异步失效链路缺少版本控制，建议重构（已记入台账）
```
