# ai-daily-02-hotfix · 线上问题定位与热修

## 能力声明

线上问题的**定位与热修**：定位 → 写复现用例 → 修复 → 补测试。

**热修牺牲的是设计质量，不能牺牲的是可追溯性。** 这是本 Skill 与普通修复的唯一区别。

**不做什么**：不顺手重构、不改契约与表结构、不做长期方案设计、不做上线后的验证——见「边界」。

## 何时用 / 何时不用

- **用**：线上故障，有故障单号，要定位并止血/修复时
- **不用**：测试阶段发现的缺陷——那不是线上问题，走常规修复流程
- **不用**：修复需要改契约或表结构——走完整流程；紧急时的正确做法是**止血而非变更**（见失败处理）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 故障单号 | 用户提供 | 是 | **无单号不热修**——无单号的热修无法追溯 |
| 故障现象 | 用户提供 / 监控 | 是 | 含发生时间、影响范围 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 技术约束 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 复现用例 | 项目代码仓 | **先于修复代码**存在 |
| 修复代码 | 项目代码仓 | 提交信息格式 `fix(<FN编号>): <描述>` |
| 故障记录 | `09_资产库/故障案例库/线上问题复盘.md` | 现象 / 影响 / 根因 / 触发条件 / 修复 / 预防 |

产出结构——复现用例（**用例名里直接写上触发条件**，它同时也是给未来读代码的人的说明）：

```java
@Test
void should_not_leak_cache_when_concurrent_write_within_1s() {
    // 触发条件：同一项目 1 秒内两次写入
    ...
    // 修复前：第二次写入后读取到旧值（此用例失败）
    // 修复后：读到新值（此用例通过）
    assertEquals(newValue, readAfterSecondWrite);
}
```

产出结构——提交信息：

```
fix(FR-CORE-045): 修正导出并发写入导致的缓存不一致
```

### 四道强制工序（与普通修复的区别）

| # | 工序 | 为什么不能省 |
|---|---|---|
| 1 | **有故障单号** | 无单号的热修无法追溯：谁发现的、影响谁、什么时候 |
| 2 | **先写复现用例** | 先写修复再补用例，等于"用例是照着实现写的"——它只能证明实现如此，不能证明问题存在过 |
| 3 | **提交信息带 FR** | 追溯链的最后一环，与常规开发同等要求 |
| 4 | **24 小时内补测试用例** | 热修常跳过单测，补上是为了让同类问题不再复发 |

补的不是"证明修复正确"的用例，而是**防止同类问题复发**的用例——
所以它应该照着重现**触发条件**来设计，而不是照着修复后的实现来写。

与普通修复逐项对比、以及"先定位再改"为什么是硬要求，见 `references/热修要点.md`。

## 前置条件

**hard（不满足则拒绝执行）**

- 有故障单号（无单号时**拒绝**，要求先建单）
- 故障现象可描述（"系统有问题"不算描述）
- **是线上问题**：若不是（只是测试阶段发现的缺陷），提示应走常规修复流程，不走热修

**soft（不满足则提示，可继续）**

- 无。热修天然是"被故障推着走"的，不存在"没轮到"的情形——时间压力下可以妥协设计，
  但不能妥协上面三条

## 执行步骤

1. 定位根因。**先定位再改**——直接猜测性修改风险极高
2. **写复现用例**，确认它在修复前失败（这一步证明用例真的复现了问题，而不是写了个恒过的用例走形式）
3. 实施最小修复。**只修问题本身**，不顺手重构
4. 确认复现用例现在通过
5. 提交：`fix(<FN编号>): <描述>`
6. 记录故障复盘，含**触发条件**——它比根因更重要，决定如何预防
7. 收尾：把复盘登记到 `09_资产库/故障案例库/线上问题复盘.md`；登记 24 小时内补测试用例的待办；
   若本次故障暴露了结构性问题，一并记入 `ai-daily-03-techdebt`

### 「触发条件」比「根因」更重要

| 项 | 回答什么 | 用途 |
|---|---|---|
| 根因 | 为什么出错 | 修复 |
| **触发条件** | 什么情况下会出错 | **预防** |

例："缓存未失效"是根因，而"当同一项目在 1 秒内被两次写入时"才是触发条件，
后者才能变成一条可检查的规则或一条回归用例。只记根因的复盘，下次还会出。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——线上故障本来就可能是单点事项
- 本 Skill 没有 soft 前置
- 批次状态文件不可写（故障单常不属于任何批次）时：复盘照样写入故障案例库、
  待办照样登记，并在报告中说明未回写批次状态

## 边界（明确不做）

- **不顺手重构。** 热修时改无关代码 = 在故障恢复过程中引入新的不确定性；
  发现该重构的地方**记下来**（进 `ai-daily-03-techdebt` 或台账），但不要在热修时动它
- 不改契约、不改表结构（这两类需要走完整流程，即使线上紧急）
- **不在根因未定位时修改代码**
- 不做长期方案设计（那是后续排期的技术债）
- 不做上线后的验证（那是回归）
- 不要在无故障单号时开工
- 不要先修复再补用例（顺序反了用例就没意义了）
- 不要接受需要改契约或表结构的热修（止血可以，变更不行）
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 无故障单号 | **拒绝执行**，要求先建单 |
| 根因定位不了 | 停止，输出已排除的可能与下一步排查方向（要看哪段日志、哪个时间点、哪个指标）。**不要"先改改看"** |
| 修复需要改契约或表结构 | **拒绝热修**，说明需走完整流程（紧急时可先降级/回滚止血，但变更本身要走流程） |
| 复现用例写不出来 | 说明现象本身还不够明确，先补充信息（日志、时间点、影响范围） |

**止血手段**（紧急但不做变更）：功能降级开关 / 回滚到上一版本 / 数据修正脚本（仅修正数据，不改结构）。
各自的适用场景见 `references/热修要点.md`。

## 输出格式

```
故障单号：INC-20261020-003
现象：列表页偶发显示旧数据，11:20 起，影响 3 个租户
定位过程：
  排除：数据库写入正常（查了 binlog）
  排除：缓存服务健康（指标正常）
  确认：并发写入时缓存失效消息丢失
根因：缓存失效走异步消息，同一项目 1 秒内两次写入时后一条消息被覆盖
触发条件：同一项目在 1 秒内被两次写入

复现用例：should_not_leak_cache_when_concurrent_write_within_1s（修复前确认失败）
修复：改为携带版本号的失效消息，提交 fix(FR-CORE-045)
补测试待办：24 小时内（已登记）

需变更契约/表结构：否
后续技术债：异步失效链路缺少版本控制，建议重构（已记入台账）
```
