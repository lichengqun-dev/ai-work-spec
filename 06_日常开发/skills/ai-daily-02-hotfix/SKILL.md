# 能力声明

线上问题的**定位与热修**：定位 → 写复现用例 → 修复 → 补测试。

**热修牺牲的是设计质量，不能牺牲的是可追溯性。** 这是本 Skill 与普通修复的唯一区别。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 故障单号 | 用户提供 | 是 | **无单号不热修**——无单号的热修无法追溯 |
| 故障现象 | 用户提供 / 监控 | 是 | 含发生时间、影响范围 |
| 生效规范快照 | `.ai/spec-effective/<项目码>.md` | 是 | 技术约束 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 复现用例 | 项目代码仓 | **先于修复代码**存在 |
| 修复代码 | 项目代码仓 | 提交信息格式 `fix(<FN编号>): <描述>` |
| 故障记录 | `09_资产库/故障案例库/线上问题复盘.md` | 现象 / 影响 / 根因 / 触发条件 / 修复 / 预防 |

## 四道强制工序（与普通修复的区别）

| # | 工序 | 为什么不能省 |
|---|---|---|
| 1 | **有故障单号** | 无单号的热修无法追溯：谁发现的、影响谁、什么时候 |
| 2 | **先写复现用例** | 先写修复再补用例，等于"用例是照着实现写的"——它只能证明实现如此，不能证明问题存在过 |
| 3 | **提交信息带 FN** | 追溯链的最后一环，与常规开发同等要求 |
| 4 | **24 小时内补测试用例** | 热修常跳过单测，补上是为了让同类问题不再复发 |

## 前置条件（不满足则拒绝执行）

- 有故障单号（无单号时**拒绝**，要求先建单）
- 故障现象可描述（"系统有问题"不算描述）
- **若不是线上问题**（只是测试阶段发现的缺陷）→ 提示应走常规修复流程，不走热修

## 执行步骤

1. 定位根因。**先定位再改**——直接猜测性修改风险极高
2. **写复现用例**，确认它在修复前失败（这一步证明用例真的复现了问题）
3. 实施最小修复。**只修问题本身**，不顺手重构
4. 确认复现用例现在通过
5. 提交：`fix(<FN编号>): <描述>`
6. 记录故障复盘（含**触发条件**——它比根因更重要，决定如何预防）
7. 登记 24 小时内补测试用例的待办

## 边界（明确不做）

- **不顺手重构。** 热修时改无关代码 = 在故障恢复过程中引入新的不确定性
- 不改契约、不改表结构（这两类需要走完整流程，即使线上紧急）
- **不在根因未定位时修改代码**
- 不做长期方案设计（那是后续排期的技术债）
- 不做上线后的验证（那是回归）

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 无故障单号 | **拒绝执行**，要求先建单 |
| 根因定位不了 | 停止，输出已排除的可能与下一步排查方向。**不要"先改改看"** |
| 修复需要改契约或表结构 | **拒绝热修**，说明需走完整流程（紧急时可先降级/回滚止血，但变更本身要走流程） |
| 复现用例写不出来 | 说明现象本身还不够明确，先补充信息（日志、时间点、影响范围） |

## 「触发条件」比「根因」更重要

| 项 | 回答什么 | 用途 |
|---|---|---|
| 根因 | 为什么出错 | 修复 |
| **触发条件** | 什么情况下会出错 | **预防** |

只记根因的复盘，下次还会出——因为没人知道该在什么条件下警惕它。

例："缓存未失效"是根因，而"当同一项目在 1 秒内被两次写入时"才是触发条件，
后者才能变成一条可检查的规则。
