# 指令：06_日常开发

> ⚠️ **本 Skill 尚未实现（P2 阶段交付）。** 收到调用请求时，明确告知用户本 Skill 未实现，
> **不得假装执行**——产生"看起来跑过了"的假象比不执行更危险，因为下游会基于假产出继续。

## 实现时应遵循的约束

以下几条是从已验证的 Skill（`01_需求设计` 域）中总结出的通用要求，实现时需要遵守：

### 1. 技术中立

技术细节**不在本文件中硬编码**，一律引用生效规范快照中的条目编号。

反例：prompt 里写「使用 `@Transactional(rollbackFor = Exception.class)`」
正例：prompt 里写「遵循生效快照中 `STD-SB*` 事务相关条目；快照未定义时向用户询问，不自行决定」

这样换技术栈只需新增一个规范包，不需要重写 Skill。

### 2. 不确定就停下

信息不足时，输出待澄清清单并中止，**不臆造**。

流水线里最贵的错误是"看起来跑完了但产出是编的"——错误会逐级放大：
上游猜错 → 中游按错的做 → 下游按错的验证且全部通过 → 上线才发现。

### 3. 产出物结构单元必须携带编号

`REQ` / `FN` / `API` / `TBL` / `TC` / `BUG` / `DEC` 等，按 `00_工作空间配置/命名与编号规范.md` 申请。

**不携带编号的产出物等于不可追溯**，下游无法按编号定位，覆盖率与断链检测都无法进行。

### 4. 读快照，不读包

执行前读 `.ai/spec-effective/<项目码>.md`。**不要自己去读 `09_资产库/规范包/` 下的多层文件做合并**——
合并在构建期已完成，运行时合并会导致结果不一致、冲突被静默吞掉。

### 5. 不越界

严格遵守 `SKILL.md` 的「边界（明确不做）」一节。AI 天然倾向"顺手多做一点"，这在流水线里是灾难——
会导致产出物互相覆盖、职责边界模糊、失败时无法定位是哪个环节出的问题。

### 6. 不执行 git 操作

除非用户当次明确要求。

## 填充指引

实现本 Skill 时，本文件应包含：

1. 明确的触发条件（什么情况下调用）
2. 读取哪些文件（含按需读取的 references）
3. 逐步的执行步骤（可判定，不含"适当处理"这类表述）
4. 产出物的精确结构与编号要求
5. 失败时应该停下还是继续，以及停下时的输出格式
