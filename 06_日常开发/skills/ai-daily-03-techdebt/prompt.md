# 指令：技术债识别与排期建议

## 一条纪律：每条债项都要有数字

| ❌ 无依据 | ✅ 有依据 |
|---|---|
| 「导出模块代码有点乱，建议重构」 | 「FN-CORE-045 近 30 天被改动 7 次（台账），其中 3 次为兼容性修补」 |
| 「这块性能可能有隐患」 | 「该模块近 60 天 2 次故障（复盘 INC-003、INC-009），均为缓存失效链路」 |
| 「测试覆盖不足」 | 「该模块缺陷数占本季度 34%（缺陷台账），且集中在上传路径」 |

**没有数字的条目不要写进清单。**

理由：清单里混入"我觉得"的条目后，读者无法区分哪些是真问题、哪些是个人偏好。
几次之后，整份清单会被当成意见集合，也就排不进计划了。

## 四类信号及其实操判据

| 信号 | 数据来源 | 判据（示例阈值，可按项目调） |
|---|---|---|
| 高频改动 | 快车道台账 | 同一 FN 30 天内改动 ≥5 次 |
| 反复出问题 | 故障复盘 | 同一模块 60 天内故障 ≥2 次 |
| 缺陷集中 | 缺陷台账 | 某模块缺陷占比 > 全部模块的 25% |
| 改动风险高 | 依赖关系图 | 被 ≥10 个 FN 依赖，且处于高频改动区 |

阈值可以调，但**要有阈值**。没有阈值的"高频"和"集中"都是主观判断。

## 分析步骤

```
1. 台账按 FN 聚合 → 改动次数排名
2. 故障复盘按模块聚合 → 故障次数排名
3. 缺陷台账按模块聚合 → 缺陷占比
4. 依赖图 → 每个候选的影响面
5. 交叉：既是高频改动、又被广泛依赖、又反复出问题 → 优先级最高
```

第 5 步的交叉最有价值。单独看"改得多"可能只是这个功能在持续迭代（正常），
但如果它同时"被很多人依赖"且"反复出故障"，那就是真债。

## 清单格式

```markdown
## 技术债清单

### TD-001 导出模块（FN-CORE-045）

**依据**
- 快车道台账：近 30 天改动 7 次（2026-09-21 ~ 2026-10-20）
- 故障复盘：1 次（INC-20261020-003，缓存失效链路）
- 依赖关系图：被 3 个 FN 依赖

**问题判断**：导出能力在持续叠加（分组维度、格式、结果列），每次改动都是打补丁式扩展，
原始设计的「单一导出任务」模型已不适用。

**影响面**：中等——3 个下游 FN，但均为主流程。

**建议处置**：重构为可扩展的导出任务模型；建议在下次迭代清出独立批次。

**优先级**：高（改动频率 + 故障均集中于此）

---

### TD-002 …（未达到阈值的候选不列入）
```

## 样本不足时

台账覆盖时间 < 4 周时，**产出结果但明确标注**：

```
⚠️ 样本说明：台账覆盖 12 天，样本不足。以下结论仅供参考，
建议积累到 4 周后重新分析。
```

标注比不标注好，不标注比乱给结论好。

## 空台账时

**拒绝执行。** 不要凭代码阅读给出"技术债清单"——
那是代码评审的结论，不是技术债分析的结论，两者的可信度差一个量级。

告诉用户：技术债识别的输入是运行数据，先积累台账。

## 不做的事

- **不自动重构。** 只识别与建议，实施由人排期后走常规流程
- **不评价代码风格。** 风格问题交给 lint，不占用技术债额度——
  把风格塞进来会让清单变长、重点变模糊
- 不排期、不分配资源

## 完成后

写入 `.ai/index/技术债清单.md`，并输出摘要（本次新增几项、优先级分布、相比上次的变化）。

## 输出格式

```
分析周期：2026-09-21 ~ 2026-10-20（30 天）
输入：快车道台账 42 条、故障复盘 2 条、缺陷台账 31 条

新增债项：3 项
  TD-001 导出模块        优先级 高（改动 7 次 + 1 次故障 + 被 3 个 FN 依赖）
  TD-002 列配置服务      优先级 中（改动 5 次，但无故障、影响面小）
  TD-003 上传路径        优先级 中（缺陷占比 34%）

未列入：4 个候选未达阈值（列出但不建议排期）
样本说明：台账覆盖 30 天，样本充分
```
