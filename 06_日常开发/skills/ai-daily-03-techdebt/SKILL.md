# 能力声明

从**快车道台账、故障复盘、缺陷台账**中识别技术债，输出带依据的排期建议。

**核心纪律：技术债必须有数据依据。** "我觉得这块代码有点乱"排不进任何计划——
"这块一个月被改了 7 次"才能。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 快车道台账 | `projects/<项目码>/.agent/index/快车道台账.md` | 是 | 含时间、FN、改动摘要 |
| 故障案例库 | `09_资产库/故障案例库/线上问题复盘.md` | 否 | 存在则纳入分析 |
| 缺陷台账 | 项目文档仓 | 否 | 存在则纳入分析 |
| 依赖关系图 | `projects/<项目码>/.agent/index/依赖关系图.md` | 否 | 用于判断影响面 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 技术债清单 | `projects/<项目码>/.agent/index/技术债清单.md` | 每项含：位置、依据（数据）、影响面、建议处置、优先级 |

## 识别依据（必须来自数据，不来自感觉）

| 信号 | 数据来源 | 说明 |
|---|---|---|
| **高频改动** | 快车道台账 | 同一 FN 在 N 天内被改 ≥M 次 → 该处设计可能不适用 |
| **反复出问题** | 故障复盘 | 同一模块 N 次故障 → 结构性问题而非偶发 |
| **缺陷集中** | 缺陷台账 | 同一模块缺陷占比显著高于其他 |
| **影响面大** | 依赖关系图 | 被很多 FN 依赖的模块，改动风险高 |
| **热修遗留** | 故障复盘 | 热修往往只止血，遗留了长期方案 |

## 前置条件（不满足则拒绝执行）

- 快车道台账存在且有数据（**空台账时拒绝**——没有数据就没有依据，见失败处理）
- 台账覆盖时间足够（建议 ≥4 周；数据太少时结论不可靠）

## 执行步骤

1. 统计快车道台账：按 FN 聚合改动次数
2. 统计故障复盘与缺陷台账：按模块聚合
3. 结合依赖关系图判断影响面
4. 对每个候选债项**列出数据依据**（具体数字，不是形容）
5. 给出建议处置与优先级
6. 写入技术债清单

## 边界（明确不做）

- **不给没有数据依据的债项。** "代码可读性差"不是债项，除非能给出具体证据
- 不排期、不分配资源（那是人的决策）
- **不自动重构**（本 Skill 只识别与建议）
- 不评价代码风格——风格问题应由 lint 解决，不占用技术债额度

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 快车道台账为空 | **拒绝执行**，说明无数据依据；建议先运行一段时间台账再分析 |
| 台账覆盖时间 < 4 周 | 产出结果但**明确标注"样本不足，结论仅供参考"** |
| 某项只有感觉没有数据 | **不列入清单**——列进去会让整份清单的可信度下降 |

## 为什么必须带数据依据

清单一旦混入"我觉得"的条目，读者就无法区分哪些是真问题、哪些是个人偏好。
**几次之后，整份清单会被当成意见集合而不是工作依据**，也就排不进计划了。

给数据依据的成本很低（台账里数一下），但它决定了这份清单有没有用。
