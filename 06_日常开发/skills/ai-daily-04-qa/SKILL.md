# ai-daily-04-qa · 基于知识库的日常答疑

## 能力声明

基于知识库回答日常提问，例如「这个字段为什么这么设计」「这条规则是谁定的」「当时为什么选了 A 不选 B」。

**这是只读路径：只回答，不产生任何改动。** 它**不建批次、不写产出物、不跑门禁、不改代码与规范**——
唯一例外见「边界」。要产生改动的任务走各自的流程 Skill，不要用本 Skill 顺手改。

**本 Skill 是知识库"有没有用"的直接检验。** 判断一套知识库是否成功的信号之一：
工程师遇到这类问题时，第一反应是查知识库而不是问人。

## 何时用 / 何时不用

- **用**：问的是"为什么这么设计""这条规则是谁定的""某个编号对应什么"这类**知识库里记过**的问题；任何时候
- **不用**：需要实时数据（"生产上现在是多少"）、需要读代码逻辑（"这个方法是干什么的"）
- **不用**：需要人决策（"这条规范该不该改"）——指出谁是 Owner 与修改流程，不代替决定
- **不用**：提问背后要做改动（改代码 / 改规范 / 建批次）——那些走对应流程 Skill，本 Skill 只读

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 提问 | 用户 | 是 | 能判断问题类型（规范 / 历史决策 / 编号 / 机制） |

## 产出契约

| 产出 | 交付方式 | 要求 |
|---|---|---|
| 回答 | 对话 | **必须标注来源**（哪个文件、哪一节、哪个条目编号） |

不标来源的回答无法被复核，也无法被追问。**能被追问是知识库回答与"聊天"的区别。**

产出结构——带来源的回答：

```
这是 `projects/<项目码>/.agent/spec-effective/<项目码>.md` 的常驻注入项，条目 `STD-VUE3-004`：
面向用户的文案必须走 i18n，禁止硬编码中文。

为什么：`STD-VUE3-004` 的「原因」写的是——硬编码文案在切语言时会残留，
而这类问题通常到测试后期才发现，返工面很大。
```

产出结构——**找不到时**（这三样必须齐全）：

```
这个问题在知识库里没有答案。

应该记在哪：`projects/<项目码>/项目约定.md`
建议补记：<一句话描述该记什么>

如果你确定答案，我可以帮你记进去（需要你提供依据与时间）。
```

产出结构——多处相关但不完全一致时（**列出各处，不隐去分歧**）：

```
关于这个问题，知识库里有三处相关但不完全一致：

1. `projects/<项目码>/.agent/spec-effective/<项目码>.md` 的 `STD-BASE-412`：所有请求走封装模块
2. `projects/<项目码>/.agent/rules/接口约定.md` 的 `STD-PRJ-<项目码大写>-003`：本项目对 412 做了收窄——
   表单组件的请求可直连（原因：封装模块未覆盖文件上传场景）
3. `projects/<项目码>/.agent/memory/项目约定.md`：2026-09 记录「上传场景待封装模块支持后再收敛」

综合：当前应以项目级条目为准（它比域级更具体、且更新）；第 3 条是待办，尚未收敛。
```

## 前置条件

**hard（不满足则拒绝执行）**

- 提问可判断类型（能判断出它属于规范 / 历史决策 / 编号 / 机制哪一类）；
  判不出类型说明问题本身还没说清，要求补充而不是猜着检索

**soft（不满足则提示，可继续）**

- 无。本 Skill 任何时候都可使用——它没有上游产出物，也不写任何产出物

## 执行步骤

1. 判断问题类型，据此确定从检索顺序的哪一层开始
2. **按顺序找，不要跳**（见下）
3. 找到 → 引用来源回答（哪个文件、哪一节、哪个条目编号）
4. 多处相关但不完全对应 → 列出各处并说明差异，让提问者判断
5. 找不到 → 明说找不到，并给出"该记在哪 + 建议补记什么"
6. 超出知识库范围 → 说明这不属于知识库能回答的范围，给出该去哪查
7. 收尾：**不写任何文件**。本 Skill 无状态回写——它是只读路径

### 检索顺序（按优先级，不要跳）

| 顺序 | 位置 | 回答什么问题 |
|---|---|---|
| 1 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 现在该遵守什么规范 |
| 2 | `projects/<项目码>/.agent/project.yaml` | 这个项目用哪些包、有哪些项目特有差异 |
| 3 | 知识库根下 `09_资产库/规范包/`（C 段来源链指向的条目） | 某条规范为什么是这样、被谁改过 |
| 4 | `projects/<项目码>/.agent/index/功能编号总表.md` | 某个编号对应什么、谁引用了它 |
| 5 | `projects/<项目码>/.agent/state/<批次号>.yaml` | 某个批次当时做了什么、卡在哪 |
| 6 | 知识库根下 `README.md`（「核心机制」与「反模式与风险」两节） | 这套机制为什么这么设计 |
| 7 | 知识库根下 `09_资产库/故障案例库/`、`projects/<项目码>/.agent/memory/项目约定.md` | 历史上的坑与约定 |

**顺序有意义**：先看"现在的结论"，再往"为什么"追。反过来的话，你会拿一条已被覆盖的旧规则当答案。

为什么"找不到"要说出来、以及这个 Skill 为什么值得单独做，见 `references/答疑要点.md`。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——它本来就不在流水线上
- 本 Skill 没有 soft 前置：任何时刻都可单独运行
- **本 Skill 不写批次状态文件**（只读路径，无回写环节）；除「边界」里的那一项例外外，
  任何产出物都不落盘，回答只存在于对话中

## 边界（明确不做）

- **不臆测。** 找不到就说找不到——编一个看起来合理的答案，比说不知道的危害大得多，
  因为提问者会照着做
- 不回答需要实时数据的问题（"现在生产上这条数据是什么"）
- 不回答需要读代码逻辑的问题（那应该直接看代码）
- **不修改任何文件**（只读）：不改代码、不改规范、不改项目产出物、不建批次、不跑门禁
- 不评价规范是否合理（可以指出"这条是 X 时候定的"，但不代替 Owner 决定）
- 不要不给来源地回答（无法复核也无法追问）
- 不要隐去分歧只给一个"综合结论"
- 不要在无依据时补记内容
- 不要执行 git 操作

> **唯一的例外**：用户明确要求补记某条约定时，**且提供了依据**（内容、时间、来源），
> 才写入 `projects/<项目码>/.agent/memory/项目约定.md`。
> **没有依据的"补记"等于把猜测变成规范。** 这一例外不延伸到任何其它文件。

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 知识库里有明确答案 | 引用来源回答 |
| 有多处相关但不完全对应 | 列出各处并说明差异，让提问者判断；**不要自己"综合"出一个唯一答案然后隐去分歧** |
| 找不到 | **明说找不到**，并指出"这个信息应该记在哪" + 建议补记内容 |
| 问题需要运行代码 / 查实时数据 | 说明这不属于知识库能回答的范围，给出该去哪查（监控 / 数据库 / 日志） |
| 提问背后要做改动 | 说明本 Skill 只读、不产生改动，指向对应的流程 Skill |

## 输出格式

```
问题：为什么导出要用异步任务而不是同步返回？

找到（2 处）：
1. `<需求名>/02_设计/功能详细设计.md` §FN-CORE-045 —— 明确写了「导出走异步任务」
2. `projects/<项目码>/.agent/index/功能编号总表.md` 的接口段 —— `API-CORE-008` 返回 taskId 而非文件流

补充（设计决策记录）：
`<需求名>/02_设计/架构设计.md` 的 `DEC-CORE-001` 记录了理由——
「导出 1 万条耗时 12 秒，同步返回会让 HTTP 连接长时间占用；被否决的方案是分页流式返回，
否决原因是前端需要展示进度而非流式下载」

结论：设计决策记录里有明确答案，不是"顺手这么做"，而是权衡后的选择。
```

## 配套知识

| 内容 | 位置 | 何时读 |
|---|---|---|
| 知识索引 | `references/INDEX.md` | 每次开始前 |
| 为什么"找不到"是最有价值的输出、分歧为什么不能自己"综合"掉 | `references/答疑要点.md` | 找不到答案、或遇到互相矛盾的内容时 |
| **检索顺序** | 本 Skill 的 `SKILL.md`「检索顺序」节 | **按它找，不要跳** |
| 设计理由 | 知识库根下 `README.md`（机制层面的问题——为什么这么设计、哪些取舍是刻意的） | 问到机制设计时 |
| 规范包来源链 | 生效快照的 C 段（"这条规则是谁定的、被改过几次"） | 追"为什么是这样"时 |
| 项目约定 | 知识库根下 `projects/<项目码>/.agent/memory/项目约定.md`（尚未稳定为规范的共识） | 问到项目特有约定时 |

## 与其他 Skill 的关系

- 只读，不写任何文件（除经用户明确要求补记之外）
- 补齐缺口时：`ai-spec-promote`（规范层面）／`projects/<项目码>/.agent/memory/项目约定.md`（约定层面）
- 与 `ai-spec-build` 的分工：那个把多层规范合成快照；这个在快照之上答题
