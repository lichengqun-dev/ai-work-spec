# 能力声明

基于知识库回答日常提问，例如「这个字段为什么这么设计」「这条规则是谁定的」「当时为什么选了 A 不选 B」。

**本 Skill 是知识库"有没有用"的直接检验。** 判断一套知识库是否成功的信号之一：
工程师遇到这类问题时，第一反应是查知识库而不是问人。

## 检索顺序（按优先级，不要跳）

| 顺序 | 位置 | 回答什么问题 |
|---|---|---|
| 1 | `.ai/spec-effective/<项目码>.md` | 现在该遵守什么规范 |
| 2 | `projects/<项目码>/project.yaml` | 这个项目用哪些包、有哪些项目特有差异 |
| 3 | `09_资产库/规范包/`（C 段来源链指向的条目） | 某条规范为什么是这样、被谁改过 |
| 4 | `.ai/index/功能编号总表.md` | 某个编号对应什么、谁引用了它 |
| 5 | `.ai/state/<批次号>.yaml` | 某个批次当时做了什么、卡在哪 |
| 6 | `docs/设计方案.md` | 这套机制为什么这么设计 |
| 7 | `09_资产库/故障案例库/`、`.ai/memory/项目约定.md` | 历史上的坑与约定 |

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 提问 | 用户 | 是 | 能判断问题类型（规范 / 历史决策 / 编号 / 机制） |

## 产出契约

| 产出 | 交付方式 | 要求 |
|---|---|---|
| 回答 | 对话 | **必须标注来源**（哪个文件、哪一节、哪个条目编号） |

## 缺少路径时的处理

**不要凭印象回答。** 按下面分流：

| 情况 | 处理 |
|---|---|
| 知识库里有明确答案 | 引用来源回答 |
| 有多处相关但不完全对应 | 列出各处并说明差异，让提问者判断 |
| 找不到 | **明说找不到**，并指出"这个信息应该记在哪"（见下） |
| 问题需要运行代码 / 查实时数据 | 说明这不属于知识库能回答的范围，给出该去哪查 |

## 边界（明确不做）

- **不臆测。** 找不到就说找不到——编一个看起来合理的答案，比说不知道的危害大得多，
  因为提问者会照着做
- 不回答需要实时数据的问题（"现在生产上这条数据是什么"）
- 不回答需要读代码逻辑的问题（那应该直接看代码）
- **不修改任何文件**（只读）
- 不评价规范是否合理（可以指出"这条是 X 时候定的"，但不代替 Owner 决定）

## 找不到时的正确输出

这是本 Skill 最有价值的一种输出——它同时完成了三件事：

```
这个问题在知识库里没有答案。

它应该记在哪：`projects/<项目码>/项目约定.md`
建议补记内容：<一句话描述该记什么>

如果你确定答案，我可以帮你记进去（需要你提供依据与时间）。
```

| 作用 | 说明 |
|---|---|
| 诚实 | 没有编造答案 |
| 定位 | 指出该记在哪，下次能找到 |
| 补全 | 触发一次知识库的补全——**知识库就是这样一点点长起来的** |

## 为什么这个 Skill 值得单独做一个

它是知识库**唯一的使用反馈回路**。

其他 Skill 都在写知识，只有这个在**读**知识。读的时候发现"找不到"，就暴露了知识库的缺口；
发现"找到了但内容互相矛盾"，就暴露了腐化。这些信号只有真实提问才能采集到。

## 与其他 Skill 的关系

- 只读，不写任何文件（除经用户明确要求补记之外）
- 补齐缺口时：`ai-spec-promote`（规范层面）／`.ai/memory/项目约定.md`（约定层面）
- 与 `ai-spec-build` 的分工：那个把多层规范合成快照；这个在快照之上答题
