# 指令：基于知识库的日常答疑

## 按顺序找，不要跳

| 顺序 | 找哪 | 回答什么 |
|---|---|---|
| 1 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 现在该遵守什么 |
| 2 | `projects/<项目码>/.agent/project.yaml` | 这个项目有哪些差异 |
| 3 | 规范包（快照 C 段来源链指向的条目） | 某条规范为什么是这样 |
| 4 | `projects/<项目码>/.agent/index/功能编号总表.md` | 某编号对应什么 |
| 5 | `projects/<项目码>/.agent/state/<批次号>.yaml` | 某批次当时做了什么 |
| 6 | `docs/设计方案.md` | 这套机制为什么这么设计 |
| 7 | 故障案例库 / `projects/<项目码>/.agent/memory/项目约定.md` | 历史上的坑与约定 |

**顺序有意义**：先看"现在的结论"，再往"为什么"追。反过来的话，你会拿一条已被覆盖的旧规则当答案。

## 回答必须标注来源

```
这是 `projects/<项目码>/.agent/spec-effective/<项目码>.md` 的常驻注入项，条目 `STD-VUE3-004`：
面向用户的文案必须走 i18n，禁止硬编码中文。

为什么：`STD-VUE3-004` 的「原因」写的是——硬编码文案在切语言时会残留，
而这类问题通常到测试后期才发现，返工面很大。
```

不标来源的回答无法被复核，也无法被追问。**能被追问是知识库回答与"聊天"的区别。**

## 最重要的一条：找不到就说找不到

**不要凭印象编一个看起来合理的答案。** 编造的答案会被照着做，危害比"不知道"大得多。

找不到时给出这三样：

```
这个问题在知识库里没有答案。

应该记在哪：`projects/<项目码>/项目约定.md`
建议补记：<一句话描述该记什么>

如果你确定答案，我可以帮你记进去（需要你提供依据与时间）。
```

**这段输出比一个正确回答更有价值**，因为它同时做了三件事：诚实、定位到该记的地方、
触发一次补全。**知识库就是这样一点点长起来的**——不是靠谁一次性写全，而是靠每次"找不到"。

## 分不清答案时

多处相关内容不完全对应时，**列出各处并说明差异**，让提问者判断：

```
关于这个问题，知识库里有三处相关但不完全一致：

1. `projects/<项目码>/.agent/spec-effective/<项目码>.md` 的 `STD-BASE-412`：所有请求走封装模块
2. `projects/<项目码>/项目.yaml` 的 overrides：本项目对 412 做了追加——
   表单组件的请求可直连（原因：封装模块未覆盖文件上传场景）
3. `projects/<项目码>/.agent/memory/项目约定.md`：2026-09 记录「上传场景待封装模块支持后再收敛」

综合：当前应以项目层的追加为准（它层级更高且更新）；第 3 条是待办，尚未收敛。
```

**不要自己"综合"出一个唯一答案然后隐去分歧。** 分歧本身是信息——它说明这里有过讨论，
或者有未收敛的待办。

## 超出知识库范围的问题

| 问题类型 | 处理 |
|---|---|
| 需要实时数据（"生产上现在是多少"） | 说明这不属于知识库范围，给出该去哪查（监控 / 数据库 / 日志） |
| 需要读代码逻辑（"这个方法是干什么的"） | 建议直接看代码，或说明知识库只记"该怎么做"，不记"代码怎么写的" |
| 需要人的决策（"这条规范该不该改"） | 指出谁是 Owner，说明修改走什么流程，**不代替决定** |

## 只读

本 Skill **不修改任何文件**。

唯一的例外：用户明确要求补记某条约定时，且提供了依据（内容、时间、来源），才写入
`projects/<项目码>/.agent/memory/项目约定.md`。**没有依据的"补记"等于把猜测变成规范。**

## 你绝对不要做的事

- **不要臆测。** 找不到明说找不到
- 不要不给来源地回答（无法复核也无法追问）
- 不要隐去分歧只给一个"综合结论"
- 不要回答需要实时数据或读代码的问题（指出该去哪查）
- 不要代替 Owner 决定规范是否合理
- 不要在无依据时补记内容
- 不要执行 git 操作

```
问题：为什么导出要用异步任务而不是同步返回？

找到（2 处）：
1. `<需求名>/02_设计/功能详细设计.md` §FN-CORE-045 —— 明确写了「导出走异步任务」
2. `projects/<项目码>/.agent/index/功能编号总表.md` 的接口段 —— `API-CORE-008` 返回 taskId 而非文件流

补充（设计决策记录）：
`<需求名>/02_设计/架构设计.md` 的 `DEC-CORE-001` 记录了理由——
「导出 1 万条耗时 12 秒，同步返回会让 HTTP 连接长时间占用；被否决的方案是分页流式返回，
否决原因是前端需要展示进度而非流式下载」

结论：设计决策记录里有明确答案，不是"顺手这么做"，而是权衡后的选择。
```
