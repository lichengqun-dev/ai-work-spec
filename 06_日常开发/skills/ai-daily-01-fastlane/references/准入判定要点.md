# 准入判定要点 · ai-daily-01-fastlane

> 本文件收纳"为什么这么判"的论证与正反例。**判据本身在 `SKILL.md` 的「准入判定」与「执行步骤」**，
> 这里只回答"为什么定成这样"。逐条核对准入、拿不准算不算跨模块、想跳过台账时读。

## 为什么判定必须先于实现

**不要先看改动、再决定要不要走快车道。** 顺序反了会有一个后果：改动做完了发现该走完整流程，
此时人已经投入进去了，于是"算了就这样吧"——**快车道就是这样被绕过的**。

## 最容易被放行的两类改动

**一、加一个字段。** "就在导出里多返回一列，很小的改动"——
但如果这一列来自新表或需要新的查询，它涉及表结构与后端逻辑，属于完整流程。

**二、改一个配置。** "配置改一下就行"——
如果这个配置影响对外行为（如分页上限、导出格式），那就涉及契约，前端可能依赖旧行为。

两类的共同点：**改动看起来小，但影响面在别的模块。** 判据不是"改多少个字"，
而是"谁会被影响"。

## 升级时要说清去哪

不要只说"这个不能走快车道"。要说：

```
本次改动涉及对外契约（导出响应新增 groupName 列）
→ 升级到完整流程：02_概要详细设计
→ 原因：前端已按旧契约实现，契约变更需通知前端负责人并走变更子批次
```

说清"为什么"和"去哪"，对方才知道下一步做什么。

## 为什么台账值得坚持

它是技术债的**唯一数据来源**。台账积累一个月后能得出具体结论——
「FN-CORE-045 一个月被改了 7 次」——而这比任何"我觉得这块该重构了"都有说服力，
因为它能排进计划。

没有台账，"这块代码有点乱"永远只是感觉。

## 为什么阈值要项目化

不同项目的模块粒度不同，同一个文件数阈值在 A 项目合适、在 B 项目可能过宽。
这类差异属于项目层，不该写进基线。
