# 能力声明

小需求的**快车道**：判定准入 → 精简实现 → 轻量评审 → 台账登记。

**设计原则：允许跳步，但必须留痕。**

日常开发占研发团队 40%–60% 的实际工时，却几乎在所有流程规范里被忽略——因为它们"太小了，
不值得走流程"。结果是这部分工作完全没有留痕，一个月后没人知道某个字段为什么变了。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 工单 / 小需求描述 | 用户提供 | 是 | 能判断改动范围 |
| 快车道准入标准 | `06_日常开发/standards/快车道准入标准.md` | 是 | 量化判据（`STD-BASE-701`） |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 技术约束 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 代码变更 | 项目代码仓 | 提交信息带 FN（沿用既有 FN 或按快车道规则编号） |
| **快车道台账** | `projects/<项目码>/.agent/index/快车道台账.md` | `日期 / 人员 / 涉及 FN / 改动摘要 / 准入判定 / 提交`（**表头不可改**） |

**台账是快车道的核心留痕机制，不是可选项。**

## 准入判定（必须量化，逐条核对）

| 条件 | 判据 |
|---|---|
| 改动范围 | 改动文件数 ≤ 阈值（按项目定，建议 5） |
| 契约 | **不涉及对外接口契约变更** |
| 数据模型 | **不涉及表结构变更** |
| 依赖 | **不涉及跨模块依赖** |

**任一不满足 → 强制升级**：涉及契约或表结构 → `02_概要详细设计`；跨模块 → `ai-iteration-01-impact`。

## 前置条件（不满足则拒绝执行）

- 改动可定位到具体文件（定位不了说明范围不明，不能判准入）
- 生效规范快照存在
- **准入判定四项已逐条核对**（不允许"看起来不大"就放行）

## 执行步骤

1. 逐条核对四项准入条件，输出判定结论与依据
2. 不满足 → 输出应升级到哪条流程，**停止**
3. 满足 → 精简实现（仍须遵循生效快照中的规范条目）
4. 轻量评审：自动检查（lint + 单测）通过即可，不需要 gate-04 的完整人工评审
5. **登记台账**：时间、人员、涉及 FN、改动摘要、准入判定的四项依据
6. 提交，提交信息带 FN 编号

## 边界（明确不做）

- **不放宽准入条件。** 不要因为"需求方催得紧"就把跨模块改动判成快车道
- **不跳过台账登记。** 台账不是审批流程，但不可省略
- 不写测试报告、不走完整门禁
- 不改契约、不改表结构（这两类一律升级）

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 改动超出阈值 | 升级到 `ai-iteration-01-impact`，输出判定依据 |
| 涉及契约变更 | 升级到完整流程，**明确说明前端会受影响** |
| 涉及表结构变更 | 升级，说明存量数据与回归范围的影响 |
| 改动范围无法确定 | 拒绝判定，要求先明确范围——**范围不明的改动不能进快车道** |

## 台账的价值：技术债的数据来源

台账积累一个月后，可以分析出：**某处一个月被改了七次，就是该重构的信号。**

这个结论只能从台账得出。没有台账，"这块代码有点乱"永远只是感觉，排不进任何计划。

## 与其他 Skill 的关系

- 上游：工单 / 小需求
- 升级去向：`ai-iteration-01-impact`（跨模块）／`02_概要详细设计`（契约或表结构）
- 下游：`ai-daily-03-techdebt`（从台账识别技术债）
- 规范依据：`STD-BASE-701`（准入量化）、`STD-BASE-702`（台账留痕）
