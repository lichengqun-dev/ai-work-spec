# ai-daily-01-fastlane · 小需求快车道

## 能力声明

小需求的**快车道**：判定准入 → 精简实现 → 轻量评审 → 台账登记。

**设计原则：允许跳步，但必须留痕。**

日常开发占研发团队 40%–60% 的实际工时，却几乎在所有流程规范里被忽略——因为它们"太小了，
不值得走流程"。结果是这部分工作完全没有留痕，一个月后没人知道某个字段为什么变了。

**不做什么**：不改对外契约、不改表结构、不写测试报告、不走完整门禁——
准入判定不满足的一律**升级**到对应流程，见「边界」。

## 何时用 / 何时不用

- **用**：小改动 / 工单 / 文案调整——先做准入判定，通过了才动手
- **不用**：涉及对外契约或表结构——升级到 `02_概要详细设计` 完整流程
- **不用**：涉及跨模块依赖——升级到 `ai-iteration-01-impact`
- **不用**：线上故障——走 `ai-daily-02-hotfix`

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 工单 / 小需求描述 | 用户提供 | 是 | 能判断改动范围 |
| 快车道准入标准 | `06_日常开发/standards/快车道准入标准.md` | 是 | 量化判据（`STD-BASE-701`） |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 技术约束 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 代码变更 | 项目代码仓 | 提交信息带 FN（沿用既有 FN 或按快车道规则编号） |
| **快车道台账** | `projects/<项目码>/.agent/index/快车道台账.md` | `日期 / 人员 / 涉及 FN / 改动摘要 / 准入判定 / 提交`（**表头不可改**） |

**台账是快车道的核心留痕机制，不是可选项。**

产出结构——台账行：

```markdown
| 日期 | 人员 | 涉及 FN | 改动摘要 | 准入判定 | 提交 |
|---|---|---|---|---|---|
| 2026-10-20 | 张三 | FN-CORE-020 | 导出行名修正 | 3 文件 / 无契约 / 无表 / 无跨模块 | abc1234 |
```

**表头不可改**——列名或列数一变，`ai-daily-03-techdebt` 按阈值统计就会解析失败，技术债识别随之失效。

**准入判定列必须写出四项依据**，不能只写"通过"——它决定了这条记录日后能否被复核：
"当时到底核对了没有，还是随手放行的"。

## 前置条件

**hard（不满足则拒绝执行）**

- 改动可定位到具体文件（定位不了说明范围不明，不能判准入）
- 生效规范快照存在
- **准入判定四项已逐条核对**（不允许"看起来不大"就放行）

**soft（不满足则提示，可继续）**

- 无。本 Skill 设计上就包含**纯工单（不走批次）**的形态，没有"顺序性"前置——
  批次状态回写与台账登记是两条并行的收尾路径（见「执行步骤」第 6 步）

## 执行步骤

1. 逐条核对四项准入条件，输出判定结论与依据（**这是第一件事，不是先看改动再决定**）
2. 不满足 → 输出应升级到哪条流程，**停止**
3. 满足 → 精简实现（仍须遵循生效快照中的规范条目）
4. 轻量评审：自动检查（lint + 单测）通过即可，不需要 gate-04 的完整人工评审
5. **登记台账**：时间、人员、涉及 FN、改动摘要、准入判定的四项依据
6. 收尾：提交，提交信息带 FN 编号；走了批次时回写批次状态文件，纯工单则直接登记台账

### 准入判定（必须量化，逐条核对）

| 条件 | 判据 | 不满足时 |
|---|---|---|
| 改动范围 | 改动文件数 ≤ 阈值（按项目定，建议 5） | 升级 `ai-iteration-01-impact` |
| 契约 | **不涉及对外接口契约变更** | 升级完整流程 |
| 数据模型 | **不涉及表结构变更** | 升级完整流程 |
| 依赖 | **不涉及跨模块依赖** | 升级 `ai-iteration-01-impact` |

每一项都要给出**依据**，不是"看起来没有"：

```
准入判定：
  ✅ 改动范围：3 个文件（ListPage.vue、ColumnConfig.ts、types.ts）≤ 5
  ✅ 对外契约：未改动任何 API 的请求/响应结构
  ✅ 表结构：未涉及
  ✅ 跨模块依赖：改动限于「列表页」模块内
  → 判定：可走快车道
```

**最容易被放行的两类改动**（"加一个字段"、"改一个配置"）为什么往往属于完整流程，
见 `references/准入判定要点.md`。

### 实现阶段仍要遵循规范

快车道跳过的是**流程**（设计评审、契约冻结、完整门禁），不是**规范**。
生效快照里的编码规范、安全基线、提交格式——一样要遵守。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——绝大多数工单就是这样用的
- 本 Skill 没有 soft 前置
- 批次状态文件不可写（纯工单、未接入批次）时：跳过状态回写，**直接登记台账**，
  并在报告中说明本次是纯工单形态

## 边界（明确不做）

- **不放宽准入条件。** 不要因为"需求方催得紧"就把跨模块改动判成快车道
- **不跳过台账登记。** 台账不是审批流程，但不可省略
- 不写测试报告、不走完整门禁
- 不改契约、不改表结构（这两类一律升级）
- 不要先实现再判定准入
- 不要把跨模块 / 契约 / 表结构变更判成快车道
- 不要在快车道里跳过规范（只跳流程）
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 改动超出阈值 | 升级到 `ai-iteration-01-impact`，输出判定依据 |
| 涉及契约变更 | 升级到完整流程，**明确说明前端会受影响** |
| 涉及表结构变更 | 升级，说明存量数据与回归范围的影响 |
| 改动范围无法确定 | 拒绝判定，要求先明确范围——**范围不明的改动不能进快车道** |
