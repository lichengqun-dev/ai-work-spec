# 指令：小需求快车道

## 你做的第一件事是判定，不是实现

**不要先看改动、再决定要不要走快车道。** 先逐条核对四项准入条件，判定通过了才动手。

顺序反了会有一个后果：改动做完了发现该走完整流程，此时人已经投入进去了，
于是"算了就这样吧"——**快车道就是这样被绕过的**。

## 四项准入条件，逐条核对

| 条件 | 判据 | 不满足时 |
|---|---|---|
| 改动范围 | 文件数 ≤ 阈值（按项目定，建议 5） | 升级 `ai-iteration-01-impact` |
| 对外契约 | **不涉及** | 升级完整流程 |
| 表结构 | **不涉及** | 升级完整流程 |
| 跨模块依赖 | **不涉及** | 升级 `ai-iteration-01-impact` |

每一项都要给出**依据**，不是"看起来没有"：

```
准入判定：
  ✅ 改动范围：3 个文件（ListPage.vue、ColumnConfig.ts、types.ts）≤ 5
  ✅ 对外契约：未改动任何 API 的请求/响应结构
  ✅ 表结构：未涉及
  ✅ 跨模块依赖：改动限于「列表页」模块内
  → 判定：可走快车道
```

**范围无法确定时拒绝判定。** 说不清要改哪几个文件的改动，不能进快车道——
它要么比想象的大，要么当事人还没想清楚。

## 最容易被放行的两类改动

**一、加一个字段。** "就在导出里多返回一列，很小的改动"——
但如果这一列来自新表或需要新的查询，它涉及表结构与后端逻辑，属于完整流程。

**二、改一个配置。** "配置改一下就行"——
如果这个配置影响对外行为（如分页上限、导出格式），那就涉及契约，前端可能依赖旧行为。

两类的共同点：**改动看起来小，但影响面在别的模块。** 判据不是"改多少个字"，
而是"谁会被影响"。

## 实现阶段仍要遵循规范

快车道跳过的是**流程**（设计评审、契约冻结、完整门禁），不是**规范**。

生效快照里的编码规范、安全基线、提交格式——一样要遵守。
跳过规范会让你修完一个小 bug、留下一个大坑。

## 台账必须登记

`.ai/index/快车道台账.md`：

```markdown
| 时间 | 人员 | 涉及 FN | 改动摘要 | 准入判定 |
|---|---|---|---|---|
| 2026-10-20 | 张三 | FN-CORE-020 | 导出行名修正 | 3 文件 / 无契约 / 无表 / 无跨模块 |
```

**为什么台账值得坚持**：它是技术债的唯一数据来源。

台账积累一个月后能得出具体结论——「FN-CORE-045 一个月被改了 7 次」——
而这比任何"我觉得这块该重构了"都有说服力，因为它能排进计划。

## 升级时要说清去哪

不要只说"这个不能走快车道"。要说：

```
本次改动涉及对外契约（导出响应新增 groupName 列）
→ 升级到完整流程：02_概要详细设计
→ 原因：前端已按旧契约实现，契约变更需通知前端负责人并走变更子批次
```

说清"为什么"和"去哪"，对方才知道下一步做什么。

## 完成后

回写批次状态文件（若走了批次）或直接登记台账（若为纯工单）。

## 你绝对不要做的事

- 不要先实现再判定准入
- 不要把跨模块 / 契约 / 表结构变更判成快车道
- 不要因为"催得紧"放宽准入
- 不要跳过台账登记
- 不要在快车道里跳过规范（只跳流程）
- 不要执行 git 操作
