**等级判定决定后续全部路径。** 判低了会跳过设计评审与契约冻结（前端可能已按旧契约写完代码）；
判高了会让小改动走重流程（团队会开始绕开流程）。

## 为什么迭代流程与新建流程有本质区别

**不是步骤少，而是存在基线。**

已交付的系统就是基线，新需求是在基线上的差异。所以核心动作不是"生成"，而是**对比**：

| | 新建流程 | 迭代流程 |
|---|---|---|
| 设计产出 | 完整的详细设计 | **差异说明**（改什么 / 为什么 / 原设计是什么 / 影响谁） |
| 文档 | 新写 | 原批次产出物**不可变**，另开变更子批次 |
| 追溯 | `REQ → FR → ...` | 加一层：`原批次 → 变更子批次` |

直接改原文档会让"上线那一刻的业务规则是什么"变成不可回答的问题——
而那是排查线上问题时判断"现在的行为对不对"的唯一依据。

## 四道边界（不接受绕过）

| 情况 | 处理 |
|---|---|
| 涉及**对外契约** | 转完整流程。前端与外部调用方受影响 |
| 涉及**表结构** | 转完整流程。存量数据、回滚方案、读写该表的所有 FR 受影响 |
| 影响等级为**大** | 转完整流程，**不接受降级为"中"来省流程** |
| 影响等级为**小** | 走 `06_日常开发` 的快车道，不走本域 |

**「涉及表结构一律判大」是刻意的。** 即使只加一个可空字段，所有读写该表的 FR 都在回归范围内——
把它判成"中"或"小"，是迭代流程里最高频的一类低估，而后果在回归阶段才暴露。

## 本域最容易塌掉的三个地方

**一、为了省流程把「大」降成「中」。** 这是最贵的一种省事：绕过了契约冻结，
而前端可能已经按旧契约写完代码了。`ai-iteration-01-impact` 与 `02-delta-spec` 都会拒绝这类降级。

**二、增量设计写成了重写全文。** 差异说明变成 200 页的新设计，结果是两份文档并存，
且没人知道哪份是当前的。正确做法是：写"改什么、为什么、原设计是什么、影响谁"，一页纸。

**三、发布说明里弱化遗留风险。** 发布说明是使用方唯一的知情渠道。把风险藏着，
等于让他们在不知情的情况下承担后果。

## 产出物去向

```
<项目文档仓>/docs/迭代/
├── <批次号>_影响面分析.md    ← 01-impact，受影响清单 + 影响等级 + 建议路径
├── <批次号>_增量设计.md      ← 02-delta-spec，**只写差异**（改什么 / 为什么 / 影响谁）
└── 变更登记.md               ← 03-change-control，变更项 + 基线对比 + 批准确认

<项目文档仓>/<需求名>/05_交付/
├── 上线步骤.md               ← 04-release，步骤 + **回滚方案**
└── 发布说明.md               ← 04-release，面向使用方的变更说明
```

其余落位：

| 产出 | 去向 |
|---|---|
| 变更子批次状态 | 本仓库 `projects/<项目码>/.agent/state/<原批次号>-C<n>.yaml`（`type: change`），由 `03-change-control` 创建 |
| 基线快照记录 | 原批次状态文件——**只追加不改**，记录被哪个子批次改动过 |
| 版本号 | 项目代码仓 |

**迭代目录用 `<批次号>_` 前缀而不是序号**——迭代是按批次发生的，不是一条线性流水线；
用序号会让人误以为有"第几个迭代"的全局顺序。

**原批次产出物不可变。** 变更走 `-C<n>` 子批次，不直接改原文档——否则"上线那一刻的业务规则是什么"
就变成不可回答的问题，而那是排查线上问题时判断"现在的行为对不对"的唯一依据。
