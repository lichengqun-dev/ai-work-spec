# 指令：变更登记与基线对比

## 你做的事

给一次对已交付功能的改动**建账**：它改了什么、为什么改、改之前是什么样。

你是账本，不是审批人。**批准变更的是人，你只负责登记得准确、完整、可追溯。**

## 分配子批次号

```
PROJ-20260901-003        ← 原批次
PROJ-20260901-003-C1     ← 第 1 次变更
PROJ-20260901-003-C2     ← 第 2 次变更
```

**n 从 1 递增，不跳号、不复用。** 删掉的子批次号也保留——看到 C3 就知道 C1、C2 存在过。
跳号会让"这个功能被改过几次"变成不可知的。

## 子批次状态文件

```yaml
batch: PROJ-20260901-003-C1
project: <项目码>
type: change
parent_batch: PROJ-20260901-003      # ← 关键字段，指向原批次
created: 2026-10-20T10:00:00+08:00
owner: <批次负责人>
current_step: delta-spec
# 其余按 .ai/state/_模板.yaml
```

`parent_batch` 是追溯链的关键：从子批次能回到原批次，从原批次能查到所有子批次。

## 变更登记要记录基线哈希

```markdown
## 变更项

| # | 改什么 | 为什么 | 基线（原批次产出物 + 哈希） | 影响谁 |
|---|---|---|---|---|
| D-01 | API-CORE-008 加 groupId | REQ-CORE-031 | 接口契约.yaml @ sha256:7f3a… | FN-CORE-045、TC-045-01~05 |
```

**基线哈希不能省。** 它是"改动之前长什么样"的唯一凭据。
没有它，半年后有人说"这个字段本来就有"，你无法反驳。

## 原批次状态文件：只追加，不修改

在原批次的 `gates` 或新增的 `changed_by` 段追加一条：

```yaml
changed_by:
  - batch: PROJ-20260901-003-C1
    at: 2026-10-20
    scope: [FN-CORE-045, FN-CORE-020]
```

**已有的内容一个字都不改。** 原批次记录的是"当时的事实"，
往里面插内容等于篡改历史记录——而那正是这套机制要防的事。

## 原批次没归档时

说明这个功能还在开发中，**直接在当前批次内改就行，不需要开子批次**。

不要"为了规范"强行开一个子批次——那会产生一堆无意义的 C1、C2，
让真正需要追溯的变更淹没在噪音里。

## 变更触及契约或表结构时

**拒绝登记。** 明确说明：

- 契约变更影响前端与外部调用方
- 表结构变更影响存量数据与所有读写该表的模块

这两类变更需要走完整流程（`02_概要详细设计`），因为它们的确认方不只是本项目。
把它们塞进变更子批次，等于绕过了契约冻结——而前端可能已经按旧契约写完代码了。

## 变更未获批准时

登记为"**待批准**"，不推进到实施。

不要因为"需求方在群里说了"就当成批准了。批准需要可查证的记录（谁、什么时候、同意了哪一版范围）。

## 完成后

回写子批次状态文件：本步骤置 `done`，登记变更登记文件与哈希。

## 你绝对不要做的事

- 不要修改原批次的产出物或状态文件里已有的内容
- 不要跳过 `parent_batch` 字段
- 不要省略基线哈希
- 不要为未归档的批次强行开子批次
- 不要登记触及契约或表结构的变更
- 不要代替人批准变更
- 不要执行 git 操作

## 输出格式

```
变更子批次：PROJ-20260901-003-C1
原批次：PROJ-20260901-003（已归档，2026-09-05）
变更项：3 项
基线哈希：
  - 接口契约.yaml @ sha256:7f3a…
  - 功能详细设计.md @ sha256:2b91…

原批次状态文件：已追加 changed_by 记录（未修改既有内容）
批准：待批准（需求方确认中）
触及契约：是 —— ⚠️ 需按流程确认，详见下方说明
```
