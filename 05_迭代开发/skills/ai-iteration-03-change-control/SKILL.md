# 能力声明

登记变更、与原基线对比、开变更子批次（`<原批次号>-C<n>`）。

**本 Skill 是变更的"账本"。** 它保证任何一次对已交付功能的改动都能被回答三个问题：
改了什么、为什么改、改之前是什么样。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 增量设计说明 | `ai-iteration-02-delta-spec` 产出 | 是 | 含差异项清单 |
| 影响面分析 | `ai-iteration-01-impact` 产出 | 是 | 含影响等级与建议路径 |
| 原批次状态文件 | `.ai/state/<原批次号>.yaml` | 是 | **`archived: true`**——原批次必须已归档 |
| 原批次产出物 | 项目文档仓 | 是 | 基线，**只读** |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 变更子批次状态 | `.ai/state/<原批次号>-C<n>.yaml` | 按 `.ai/state/_模板.yaml`，`type: change` |
| 变更登记 | 项目文档仓 `docs/迭代/变更登记.md` | 变更项 + 基线对比 + 批准确认 |
| 基线快照记录 | 原批次状态文件（**只追加不改**） | 记录被哪个子批次改动 |

## 前置条件（不满足则拒绝执行）

- 原批次状态文件存在且 `archived: true`（未归档批次直接改即可，无需开子批次）
- 增量设计说明已产出
- **变更未触及契约或表结构**（触及则应走完整流程，见失败处理）

## 执行步骤

1. 定位原批次的状态文件与产出物，记录**基线哈希**
2. 分配子批次编号 `<原批次号>-C<n>`（n 从 1 递增，不跳号）
3. 生成子批次状态文件，`type: change`，并记录 `parent_batch`（原批次号）
4. 逐个差异项登记：改什么、为什么、基线是什么、影响谁
5. 在原批次状态文件中**只追加**一条记录：被哪个子批次改动、改动日期
6. 回写批次状态文件

## 边界（明确不做）

- **不修改原批次的产出物**（一个字都不改）
- 不修改原批次状态文件里已有的内容（只追加）
- 不实施变更（那是增量开发）
- **不批准变更**——批准是人（需求方或技术负责人）的事，本 Skill 只做登记
- 不判断变更"值不值得做"

## 编号规则

| 项 | 规则 |
|---|---|
| 子批次号 | `<原批次号>-C<n>`，如 `PROJ-20260901-003-C1` |
| 递增 | n 从 1 开始，**不跳号、不复用**（删掉的子批次号也保留） |
| 同批次多次变更 | C1、C2、C3……各自独立 |

**不跳号的意义**：看到 C3 就知道 C1、C2 存在过。跳号会让"这个功能被改过几次"变成不可知的。

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 原批次未归档 | 说明可直接在当前批次内修改，无需开子批次；**不强行开** |
| 变更触及契约或表结构 | **拒绝登记**，说明需走完整流程（涉及前端、外部调用方、存量数据） |
| 变更未获批准 | 登记为"待批准"，**不推进到实施** |
| 原批次状态文件被外部修改 | 报告，由人确认后再继续（基线不可信时，对比也无意义） |

## 为什么原批次不可变

这是整个变更机制的地基。如果原批次产出物可以被改：

| 问题 | 能回答吗 |
|---|---|
| 上线那一刻的业务规则是什么？ | ❌ |
| 这次改动之前是什么样？ | ❌ |
| 那个缺陷是本次引入的，还是原来就有？ | ❌ |

三个问题都答不了，排障就只能靠回忆。
