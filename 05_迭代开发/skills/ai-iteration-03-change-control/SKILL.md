# ai-iteration-03-change-control · 变更登记与基线对比

## 能力声明

登记变更、与原基线对比、开变更子批次（`<原批次号>-C<n>`）。

**本 Skill 是变更的"账本"。** 它保证任何一次对已交付功能的改动都能被回答三个问题：
改了什么、为什么改、改之前是什么样。

**本 Skill 只做登记，不做审批。** 批准变更的是人（需求方或技术负责人）；也**不实施变更**、不判断变更"值不值得做"——见「边界」。

## 何时用 / 何时不用

- **用**：增量设计已完成，要为一次对**已交付功能**的改动建账时
- **不用**：原批次还没归档——这个功能还在开发中，**直接在当前批次内改即可**，不需要开子批次
- **不用**：变更触及契约或表结构——那要走完整流程（`02_概要详细设计`）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 增量设计说明 | `ai-iteration-02-delta-spec` 产出 | 是 | 含差异项清单 |
| 影响面分析 | `ai-iteration-01-impact` 产出 | 是 | 含影响等级与建议路径 |
| 原批次状态文件 | `projects/<项目码>/.agent/state/<原批次号>.yaml` | 是 | **`archived: true`**——原批次必须已归档 |
| 原批次产出物 | 项目文档仓 | 是 | 基线，**只读** |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 变更子批次状态 | `projects/<项目码>/.agent/state/<原批次号>-C<n>.yaml` | 按 `projects/_template/.agent/state/_模板.yaml`，`type: change` |
| 变更登记 | 项目文档仓 `<需求名>/迭代/变更登记.md` | 变更项 + 基线对比 + 批准确认 |
| 基线快照记录 | 原批次状态文件（**只追加不改**） | 记录被哪个子批次改动 |

产出结构——变更子批次状态文件：

```yaml
batch: PROJ-20260901-003-C1
project: <项目码>
type: change
parent_batch: PROJ-20260901-003      # ← 关键字段，指向原批次
created: 2026-10-20T10:00:00+08:00
owner: <批次负责人>
current_step: delta-spec
# 其余按 projects/_template/.agent/state/_模板.yaml
```

`parent_batch` 是追溯链的关键：从子批次能回到原批次，从原批次能查到所有子批次。

产出结构——变更登记的变更项表（**基线哈希不能省**）：

```markdown
## 变更项

| # | 改什么 | 为什么 | 基线（原批次产出物 + 哈希） | 影响谁 |
|---|---|---|---|---|
| D-01 | API-CORE-008 加 groupId | REQ-CORE-031 | 接口契约.yaml @ sha256:7f3a… | FR-CORE-045、TC-045-01~05 |
```

产出结构——原批次状态文件的追加记录（**只追加，已有的内容一个字都不改**）：

```yaml
changed_by:
  - batch: PROJ-20260901-003-C1
    at: 2026-10-20
    scope: [FR-CORE-045, FR-CORE-020]
```

## 前置条件

**hard（不满足则拒绝执行）**

- 原批次状态文件存在且 `archived: true`（未归档批次直接改即可，无需开子批次）
- 增量设计说明已产出
- **变更未触及契约或表结构**（触及则应走完整流程，见失败处理）

**soft（不满足则提示，可继续）**

- 变更已获批准（未获批准时照常登记为「**待批准**」，但**不推进到实施**）
  ——批准需要可查证的记录（谁、什么时候、同意了哪一版范围）

## 执行步骤

1. 定位原批次的状态文件与产出物，记录**基线哈希**
2. 分配子批次编号 `<原批次号>-C<n>`（n 从 1 递增，不跳号）
3. 生成子批次状态文件，`type: change`，并记录 `parent_batch`（原批次号）
4. 逐个差异项登记：改什么、为什么、基线是什么、影响谁
5. 在原批次状态文件中**只追加**一条记录：被哪个子批次改动、改动日期
6. 回写子批次状态文件：本步骤置 `done`，登记变更登记文件与哈希

### 编号规则

| 项 | 规则 |
|---|---|
| 子批次号 | `<原批次号>-C<n>`，如 `PROJ-20260901-003-C1` |
| 递增 | n 从 1 开始，**不跳号、不复用**（删掉的子批次号也保留） |
| 同批次多次变更 | C1、C2、C3……各自独立 |

**不跳号的意义**：看到 C3 就知道 C1、C2 存在过。跳号会让"这个功能被改过几次"变成不可知的。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始（例如只补一次登记）
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— 变更尚未获批准」，
  状态记 `partial`，**不推进到实施**
- 批次状态文件不可写时：变更登记落到 `<需求名>/迭代/变更登记.md`，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不修改原批次的产出物**（一个字都不改）
- 不修改原批次状态文件里已有的内容（只追加）
- 不实施变更（那是增量开发）
- **不批准变更**——批准是人（需求方或技术负责人）的事，本 Skill 只做登记
- 不判断变更"值不值得做"
- 不要跳过 `parent_batch` 字段
- 不要省略基线哈希
- 不要为未归档的批次强行开子批次
- 不要登记触及契约或表结构的变更
- 不要代替人批准变更
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 原批次未归档 | 说明可直接在当前批次内修改，无需开子批次；**不强行开** |
| 变更触及契约或表结构 | **拒绝登记**，说明需走完整流程（涉及前端、外部调用方、存量数据） |
| 变更未获批准 | 登记为"待批准"，**不推进到实施**（不要因为"需求方在群里说了"就当成批准了） |
| 原批次状态文件被外部修改 | 报告，由人确认后再继续（基线不可信时，对比也无意义） |

## 输出格式

```
变更子批次：PROJ-20260901-003-C1
原批次：PROJ-20260901-003（已归档，2026-09-05）
变更项：3 项
基线哈希：
  - 接口契约.yaml @ sha256:7f3a…
  - 功能详细设计.md @ sha256:2b91…

原批次状态文件：已追加 changed_by 记录（未修改既有内容）
批准：待批准（需求方确认中）
触及契约：是 —— ⚠️ 需按流程确认，详见下方说明
```
