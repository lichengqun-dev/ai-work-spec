# 能力声明

输入一个新需求，输出**变更影响面**：受影响的 `FN`、接口、数据表、测试用例范围，以及影响等级。

**这是迭代流程的枢纽。** 它决定后面要不要重跑设计、回归测哪些、走哪条路径。
这一步做好了，迭代成本可控；做不好，团队要么过度设计（小改动走全流程），要么回归不足（改了 A 崩了 C）。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 迭代需求 | 用户提供 | 是 | 能判断出它改的是哪个已有功能 |
| 依赖关系图 | `.ai/index/依赖关系图.md` | 是 | 非空；**为空时拒绝** |
| 功能编号总表 | `.ai/index/功能编号总表.md` | 是 | 含已有 FN、接口、表 |
| 已归档批次产出物 | 项目文档仓 | 是 | 基线设计的来源 |
| 生效规范快照 | `.ai/spec-effective/<项目码>.md` | 是 | 判断改动是否触及技术栈约束 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 影响面分析 | 项目文档仓 `docs/迭代/<批次号>_影响面分析.md` | 受影响清单 + 影响等级 + 建议路径 |

## 影响等级的判定（决定后续走哪条路）

| 等级 | 判据 | 后续路径 |
|---|---|---|
| **小** | 单个页面或单个接口；不涉及数据模型；不涉及对外契约 | 快速通道（`ai-daily-01-fastlane`） |
| **中** | 跨模块，但不改架构与数据模型 | 增量设计 → 增量开发 → 回归 |
| **大** | 触及架构、数据模型，或对外契约 | **转完整流程**，回到 `02_概要详细设计` |

**判据必须量化。** 不写"你觉得这个改动大不大"——那个判断在赶工时永远倾向于"不大"。

## 前置条件（不满足则拒绝执行）

- 依赖关系图非空（无图无法遍历，只能靠猜）
- 已有基线：该功能至少有一个已归档批次（**全新功能应走新建流程，不走迭代流程**）
- 能确定改动针对的是哪个已有 `FN`（确定不了时向用户澄清，**不猜**）

## 执行步骤

1. 把需求映射到已有的 `FN`（可能涉及多个：改行为 / 加字段 / 改交互）
2. 从这些 FN 出发，按依赖关系图**双向遍历**，得到受影响 FN 集合
3. 展开到三类影响面：
   - **接口**：哪些 `API` 的请求/响应需要改
   - **数据表**：哪些 `TBL` 需要加列/改类型（**涉及表结构即为"大"**）
   - **测试用例**：受影响的 `TC` 集合（供回归使用）
4. 判定影响等级，给出建议路径
5. 列出**不受影响的部分**（防止设计蔓延，也让人能复核范围）
6. 回写批次状态文件

## 边界（明确不做）

- **不做设计**（那是 `ai-iteration-02-delta-spec`）
- **不决定要不要做**——那是需求方的判断
- 不执行改动、不跑回归
- 不改依赖关系图里已有的关系

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 依赖关系图为空 | **拒绝执行**，说明无图只能猜范围；给出两条路：补维护依赖图，或由人显式圈定范围 |
| 需求映射不到已有 FN | 澄清：这是改已有功能（迭代），还是加新功能（新建）？**不默认按迭代处理** |
| 判定为"大"（触及数据模型或契约） | **明确输出"建议转完整流程"**，不要为了省事降到"中" |
| 需求描述本身不清晰 | 输出待澄清清单，中止 |

## 为什么"涉及表结构即为大"

表结构变更的影响面超出本项目范围：

| 影响 | 说明 |
|---|---|
| 数据迁移 | 存量数据如何转换，能否回滚 |
| 历史兼容 | 旧版本代码/接口读到新结构会怎样 |
| 回归范围 | 所有读写该表的 FN 都受影响，通常是一大片 |

把它当成"中"或"小"，是迭代流程里最容易出问题的一类低估。
