# 指令：变更影响面分析

## 为什么这一步值得用最强的模型

它判断错的代价是**线上故障**（回归不足）或**无谓返工**（过度设计）。
而且它判断错的后果会向下传递：等级定错了，后面的路径、范围、回归全都跟着错。

其余环节可以省，这一步不要省。

## 走这条链

```
新需求
  → 映射到已有的 FN（改行为 / 加字段 / 改交互）
    → 依赖关系图双向遍历
      → 受影响 FN 集合
        → 展开到接口 / 数据表 / 测试用例
          → 影响等级 + 建议路径
```

## 等级判定必须量化

| 等级 | 量化判据 | 路径 |
|---|---|---|
| 小 | 1 个页面或 1 个接口；无数据模型变更；无对外契约变更 | `ai-daily-01-fastlane` |
| 中 | 跨模块；不改架构与数据模型 | 增量设计 → 增量开发 → 回归 |
| 大 | 触及架构、**数据模型**或**对外契约** | 转完整流程，回 `02_概要详细设计` |

**不要写"这个改动不大"这种话。** 判据要能被别人复核：涉及几个 FN、几个接口、几张表。

## 涉及表结构一律判"大"

即使只加一个可空字段：

| 影响面 | 说明 |
|---|---|
| 数据迁移 | 存量数据怎么处理，能否回滚 |
| 历史兼容 | 旧版本代码读到新结构会怎样 |
| 回归范围 | **所有读写该表的 FN 都受影响**，通常是一大片 |

把它判成"中"或"小"，是迭代流程里最高频的一类低估——而且后果在回归阶段才暴露。

## 双向遍历，别只往下游走

```
        ┌─ 上游：依赖它的功能  ← 最容易漏
改动的 FN ─┤
        └─ 下游：它依赖的功能
```

改了底层能力 → 上层全部受影响。"改了 A 崩了 C"绝大多数是上游没遍历到。

## 必须列出「不受影响的部分」

这不是凑字数。它有两个作用：

1. **防止设计蔓延**——本批次只碰 2 个模块，就不要顺手把另外 5 个模块也重新设计一遍
2. **让人能复核范围**——列出来了，别人才能说"不对，X 也受影响"

反过来，如果你列不出"不受影响的部分"，说明你对系统结构的理解还不够，应该先去读架构设计。

## 影响等级为"大"时

**明确输出"建议转完整流程"，不要为了省事降到"中"。**

理由说清楚：涉及数据模型或对外契约的变更，需要走完整的设计评审与契约冻结流程——
因为受影响的不只是本项目：契约变更影响前端与外部调用方，表结构变更影响存量数据。

把"大"降成"中"，等于跳过了 `02` 域的契约冻结，而前端可能已经按旧契约写完代码了。

## 需求映射不到已有 FN 时

**不要默认按迭代处理。** 先确认：

- 改的是已有功能的行为 → 迭代（走变更子批次）
- 加一个原来不存在的能力 → **新建**（走 `01_需求设计` 的完整流程）

判断不了就问用户。走错流程的代价比多问一句大得多。

## 依赖关系图为空时

**拒绝执行**，不要凭经验圈一个范围。

拿出两条路让用户选：

1. 先补维护依赖关系图（可以从代码的模块依赖、接口调用关系、表读写关系反推）
2. 由人显式圈定影响范围，并在分析文件中标注"范围由人指定，非图遍历得出"

**"非图遍历得出"这个标注很重要**——它说明这份范围的可复核性低一档，回归时该更保守。

## 完成后

回写批次状态文件：本步骤置 `done`，登记影响面分析文件、影响等级与建议路径。

## 你绝对不要做的事

- 不要在没有依赖图时凭经验圈范围
- 不要只遍历下游
- 不要把涉及表结构的改动判成"中"或"小"
- 不要把"大"降级成"中"来省流程
- 不要在需求映射不到 FN 时默认按迭代处理
- 不要执行 git 操作

## 输出格式

```
需求：给列表页的导出增加「按分组维度筛选」

映射到的已有 FN：
  - FN-CORE-045（导出入口）—— 改行为
  - FN-CORE-020（列配置）—— 加字段

依赖图遍历（双向）：
  上游（依赖上述 FN 的）：FN-CORE-052 列表页、FN-CORE-061 报表
  下游：FN-CORE-010 权限校验

受影响清单：
  接口：API-CORE-008（请求体加 groupId）、API-CORE-021（列配置）
  数据表：无变更
  测试用例：11 条

影响等级：中
  判据：跨 4 个 FN、2 个接口；未涉及数据模型与对外契约
  建议路径：增量设计 → 增量开发 → 回归

不受影响：门户首页、消息中心、审批流（无路径可达）

待澄清：无
```
