# 上线方案要点 · ai-iteration-04-release

> 本文件收纳不可逆步骤、发布说明读者口径的论证与正反例。**规则本身在 `SKILL.md` 的
> 「产出契约」「执行步骤」「边界」**，这里只回答"为什么定成这样"。组织上线步骤、写回滚方案时读。

## 哪些变更不可逆

| 变更 | 能否回滚 |
|---|---|
| 建表 / 加列 / 加索引 | 能 |
| 删列 / 改类型（缩小精度） | **不能** |
| 数据清洗（覆盖原值） | **不能**（除非先备份） |

## 为什么"假装可回滚"比明说"回不去"危险

写一句看起来能回滚实则无效的 SQL（如 `-- 反向：ALTER TABLE ...`），
会让人在**有退路的心态下**执行不可逆操作。

第三点很重要：**写 `无`，不要写假的反向 SQL**。一个假装可回滚的方案比明说"回不去"危险得多。

## 为什么本 Skill 排在 gate-05 之前

gate-05 要校验的就是它产出的上线方案（`rollout-plan-present`，BLOCK）。
"门禁要的文件，只有门禁通过才允许产出"会形成死锁——所以前置条件里刻意**不**要求 gate-05 已通过。

「不带着未关闭的 P0/P1 上线」由 gate-05 在本 Skill 之后强制执行，不靠前置条件。

## 发布说明的读者是使用方

| 该写 | 不该写 |
|---|---|
| 新增能力、怎么用 | 内部重构细节 |
| 行为变化（含兼容性影响） | 纯技术优化（除非外部可感知） |
| 注意事项（限制、暂不支持） | 缺陷编号等内部信息 |
| **遗留风险（不弱化）** | — |

**遗留风险必须写，且不弱化。** 发布说明是使用方唯一的知情渠道，
把风险藏着，等于让他们在不知情的情况下承担后果。

## 多服务发布顺序错了会怎样

新版本服务调用旧版本服务，接口不兼容——而这类问题在灰度阶段不一定暴露，全量后才出现。
所以顺序不明确时**停下问用户**，不要假定。
