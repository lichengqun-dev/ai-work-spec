# 指令：增量设计（只写差异）

## 一条要求贯穿始终：写差异，不写全文

**你产出的是一份「变更说明」，不是一份新的详细设计。**

这个区别不是排版问题，它决定了两件事：

| | 差异说明 | 重写全文 |
|---|---|---|
| 成本 | 一页纸 | 可能两百页 |
| 后果 | 一份权威描述 | **两份文档，且没人知道哪份是当前的** |

第二种后果是致命的：原文档还在，新文档也在，半年后的人不知道以哪个为准。

## 每项差异写四件事

```markdown
### D-01 导出接口新增分组维度筛选

**改什么**：`API-CORE-008` 请求体新增 `groupId`（可选，string，最长 32）
**为什么改**：对应需求 REQ-CORE-031「按分组维度导出」
**原设计是什么**：详见 `docs/02_设计/接口契约.yaml`（原批次 PROJ-20260901-003）
**影响谁**：FN-CORE-045（导出入口）、TC-FN-CORE-045-01~05（需重跑）
```

四件事都要有。缺「原设计是什么」，读者无法判断改动幅度；
缺「影响谁」，回归范围就断了。

## 粒度：能实现，但别滑向重写

| ❌ 反例 | ✅ 正例 |
|---|---|
| 「优化导出模块的设计」 | 「`API-CORE-008` 请求体新增 `groupId`（可选，string，最长 32）」 |
| 把「导出」整章重写一遍 | 「原设计 §FN-CORE-045 时序第 3 步改为先过滤再导出；原因：数据量大时全量加载会 OOM」 |

判断标准：**写出来的东西能不能直接用来改代码？** 能，就够细了；如果开始复述没变的部分，就过头了。

## 不要碰原批次的产出物

原批次的文档**保持不可变**。你的差异说明引用它，不改它。

为什么这很重要：排查线上问题时，"上线那一刻的业务规则是什么"是判断"现在对不对"的唯一依据。
原文改掉之后，那个状态就永久丢失了——**这不是洁癖，是审计链的基础。**

## 发现需要改表时，停下来

影响面分析里，"涉及数据模型"应该被判为**大**，走完整流程。

如果你在增量设计阶段发现确实要改表，说明**影响等级判错了**。此时：

1. 停止
2. 明确说明：这一步不该出现表结构变更
3. 回到 `ai-iteration-01-impact` 重新判定等级

**不要顺手把表结构变更写进增量设计。** 绕过完整流程的代价在回归阶段才暴露。

## 影响等级不对时

| 等级 | 你的动作 |
|---|---|
| 小 | 拒绝执行，提示走 `ai-daily-01-fastlane` |
| 中 | 正常执行 |
| 大 | **拒绝执行**，说明需转 `02_概要详细设计` 完整流程 |

「大」不接受绕过。它涉及数据模型或对外契约，受影响的不只是本项目——
契约变更影响前端与外部调用方，表结构变更影响存量数据。

## 发现影响面分析漏了东西时

如果差异描述里涉及的 FN 没在影响面分析中列出：**停止，回到 `ai-iteration-01-impact` 补全范围。**

顺手加上去会让两份文档不一致，而回归范围是按影响面分析圈定的——漏掉的 FN 就不会被回归。

## 完成后

回写批次状态文件：本步骤置 `done`，登记增量设计说明与哈希。

## 你绝对不要做的事

- 不要重写原文档的任何章节
- 不要修改原批次产出物
- 不要接受"大"级变更
- 不要把表结构变更写进增量设计
- 不要在影响面分析漏项时顺手补上（回去补范围）
- 不要执行 git 操作
