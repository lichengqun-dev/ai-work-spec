# 能力声明

依据影响面分析产出**增量设计**——只写差异，不重写文档。

**输出的是一份「变更说明」，不是一份新的详细设计。** 这个区别直接决定了 AI 的上下文消耗量级：
重写一份 200 页的详细设计，与描述"某表加一列、某接口加一个参数"，成本差两个数量级。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 影响面分析 | `ai-iteration-01-impact` 产出 | 是 | 含受影响 FN / 接口 / 表清单 |
| 原设计文档 | 已归档批次的产出物 | 是 | 基线设计的来源 |
| 生效规范快照 | `.ai/spec-effective/<项目码>.md` | 是 | 技术约束 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 增量设计说明 | 项目文档仓 `docs/迭代/<批次号>_增量设计.md` | **差异描述**（改什么 / 为什么 / 影响谁） |
| 变更子批次编号 | `.ai/state/<原批次号>-C<n>.yaml` | 见 `ai-iteration-03-change-control` |

## 前置条件（不满足则拒绝执行）

- 影响面分析已产出，且影响等级为**中**（小 → 走快车道；大 → 转完整流程，**不接受绕过**）
- 原设计文档可定位（找不到基线时拒绝——**没有基线就没有"差异"这个概念**）

## 执行步骤

1. 逐项描述差异，每项写清四件事：
   - **改什么**（精确到字段、参数、页面元素）
   - **为什么改**（对应哪条需求）
   - **原设计是什么**（引用原文档章节号）
   - **影响谁**（受影响 FN / 接口 / 用例）
2. **不重写原文档的任何章节**——只描述差异，原文档保持不可变
3. 建议的变更子批次编号 `<原批次号>-C<n>`
4. 标注哪些差异需要更新契约、哪些需要改表（后者在影响面分析里应为"大"，出现了要停下来重新确认）
5. 回写批次状态文件

## 边界（明确不做）

- **不重写完整设计文档。** 重写会产生两份文档（新的与旧的），而没人知道哪份是当前的
- 不改原批次的产出物（原批次不可变，这是审计链的基础）
- 不实现代码（`03_编码开发`）
- 不做影响面分析（那是上一步）
- **不自行决定"大"级变更怎么处理**——那需要回完整流程

## 为什么原文档不可变

| 做法 | 能否回答"上线那一刻的业务规则是什么" |
|---|---|
| 原文档不可变 + 增量说明 | ✅ 能：看原批次产出物 + 变更子批次 |
| 直接改原文档 | ❌ 不能：原文改掉后再也无法复原当时的状态 |

**这不是洁癖。** 排查线上问题时，"当时规则是什么"是判断"现在的行为对不对"的唯一依据。

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 影响等级为"大" | **拒绝执行**，说明需转完整流程（`02_概要详细设计`） |
| 影响等级为"小" | 拒绝执行，提示走 `ai-daily-01-fastlane` |
| 找不到原设计文档 | 拒绝执行——无基线则差异无从谈起 |
| 增量设计中发现需要改表 | 停止并重新确认影响等级（这一步不该出现表结构变更） |
| 差异描述涉及未在影响面分析中列出的 FN | 停止，回到 `ai-iteration-01-impact` 补全范围 |

## 差异描述的粒度

**精确到能被实现的程度**，但不要滑向"重写设计"：

| 反例 | 正例 |
|---|---|
| 「优化导出模块的设计」 | 「API-CORE-008 请求体新增 `groupId`（可选，string，最长 32）；对应 FN-CORE-045」 |
| 把整个「导出」章节重写一遍 | 「原设计 §FN-CORE-045 的时序第 3 步改为先过滤再导出，原因是……」 |
