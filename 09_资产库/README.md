# 09_资产库

> **沉淀层。** 前八个域是"流程"，本域是"随流程长出来的东西"。
>
> 它与 `standards/` 的区别：`standards/` 是**已经定稿、必须遵守**的规则；
> 本域装的是**素材**——它们还没有稳定到可以成为规范，但已经比"口口相传"可靠。

|---|---|---|---|
| [规范包](./规范包/INDEX.md) | **唯一机器可读的资产**：L1 技术栈包 + L2 领域包 | 知识库 Owner / 各栈负责人 | 6 技术栈包（`skeleton`/`partial`）+ 2 领域包（空骨架） |

**除规范包外，其余五个当前都是空的——这是正确状态，不是待办。**

它们必须**实测得来**：坐在会议室里凭空写的"通用实体字典"和"度量基线"，
实战中一条都用不上，然后被整体废弃。**用真实批次反推**，不要为了"看起来完整"先填上。

## 这一域为什么值得单独存在

前八个域解决的是"怎么做"，本域解决的是**"做过之后留下了什么"**。

两者对 AI 的作用不同：规范条目容易被"合理理解"成各种变体，而**具体案例是不可曲解的**。
"接口必须幂等"可以被理解出十种实现；"某次重复提交导致两条流水记录，因为幂等键用的是时间戳"
只有一种意思。

**当同一个问题在三个项目里都出现过，它就应该成为一条规范**——这是本域通往 `standards/`
和规范包的路径，走 `ai-spec-promote` 的逆向方向。

## 填充顺序建议

按"投入产出比"排，而不是按目录顺序：

1. **组件库**（前端 + 后端）——直接影响产出质量。`ai-requirement-03-prototype` 的第一步就是"先匹配已有组件"，
   清单为空时它会画出一堆项目里不存在的组件，业务方确认之后才发现要重做
2. **领域模型**——从**数据敏感度**入手，不要从表清单入手：先列"删错会出事的表"和"改错会污染下游的表"
3. **故障案例库**——第一次真实线上问题之后立刻开始，不要等"攒够了再写"
4. **指标基线**——批次跑起来后自然积累，**空着比填假数字好**
5. **提示词库**——调优时顺手记，不要专门开会写

## 与其他域的关系

- 被 `02_概要详细设计` 与 `03_编码开发` 读（领域模型、组件库）
- 被 `01_需求设计` 读（组件库——原型要先匹配已有组件）
- 被 `06_日常开发` 写入（故障案例库）
- `规范包/` 是唯一被**脚本**读的部分（`ai-spec-build`），其余五个都只被人和模型读

> **判据**：需要机器校验的 → 规范条目（进规范包，带编号）；
> 需要人理解判断的 → 素材（放本域）。把素材硬做成带编号的"规范"会得到一堆没人遵守的空条文。
