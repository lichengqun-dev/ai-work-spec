# 命名与编号规范

> **本规范在 P0 一次性定稿，之后只增不改。** 编号体系是追溯链的主键，改动成本随批次数线性上升。
> 所有前缀一经启用不得复用、不得重编。

## 1. 为什么编号必须先行

任意一个上线功能，要能在 30 秒内回答"它来自哪条原始需求、经过哪些设计决策、被哪些测试用例覆盖、谁在什么时候评审过"。这个能力**完全依赖编号**，不依赖文档写得好不好。

自然语言描述无法承担这个角色——"订单导出那个功能"在不同人嘴里指不同东西，而 `FN-ORDER-045` 只指一个东西。

## 2. 项目码与模块码

### 2.1 项目码（一等公民）

小写、短、稳定。一旦分配不再变更，即使项目改名。

**项目码即 `projects/` 下的目录名。** 本仓库不维护全局项目清单——清单就是目录本身。

新增项目时建 `projects/<项目码>/` 目录并写 manifest。**项目码一经分配不再变更**，即使项目改名——
改名会让历史批次与编号中的项目码全部对不上。

### 2.2 模块码

模块码在项目内定义，写在 `projects/<项目码>/project.yaml` 的 `modules` 段。**大写，2-8 字符。**

各项目自行定义。格式示例如下（取值由项目自定，本仓库不预置）：

| 模块码 | 模块 |
|---|---|
| `CORE` | 核心业务 |
| `TASK` | 任务管理 |
| `REPORT` | 报表与统计 |

**模块码由各项目自行定义，写在 `projects/<项目码>/project.yaml` 的 `modules` 段。** 本仓库只规定格式（大写、2-8 字符），不规定取值。

## 3. 编号前缀全集

| 前缀 | 含义 | 格式 | 示例 |
|---|---|---|---|
| `REQ` | 需求条目 | `REQ-<模块码>-<3位>` | `REQ-CORE-012` |
| `FN` | 功能点 | `FN-<模块码>-<3位>` | `FN-CORE-045` |
| `FN-...-D` | 功能变更（迭代） | `FN-<原编号>-D<序号>` | `FN-CORE-045-D1` |
| `API` | 接口 | `API-<模块码>-<3位>` | `API-CORE-008` |
| `TBL` | 数据表 | `TBL_<模块码>_<表名>` | `TBL_CORE_MAIN` |
| `PAGE` | 页面 | `PAGE-<模块码>-<3位>` | `PAGE-CORE-003` |
| `TC` | 测试用例 | `TC-<FN编号>-<2位>` | `TC-FN-CORE-045-01` |
| `BUG` | 缺陷 | `BUG-<批次号>-<3位>` | `BUG-PROJ-20261019-001-007` |
| `DEC` | 设计决策 | `DEC-<模块码>-<3位>` | `DEC-CORE-004` |
| `STD` | 规范条目 | 见第 5 节 | `STD-VUE3-014` |

编号到 **3 位**（999 条后升 4 位），在 `.ai/index/功能编号总表.md` 中统一登记。

## 4. 批次号

格式：`<项目码大写>-<YYYYMMDD>-<3位序号>`，示例 `PROJ-20261019-001`。

批次是**一次完整的交付闭环**，不是"一次会议"。一个批次从需求进来开始到归档结束。迭代场景下一个批次可能就是"给列表加导出"，它仍完整走一遍精简流程。

变更子批次：`<原批次号>-C<序号>`，示例 `PROJ-20261019-001-C1`。原批次产出物保持不可变——这个设计保护了审计链：你永远能回答"上线那一刻的业务规则是什么"。

## 5. 规范条目编号（STD）

规范编号到**条目**，不到文件。这是覆盖能精确到条而非整份文件的技术前提。

| 层级 | 前缀 | 示例 |
|---|---|---|
| L0 团队基线 | `STD-BASE-` | `STD-BASE-012` |
| L1 技术栈包（前端） | `STD-VUE2-` / `STD-VUE3-` / `STD-REACT-` | `STD-VUE3-014` |
| L1 技术栈包（后端） | `STD-SB2-` / `STD-SB3-` | `STD-SB3-007` |
| L1 技术栈包（数据库） | `STD-DM8-` | `STD-DM8-003` |
| L2 领域包 | `STD-DOM-<领域缩写>-` | `STD-DOM-PLAT-021` / `STD-DOM-INFOSEC-002` |
| L3 项目层 | `STD-PRJ-<项目码大写>-` | `STD-PRJ-PROJ-001` |
| L4 批次层 | `STD-BATCH-<批次号>-` | `STD-BATCH-PROJ-20261019-001-01` |

条目编号在包内**顺序分配、永不复用**。删除条目时保留编号并标记 `[已废弃]`，不回收。

**前缀必须与所在包一致**（由 `ai-spec-build` 校验）。例如 `fe-vue3-elementplus` 包内只允许 `STD-VUE3-` 前缀；跨包重复的条目编号视为错误。

## 6. Skill 命名

格式：`ai-<段>-<...>-<动作>`，其中 `ai` 是知识库统一前缀。

### 6.1 阶段 Skill

`ai-<域>-<两位序号>-<动作>`。域枚举固定为：

`requirement` / `design` / `dev` / `test` / `iteration` / `daily` / `gate` / `archive` / `spec`

| 示例 | 归属域 |
|---|---|
| `ai-design-03-db` | `02_概要详细设计` |
| `ai-requirement-02-analysis` | `01_需求设计` |
| `ai-spec-build` | `00_工作空间配置` |

### 6.2 编排 Skill

域前缀 + `-autopilot` 后缀：`ai-requirement-autopilot`。

### 6.3 工具 Skill

`ai-<工具名>-<...>-<runner|convert>`，**不要求工具名落在域枚举内**——工具是按它操作的对象命名的，不是按阶段命名的。

| 示例 | 说明 |
|---|---|
| `ai-gate-runner` | 门禁执行器（`gate` 恰好也是域枚举成员） |
| `ai-figma-axure-convert` | 设计稿转换器（`figma` / `axure` 是对象，不是阶段） |

**区分方法**：这个 Skill 是"流程中的一步"还是"随时可调用的工具"？前者用 6.1，后者用 6.3。判据是它有没有在流水线中固定的位置。

### 6.4 为什么域枚举要固定

固定枚举的价值是可以批量调用（如 `ai-test-*` 一次跑完整个测试域），以及让编排层能按域判断前置条件是否齐备。

但它只约束**阶段 Skill**。工具 Skill 套用域枚举会得到 `ai-convert-figma-axure` 这种别扭的名字——为了形式一致牺牲可读性，不划算。

### 6.5 命名一次性定稿

Skill 名称**一经启用不再变更**。改名会让 `.ai/state/` 里历史批次状态文件的 `skill` 字段失效，从而破坏"这个批次当时跑了哪些 Skill"的追溯能力。

## 7. 文件与目录命名

- 目录：`<两位序号>_<中文名>`（如 `03_编码开发`），或全小写连字符（如 `fe-vue3-elementplus`）。
- 规范与文档文件：中文名 + `.md`。
- 产出物文件：中文名 + `.md`，**不使用日期前缀**（日期由批次号承载）。

## 8. 强制校验

以下由 `ai-gate-runner` 或 `ai-spec-build` 自动检查，不通过则阻断：

1. 提交信息必须包含 FN 编号，格式 `feat(FN-CORE-045): 描述`。
2. 测试用例编号必须挂载到 FN 编号下（`TC-FN-CORE-045-01`），不允许游离编号。
3. 原型页面上每个可交互元素带 `data-fn="FN-CORE-045"` 标记。
4. 任何 Skill 不得自行生成编号，必须向 `.ai/index/功能编号总表.md` 申请。
5. 规范条目前缀必须与所在包一致，且全库唯一。

## 9. 断链检测（gate-06）

每次批次归档时执行一次全链路检测，输出以下几类断链：

- 没有 `REQ` 来源的 `FN`
- 没有设计章节对应的 `FN`
- 没有 `TC` 覆盖的 `FN`
- 没有对应提交的 `FN`
- 总表中存在但任何文档都未引用的孤儿编号

**断链数是一个硬指标，目标为 0。**
