# AI 工作空间配置

> 本文件是整个知识库的**总配置**：目录权重、加载顺序、读取规则、操作红线。
> AI 助手读完根 `CLAUDE.md` 之后读本文件。

## 1. 工作空间的边界

本仓库是**规范与 Skill 仓**，不存放业务产出物。

| 内容 | 位置 |
|---|---|
| 规范（跨项目复用） | 本仓库 `09_资产库/规范包/` + 各域 `standards/` |
| Skill 定义 | 本仓库各域 `skills/` |
| 项目组合声明 | 本仓库 `projects/<项目码>/` |
| 生效规范快照 | 本仓库 `projects/<项目码>/.agent/spec-effective/`（生成物，不手工编辑） |
| PRD、设计文档、测试报告、上线手册 | **各项目的文档仓**，不在本仓库 |
| 业务代码 | 各项目的代码仓，不在本仓库 |

## 2. 目录权重与读取优先级

| 目录 | 层级 | 内容 | 读取权重 |
|---|---|---|---|
| `CLAUDE.md` | 全局 | 技术栈基线、全局禁止、Skill 路由 | 每次会话必读 |
| `00_工作空间配置/` | 全局 | 本文件及配套规范 | 涉及流程决策时读 |
| `01_需求设计/` … `08_归档交付/` | 阶段 | 各阶段的 Skill 与模板 | 进入该阶段时读 |
| `09_资产库/规范包/` | 资产 | L1 技术栈包 + L2 领域包 | **不直接读**，经 `ai-spec-build` 合并 |
| **`projects/<项目码>/` 根下** | **项目级** | **本项目实际是什么样**：架构 / 模块目录 / 业务模型 / 测试策略 / 环境 / 特有条目 | 涉及具体项目时读 |
| **`projects/<项目码>/<需求名>/`** | **业务级** | **该需求的全部产出物**（PRD、设计、测试、交付） | **权重最高**——具体需求的一切以它为准 |
| `projects/<项目码>/.agent/spec-effective/` | 快照 | 合并后的生效规范 | **写代码、做设计前的第一读物** |
| `projects/<项目码>/.agent/state/` | 状态 | 批次状态机 | 接手一个批次时的第一读物 |
| `projects/<项目码>/.agent/index/` | 索引 | 功能编号总表、依赖关系图、台账 | 需要追溯时读 |
| `projects/<项目码>/.agent/logs/` | 日志 | Skill 执行元数据 | 排查执行异常时读 |

**内容冲突时的优先级（三层）**：**业务级 > 项目级 > 用户级**。
规范条目另有五层优先级：批次特例 > 项目层 > 领域包 > 技术栈包 > 团队基线（`frozen: true` 的条目除外）。

## 3. 读取规则

**规则一：规范读快照，不读包。** 写代码前读 `projects/<项目码>/.agent/spec-effective/<项目码>.md`。不要自己去找 `09_资产库/规范包/` 下的文件做合并——合并在构建期已完成；运行时合并会导致结果不一致、冲突被静默吞掉。

**规则二：Skill 读索引，不读全文。** `references/` 目录默认只加载 `INDEX.md`，按索引判断需要哪些知识再按需读取，单次最多 3 个文件。

**规则三：产出物读相关段落，不读全文。** 处理 `FN-XXX-045` 时只读详细设计中该 FN 的章节，不读整份详细设计。这要求所有产出物**按编号分节**。

**规则四：上下文预算硬约束，超预算报错而非硬跑。**

| 部分 | 预算 |
|---|---|
| 全局 `CLAUDE.md` | ≤ 200 行 |
| 批次 `CLAUDE.md` | ≤ 80 行 |
| Skill 自身 `SKILL.md` | ≤ 150 行 |
| `prompt.md` | ≤ 300 行 |
| `references/` 按需加载 | ≤ 3 个文件，合计 ≤ 1500 行 |
| 生效快照「常驻注入」段 | ≤ 120 行 |
| **单次 Skill 执行合计** | **≤ 3000 行** |

## 4. 操作红线

1. **不改 `projects/<项目码>/.agent/spec-effective/` 下的快照。** 它是生成物，手改会被下次构建覆盖。要改规范就改包或 manifest。
2. **不在 manifest 里复制规范正文。** 只允许按条目编号引用。这是防止"基线副本化"复发的唯一机制。
3. **不覆盖或禁用 `frozen: true` 的条目。** 构建会直接失败；确需修改走知识库 Owner 流程。
4. **不删除文件。** 冗余或被替换的文档移入 `_archive/`（保持原相对路径），删除原文前校验副本一致。
5. **不删除已归档批次的状态文件。** 追溯链依赖 `projects/<项目码>/.agent/state/`。
6. **不改动规范却不重建快照。** 改了包或 manifest 却不跑 `ai-spec-build`，等于规范没生效。
7. **不在共享层写具体项目信息。** `00`–`09` 与**顶层** `.agent/`（只放机制：批次状态 Schema、
   日志格式约定）是**通用资产**，不得出现任何具体项目的名称、模块码、表名、接口路径或业务规则。
   项目相关内容一律只写在 `projects/<项目码>/` 下——包括**项目的机器数据**
   （`projects/<项目码>/.agent/` 下的批次状态、编号总表、台账）。

   判断方法：把这份知识库交给另一个团队用，这条内容还成立吗？不成立就说明放错了地方。
   边界规则与三层结构见 `../projects/README.md`。

   > **这条早期写成「`00`–`09` 与 `.ai/` 是通用资产」，而 `.ai/state/` 装的正是某个项目的批次状态**
   > ——规则与结构自相矛盾，于是"项目名不该出现在机器状态区里"这条实际从未成立过。
   > **现在：机器状态区改名为 `.agent/`，且只在项目下**（`projects/<项目码>/.agent/`），顶层不再有它。
   > 机制模板（批次状态 Schema、日志格式约定）住在项目骨架 `projects/_template/.agent/` 里。
8. **不执行 git 操作**（除非用户当次明确要求）。

## 5. 一次典型会话的读取顺序

```
1. CLAUDE.md                              ← 我在哪个仓库、技术栈是什么
2. 00_工作空间配置/AI工作空间配置.md        ← 读取规则与红线（本文件）
3. projects/<项目码>/.agent/project.yaml          ← 这个项目用了哪些包、有哪些差异
4. projects/<项目码>/.agent/spec-effective/<项目码>.md          ← 我要遵守的规范全文（只读这一份）
5. 需要追溯时：projects/<项目码>/.agent/index/功能编号总表.md
6. 接手批次时：projects/<项目码>/.agent/state/<批次号>.yaml
```

## 6. 新增项目接入（三步）

```
1. cp -r projects/_template projects/<新项目码>
2. 填 .agent/project.yaml（选包 + 仓库路径）
3. 写项目级散文文档（自由格式，不用管编号）
4. 调用 **ai-spec-extract** 把散文里的约束摘成条目，落 `.agent/rules/`
5. 调用 ai-spec-build（说"接入 <项目码>"即可）编译出生效规范快照
```

**目标：接入耗时 ≤ 30 分钟。** 超过说明包粒度太细（选项太多）或 manifest 结构太复杂——这是衡量分层设计是否成功的硬指标。
