# 模型与工具矩阵

> 决定每个步骤用哪个模型、哪个工具，以及**什么时候用脚本而不是模型**。

## 1. 核心判断：脚本优先于模型

每一步先问："这件事能不能写成脚本？"

能写成脚本的一律自动化。**这不仅是成本问题，更是确定性问题**——脚本每次跑出同样的结果，模型每次可能不同。规范类、校验类、合并类的工作必须用脚本；只有需要判断力的工作才交给模型。

| 工作类型 | 实现方式 | 例 |
|---|---|---|
| 格式校验、编号查重、断链检测 | **脚本** | `ai-spec-build` 的冲突检测、gate 的自动检查项 |
| 多层规范合并 | **脚本** | 合并结果必须可复现、可 diff |
| 覆盖率统计、契约 diff | **脚本** | 客观指标 |
| 需求结构化、方案设计、代码生成 | **模型** | 需要理解与判断 |
| 代码评审的意见生成 | **模型 + 脚本兜底** | 脚本查规范符合性，模型查逻辑合理性 |

**判据**：如果两个人做同一件事应该得到相同结果，用脚本；如果需要理解上下文才能做，用模型。

## 2. 模型分档

按任务的判断难度分档，不按"重要性"分档——重要的格式化工作仍然是低档任务。

| 档 | 适用任务 | 例 |
|---|---|---|
| **小** | 格式化、抽取、分类、映射、转达脚本输出 | 用例编号挂载、门禁结果转达、批次状态回写 |
| **中** | 结构化生成、按模板产出、单模块编码 | 需求分析文档、PRD 生成、前后端实现、用例生成 |
| **大** | 架构选型、跨模块影响面分析、疑难缺陷定位 | 架构设计、影响面分析、线上故障定位 |
| **无模型** | 纯脚本，确定性要求最高 | 规范编译、一致性检查、挂载层重建 |

**不要用大模型做格式化。** 成本差几十倍，质量没有区别。

## 3. 各阶段默认配置

**权威来源是每个 `prompt.md` 顶部的 `<!-- model-tier: … -->` 注释**——编排层读它，不读本表。
本表是它的镜像，用来一眼看出分布；两者不一致时以 `prompt.md` 为准。

| 档 | 数量 | Skill |
|---|---|---|
| **无模型** | 3 | `ai-spec-build` · `ai-spec-check` · `ai-spec-mount` |
| **小** | 7 | `ai-requirement-00-intake` · `ai-requirement-01-init` · `ai-design-06-review` · `ai-dev-05-codereview` · `ai-iteration-03-change-control` · `ai-gate-runner` · `ai-archive-01-close` |
| **大** | 4 | `ai-design-01-arch` · `ai-test-04-regression` · `ai-iteration-01-impact` · `ai-daily-02-hotfix` |
| **中** | 25 | `ai-flow-autopilot` · `ai-spec-promote` · `ai-figma-axure-convert` · `ai-requirement-02-analysis` · `03-prototype` · `04-prd` · `ai-requirement-autopilot` · `ai-design-02-detail` · `03-db` · `04-api` · `05-frontend-spec` · `ai-dev-01-scaffold` · `02-backend` · `03-frontend` · `04-unittest` · `06-docsync` · `ai-test-01-cases` · `02-automation` · `03-execute` · `05-report` · `ai-iteration-02-delta-spec` · `04-release` · `ai-daily-01-fastlane` · `03-techdebt` · `04-qa` |

合计 39 = 34 阶段 Skill + 4 知识库治理工具 + 1 全流程编排入口。

**几处不显然的定档，理由记在这里：**

- **`ai-gate-runner` 是「小」而不是「无模型」**：判定由脚本完成，模型只负责原样转达输出。
  「无模型」只给真正的纯脚本 Skill（编译 / 检查 / 挂载），它们连转达都不需要。
- **`ai-design-06-review` / `ai-dev-05-codereview` 是「小」**：它们是**编排 Skill**，
  不做检查项判断——调用 `ai-gate-runner` 并把清单原样列出。判断力要求低，纪律要求高。
- **`ai-daily-02-hotfix` 是「大」**：线上定位是这套体系里最需要强推理的一步，
  而且它的输入往往残缺（只有现象、没有日志）。**这里省钱省不出东西来。**

## 4. 成本与质量的权衡点

以下三处是成本敏感点，改配置收益最大。**注意它们当前声明的都不是「小」**——
下表写的是**可下探的空间**，不是现状；要改就得改对应 `prompt.md` 的 `model-tier`：

| Skill | 当前声明 | 可下探到 | 为什么可以 |
|---|---|---|---|
| `ai-requirement-03-prototype` | 中 | 小 + 严格模板约束 | 调用量大、结构化程度高 |
| `ai-test-01-cases` | 中 | 小 | 数量大、模式重复 |
| `ai-dev-04-unittest` | 中 | 小 | 同上 |

**下探前先量一遍**：这三处都是"产出结构固定、判断成分低"，所以下探空间存在；
但"应该能行"和"实际行"是两回事，降档要用真实批次对比产出质量，不要凭感觉降。

以下三处**不要省钱**：

1. **影响面分析**（`ai-iteration-01-impact`，已声明「大」）——判断错的代价是线上故障。
2. **架构设计与技术选型**（`ai-design-01-arch`，已声明「大」）——返工成本最高。
3. **契约冻结前的评审**——契约错了，前后端全部返工。
4. **线上故障定位**（`ai-daily-02-hotfix`，已声明「大」）——输入往往残缺（只有现象、没有日志），
   强推理正是用在补这个缺口上。

## 5. 工具约定

- **达梦 DM8 查询**：使用 `00_工作空间配置/skills/` 之外的独立查询工具，不要把 JDBC 连接信息写进代码或规范文档。连接信息通过环境变量注入。
- **规范合并与校验**：调用 `ai-spec-build`。它是纯脚本 Skill，不调用模型——合并结果必须可复现、可 diff、可审计。**不要教使用者敲命令行**：参数是实现细节，写在脚本自己的 docstring 里。
- **知识库自检**：调用 `ai-spec-check`。同理，纯脚本、只读、不调用模型。
- **不要重复造 Skill**：新增 Skill 前先检查各域 `README.md` 的技能清单，确认没有重叠。

## 6. 模型解耦要求

`prompt.md` 中**不得使用模型特有语法**（如某家独有的函数调用格式、独有标签）。目的是保留多模型切换能力。

需要区分模型时，在 `prompt.md` 顶部用注释声明建议档位，由编排层读取，而不是把差异写进正文：

```markdown
<!-- model-tier: small -->
<!-- deps: references/INDEX.md -->
```
