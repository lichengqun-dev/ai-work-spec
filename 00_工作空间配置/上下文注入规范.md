# 上下文注入规范

> 定义"什么内容在什么时机注入"。本规范决定知识库能否规模化运行——塞太多会失控，塞太少会胡编。

## 1. CLAUDE.md 三级体系

| 级别 | 位置 | 内容 | 预算 | 何时加载 |
|---|---|---|---|---|
| L1 全局 | 仓库根 `CLAUDE.md` | 技术栈基线、全局禁止、Skill 路由 | ≤ 200 行 | 每次会话 |
| L2 阶段 | 各域 `README.md` | 该域有哪些 Skill、执行顺序、依赖哪些资产 | ≤ 150 行 | 进入该阶段 |
| L3 批次 | 项目文档仓 `CLAUDE.md` | 当前批次状态摘要 | ≤ 80 行 | 每次 Skill 执行 |

**L3 是全套体系的效率杠杆。** 它让每次 Skill 执行只读一个 80 行文件，就知道当前该做什么、什么不能碰，而不需要读全部文档。

L3 由 `ai-requirement-01-init` 生成并随流程回写。模板：

```markdown
# 当前批次上下文

批次号：PROJ-20261019-001
当前步骤：backend-dev
已冻结契约：<需求名>/02_设计/接口契约.yaml（v1，2026-10-19 冻结）
已完成 FR：FR-CORE-041 ~ FR-CORE-044
待澄清问题：2 条（见 <需求名>/01_需求/需求问题汇总.md）
本批次禁止修改：TBL_CORE_MAIN 既有字段（迁移成本高）
生效规范快照：projects/<项目码>/.agent/spec-effective/<项目码>.md @ sha256:7f3a…
```

## 2. L1 只写三类内容

全局 `CLAUDE.md` 是预算最紧张的文件，只允许放：

1. **技术栈基线** —— 但不展开写编码细节，那是规范包的职责。
2. **全局禁止事项** —— 禁止事项比推荐事项重要得多。推荐事项 AI 可能忽略，禁止事项被忽略会直接造成损失。
3. **Skill 路由表** —— 什么场景调用什么 Skill。

**不允许放进 L1 的**：具体编码规范（属于包）、业务流程描述（属于项目文档）、历史决策记录（属于 `projects/<项目码>/.agent/memory/`）。

## 3. 渐进式披露

Skill 的 `references/` 目录**不整体加载**。结构：

```
references/
├── INDEX.md              ← 只有这个被默认加载
├── 需求分析规范范本.md
├── 业务场景清单.md
└── 常见歧义需求案例.md
```

`INDEX.md` 格式：

```markdown
# 知识索引

| 文件 | 何时读取 |
|---|---|
| 需求分析规范范本.md | 每个需求开始分析时必读 |
| 业务场景清单.md | 需要判断需求属于哪个业务场景时 |
| 常见歧义需求案例.md | 遇到表述模糊的需求时读取 |
```

模型先读索引 → 判断需要哪些知识 → 按需读取。这把默认注入量从"全部知识"降到"索引 + 1-3 个文件"。

## 4. 生效规范快照的注入方式

`projects/<项目码>/.agent/spec-effective/<项目码>.md` 分三段，注入方式不同：

| 段 | 内容 | 注入方式 |
|---|---|---|
| **A. 常驻注入** | 每次执行都必须知道的硬约束 | 进 L1 或 L3 `CLAUDE.md`，常驻 |
| **B. 按需检索索引** | 其余条目的编号 + 摘要 + 触发场景 | Skill 按当前任务读取对应条目原文 |
| **C. 来源链** | 被覆盖/禁用条目的裁决记录 | 只在审计和排障时读 |

**A 段控制在 120 行以内是硬约束。** 它迫使团队回答一个问题："哪些规则是每次都必须知道的？"实测答案通常只有 15-25 条。

**A 段的筛选判据**：不看这条会不会**做错**（而不是"这条重不重要"）。"接口必须带租户参数"符合——不看就会写出越权代码；"变量命名用驼峰"不符合——不看也基本不会错，且 lint 能兜住。

## 5. 注入前的自检清单

任何内容进入上下文前，过一遍这五问：

1. 这条内容**每次执行**都需要吗？不是 → 放按需检索。
2. 这条内容 AI **不看也能做对吗**？能 → 删掉，不要浪费预算。
3. 这条内容**在别处已经有了吗**？有 → 引用编号，不要复制。
4. 这条内容是**约束**还是**背景知识**？背景 → 放 `references/` 或 `projects/<项目码>/.agent/memory/`。
5. 这条内容**三个月后还成立吗**？不成立 → 别写进规范，写进批次状态。

## 6. 防腐化机制

知识库运行三个月后必然出现互相矛盾的条目。三条机制对抗它：

**一是规范条目挂编号。** 发现矛盾时能查出哪条是新的、哪条该废。同层冲突时以编号大者（更新者）为准，并归档旧条目。

**二是每月一致性检查。** 检查：Skill 引用的 `references` 文件是否还存在？规范中的示例代码是否还能通过 lint？编号总表中是否有失效编号？`project.yaml` 引用的包版本是否还有效？

**三是"不被执行的规则即删除"。** 某条规范连续三个批次没有被任何 Skill 引用，标记为候选删除。这条机制让知识库保持精瘦，而不是逐年膨胀成无人敢改的巨物。

**执行方式**：调用 `ai-spec-check`。它自己知道该查什么，调用者不需要记任何参数。

它检查的是**跨文件的接缝**——单文件检查发现不了、拼起来才暴露的那类问题：STD 条目悬空引用、
Skill 名引用有效性、Skill 目录结构完整性、上下文预算超标、门禁引用了未实现的检查项、
文档状态描述与实际矛盾、挂载层与真实定义不同步。

**建议每次改完规范或 Skill 后跑一次**，不必等到月度。2026-10-20 的一次端到端演练发现，
这套体系的卡点几乎全部落在这种接缝上（某个编号被 5 处引用却没有定义、
文档写着"未实现"而 Skill 早已实现）——单看每个文件都没问题。

**它只报告，不自动修复。** 修复涉及规范语义，必须由人决定；一次执行改掉几十个文件，
只要有一条判断错了，这份清单就再也没人信了。

## 7. 超预算的处理

触发预算是**报错**，不是警告，也不是硬跑。

| 触发项 | 处理 |
|---|---|
| `SKILL.md` 超 400 行 | 把「为什么」挪进 `references/`；**删执行步骤不是办法** |
| 快照 A 段超 120 行 | 有非硬约束的条目混进来了，重新筛选 |
| 单次执行超 3000 行 | 检查是否读了整份产出物而非按编号读相关段落 |

**上下文超预算率**（触发预算上限的执行次数占比）超过 10%，说明 Skill 需要系统性拆分。
