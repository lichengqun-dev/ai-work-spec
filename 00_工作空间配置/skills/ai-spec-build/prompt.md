# 指令：执行规范编译

## 你要做的事

当用户要求"更新规范""重新生成快照""规范好像没生效""新项目接入"时，
**执行本 Skill 的实现脚本**（位于本 Skill 目录下的 `scripts/spec_build.py`）。

脚本要的参数由用户的意图决定：

| 用户说的 | 该给脚本什么 |
|---|---|
| 点名了某个项目 | 编译那一个项目 |
| "全部""所有项目" | 编译全部 |
| "只看看有没有问题"（CI 场景） | 只校验，不写文件 |
| "有哪些包可选" | 列出包与版本 |

参数写法见脚本自身的 docstring——**调用者不需要知道，也不该被要求记。**

## 执行后必须做的事

**逐条读出脚本输出，不要总结成"已完成"。** 输出包含三类信息，都要如实转达：

1. **成功行**：`✅ <项目>：生效 N 条（常驻 M），覆盖/禁用 K 条`
   —— 把 N、M、K 念出来。M 异常大（如超过 40）时提示用户检查 `tier: resident` 是否滥用。

2. **警告行**（以 `⚠️` 开头）：原样转达，并解释含义。
   - A 段超预算 → 有非硬约束的条目被打成 `tier: resident`。判据是"不看这条会不会做错"，不是"这条重不重要"。
   - 项目级条目超 30 条 → 该项目的共性可能还没抽象成包，建议运行 `ai-spec-promote` 分析候选。
   - **源文档已变更（漂移）** → 项目级散文改了但还没重新提炼。**这条要重点转达，不要一句"有警告"带过**：
     把「哪个提炼文件 ← 哪个源文档」逐行列出来，说明**快照里的项目级约束可能缺条或过时**，
     并给出处理方式——调用 `ai-spec-extract` 重新提炼，然后重跑构建。
     **不要建议手工去改 `.agent/rules/` 里的文件**：那会让来源指纹对不上，等于制造一个假告警。
   - 项目根有看似条目头却不会被解析的行 → 那些是散文里的残留（早期把条目写进散文留下的）。
     逐行列出，说明项目级条目现在只从 `.agent/rules/` 读，并指向 `ai-spec-extract`。

3. **失败行**（以 `❌` 开头）：**原样转达全部内容，包括多行缩进的细节**，然后给出处理建议。
   **不要试图"绕过"失败**——不要建议修改脚本、不要建议删掉校验、不要建议把 frozen 条目改成 false。
   每一条校验失败都对应一种真实会出问题的情况，见 `references/冲突仲裁规则.md`。

## 常见失败与正确应对

| 失败信息 | 含义 | 正确应对 |
|---|---|---|
| `禁止对 frozen 条目执行 …` | 想改一条不可协商的规则 | 告知用户走知识库 Owner 流程修改基线；说明 frozen 只应用于安全红线、编号体系、审计留痕这类条目 |
| `disable …『expires』必填` | 想禁用但没写有效期 | 让用户补 `expires`。**不要**建议填一个很远的日期（如 9999）——那等于把临时变永久 |
| `disable … 需要 approved_by` | 禁用基线/包条目缺审批 | 让用户找对应 Owner 审批。项目层不能单方面禁用共享规范 |
| `override 引用了不存在的条目` | 条目编号写错或已被删除 | 用 `--list` 确认包与条目；注意编号一经启用不复用，删除的条目应标记 `[已废弃]` 而不是删掉 |
| `条目前缀与包不一致` | 条目放错包，或包前缀写错 | 判断是条目该挪包，还是包的 `prefix` 该改。前者更常见 |
| `条目编号冲突` | 两个包用了同一个编号 | 改其中一个的编号。**不要**只改前缀绕过——前缀和编号必须同时自洽 |
| `版本不匹配` | manifest 锁定的版本与包实际版本不同 | 这是设计使然：包升级不会自动影响项目。升级要显式改 manifest 并走升级评估 |
| `同层条目冲突且无法裁决` | 两个领域包对同一决策点给出不同答案 | 在 manifest 的 `domains` 里显式声明优先级。这是业务决策，要问业务负责人，不要替他们决定 |

## 你绝对不要做的事

- **不要手工编辑 `projects/<项目码>/.agent/spec-effective/` 下的文件。** 它是生成物，手改会被下次构建覆盖。要改规范就改包或 manifest。
- **不要为了让构建通过而放宽校验。** 校验是这套体系的全部价值来源；放宽一次，后面就没人再信任快照。
- **不要在 manifest 里粘贴包内规范的正文。** 只允许按条目编号引用——`overrides` 的 `content` 字段只写"本项目要追加或替换的那部分"。
- **不要自动升级包版本。** 版本锁定是刻意设计，防止包一改全体项目跟着抖动。
- **不要执行 git 操作。**

## 输出格式

执行完用下面结构回复（保持简短）：

```
项目：<项目码>
结果：生效 N 条（常驻 M 条），覆盖/禁用 K 条
快照：projects/<项目码>/.agent/spec-effective/<项目码>.md

<如有警告或失败，原样列出>
<如失败，给出上表中的对应处理建议>
```
