# 冲突仲裁规则

> 回答两个问题：为什么这些校验存在，以及构建失败时该怎么处理。

## 1. 优先级总表

**批次特例 > 项目层 > 领域包 > 技术栈包 > 团队基线**

`frozen: true` 的条目是例外：它不接受**任何**形态的项目层修改（override / disable / append 全部拒绝）。

## 2. 为什么 frozen 连 append 都拒绝

一个自然的疑问：append 只是"追加约束"，不改变原意，为什么也拒？

因为 append 可以被用来实质架空原条目。例如 frozen 条目写"AI 不得执行 git 操作"，项目层 append 一句"本项目例外：允许在开发分支直接提交"——形式上没改原文，实质已经废掉了它。

**frozen 的语义是"不可协商"。既然不可协商，就不存在"部分修改"这种状态。** 确需修改走知识库 Owner 流程，而不是在项目层找缝。

frozen 的合理使用范围很小：安全红线、编号体系、审计留痕要求、AI 协作红线。**建议不超过基线条目的 10%–15%。** 一旦滥用到"所有基线条目都 frozen"，项目层就失去意义，团队会转而绕开知识库。

## 3. 三类冲突的处理方式

| 情形 | 处理 | 是否阻断 |
|---|---|---|
| **跨层冲突**（项目 vs 包、包 vs 基线） | 高层胜出，自动裁决并记录来源链 | 否 |
| **同层不同包冲突**，manifest 已声明 `domains` 顺序 | 顺序靠前者胜出，记录裁决 | 否 |
| **同层不同包冲突**，未声明优先级 | 报错 | **是** |
| 同一条目编号出现在两个来源 | 报错 | **是** |
| 对 frozen 条目做任何修改 | 报错 | **是** |

### 为什么"未声明优先级"要报错而不是随便挑一个

因为静默的选择会产生**隐性债务**：三个月后有人发现金额字段类型不对，追查下去发现是两个领域包冲突，而当时的裁决是工具随机做的——没有人能解释为什么。

**任何自动裁决都必须留下可追溯的记录，做不到记录的就应该失败。**

## 4. 冲突如何被检测出来

跨包的语义矛盾（两条不同的规则对同一决策点给出不同答案）**无法机械判定**——需要读懂自然语言。所以采用显式声明：

条目在 meta 中声明 `conflicts_with`：

```
<!-- meta
tier: indexed
scope: 金额字段类型
frozen: false
conflicts_with: STD-DOM-PAYMENT-012
-->
```

只有声明了冲突，构建器才会去裁决。没有声明的语义矛盾不会被发现——**这是本机制的已知边界**，需要靠评审来补。声明 `conflicts_with` 的纪律：

- 只在两条规则对**同一个决策点**给出**不同答案**时使用
- "表单用自研组件库" 与 "表格用虚拟滚动" **不是冲突**，只是不同主题
- 宁可不声明也不要滥声明——滥用会让优先级声明变成噪音，最终没人认真填

## 5. overrides 三种动作的选择顺序

**优先 append，其次 disable，最后才 override。**

| 动作 | 语义 | 代价 |
|---|---|---|
| `append` | 在原条目后补充分内容，不改原意 | 无。仍能跟随包更新 |
| `disable` | 本条目不适用于本项目 | 失去该条约束；必须带 `expires` 到期复查 |
| `override` | 替换原条目内容 | **失去该条目后续的一切包更新**，从此这条规范由项目自己维护 |

很多被当成"冲突"的情况其实只是"项目想把约束写得更严"——那用 append 就够了。

## 6. 为什么 disable 必须带 expires

`expires` 是防止**"临时禁用变永久遗忘"**的唯一机制。

现实里绝大多数禁用都始于一个合理理由（赶工期、客户特殊要求、环境限制），然后没有人再回来看它。一年后项目里积压二十条 disable，没人知道哪些还有必要、哪些早就该恢复。

到期后**不自动续期**，而是生成复查任务。强制人重新做一次判断——这个动作本身就是价值。

**反模式**：把 `expires` 填成 `9999-12-31`。这等于没填，属于规避机制而非使用机制。

## 7. 构建失败时的排查顺序

```
1. 看清失败信息里的条目 ID 和来源文件（脚本会打印）
2. 判断失败类型：
   - 配置写错（编号不存在、前缀不对、缺字段）→ 改 manifest 或包
   - 设计冲突（同层冲突、想改 frozen）→ 这是需要人做决策的，不要自己绕过
3. 修完重跑。不要用 --check 跳过校验（它只是不写文件，校验照跑）
```

**绝对不要做的三件事**：改脚本放宽校验、把 frozen 改成 false、删掉报错的条目。
