# 输出结构与解读

> 快照 `projects/<项目码>/.agent/spec-effective/<项目码>.md` 分四段。理解这四段的**用途差异**比理解内容更重要。

## 段位速览

| 段 | 内容 | 谁读 | 注入方式 |
|---|---|---|---|
| **A** | 常驻注入 | 每次执行代码生成/设计的模型 | 进项目 CLAUDE.md，**常驻** |
| **B** | 按需检索索引 | 执行到具体任务的模型 | 按 `触发场景` 列定位后读条目原文 |
| **C** | 来源链与裁决记录 | 人（审计、排障） | 一般不注入 |
| **D** | 项目声明摘要 | 人（确认配置是否符合预期） | 不注入 |

## A 段：常驻注入

**这是预算最紧张的一段，硬上限 120 行。**

每条格式为两行：条目 ID + 标题 + 来源，以及规则首句。来源标注为 `baseline` / 包名 / `项目特有`，末尾带 `← 已覆盖` 或 `← 本项目追加` 标记的表示该条在本项目被改过。

**判据是"不看这条会不会做错"**，不是"这条重不重要"。举例：

- ✅ 符合：「接口必须携带隔离标识」——不看就会写出越权代码
- ❌ 不符合：「变量命名用驼峰」——不看也基本不会错，且 lint 能兜住

**A 段条目过多（超过 ~35 条）是设计信号**，说明 `tier: resident` 被滥用了。要么收紧判据，要么把条目拆到更具体的包里。段位膨胀会让常驻上下文失去焦点，最终所有规则都被稀释。

## B 段：按需检索索引

一张表：条目 ID、摘要、来源、触发场景。

**表里没有正文**，只有定位信息。模型执行到具体任务时（如"编写 Service 层"）按 `触发场景` 列找到相关条目，再回包文件读原文。

这个设计的意义：不需要把全部规范塞进上下文，只需要让模型知道"有哪些规范、什么时候该看哪条"。

**隐含要求**：条目的 `scope` 字段必须写清触发场景（如"编写 Service 层时"），写"后端"这种过于宽泛的词会让索引失去检索价值。

## C 段：来源链与裁决记录

只列**被改动过**的条目：覆盖（overridden）、追加（appended）、禁用（disabled）、被优先级覆盖（shadowed）。每条带来源与原因。

**这段是审计的入口。** 当有人问"为什么这条规则现在是这样"，答案在这里，而不是在规范文件里——因为规范文件只有"当前状态"，没有"为什么变成这样"。

如果没有改动，显示"本次构建无覆盖、无追加、无禁用、无冲突裁决"。

## D 段：项目声明摘要

列出本项目选了哪些包、版本、包状态，以及领域包优先级顺序和项目特有条目数。

**快速确认配置是否符合预期的地方。** 常见用途：

- 新项目接入后核对选包是否正确
- 排查"某条规范为什么没生效"——先看 D 段确认那个包是否真的被选中了
- 看到包状态是 `skeleton` 就该意识到：这个包的内容还很少，别指望它约束质量

## 机读版 JSON

`projects/<项目码>/.agent/spec-effective/<项目码>.json` 含逐条完整信息（含 `layer_label`、`origin_file`、`note`）。用途：

- 生成统计报表（哪条规范被最多项目禁用 → 该规范可能有问题）
- 做断链检测与覆盖率统计
- 给其他工具消费

## 执行日志

`projects/<项目码>/.agent/logs/spec-build.jsonl` 每次构建追加一行：

```json
{"at": "2026-10-19T16:59:45+08:00", "project": "<项目码>", "entries": 54,
 "manifest_hash": "sha256:38400d095a225331", "snapshot_hash": "sha256:89cc009a05c096ac",
 "overrides": 1, "conflicts": 0}
```

`manifest_hash` 与 `snapshot_hash` 是**可审计性的关键**：批次状态文件里记录快照哈希后，就能精确回答"这个批次开发时用的是哪版规范"。

`snapshot_hash` 变了说明规范内容变了——如果这个变化发生在批次进行中且没人察觉，就是一个值得追查的信号。
