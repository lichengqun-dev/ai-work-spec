# ai-spec-build · 规范编译

## 能力声明

把**项目级**规范编译成单一「项目规范底座」（快照）：项目级条目 + 包指针 + 来源链。

**域级规范不在它的输入里**——各域 `standards/` 与 `09_资产库/规范包/` 到对应阶段按原文读取，
不参与编译。曾经的覆盖、禁用、frozen、冲突仲裁四类机制因此全部退役（见
`references/机制退役说明.md`）。

这是纯脚本 Skill，**不调用模型**——合并结果必须可复现、可 diff、可审计。

**不做什么**：不从散文文档里提取条目（那是 `ai-spec-extract`）；不修改任何规范内容；
不因"源文档改了"而判失败。

## 何时用 / 何时不用

- **用**：接入新项目后；改了规范包条目或项目 manifest 后；批次启动前（确认快照与当前规范一致）；
  CI 里作为门禁（只校验不写文件）
- **不用**：项目根的散文改了（走 `ai-spec-extract`）；只想核对条目引用是否悬空（走 `ai-spec-check`）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 项目 manifest | `projects/<项目码>/.agent/project.yaml` | 是 | `project` 字段须与目录名一致 |
| 项目级条目（提炼） | `projects/<项目码>/.agent/rules/*.md` | 否 | 条目前缀须为 `STD-PRJ-<项目码大写>-`；frontmatter 的 `source_hash` 与源文档比对 |
| 项目级条目（内联） | manifest 的 `project_only` | 否 | 同上 |
| 规范包 | 知识库根下 `09_资产库/规范包/{stacks,domains}/*/PACK.md` | 是 | frontmatter 必填字段齐全，`files` 列出的文件都存在 |

> **项目根的散文文档不是本 Skill 的输入。** 它们由 `ai-spec-extract` 摘成条目后才进快照——
> 本 Skill **不理解散文**，也不会去猜哪句话是约束。

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 生效规范快照（人读） | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | Markdown，分 A/B/C/D 四段 |
| 生效规范快照（机读） | `projects/<项目码>/.agent/spec-effective/<项目码>.json` | JSON，含逐条来源链 |
| 执行日志 | `projects/<项目码>/.agent/logs/spec-build.jsonl` | 追加一行 JSON |

## 执行方式

调用本 Skill 时说明要做什么即可：

| 你要做什么 | 本 Skill 的行为 |
|---|---|
| 接入新项目 / 改了规范包或 manifest | **编译**该项目的快照，并做全部校验 |
| 一次重建所有项目 | **编译全部** |
| 只想知道有没有问题，不写文件（CI 用） | **只校验** |
| 想知道有哪些包可选、包里各有多少条 | **列出包与版本** |

实现是本 Skill 目录下的 `scripts/spec_build.py`，参数说明见脚本自身的 docstring——
**调用者不需要记参数，也不该被要求记。** 依赖 Python 3.8+ 与 PyYAML；
缺 PyYAML 时本 Skill **拒绝执行并说明**，不会退化成"编译失败就当通过"。

## 前置条件

**hard（不满足则拒绝执行）**

- `CLAUDE.md` 与 `09_资产库/` 均存在（脚本据此定位仓库根目录）
- 目标项目的 `project.yaml` 存在且 `project` 字段与目录名一致
- **任一校验项失败即整体失败，不生成任何文件**（不产生"半成品快照"）

**soft**

- 无。本 Skill 的输入全在仓库内，没有"顺序性"前置——任何时刻单独运行都成立

## 校验项（任一失败即中止）

1. `PACK.md` frontmatter 必填字段齐全，`files` 列出的文件**都存在**——
   路径写错会让人在对应阶段找不到规范，而那时已经离错误现场很远
2. manifest 引用的包存在，且**版本与锁定的版本一致**（包升级不会自动影响项目，升级要显式改 manifest）
3. manifest 中 `stacks` 的键与该包的 `key` 一致（`db` 维度选错包会注入方向相反的规则）
4. 项目级条目前缀正确（`STD-PRJ-<项目码大写>-`）、编号在项目内唯一

**包内条目不参与校验**——它们不进快照，编号唯一性与引用有效性由 `ai-spec-check` 兜底。

## 执行后必须做的事

**逐条读出脚本输出，不要总结成"已完成"。** 输出含三类信息，都要如实转达：

1. **成功行**：`✅ <项目>：生效 N 条（常驻 M），覆盖/禁用 K 条`
   —— 把 N、M、K 念出来。M 异常大（如超过 40）时提示用户检查 `tier: resident` 是否滥用。

2. **警告行**（以 `⚠️` 开头）：原样转达，并解释含义。
   - A 段超预算 → 有非硬约束的条目被打成 `tier: resident`。判据是"不看这条会不会做错"，不是"这条重不重要"。
   - 项目级条目超 30 条 → 该项目的共性可能还没抽象成包，建议运行 `ai-spec-promote` 分析候选。
   - **源文档已变更（漂移）** → 项目级散文改了但还没重新提炼。**这条要重点转达，不要一句"有警告"带过**：
     把「哪个提炼文件 ← 哪个源文档」逐行列出来，说明**快照里的项目级约束可能缺条或过时**，
     并给出处理方式——调用 `ai-spec-extract` 重新提炼，然后重跑构建。
     **不要建议手工去改 `.agent/rules/` 里的文件**：那会让来源指纹对不上，等于制造一个假告警。
   - 项目根有看似条目头却不会被解析的行 → 那些是散文里的残留。
     逐行列出，说明项目级条目现在只从 `.agent/rules/` 读，并指向 `ai-spec-extract`。

3. **失败行**（以 `❌` 开头）：**原样转达全部内容，包括多行缩进的细节**，然后给出处理建议。
   **不要试图"绕过"失败**——不要建议修改脚本、不要建议删掉校验、不要建议把 frozen 条目改成 false。

## 常见失败与正确应对

| 失败信息 | 含义 | 正确应对 |
|---|---|---|
| `版本不匹配` | manifest 锁定的版本与包实际版本不同 | 这是设计使然：包升级不会自动影响项目。升级要显式改 manifest 并走升级评估 |
| `包引用了不存在的技术栈包 / 领域包` | 包名写错，或包还没建 | 用 `--list` 确认包名与版本 |
| `中列出的条目文件不存在` | 包内规范文件被改名或删除，而 `PACK.md` 的 `files` 没跟着改 | 改 `PACK.md` 的 `files`。**这条校验存在的理由**：路径错了要到对应阶段才会暴露，那时已经离现场很远 |
| `项目级条目前缀不符` | 规则文件里写了别的项目前缀，或把格式示例写成了真实编号 | 改前缀；格式示例写成占位形式（`STD-PRJ-<项目码大写>-<序号>`）就不会被解析 |
| `项目级条目编号重复` | 两个提炼文件用了同一个编号 | 改其中一个。**不要**只改结尾数字凑合——编号一经启用不复用，改编号等于断掉所有引用 |
| 快照被重新编译成全量合并 | 有人把域级装回了快照 | 这是异常。查 `spec_build.py` 是否被改回旧版本；`ai-spec-check` 会报「快照混入非本项目条目」 |

## 独立执行

纯脚本 Skill，不依赖批次状态：**任何时刻都可单独运行**。
最安全的单独执行形态是"只校验不写文件"——它在任何仓库状态下都不会改动任何东西。

## 边界（明确不做）

- **不修改任何规范内容。** 只读包、manifest、rules，只写 `spec-effective/` 与 `logs/`
- **不从散文文档里提取条目。** 本 Skill 只认已经带编号的条目
- **不因漂移而失败。** 源文档变了就报「已变更」，但快照照常产出（改文档是常态）
- **不手工编辑 `spec-effective/` 下的文件。** 它是生成物，手改会被下次构建覆盖
- **不为让构建通过而放宽校验。** 校验是这套体系的全部价值来源；放宽一次，后面就没人再信任快照
- **不在 manifest 里粘贴包内规范的正文。** manifest 只写"选了哪些包"，正文留在包里
- 不自动升级包版本。包升级必须由人改 manifest
- **不解析域级规范文件**——它们不进快照，文件里的 `## STD-…` 标题只是给人用的段落锚点
- 不调用模型
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 校验失败 | 打印具体条目 ID、来源文件、失败原因，退出码 1，不写文件 |
| **源文档已变更（漂移）** | **不失败**。告警同时写进 stderr 与**快照正文顶部**，并在 JSON 的 `rules_drift` 里列出。处理是调用 `ai-spec-extract` 重新提炼 |
| 项目根有看似条目头却不会被解析的行 | 告警列出具体文件与行号，**不失败**。提示改用 `ai-spec-extract` |
| A 段超过 120 行预算 | 打印警告但**不失败**（提示有非硬约束条目被打成了 resident） |
| 项目级条目超过 30 条 | 在快照 D 段标注警告，建议运行 `ai-spec-promote` |
| 仓库根目录定位失败 | 退出码 2，提示用 `--repo` 显式指定 |

## 输出格式

执行完用下面结构回复（保持简短）：

```
项目：<项目码>
结果：生效 N 条（常驻 M 条），覆盖/禁用 K 条
快照：projects/<项目码>/.agent/spec-effective/<项目码>.md

<如有警告或失败，原样列出>
<如失败，给出上表中对应的处理建议>
```
