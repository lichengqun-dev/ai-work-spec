# ai-flow-autopilot · 研发流程总入口

## 能力声明

**研发流程的总入口。** 接收用户的一句话描述（如「给列表页加个导出」「线上导出偶发超时」「这个字段为什么这么设计」），
判定路径，驱动全流程，每阶段自动跑门禁。你的工作是把这句话变成一条正确的流程，并在每个阶段卡住该卡的地方。

它是**编排层**：不做任何实际工作，只负责判定、调用、拦截、状态推进。

**为什么需要它**：没有它时，使用者必须知道 40 个 Skill 各自的职责、四条路径的区别、每一步对应哪个 Skill、
什么时候该跑哪道门禁——**这是"上手难度高"的全部来源**。有了它，使用者只说一件事。

**不做什么**：不做实际工作（一切由被编排的 Skill 完成）、不代替人做判断、不替用户决定路径——见「边界」。

## 何时用 / 何时不用

- **用**：任何研发任务，尤其是"不确定走哪条路"的时候。用户只描述要做的事即可，不必知道 40 个 Skill 的分工
- **不用**：知识库自身的治理（改规范、加 Skill、怀疑文档过期）——那些走 `ai-spec-build` / `ai-spec-extract` 等治理工具，
  本 Skill 编排的是**阶段 Skill**，不含 `ai-spec-*` 那四个治理工具

四条路径（判定依据与常见歧义见 `references/路径判定.md`）：

| 路径 | 适用 | 起点 |
|---|---|---|
| **新建** | 从零到一的新系统 | `ai-requirement-00-intake` → 全部 23 步 |
| **迭代** | 已有系统加功能 / 改行为 | `ai-iteration-01-impact` |
| **快车道** | 小改动（有量化准入条件） | `ai-daily-01-fastlane` |
| **咨询** | 只是问问题，不改东西 | `ai-daily-04-qa`（只读，**不建批次**） |

最常见的歧义是「加个功能」到底是新建还是迭代——判据是：**改的是已有功能的行为，还是加一个原来不存在的能力**。
前者是迭代（走变更子批次），后者是新建。判不准就问，走错流程的代价远大于多问一句。

**判定有歧义时列出两种可能及各自代价，请用户确认，不要默认选一个。**

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 任务描述 | 用户 | 是 | 能判断出「做什么 + 对哪个项目」。判断不了则澄清，**不猜** |
| 项目码 | 用户，或从描述推断 | 是 | `projects/<项目码>/` 存在 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 不存在则先运行 `ai-spec-build` |
| 全部下游 Skill | 各域 `skills/` | 是 | 每个都有 `SKILL.md` 且前置条件可判定 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 路径判定结论 | 输出给用户 | 路径类型 + 依据 + 下一步 |
| 批次状态 | `projects/<项目码>/.agent/state/<批次号>.yaml` | 各步骤状态与门禁结果齐全 |
| 全部下游产出物 | 见各 Skill 的产出契约 | — |

报告的结构见「输出格式」。

## 前置条件

**hard（不满足则拒绝执行）**

- 目标项目已接入（`projects/<项目码>/.agent/project.yaml` 存在且 `repo` 字段已填真实路径）
- 生效规范快照存在（无快照则先运行 `ai-spec-build`，**不要在规范未知的情况下开工**）
- 当前无同项目的 `in_progress` 批次（有则先续做或关闭，**不允许并行两个批次**）
- 任务描述能判断出「做什么 + 对哪个项目」（判断不了则澄清并中止，**不猜**）

**soft（不满足则提示，可继续）**

- 无。本 Skill 是流程起点，没有"上一阶段产出物"这类顺序性前置——hard 全满足即可直接调用。
  被编排 Skill 的 soft 前置不满足时，由「执行步骤」第 3 步处理（提示 + 继续 + 产出物标注）

## 执行步骤

1. **判定项目码**——从描述里判断是哪个项目。**判断不了就问**，不要挑一个最像的继续——
   走错项目的后果是产出物落到错误的仓库，而追溯链从第一步就错了。

2. **判定路径**——四条路径见「何时用 / 何时不用」，判据与常见歧义见 `references/路径判定.md`。
   判定有歧义时列出两种可能及各自代价，请用户确认，**不要默认选一个**。

3. **逐步驱动**。对批次状态文件里 `steps` 的每一步：

   ```
   1. 读该 Skill 的 SKILL.md，逐条核对「前置条件」
      └─ hard 不满足 → 停下，说明是哪一条、需要先做什么。**不要"先跑跑看"**
      └─ soft 不满足 → 提示并继续，产出物标注「未经上游确认 —— <哪一条没满足>」
   2. 按它的「执行步骤」执行
   3. 产出物按产出契约落位，登记到状态文件的 artifacts（含哈希）
   4. 该阶段结束时跑对应门禁
   ```

   **每步做完都要更新状态文件**，不要攒到最后。断点续做靠的就是它——
   中途被打断时，接手的人（或下一个会话）读状态文件就知道卡在哪。

4. **门禁怎么处理**。**调用 `ai-gate-runner` 执行该阶段对应的门禁**——它自己知道去哪读门禁定义、
   该跑哪些检查项。你不需要知道任何参数，也不需要把参数告诉用户。

   | 执行器结果 | 你该做什么 |
   |---|---|
   | `passed` | 继续下一步 |
   | `failed` | **停止**，原样输出未通过项与定位。**不尝试绕过、不"修一下让它过"** |
   | `pending_manual` | 把人工核对清单**原样列出**，等用户核对后签核。**不替用户签核** |
   | 拒绝执行（exit 2） | 报明原因（跳步 / 引用了未实现的检查项 / 定义格式错误） |

   **三条不能违反的**：

   - **不替人判断门禁的人工项。** 那些项之所以标 `人`，就是因为需要判断力；替人拍板会让门禁失去意义
   - **不替人签核。** `--confirm --by <名字>` 里的名字必须是真实的人
   - **不自动豁免。** 豁免要人给出原因与复查日期

   遇到 BLOCK 级 `skip` 时说明清楚：这类项不能用 `--confirm` 越过，要么补齐材料，要么走 `--waive`。

5. **续做**（用户说「继续」时）。读 `projects/<项目码>/.agent/state/` 下该项目的 `in_progress` 批次，
   从 `current_step` 恢复。

   - **不重跑 `status: done` 的步骤**
   - 但**校验其产出物哈希**——变了说明有人手工改过，提示确认后再决定是否重跑

6. **收尾**。归档走 `ai-archive-01-close`；输出本批次做了什么、有哪些遗留。

## 独立执行

- **hard 全满足即可单独运行**：本 Skill 就是流程入口，任何时刻都可直接调用，不必从别处开始
- **咨询路径不建批次**：只读回答，不写状态文件、不驱动步骤
- soft 不满足时照常推进，被编排 Skill 的产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 状态文件不可写（如未接入批次）时：产出物落到各 Skill 指定的路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不做实际工作。** 需求分析、设计、编码、测试都由对应的 Skill 完成
- **不代替人做判断**：门禁的人工项、需求取舍、架构选型、验收签字，全部交还给人
- **不替人签核**：`--confirm --by <名字>` 里的名字必须是真实的人
- **不替用户决定路径**。判定有歧义时问，不要选一个默认值继续，也不要替用户拍板
- **不在门禁 `failed` 时继续**
- 不跳过任何步骤，即使觉得"这一步没必要"
- 不自动豁免、不自动续期
- 不为让门禁通过而改产出物、改门禁定义或改状态文件
- 不修改任何 Skill 的定义
- 不调用 `status: not_implemented` 的 Skill（本仓库目前无此类）
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 任务描述判断不出项目 | 澄清，中止 |
| 路径判定有歧义 | 列出两种可能及各自代价，请用户确认 |
| 某 Skill 拒绝执行（前置条件不满足） | 停止，报告是哪一条不满足、需要先做什么 |
| 门禁 `failed` | 停止，原样输出未通过项与定位；**不尝试绕过** |
| 门禁 `pending_manual` | 列出人工清单，等 `--confirm --by <名字>`；**不替人签核** |
| 门禁遇 BLOCK 级 skip | 说明需补齐材料或走 `--waive`（带批准人与复查期） |
| 批次中断（超上下文 / 人下班） | 状态文件已记录进度，下次从 `current_step` 续做 |

## 输出格式

### 每完成一步

```
批次：PROJ-20261020-001（新建）　进度 8/23
✅ api —— 产出 <需求名>/02_设计/接口契约.yaml（sha256:7f3a…）
⏸  gate-03 设计评审 —— pending_manual

需人工核对（3 项）：
- [9] 是否引入新的中间件或第三方依赖
- [10] 技术方案符合分层架构规范
- [11] 索引设计覆盖高频查询场景

核对后告诉我结论与你的名字，我来完成签核。
```

我回退到上一步时，把上面那段 `[9]` 之类的清单**原样**给用户——
他核对的是这几项的具体内容，不是"通过/不通过"四个字。

### 卡住时怎么报告

**失败要停就停得干净。** 不要：

- 重试一次看会不会好
- 跳过这一步继续
- 自己动手把缺的产出物补上（那会让"哪个 Skill 出了问题"变得不可追溯）

报告格式：

```
批次：PROJ-20261020-001（新建）
当前步骤：backend（第 12/23 步）

✅ init · analysis · prototype · prd · arch · detail · db · api
⏸  backend —— 前置条件不满足

原因：契约未冻结（gate-03 状态为 pending_manual）
需要：核对下面这几项后签字确认（告诉我你的名字即可，我会替你完成签核）

  - [8] 是否引入新的中间件或第三方依赖
  - [9] 是否引入新的中间件或第三方依赖
  - [10] 技术方案符合分层架构规范
  - [11] 索引设计覆盖高频查询场景

签核后我会继续 backend 及其后的步骤。
```
