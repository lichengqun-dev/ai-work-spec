# ai-spec-check · 跨文件一致性检查

## 能力声明

对全库做**跨文件一致性检查**，输出问题清单。

它查的不是"某个文件写错了"，而是**单看每个文件都没问题、拼起来才暴露**的那类问题：
编号被引用却没有定义、Skill 名拼错、目录结构不完整、文档状态与 `status` 字段矛盾、
挂载层与真实定义不同步、门禁引用了不存在的检查项。

**知识库的腐化从不出现在单个文件里。** 设计文档把"每月一致性检查"列为防腐化三机制之一，
但 2026-10-20 的一次端到端演练发现：**卡点几乎全部落在跨域的接缝上**——
某个编号被 5 处引用却根本没有定义；文档写着"未实现"而 Skill 早已实现。
这两类问题的共同点是**单文件检查发现不了**。所以它是"每次改完就跑一次"，不是"每月想起来才跑"。

**只读。** 不修改任何文件，包括不"顺手修复"——修复是人的决定。

这是纯脚本 Skill，**不调用模型**：一致性判定必须可复现，同一次输入必须给同一份清单。

**不做什么**：不自动修复、不检查条目正文的语义矛盾、不做 Markdown 渲染与拼写检查——见「边界」。

## 何时用 / 何时不用

- **用**：
  - 改完任何规范条目、Skill 定义或门禁定义后
  - 新增或重命名 Skill 后
  - 重建挂载层后（`ai-spec-mount` 的下游）
  - 发版前
  - 怀疑文档与实现对不上时的第一动作
- **不用**：
  - 检查范围之外的那几类问题（语义矛盾、Markdown 结构、拼写）——它不查这些，见「检查项」
  - 想让检查器替你做修复——它只报告

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 仓库根目录 | 由 `CLAUDE.md` + `09_资产库/` 自动定位 | 是 | 两者都存在；否则拒绝执行 |
| 被测文件集 | 全库 `*.md` | 是 | 自动枚举，排除 `projects/`、`.claude/`、`.git/` |

无需任何参数。**调用者不需要知道检查项清单**——它自己知道该查什么。

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 问题清单 | 输出给调用者 | 按类别分组的 Markdown，每条含定位与原文 |
| 统计摘要 | 输出首行 | STD 条目数 / Skill 数 / 门禁检查项数 |
| 机读结果 | 输出给调用者（可选） | JSON，供 CI 消费 |

**不写任何文件。** 需要留档时由调用者自行落盘。

## 前置条件

**hard（不满足则拒绝执行）**

- 仓库根可定位（`CLAUDE.md` 与 `09_资产库/` 同时存在）
- Python 与 PyYAML 可用（缺 PyYAML 时**拒绝执行并说明**，不要退化成"没检查就说通过"）

**soft**

- 无。本 Skill 是只读检查，不依赖任何上游产出——任何时刻单独运行都成立

## 检查项（当前 14 类）

| # | 查什么 | 为什么它属于"接缝" |
|---|---|---|
| 1 | `STD-*` 条目悬空引用 | 条目可能只存在于别人的引用里 |
| 2 | Skill 名引用有效性 | 引用方与被引用方分属两个文件 |
| 3 | 目录结构与 frontmatter 完整性 | 缺 `description` 会让该 Skill 不被任何会话发现；残留 `prompt.md`、引用了不存在的 `references/`/`scripts/`/`assets/` 文件、账本字段没放进 `metadata`，都会被查出来 |
| 4 | 上下文预算超标 | 预算写在配置里，实际行数在另一个文件里 |
| 5 | 门禁引用的检查项都有实现 | 门禁定义与执行器是两个文件 |
| 6 | 文档状态描述与 `status` 字段矛盾 | 字段在一处，正文在另一处 |
| 7 | 挂载层与真实定义同步 | 挂载层是生成物，会悄悄过期 |

**检查项会随腐化方式增加。** 增加了哪些写在脚本里，不在这里复述——避免"两处清单需要同步"这种问题再生一层。

## 执行步骤

1. **执行本 Skill 的实现脚本**（**知识库根下** `00_工作空间配置/scripts/consistency_check.py`）。
   脚本**不需要任何参数**：它自己定位仓库根目录、自己枚举被测文件集。
   参数说明见脚本自身的 docstring——**调用者不需要知道，也不该被要求记。**

   **不要自己"顺便看一下"就下结论。** 检查必须是脚本跑出来的：人眼看不出"某个编号被 5 处引用却没有定义"。

2. **逐条读出脚本输出，不要总结成"已检查完毕"。**

3. **首行统计**：`STD 条目 N 个（被引用 M 个）｜ Skill X 个 ｜ 门禁检查项 Y 个`
   —— 把 N、M、X、Y 念出来。这四个数字是判断"知识库有没有在长大"的依据。

4. **无问题时**：脚本报 `✅ 未发现跨文件不一致`。
   **转达时必须同时说明覆盖边界**——它只覆盖脚本实际实现的那些检查类，
   不代表"整库已验证"。漏掉这句，用户会把"没查到"当成"没问题"。

5. **有问题时**：脚本按类别分组输出（每类含文件、行号、原文片段）。
   **原样转达，不要合并、不要挑重点、不要按自己的判断删减。**
   然后按「失败处理」表给出处理建议。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——它是只读终点，不依赖任何上游产出
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- **本 Skill 不写任何文件**，因此不存在"批次状态文件不可写"的情况

## 边界（明确不做）

- **不自动修复。** 只报告。就算问题看起来一目了然（"这不就是拼错了吗"），也先报告再等确认——
  自动修复会在一次执行里改掉几十个文件，而其中只要有一条判断错了，用户就再也无法信任这份清单
- **不要为了让检查通过而放宽检查。** 检查项是这套体系的防腐化机制本身；放宽一次，它就不再是信号
- **不要把"没查出问题"说成"已经验证没问题"。** 按「失败处理」所述转达覆盖边界
- **不要跳过脚本自己判断。** 你读不完 200 多个文件，也记不住哪些编号在哪里被引用过
- 不检查条目正文的**语义**矛盾（如"这条规范与那条规范冲突"），只处理显式声明的关系
- 不做 Markdown 渲染检查、不做拼写检查
- 不写任何文件
- 不调用模型
- 不执行 git 操作

## 失败处理

| 输出类别 | 含义 | 处理 |
|---|---|---|
| `STD 条目悬空引用` | 引用了一个没有定义的编号 | 二选一：补上定义，或改掉引用。**先确认是哪个方向错了**——新条目忘了写、还是引用方抄错了编号 |
| `Skill 名引用无效` | 引用了一个不存在的 Skill 名 | 核对是拼写错误，还是该 Skill 被重命名/删除了。**不要**直接改引用方——先确认被引用方是不是真的不存在 |
| `SKILL.md 元信息` | 缺字段或 `name` 与目录名不符 | 补齐字段。**`description` 缺失最严重**——它是 Claude 决定"什么时候用哪个 skill"的唯一依据，缺了该 Skill 不会被任何会话发现 |
| `Skill 命名` | 域前缀不在枚举内 | 改名为符合 `ai-<域>-<序号>-<动作>` 的形式，或在 `命名与编号规范.md` 里显式扩展枚举。**不要**为了消掉告警而随手改前缀 |
| `目录结构` | 缺 `references/INDEX.md`、残留 `prompt.md`、或 `SKILL.md` 引用了不存在的 `references/`/`scripts/`/`assets/` 文件 | 补齐或修正引用——官方格式下 `SKILL.md` 用**相对 skill 目录**引用资源，写成知识库根相对路径在挂载位置就读不到 |
| `上下文预算超标` | 某个文件超了行数上限 | 按 `上下文注入规范.md` 第 7 节处理：拆 Skill / 把领域知识挪进 `references/`。**不要**提高预算上限来消掉告警 |
| `门禁检查项` | 门禁引用了未实现的检查项 | 补齐实现，或从门禁定义里删掉该行。**不要**让执行器静默跳过——失效的门禁比没有门禁更糟 |
| `状态描述与实现矛盾` | 文档写着"未实现"而 `status` 是 `implemented` | **改文档，不改 `status`。** 这类矛盾几乎总是文档过期——它是这套体系里复现率最高的一类问题 |
| `Skill 挂载层不同步` | 挂载层的 `description` 与真实定义不一致，或存在孤儿挂载 | 运行 `ai-spec-mount` 重建挂载层。**不要手改** `.claude/skills/` 下的文件 |
| 查出问题 | 逐条列出（含文件、行号、原文片段） | 退出码 1 |
| 无问题 | 明确报"未发现跨文件不一致" | 退出码 0 |
| 缺 PyYAML / 找不到仓库根 | 检查根本没跑起来 | 退出码 2，**说明缺什么**，不要静默跳过 |

**"没查出问题"不等于"没问题"。** 它只覆盖「检查项」表中的 14 类；报告"未发现不一致"时必须同时说明这一边界，
否则会被当成"整库已验证"——那比不检查更危险。

## 输出格式

执行完用下面结构回复（保持简短）：

```
一致性检查结果：<通过 / N 处问题>
统计：STD 条目 N｜Skill X｜门禁检查项 Y
覆盖范围：<脚本实际检查的类别数> 类

<如有问题，按类别原样列出，每条带定位>

建议：<按上表给处理方向，逐条对应>
```

## 与其他 Skill 的关系

- 上游：无。它读全库，不依赖任何前置产出
- 下游：无。它是只读终点，产出的问题清单交由人处理
- 配套：改完规范跑 `ai-spec-build`，改完 Skill 跑 `ai-spec-mount`，然后跑本 Skill 收口
- 被调用：`ai-flow-autopilot` 在批次收尾时调用它
