# 指令：执行跨文件一致性检查

## 你要做的事

当用户要求"检查一下""文档是不是对不上了""改完规范跑一遍""发版前过一遍"时，
**执行本 Skill 的实现脚本**（位于本 Skill 目录下的 `scripts/consistency_check.py`）。

脚本**不需要任何参数**：它自己定位仓库根目录、自己枚举被测文件集。
参数说明见脚本自身的 docstring——**调用者不需要知道，也不该被要求记。**

不要自己"顺便看一下"就下结论。**检查必须是脚本跑出来的**：人眼看不出"某个编号被 5 处引用却没有定义"。

## 执行后必须做的事

**逐条读出脚本输出，不要总结成"已检查完毕"。**

1. **首行统计**：`STD 条目 N 个（被引用 M 个）｜ Skill X 个 ｜ 门禁检查项 Y 个`
   —— 把 N、M、X、Y 念出来。这四个数字是判断"知识库有没有在长大"的依据。

2. **无问题时**：脚本报 `✅ 未发现跨文件不一致`。
   **转达时必须同时说明覆盖边界**——它只覆盖脚本实际实现的那些检查类，
   不代表"整库已验证"。漏掉这句，用户会把"没查到"当成"没问题"。

3. **有问题时**：脚本按类别分组输出（每类含文件、行号、原文片段）。
   **原样转达，不要合并、不要挑重点、不要按自己的判断删减。**
   然后按下面的表给出处理建议。

## 各类问题的正确应对

| 类别 | 含义 | 正确应对 |
|---|---|---|
| `STD 条目悬空引用` | 引用了一个没有定义的编号 | 二选一：补上定义，或改掉引用。**先确认是哪个方向错了**——新条目忘了写、还是引用方抄错了编号 |
| `Skill 名引用无效` | 引用了一个不存在的 Skill 名 | 核对是拼写错误，还是该 Skill 被重命名/删除了。**不要**直接改引用方——先确认被引用方是不是真的不存在 |
| `SKILL.md 元信息` | 缺字段或 `name` 与目录名不符 | 补齐字段。**`description` 缺失最严重**——它是 Claude 决定"什么时候用哪个 skill"的唯一依据，缺了该 Skill 不会被任何会话发现 |
| `Skill 命名` | 域前缀不在枚举内 | 改名为符合 `ai-<域>-<序号>-<动作>` 的形式，或在 `命名与编号规范.md` 里显式扩展枚举。**不要**为了消掉告警而随手改前缀 |
| `三件套缺失` | 缺 `prompt.md` 或 `references/INDEX.md` | 补齐。三件套不全会让编排层无法判断这个 Skill 能不能调用 |
| `上下文预算超标` | 某个文件超了行数上限 | 按 `上下文注入规范.md` 第 7 节处理：拆 Skill / 把领域知识挪进 `references/`。**不要**提高预算上限来消掉告警 |
| `门禁检查项` | 门禁引用了未实现的检查项 | 补齐实现，或从门禁定义里删掉该行。**不要**让执行器静默跳过——失效的门禁比没有门禁更糟 |
| `状态描述与实现矛盾` | 文档写着"未实现"而 `status` 是 `implemented` | **改文档，不改 `status`。** 这类矛盾几乎总是文档过期——它是这套体系里复现率最高的一类问题 |
| `Skill 挂载层不同步` | 挂载层的 `description` 与真实定义不一致，或存在孤儿挂载 | 运行 `ai-spec-mount` 重建挂载层。**不要手改** `.claude/skills/` 下的文件 |

## 你绝对不要做的事

- **不要自动修复。** 本 Skill 只读。就算问题看起来一目了然（"这不就是拼错了吗"），也先报告再等确认——
  自动修复会在一次执行里改掉几十个文件，而其中只要有一条判断错了，用户就再也无法信任这份清单。
- **不要为了让检查通过而放宽检查。** 检查项是这套体系的防腐化机制本身；放宽一次，它就不再是信号。
- **不要把"没查出问题"说成"已经验证没问题"。** 按上一条转达覆盖边界。
- **不要跳过脚本自己判断。** 你读不完 200 多个文件，也记不住哪些编号在哪里被引用过。
- **不要执行 git 操作。**

## 输出格式

执行完用下面结构回复（保持简短）：

```
一致性检查结果：<通过 / N 处问题>
统计：STD 条目 N｜Skill X｜门禁检查项 Y
覆盖范围：<脚本实际检查的类别数> 类

<如有问题，按类别原样列出，每条带定位>

建议：<按上表给处理方向，逐条对应>
```
