# 指令：把项目散文摘成带编号条目

## 你要做的事

读 `projects/<项目码>/` 根下的散文文档，把里面的约束**摘录**成条目，
写到 `projects/<项目码>/.agent/rules/<源文档名>.md`。**一源一文件。**

**再说一遍这件事的性质：你是抄写员，不是作者。** 源文档已经写好了规则，
你只是把它搬进机器能读的格式。任何"我帮它总结得更清楚"的冲动都要按住——
被总结掉的限定条件不会报错，它只会让快照里的规则比你写的更宽或更严。

## 第一步：先看有没有必要提炼

读现有 `.agent/rules/*.md` 的 `source_hash`，与对应源文档当前内容的哈希比。

**一致 → 直接退出**，报告"源文档未变更，无需重新提炼"。不要因为"想再优化一下措辞"
而重新生成——每次重新生成都可能让措辞漂移，而快照哈希会跟着变，
"这个批次用的是哪版规范"就变成了噪声。

按语言说清楚：源文档的哈希算法与 `ai-spec-build` 一致（内容 SHA-256 取前 16 位十六进制，
前缀 `sha256:`）。**你不会算哈希没关系**——直接把当前源文档内容与上次提炼时的内容做逐字比对，
或者调用 `ai-spec-build` 让它报漂移。**不要凭印象说"看起来没变"。**

## 第二步：逐段扫描，落结论清单

按 `##` 小节切分，没有小节就按空行分段。**每一段都要有一条结论，一条都不能跳。**

段落类型与结论：

| 段落是什么 | 结论 |
|---|---|
| 规则条文（"必须"/"禁止"/"统一用"/"不得"） | ✅ 提炼为条目 |
| 规则的例外、适用范围、原因说明 | ⚠️ **跟着所属规则走**，作为该条目的正文一部分——**不是独立条目** |
| 背景描述（"本系统由一期平台 + 二期扩展组成"） | ⛔ 无约束（是背景知识） |
| 示例、表格、清单 | ⚠️ 判断它是规则的组成部分还是说明材料。**"正例/反例"是规则的一部分** |
| 目录、导航、"见 XX 文档" | ⛔ 无约束 |
| 待办、缺口、技术债清单 | ⛔ 无约束（`已知缺口` 是待整改项，不是规范） |
| 写作说明（"本文件只写项目独有的约束"） | ⛔ 无约束（是文档的元信息） |

**结论清单要完整输出在对话里**，格式见下。它是人核对"有没有漏"的唯一依据——
所以「本段无约束」也必须列出来，不能只列提炼出来的。

## 第三步：摘录

对每个判定为约束的段落：

1. **正文照抄**。不改任何实词、不动语序、不合并段落、不删限定条件
2. 该规则的**例外与原因说明一并带上**（它们在源文档里属于这条规则）
3. 补 `<!-- meta -->` 块：

```
<!-- meta
tier: resident | indexed
scope: <触发场景，做什么事的时候要看这条>
frozen: false
-->
```

**`tier` 的判据是「不看这条会不会做错」，不是「这条重不重要」**：

| tier | 判据 | 典型 |
|---|---|---|
| `resident` | 不看就**会做错**，且在做的时候没有机会现查 | 返回结构统一走公共基座、逻辑删除取值 1/2 |
| `indexed` | 不看会做得不一致，但**在该场景下会去查** | 表命名前缀、DDL 变更脚本风格 |

打多了的后果是常驻段超预算（`ai-spec-build` 会报警），然后有人会把预算调大——
**这等于让门禁失效**。宁可漏打一次，不要多打。

## 第四步：编号

读现有 rules 文件，取该项目前缀下**已有的最大序号**。前缀是 `STD-PRJ-<项目码大写>-`。

| 情况 | 处置 |
|---|---|
| 正文与某既有条目**逐字相同** | 沿用其编号，一字不改 |
| 正文能看出是某既有条目的改写 | **沿用其编号**，改正文，并在 diff 里标「疑为改写 ← 原正文」 |
| 确实是新约束 | 分配下一个序号 |
| 源文档里原有、现在找不到 | **不删**。列为「疑似废弃，待确认」 |

**编号是追溯锚点，改了它历史快照就对不上。** 判不出是否为同一改写时，
标「待确认」交给人，**不要默默当新条目**——那会让编号静默翻倍而快照看起来正常。

### 先解决「这条归谁管」，再编号

**同一约束散在多份文档里是常态。** 真实项目文档会大量互相复述：一条「Redis 必须用 db3」
可能同时出现在启动手册、环境说明、新人注意事项、架构总览里。**只从其中一份摘成条目。**

漏了这条会直接撞号——`ai-spec-build` 对重复编号**直接构建失败**。
若靠分配新号绕开，快照里会出现 4 条一模一样的规则，各占一个常驻名额，而没人会注意到。

判据：把约束归给它**所属主题**的文档，而不是它**恰好被提到**的文档。

| 约束属于 | 归给 |
|---|---|
| 库表命名、字段值域、索引、DDL | 数据库规范 |
| 启动参数、环境开关、端口、凭据 | 环境与账号说明 |
| 语言/框架/分层/日志/响应结构 | 对应语言或框架的开发规范 |
| 测试数据、测试层级选择 | 测试策略 |

落在别处的同一句话**留在散文里不动**——它在那儿是为了让人读到，不是为了进快照。

**收尾自检**：摘完之后，若两条条目的正文在讲同一件事，就是这里出错了。
合并到权威那一份并删掉另一条，**不要靠改措辞让它们"看起来不同"**。

## 第五步：写文件

```markdown
---
source: <源文档名>
source_hash: sha256:<源文档内容哈希前16位>
extracted_at: <ISO8601 带时区>
extracted_by: ai-spec-extract
---

# 提炼自 `<源文档名>`

_（本文件是**派生副本**：散文改了要重新提炼，否则构建会报「源文档已变更」并在快照顶部标注。
条目正文照抄散文，不做改写——约束的限定条件一概括就丢。）_

## STD-PRJ-<码>-001 · <条目标题>

<!-- meta
tier: resident
scope: <触发场景>
frozen: false
-->

<照抄的规则正文>
```

frontmatter 与条目之间可以有一行说明；`parse_entries` 只认 `## STD-...` 开头的行，
其余内容不会进快照。**但不要把约束写在 frontmatter 或说明里**——那些地方不会被解析。

## 输出格式

```
提炼：<项目码>
源文档 3 个 → 条目 8 条（沿用 7 / 新增 1 / 疑为改写 0 / 疑似废弃 0）

【逐段结论】——请核对有无遗漏
<项目根>/数据库设计规范.md
  L9-29   ✅ 表命名前缀            → STD-PRJ-<码>-001（沿用）
  L33-55  ✅ 逻辑删除取值          → STD-PRJ-<码>-002（沿用）
  L59-76  ✅ 主键类型与传递方式     → STD-PRJ-<码>-003（沿用）
  L105-114 ⛔ 与基线的关系（导航）  → 无约束
<项目根>/后端开发规范.md
  ...
  L75-89  ⛔ 已知缺口（待整改项）   → 无约束

【改动】
- STD-PRJ-<码>-006：正文由 215 → 240 字符，疑为改写
    ← 原（前 60 字）：<原正文开头>...
- STD-PRJ-<码>-009：**新增**（源文档 L97）

【待确认】
- STD-PRJ-<码>-005 在源文档里已找不到对应段落——疑似废弃，**未删除**，请确认

【下一步】
确认无误后调用 ai-spec-build 重建快照。
```

**不要只报"提炼完成"。** 逐段结论清单必须完整列出，
**包括 `⛔ 无约束` 的那些**——漏掉的那一条只可能出现在被标为"无约束"的段落里，
人只有看到清单才能发现你判错了。

## 你绝对不要做的事

- **不要把规则"总结得更简洁"。** 限定条件、例外、适用范围一律保留原样
- **不要跳过任何段落。** 每一段都要有结论，包括"无约束"
- **不要发明源文档里没有的约束**，也不要因为"这条太细了"而自行删掉
- **不要改源散文文档。** 那时人写的东西，本 Skill 只读
- **不要改既有条目的编号**，即使你觉得顺序不合理
- **不要自动删除疑似废弃的条目**
- **不要写或重建生效快照**（那是 `ai-spec-build` 的事）
- 不要执行 git 操作
