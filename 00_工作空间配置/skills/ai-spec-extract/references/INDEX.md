## 为什么条目不直接写在散文文档里

这是本 Skill 存在的理由，值得单独说清楚，因为它看起来像是"多一道手续"。

项目级文档是**人读的散文**：人工维护后复制进来，或由 AI 读代码仓梳理产出。
它**不遵守编号约定，且改动频繁**——这正是它好用的地方。
而生效快照要的是稳定的、可审计的、能追回出处的条目。两者性质不同。

**硬把两者塞进同一份文件，会有两种结局，都很难看：**

| 结局 | 症状 |
|---|---|
| 人烦到不写 | 加一条约束要先想"这算不算条目""编号排到几了"，于是干脆不写进文档 |
| 格式偷偷漂掉 | 编号重复、漏写 `##`、标题符号写成 `：` 而不是 `·`——而**构建不会报错**，它只是少算几条 |

第二种更危险。它曾经真实发生过：条目被拆进主题文档后，**每篇文档的最后一条条目都把文档尾部的章节吞进了正文**——
一篇里一条规则的正文从 215 字符涨到 1723 字符，把「已知缺口」表和「与基线的关系」整段算了进去。
不报错，只是快照里那条规则的正文变成了别的章节内容。

分两层之后，散文怎么改都行，机器读的只有 `.agent/rules/`，
而 `source_hash` 让两者**是否已经分叉**变成可机械检测的事。

## 什么时候该在本目录新增文件

当出现**只有这个 Skill 用得上**的知识时。例如：

- 已确认的提炼错误案例（"某次把两条独立规则合并成一条，导致例外被吞"）
- 某类文档结构的处理约定（如 docs 站点导出的 HTML 转来的 Markdown 该怎么切段）

**判据**：同域其他 Skill 会不会用到？会 → 放域级。
共用知识在每个 Skill 下各存一份，是知识库腐化的典型起点——改一处忘另一处。
