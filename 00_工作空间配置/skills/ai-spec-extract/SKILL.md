# ai-spec-extract · 项目散文条目提炼

## 能力声明

读项目根的**散文文档**，把其中的约束**摘录**成带编号的条目，落到 `projects/<项目码>/.agent/rules/`。

解决的是「人写的文档」与「机器读的规范」之间的格式鸿沟。项目级文档由人工维护后复制进来、
或由 AI 读代码仓梳理产出，**不遵守任何编号约定，且改动频繁**。而生效快照要的是稳定的、
可审计的、能追回出处的条目。本 Skill 是一次**受控的格式转换**，把前者变成后者。

**它不是"用 AI 读文档总结规范"。它是"用 AI 把已有的规范条文抄成条目"。** 这两件事的差别，
就是这套机制能不能用的差别。**你是抄写员，不是作者**：源文档已经写好了规则，
你只是把它搬进机器能读的格式。任何"我帮它总结得更清楚"的冲动都要按住——
被总结掉的限定条件不会报错，它只会让快照里的规则比你写的更宽或更严。

**不做什么**：不写、不重建生效快照（那是 `ai-spec-build`）；不修改源散文文档；
不判断约束的技术正确性——见「边界」。

## 何时用 / 何时不用

- **用**：
  - **新接入项目**首次建立 `.agent/rules/`
  - **构建报「源文档已变更」**时（快照顶部会出现该告警）
  - 项目级散文文档有一次**成规模的修改**之后
- **不用**：
  - **不要每改一个错别字就跑一次**——源文档哈希没变时会直接退出，但也别把它当成高频动作
  - 要写 / 重建生效快照（走 `ai-spec-build`）
  - 只是怀疑引用悬空、挂载层不同步（走 `ai-spec-check`）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 项目散文文档 | `projects/<项目码>/*.md` | 是 | 只扫项目根，**不递归**（`<需求名>/` 下是业务级产出物，不是规范） |
| 项目组合声明 | `projects/<项目码>/.agent/project.yaml` | 是 | `project` 字段须与目录名一致（取编号前缀用） |
| 现有提炼产物 | `projects/<项目码>/.agent/rules/*.md` | 否 | 首次提炼时不存在，属正常 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 提炼产物 | `projects/<项目码>/.agent/rules/<源文档名>.md` | YAML frontmatter + 带编号条目 |

**一源一文件**，文件名与源文档同名。**不写生效快照**（那是 `ai-spec-build` 的事）。

frontmatter 固定四个字段，**不可省**（`source_hash` 是漂移检测的支点，`extracted_at` 供追溯）：

```markdown
---
source: <源文档名>                 # 源文档，相对项目目录
source_hash: sha256:<源文档内容哈希前16位>
extracted_at: <ISO8601 带时区>
extracted_by: ai-spec-extract
---

# 提炼自 `<源文档名>`

_（本文件是**派生副本**：散文改了要重新提炼，否则构建会报「源文档已变更」并在快照顶部标注。
条目正文照抄散文，不做改写——约束的限定条件一概括就丢。）_

## STD-PRJ-<码>-001 · <条目标题>

<!-- meta
tier: resident
scope: <触发场景>
-->

<照抄的规则正文>
```

frontmatter 与条目之间可以有一行说明；`parse_entries` 只认 `## STD-...` 开头的行，
其余内容不会进快照。**但不要把约束写在 frontmatter 或说明里**——那些地方不会被解析。

## 前置条件

**hard（不满足则拒绝执行）**

- `projects/<项目码>/` 目录存在
- 项目根至少有一个 `.md` 文件
- `projects/<项目码>/.agent/project.yaml` 存在且可解析

**soft**

- 无。首次提炼时 `.agent/rules/` 为空属正常（输入契约里已标为"否"），不存在"顺序性"前置

## 执行步骤

1. **先看有没有必要提炼。** 读现有 `.agent/rules/*.md` 的 `source_hash`，
   与对应源文档当前内容的哈希比。

   **一致 → 直接退出**，报告"源文档未变更，无需重新提炼"。不要因为"想再优化一下措辞"
   而重新生成——每次重新生成都可能让措辞漂移，而快照哈希会跟着变，
   "这个批次用的是哪版规范"就变成了噪声。

   哈希算法与 `ai-spec-build` 一致（内容 SHA-256 取前 16 位十六进制，前缀 `sha256:`）。
   **你不会算哈希没关系**——直接把当前源文档内容与上次提炼时的内容做逐字比对，
   或者调用 `ai-spec-build` 让它报漂移。**不要凭印象说"看起来没变"。**

2. **逐段扫描，落结论清单。** 按 `##` 小节切分，没有小节就按空行分段。
   **每一段都要有一条结论，一条都不能跳。**

   | 段落是什么 | 结论 |
   |---|---|
   | 规则条文（"必须"/"禁止"/"统一用"/"不得"） | ✅ 提炼为条目 |
   | 规则的例外、适用范围、原因说明 | ⚠️ **跟着所属规则走**，作为该条目的正文一部分——**不是独立条目** |
   | 背景描述（"本系统由一期平台 + 二期扩展组成"） | ⛔ 无约束（是背景知识） |
   | 示例、表格、清单 | ⚠️ 判断它是规则的组成部分还是说明材料。**"正例/反例"是规则的一部分** |
   | 目录、导航、"见 XX 文档" | ⛔ 无约束 |
   | 待办、缺口、技术债清单 | ⛔ 无约束（`已知缺口` 是待整改项，不是规范） |
   | 写作说明（"本文件只写项目独有的约束"） | ⛔ 无约束（是文档的元信息） |

   **不许"读完文档挑出几条"**——那样漏掉的约束不会报错，只是不在快照里，
   而「少一条约束」和「本来就没有这条」在快照里长得一模一样。

3. **摘录**（对每个判定为约束的段落）：

   1. **正文照抄**。不改任何实词、不动语序、不合并段落、不删限定条件
   2. 该规则的**例外与原因说明一并带上**（它们在源文档里属于这条规则）
   3. 补 `<!-- meta -->` 块：

      ```
      <!-- meta
      tier: resident | indexed
      scope: <触发场景，做什么事的时候要看这条>
      -->
      ```

   **`tier` 的判据是「不看这条会不会做错」，不是「这条重不重要」**：

   | tier | 判据 | 典型 |
   |---|---|---|
   | `resident` | 不看就**会做错**，且在做的时候没有机会现查 | 返回结构统一走公共基座、逻辑删除取值 1/2 |
   | `indexed` | 不看会做得不一致，但**在该场景下会去查** | 表命名前缀、DDL 变更脚本风格 |

   打多了的后果是常驻段超预算（`ai-spec-build` 会报警），然后有人会把预算调大——
   **这等于让门禁失效**。宁可漏打一次，不要多打。

   **摘录 ≠ 总结。** 条目正文照抄源文档的句子——不改词、不改语序、不合并、不"提炼要点"。
   约束是条文性质的东西，一"总结"就会丢限定条件，而限定条件恰恰是约束里最要命的部分。
   源文档写「除历史遗留的 `legacy.file` 包外，删除标记一律取 1/2」，
   总结成「删除标记统一用 1/2」就**把例外抹掉了**，而这不报错——它只是变成一条更严也更错的规则。

   允许做的只有：把散在几处的同一句话收进一个条目、补 `<!-- meta -->` 块、去掉段落间的分隔线。
   **不允许做的**：改任何一个实词、调整因果顺序、把两个段落"综合"成一句。
   五个正反例对照见 `references/摘录判据与反例.md` §一。

4. **编号**。读现有 rules 文件，取该项目前缀下**已有的最大序号**。前缀是 `STD-PRJ-<项目码大写>-`。

   | 情况 | 处置 |
   |---|---|
   | 正文与某既有条目**逐字相同** | 沿用其编号，一字不改 |
   | 正文能看出是某既有条目的改写 | **沿用其编号**，改正文，并在 diff 里标「疑为改写 ← 原正文」 |
   | 确实是新约束 | 分配下一个序号 |
   | 源文档里原有、现在找不到 | **不删**。列为「疑似废弃，待确认」 |

   **编号是追溯锚点，改了它历史快照就对不上。** **判据是正文原文精确匹配**：
   正文没变 → 就是同一条 → 编号不变。正文变了而匹配不上时，由你判断它是否为同一条的改写，
   **并在 diff 里显式标注「疑为改写」**让人复核。

   > ⚠️ **这是本机制唯一的弱判断点，说清楚**：散文改了措辞，机器无法知道它还是不是原来那条。
   > 所以正文精确匹配是主路径，判不出的地方必须标出来交给人——
   > 悄悄当新条目处理，会让编号静默翻倍，而快照看起来一切正常。

   **先解决「这条归谁管」，再编号。** **同一约束散在多份文档里时（这是常态，不是例外），
   只能从其中一份摘成条目。** 一条「Redis 必须用 db3」会同时出现在启动手册、环境说明、
   新人注意事项、架构总览里。每份都摘一遍的后果：同一编号出现在两个 rules 文件 →
   **构建直接失败**；若各自分新号 → 快照里 4 条一模一样的规则并列，
   各占一个常驻名额而没人会注意到。

   **判据一句话：这条约束「归谁管」？** 归给它**所属主题**的文档，而不是它**恰好被提到**的那份。

   | 约束属于 | 归给 |
   |---|---|
   | 库表命名、字段值域、索引、DDL | 数据库规范 |
   | 启动参数、环境开关、端口、凭据 | 环境与账号说明 |
   | 语言/框架/分层/日志/响应结构 | 对应语言或框架的开发规范 |
   | 测试数据、测试层级选择 | 测试策略 |

   落在别处的同一句话**留在散文里不动**——它在那儿是为了让人读到，不是为了进快照。

   **收尾自检**：摘完之后，若两条条目的正文在讲同一件事，就是这里出错了。
   合并到权威那一份并删掉另一条，**不要靠改措辞让它们"看起来不同"**。
   归属表与自检方法见 `references/摘录判据与反例.md` §六。

5. **写出 rules 文件**（含 `source_hash`）——结构见「产出契约」。

6. **输出 diff 摘要 + 逐段结论清单**，交人确认，格式见「输出格式」。
   **不要只报"提炼完成"。**

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不要把规则"总结得更简洁"。** 限定条件、例外、适用范围一律保留原样
- **不要跳过任何段落。** 每一段都要有结论，包括"无约束"
- **不要发明源文档里没有的约束**，也不要因为"这条太细了"而自行删掉。
  没有提取到就报「未发现可提取的约束」，不要为了填满而造
- **不要改源散文文档。** 散文是人写的，本 Skill 只读它。要改文档的措辞是人的事
- **不要改既有条目的编号**，即使你觉得顺序不合理
- **不要自动删除疑似废弃的条目**
- **不要写或重建生效快照**（那是 `ai-spec-build` 的事）
- 不做技术正确性判断。那条规则对不对是评审的事，不是提炼的事
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 某源文档里没发现任何约束 | 该文件**不产出 rules 文件**，并在结论清单里明确说明——不要产出一个空壳 |
| 规则条文的边界判不出来（某段算不算约束） | 列入「待人工判断」，**不要猜**。猜错的代价是快照里多一条或漏一条，两者都不报错 |
| 源文档结构变化太大，无法与既有条目对应 | 停止提炼，报告「需要人工重建该文件的条目对应关系」，不做自动重编号 |
| `source_hash` 与现有值一致 | 说明源文档没变，**不重新提炼**，直接退出（避免无谓的措辞漂移） |

## 输出格式

执行完用下面结构回复（保持简短）：

```
提炼：<项目码>
源文档 3 个 → 条目 8 条（沿用 7 / 新增 1 / 疑为改写 0 / 疑似废弃 0）

【逐段结论】——请核对有无遗漏
<项目根>/数据库设计规范.md
  L9-29   ✅ 表命名前缀            → STD-PRJ-<码>-001（沿用）
  L33-55  ✅ 逻辑删除取值          → STD-PRJ-<码>-002（沿用）
  L59-76  ✅ 主键类型与传递方式     → STD-PRJ-<码>-003（沿用）
  L105-114 ⛔ 与基线的关系（导航）  → 无约束
<项目根>/后端开发规范.md
  ...
  L75-89  ⛔ 已知缺口（待整改项）   → 无约束

【改动】
- STD-PRJ-<码>-006：正文由 215 → 240 字符，疑为改写
    ← 原（前 60 字）：<原正文开头>...
- STD-PRJ-<码>-009：**新增**（源文档 L97）

【待确认】
- STD-PRJ-<码>-005 在源文档里已找不到对应段落——疑似废弃，**未删除**，请确认

【下一步】
确认无误后调用 ai-spec-build 重建快照。
```

**结论清单要完整输出在对话里**，它是人核对"有没有漏"唯一的可核对形式——
所以「本段无约束」也必须列出来，不能只列提炼出来的。
**漏掉的那一条只可能出现在被标为"无约束"的段落里**，人只有看到清单才能发现你判错了。

## 与其他 Skill 的关系

| Skill | 关系 |
|---|---|
| `ai-spec-build` | 下游。它读本 Skill 的产出，并校验 `source_hash` 是否与源文档一致 |
| `ai-spec-promote` | 平行。本 Skill 把散文变成项目条目；它把多个项目的重复条目往共享包提升 |
| `ai-spec-check` | 平行。它做跨文件一致性检查，会报 `source_hash` 漂移 |
