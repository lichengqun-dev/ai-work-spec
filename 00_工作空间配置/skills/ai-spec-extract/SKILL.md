# 能力声明

读项目根的**散文文档**，把其中的约束**摘录**成带编号的条目，落到 `projects/<项目码>/.agent/rules/`。

解决的是「人写的文档」与「机器读的规范」之间的格式鸿沟。项目级文档由人工维护后复制进来、
或由 AI 读代码仓梳理产出，**不遵守任何编号约定，且改动频繁**。而生效快照要的是稳定的、
可审计的、能追回出处的条目。本 Skill 是一次**受控的格式转换**，把前者变成后者。

**它不是"用 AI 读文档总结规范"。它是"用 AI 把已有的规范条文抄成条目"。** 这两件事的差别，
就是这套机制能不能用的差别——见「五条硬约束」第 1 条。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 项目散文文档 | `projects/<项目码>/*.md` | 是 | 只扫项目根，**不递归**（`<需求名>/` 下是业务级产出物，不是规范） |
| 项目组合声明 | `projects/<项目码>/.agent/project.yaml` | 是 | `project` 字段须与目录名一致（取编号前缀用） |
| 现有提炼产物 | `projects/<项目码>/.agent/rules/*.md` | 否 | 首次提炼时不存在，属正常 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 提炼产物 | `projects/<项目码>/.agent/rules/<源文档名>.md` | YAML frontmatter + 带编号条目 |

frontmatter 固定四个字段，**不可省**（`source_hash` 是漂移检测的支点，`extracted_at` 供追溯）：

```yaml
---
source: 数据库设计规范.md          # 源文档，相对项目目录
source_hash: sha256:8ade6e7316cbe624
extracted_at: 2026-10-21T10:48:11+08:00
extracted_by: ai-spec-extract
---
```

**一源一文件**，文件名与源文档同名。**不写生效快照**（那是 `ai-spec-build` 的事）。

## 五条硬约束

### 1. 摘录，不是总结

**条目正文照抄源文档的句子——不改词、不改语序、不合并、不"提炼要点"。**

约束是条文性质的东西，一"总结"就会丢限定条件，而限定条件恰恰是约束里最要命的部分。
源文档写「除历史遗留的 `legacy.file` 包外，删除标记一律取 1/2」，
总结成「删除标记统一用 1/2」就**把例外抹掉了**，而这不报错——它只是变成一条更严也更错的规则。

允许做的只有：把散在几处的同一句话收进一个条目、补 `<!-- meta -->` 块、去掉段落间的分隔线。
**不允许做的**：改任何一个实词、调整因果顺序、把两个段落"综合"成一句。

### 2. 逐段覆盖，每段显式给出结论

**不许"读完文档挑出几条"**——那样漏掉的约束不会报错，只是不在快照里，
而「少一条约束」和「本来就没有这条」在快照里长得一模一样。

做法：按段落（或 `##` 小节）逐个过，**每一段都要落一个结论**，包括「本段无约束」。
结论清单在对话里完整输出给人核对——**那是"有没有漏"唯一的可核对形式**。

### 3. 编号只增不改

- 新条目 → 接着现有最大序号往后排
- 已有条目 → **编号保持不变**，哪怕正文改了
- 源文档里删掉的约束 → **不自动删**。列为「疑似废弃，待确认」，由人决定

编号是追溯锚点。改了编号，历史快照、门禁引用、变更记录全部对不上。
**判据是正文原文精确匹配**：正文没变 → 就是同一条 → 编号不变。
正文变了而匹配不上时，由你判断它是否为同一条的改写，**并在 diff 里显式标注「疑为改写」**让人复核。

> ⚠️ **这是本机制唯一的弱判断点，说清楚**：散文改了措辞，机器无法知道它还是不是原来那条。
> 所以正文精确匹配是主路径，判不出的地方必须标出来交给人——
> 悄悄当新条目处理，会让编号静默翻倍，而快照看起来一切正常。

### 4. 不发明，不动源文档

- **不发明源文档里没有的约束。** 没有提取到就报「未发现可提取的约束」，不要为了填满而造
- **不修改源散文。** 散文是人写的，本 Skill 只读它。要改文档的措辞是人的事
- **不判断约束的技术正确性。** 那条规则对不对是评审的事，不是提炼的事

### 5. 一项约束只有一个权威出处

**同一约束散在多份文档里时（这是常态，不是例外），只能从其中一份摘成条目。**

一条「Redis 必须用 db3」会同时出现在启动手册、环境说明、新人注意事项、架构总览里。
每份都摘一遍的后果：同一编号出现在两个 rules 文件 → **构建直接失败**；
若各自分新号 → 快照里 4 条一模一样的规则并列，各占一个常驻名额而没人会注意到。

**判据一句话：这条约束「归谁管」？** 归给它**所属主题**的文档，而不是它**恰好被提到**的那份。
落在别处的同一句话**留在散文里不动**——它在那儿是为了让人读到，不是为了进快照。

归属表与自检方法见 `references/摘录判据与反例.md` §六。

## 前置条件（不满足则拒绝执行）

- `projects/<项目码>/` 目录存在
- 项目根至少有一个 `.md` 文件
- `projects/<项目码>/.agent/project.yaml` 存在且可解析

## 执行步骤

1. 列出项目根的 `.md`，以及 `.agent/rules/` 下已有的提炼文件
2. 每个源文档：逐段扫描，落结论清单（含「本段无约束」）
3. 每个被判定为约束的段落 → 原样摘录为条目
4. 与已有条目比对，按「正文原文精确匹配」决定编号：沿用 / 新增 / 疑为改写
5. 写出 rules 文件（含 `source_hash`）
6. **输出 diff 摘要 + 逐段结论清单**，交人确认

## 边界（明确不做）

- 不写、不重建生效快照（是 `ai-spec-build` 的事）
- 不修改源散文文档
- 不自动删除疑似废弃的条目
- 不做技术正确性判断
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 某源文档里没发现任何约束 | 该文件**不产出 rules 文件**，并在结论清单里明确说明——不要产出一个空壳 |
| 规则条文的边界判不出来（某段算不算约束） | 列入「待人工判断」，**不要猜**。猜错的代价是快照里多一条或漏一条，两者都不报错 |
| 源文档结构变化太大，无法与既有条目对应 | 停止提炼，报告「需要人工重建该文件的条目对应关系」，不做自动重编号 |
| `source_hash` 与现有值一致 | 说明源文档没变，**不重新提炼**，直接退出（避免无谓的措辞漂移） |

## 与其他 Skill 的关系

| Skill | 关系 |
|---|---|
| `ai-spec-build` | 下游。它读本 Skill 的产出，并校验 `source_hash` 是否与源文档一致 |
| `ai-spec-promote` | 平行。本 Skill 把散文变成项目条目；它把多个项目的重复条目往共享包提升 |
| `ai-spec-check` | 平行。它做跨文件一致性检查，会报 `source_hash` 漂移 |

## 执行时机

- **新接入项目**首次建立 `.agent/rules/`
- **构建报「源文档已变更」**时（快照顶部会出现该告警）
- 项目级散文文档有一次**成规模的修改**之后
- **不要每改一个错别字就跑一次**——源文档哈希没变时会直接退出，但也别把它当成高频动作
