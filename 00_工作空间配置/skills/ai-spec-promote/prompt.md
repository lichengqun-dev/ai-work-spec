# 指令：分析规范提升与淘汰候选

## 你要做的事

扫描 `projects/*/` 下的项目特有条目，找出**重复出现的约束**，输出提升候选；同时统计包内条目的引用率，输出淘汰候选。**只产出清单，不改任何文件。**

## 扫描对象

两类来源，都要看：

1. `projects/*/project.yaml` 的 `project_only` 列表
2. `projects/*/项目特有规范.md` 里的条目

跳过 `_template` 目录。

## 聚类规则

**判据是语义相同，不是文字相同。** 下面三条属于同一个聚类：

- 「所有对外接口必须携带 tenant_id」
- 「查询条件必须带隔离标识，禁止跨租户聚合」
- 「接口入参必须包含所属组织，用于数据隔离」

聚类时按「这条约束约束的是什么决策点」分组，而不是按用词。分组名用决策点描述，如"数据隔离标识"。

## 提升阈值

| 出现项目数 | 处置 |
|---|---|
| ≥ 3 个项目 | **建议提升**为共享包条目 |
| 恰好 2 个项目 | 标记为"观察"，不进候选清单，下次再看 |
| 1 个项目 | 不处理，这是正常的项目特例 |

为什么是 3 而不是 2：两个项目共同出现的约束可能只是这两个项目恰好相似（同一批人、同一时期、同一客户）。三个项目同时出现，才更可能是团队的共性。

## 建议归属的判断

| 约束的性质 | 建议归属 | 编号前缀 |
|---|---|---|
| 跟具体技术栈有关（框架写法、语言语法） | `09_资产库/规范包/stacks/<对应包>` | 该包的 prefix |
| 跟业务领域有关（业务规则、领域合规） | `09_资产库/规范包/domains/<对应包>` | `STD-DOM-<领域>-` |
| 所有项目都适用（流程、编号、文档写法） | 对应业务域的 `standards/` 基线 | `STD-BASE-` |

**判断有疑问时，标注「建议人工复核」，不要强行归属。** 归错包比不归更糟——它会让一个包混入不属于它的约束，后续没人敢动。

## 淘汰候选的判断

从 `.ai/spec-effective/*.json` 统计：每条包内条目被多少个项目的生效快照包含（即"被引用"）。

| 情况 | 处置 |
|---|---|
| 被 0 个项目选中，且包内条目连续 3 个月零引用 | 列入淘汰候选 |
| 被 1 个项目选中 | 不处理 |
| 被禁用次数 ≥ 2 个项目 | **单独列一类**：这不是"没人用"，而是"多个项目都不适用"——说明该条目可能约束过严或归属错了包 |

最后那一类最重要：**被多个项目禁用的条目，比零引用的条目更值得审查。** 它说明这条规则与实际做法脱节。

## 输出格式

写入 `.ai/index/规范提升候选.md`：

```markdown
# 规范提升候选

生成时间：<时间>　｜　扫描项目数：N

## 建议提升（≥3 个项目出现）

| # | 约束内容（决策点） | 出现项目 | 建议归属 | 建议编号 | 置信度 |
|---|---|---|---|---|---|
| 1 | 数据隔离标识必须显式传入 | 项目 A、项目 B、项目 C | domains/platform-base | STD-DOM-PLAT-011 | 高 |

## 已存在于包中（建议改为引用）

| 约束内容 | 已有条目 | 涉及项目 | 处理建议 |
|---|---|---|---|

## 观察中（恰好 2 个项目出现）

| 约束内容 | 出现项目 |
|---|---|
```

以及 `.ai/index/规范淘汰候选.md`：

```markdown
# 规范淘汰候选

生成时间：<时间>　｜　统计来源：.ai/spec-effective/*.json

## 零引用（候选淘汰）

| 条目 ID | 摘要 | 所在包 | 引用项目数 |
|---|---|---|---|

## 被多项目禁用（优先审查）

| 条目 ID | 摘要 | 所在包 | 禁用项目 |
|---|---|---|---|
```

## 产出后必须做的事

**不要只给清单就结束。** 对清单里每一条"建议提升"，补一句人话解释：这条约束现在散在几个项目里，各自措辞不同，如果不提升会发生什么（通常是：改一处不改另一处，行为逐渐分叉）。

然后明确告诉用户下一步动作是什么：

```
1. 人工确认候选（建议由知识库 Owner 拍板）
2. 改包文件：新增条目到对应包，更新 PACK.md 的 files 列表（若新建文件）
3. 包版本号 +0.1.0（新增条目属次版本变更）
4. 改各项目 manifest：把原 project_only 条目改为 disable 并指向新编号
5. 重跑 ai-spec-build --all
```

## 你绝对不要做的事

- 不要自动修改任何包文件或项目 manifest
- 不要删除任何条目（淘汰也只是出候选）
- 不要因为"看起来重复"就下结论——注意区分「同一决策点的相同约束」与「碰巧都用到了某个词」
- 不要执行 git 操作
