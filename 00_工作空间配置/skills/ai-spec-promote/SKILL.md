# 能力声明

扫描各项目的特有条目，找出**重复出现**的约束，输出「提升为共享包条目」的候选清单，供人确认。

解决的是知识库的**单向膨胀**问题：如果规范只增不减，三年后会变成没人敢改的巨物。本 Skill 提供反向的流动性——把项目里的共性往上提，把包里的僵尸条目往下删。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 全部项目 manifest | `projects/*/.agent/project.yaml` | 是 | 至少 2 个非模板项目 |
| 项目特有条目 | `projects/*/.agent/rules/*.md` + manifest 的 `project_only` | 否 | — |
| 现有包条目 | `09_资产库/规范包/**` | 是 | 用于判断"是否已存在于包中" |
| 规则引用率数据 | `projects/<项目码>/.agent/spec-effective/*.json` | 否 | 用于淘汰分析 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 提升候选清单 | `projects/<项目码>/.agent/index/规范提升候选.md` | Markdown 表格 + 建议归属 |
| 淘汰候选清单 | `projects/<项目码>/.agent/index/规范淘汰候选.md` | Markdown 表格 + 零引用证据 |

**只产出候选，不自动修改任何包或项目文件。** 提升是规范变更，必须由人确认。

## 前置条件（不满足则拒绝执行）

- 至少存在 2 个非 `_template` 的项目目录
- 每个被扫描项目的 `project.yaml` 能通过 YAML 解析
- 若 `09_资产库/规范包/` 不存在 → 拒绝（无法判断"是否已存在于包中"）

## 执行步骤

1. 收集全部项目的 `project_only`（manifest）与 `.agent/rules/` 里的 `STD-PRJ-` 条目
2. 语义聚类：找出**表达同一约束**的条目（措辞不同但含义相同）
3. 对每个聚类判断：出现在 ≥3 个项目？（阈值见 `references/提升与淘汰判据.md`）
4. 对达阈值的聚类，判断建议归属：
   - 与技术栈相关 → 对应 `stacks/*` 包
   - 与业务领域相关 → 对应 `domains/*` 包
   - 所有项目适用 → 对应业务域的 `standards/` 基线
5. 生成候选清单（含建议编号、出现项目、建议归属、理由）
6. 反向：从 `spec-effective/*.json` 统计各条目的**引用率**，输出长期零引用的淘汰候选

## 边界（明确不做）

- **不自动提升。** 只出候选清单，提升动作由人执行（改包文件 + 改项目 manifest + 重建快照）
- 不自动删除任何条目。淘汰同样是人的决策
- 不判断条目的技术正确性——只判断"重复出现的模式"
- 不修改 `projects/` 下的任何文件

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 项目数不足 2 个 | 提示信息不足，不做聚类，直接退出 |
| 聚类结果置信度低 | 在候选中标注"建议人工复核"，不做推断 |
| 候选条目已在包中存在 | 标记为 "已存在"，建议改为在项目中 disable + 指向已有编号 |

## 执行频率

**按月执行一次**，或当某个项目的 `project_only` 超过 30 条时触发（`ai-spec-build` 会在快照 D 段给出该警告）。
