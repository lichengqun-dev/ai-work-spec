# 提升与淘汰判据

> 回答"为什么是 3 个项目""为什么不自动改""什么样的条目该淘汰"。

## 1. 提升阈值为什么是 3 个项目

**同一条约束出现在 ≥3 个项目，才建议提升为共享包条目。**

为什么不是 2：两个项目同时出现某条约束，很可能只是这两个项目恰好相似——同一批人、同一时期、同一个客户、同一套历史代码。把这种"巧合的相似"提升为团队规范，会让第三个不相关的项目被套上一条它不需要的约束。

三个项目同时出现，才更可能是**团队的共性**而非局部巧合。

**恰好 2 个项目出现的**：标记为"观察"，不进候选清单，下次分析时再看。如果第三次出现，自动达阈值。

## 2. 为什么不自动提升

提升是**规范变更**，不是数据整理。它的后果是：

- 包版本号变更（次版本 +1，或主版本视情况）
- 所有引用该包的项目，快照在下一次构建时都会多出这一条
- 原本只在 A 项目生效的约束，变成三个项目都必须遵守

**这个决定的影响面超出一条规则本身。** 谁有权把"A 项目的做法"变成"所有项目的义务"？只有规范 Owner。工具能做的是把候选找出来、把证据摆清楚，而不是替人拍板。

工具的定位是**降低判断成本**，不是**替代判断**。

## 3. 提升后的项目侧处理

提升只完成了"往上提"，项目里那份重复条目还在。必须同时处理，否则会出现两处维护：

| 项目 | 处理 |
|---|---|
| 原条目所在的项目 | 把 `project_only` 中的原条目改为 `disable`，`reason` 写"已提升为 `<新条目编号>`，见包" |
| 其他项目 | 不需要改（它们本来就是各自维护的） |

**为什么用 disable 而不是直接删掉**：disable 会记录在快照的 C 段来源链里，回答"为什么项目里这条被禁用了"。直接删除则不留痕迹，半年后有人看到包里的条目会疑惑"这跟某个项目的做法不一样，是冲突吗"。

同时，disable 需要 `expires`——到期复查时会重新审视这条提升是否仍然合理。

## 4. 什么时候该淘汰

淘汰和提升是同一个机制的两端。**只增不减的知识库三年后没人敢改。**

### 淘汰候选的三类证据

| 类型 | 判据 | 含义 |
|---|---|---|
| **零引用** | 条目连续 3 个月未被任何项目的快照包含 | 这个包可能切分维度选错了，或者这条约束没有实际价值 |
| **多项目禁用** | 条目被 ≥2 个项目 `disable` | **比零引用更值得审查**——说明这条规则与实际做法脱节 |
| **长期未变** | 条目 12 个月未被修改且未被引用 | 可能是"写下来就没人看过"的规则 |

**第二类最关键。** 零引用可能是"刚好这几个项目不需要"，但被多个项目主动禁用，说明这条规则要么约束过严，要么归属错了包（放进了不适用的项目）。

### 淘汰不是删除

淘汰的处理方式按情况分：

| 情况 | 处理 |
|---|---|
| 条目内容已过时 | 标记 `[已废弃]` 并保留编号，注明被哪条取代 |
| 条目归属错了包 | 移到正确的包，编号不变（前缀需相应调整，属主版本变更） |
| 条目约束过严 | 放宽表述，而非删除——它的意图可能是对的 |
| 条目纯属冗余 | 保留编号并标记 `[已废弃]`，**不回收编号** |

**编号永不回收**，因为历史文档中的引用会指向错误的对象。

## 5. 触发时机

| 触发条件 | 动作 |
|---|---|
| 每月一次 | 例行执行 `ai-spec-promote` |
| 某项目 `project_only` 超过 30 条 | `ai-spec-build` 会在快照 D 段给出警告，触发分析 |
| 某包被 3 个以上项目禁用其条目 | 该包的切分方式需要重新审视 |
| 包内条目连续 3 个月零引用 | 生成淘汰候选 |

## 6. 低频但必要的动作

如果连续几个月 `ai-spec-promote` 都输出空清单，有两种可能：

1. **知识库已经很健康**——包的切分准确，项目侧几乎没有特有条目。这是理想状态。
2. **知识库已经没人用了**——没有真实批次产生数据，自然也就没有候选。

**区分方法**：看 `.ai/logs/` 与 `.ai/state/` 是否有新的批次记录。有批次但无候选 = 状态 1；没有批次 = 状态 2，此时应该先解决"为什么没有新批次"的问题，而不是继续优化知识库。
