# 00_工作空间配置

> **地基域。** 它不产出业务交付物，而是定义"AI 在这个仓库里怎么工作"——
> 读什么、按什么顺序读、不能做什么、以及所有编号的规则。
>
> 进入仓库的读取顺序：根 `CLAUDE.md` → 本域的 `AI工作空间配置.md` → 具体任务。

| 文件 | 讲什么 | 什么时候读 |

| [AI工作空间配置.md](./AI工作空间配置.md) | **总配置**：目录权重、加载顺序、读取规则、八条操作红线 | 每次会话，读完 `CLAUDE.md` 之后 |

## 这个域的 Skill

| Skill | 职责 | 状态 |
|---|---|---|
| **`ai-flow-autopilot`** | **全流程总入口**——用户说一句话，它判定路径、驱动全流程 | ✅ |
| [`ai-spec-build`](./skills/ai-spec-build/SKILL.md) | 把多层规范编译成单一生效快照 | ✅ |
| [`ai-spec-check`](./skills/ai-spec-check/SKILL.md) | 跨文件一致性检查（只读） | ✅ |
| [`ai-spec-mount`](./skills/ai-spec-mount/SKILL.md) | 重建 `.claude/skills/` 挂载层 | ✅ |
| [`ai-spec-promote`](./skills/ai-spec-promote/SKILL.md) | 项目特例提升为共享包条目 | ✅ |

后四个是**知识库自身的治理工具**，同属 `ai-spec-*` 这一族。它们不参与交付流程，
但每次改完规范或 Skill 都要用到。配合方式：改规范 → `ai-spec-build`；改 Skill → `ai-spec-mount`；收口 → `ai-spec-check`。

## 两个"域级"不是 Skill 的资产

本域有两个资产不在任何 Skill 目录下，**这是刻意的不对称**：

| 资产 | 为什么在域级而不是放某个 Skill 里 |
|---|---|
| `scripts/consistency_check.py` | 它是**全库**检查器，不属于任何单个步骤。放进某个 Skill 会让"谁负责跑它"变成一个没有答案的问题 |
| `scripts/build_claude_skills.py` | 它作用于**全部** Skill，不是某一步的产出 |

**通则**：`references/` 与 `scripts/` 默认在 Skill 目录内。只有当某资产被**同域 3 个以上 Skill 共用**、
或**不属于任何单个步骤**（如全库检查器）时，才提到域级。
`01_需求设计/references/` 是前一种情况，本域 `scripts/` 是后一种。

## 八条操作红线

完整表述见 `AI工作空间配置.md` 第 4 节。这里只列最容易被忽略的两条：

- **不在共享层写具体项目信息。** `00`–`09` 是通用资产——判据是"把这份知识库交给另一个团队，这条内容还成立吗？"
  项目的机器状态（`.agent/`）也只在 `projects/<项目码>/` 下，不在顶层。
- **不删除文件。** 冗余或被替换的文档移入 `_archive/`（保持原相对路径），删除原文前校验副本一致。

## 这个域最容易塌的地方

**规范写了但没人读。** 本域五份文档是"读一次就该记住"的类型，不是"每次都要重读"的类型。
所以它们的价值不在篇幅，在于**规则是否被机制强制**——比如"不在 manifest 里复制规范正文"
这条，`ai-spec-build` 会拒绝；"改了规范要重建快照"，`ai-spec-check` 会发现。

**规则一旦只靠人记，就会在第三次被绕过。** 判断一份规范该不该写进本域的标准是：
它能不能被某个 Skill 或脚本检查？不能的话，考虑它是否真的属于这里。
