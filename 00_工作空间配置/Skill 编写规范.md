# Skill 编写规范

> Skill 不是提示词，是**可发现、可编排、可校验的组件**。
> 本规范以 **Anthropic Agent Skills 官方格式**为基线，再叠加本知识库的约定：
> **官方格式是硬要求**（发现机制只认它，写错就不会被任何会话看到）；
> **本库约定是团队纪律**（一致性检查会查）。

## 1. 目录结构（官方四件套）

```
<域>/skills/<name>/          # 目录名必须等于 frontmatter 的 name
├── SKILL.md                 # 必需：frontmatter + 指令本体
├── scripts/                 # 可选：可执行脚本
├── references/              # 可选：按需读取的知识（默认只加载 INDEX.md）
└── assets/                  # 可选：产出物要用的模板 / 示例 / 图片
```

**三条硬要求：**

1. **目录名 = `name`**。发现机制按目录名定位 Skill。
2. **`SKILL.md` 里的资源引用必须相对 skill 目录**（`references/x.md`、`scripts/y.py`、`assets/z.md`），
   不写知识库根路径。写根路径在挂载位置会直接断——挂载目录里没有知识库的其它部分。
3. **没有 `prompt.md`。** 官方格式里 `SKILL.md` 就是指令本体，不存在"第二类指令文件"。
   旧的三件套已并入四件套：

| 旧 | 新 | 处理 |
|---|---|---|
| `SKILL.md`（合同） | `SKILL.md` 前半 | 保留，前置条件拆 hard / soft |
| `prompt.md`（指令） | 并入 `SKILL.md` | 原文合并，不重写内容 |
| `references/` | `references/` | 原样保留 |
| `scripts/` | `scripts/` | 原样保留 |
| 域级 `templates/*.md` | 用它的 Skill 的 `assets/` | 被多个域共用的模板留在域级 `templates/`，由约束表引用 |

**`assets/` 与 `references/` 的区别**（容易混）：`references/` 是**给模型读的知识**（规范范本、清单、案例）；
`assets/` 是**给产出物用的文件**（模板、示例文档、图片）。模板进 `assets/`，不要进 `references/`。

### 引用的两种写法（不要混）

Skill 要引用的东西分两类，写法不同，**混淆是挂载后"读不到"的唯一来源**：

| 引用对象 | 写法 | 例 |
|---|---|---|
| **skill 内部资源**（`references/` `scripts/` `assets/`） | **相对 skill 目录** | `references/INDEX.md`、`scripts/spec_build.py` |
| **skill 外部资源**（域级规范、规范包、项目产出物） | **知识库根相对路径**，并写明"知识库根下" | 知识库根下 `09_资产库/规范包/stacks/db-gaussdb/SQL 方言规范.md` |

理由：挂载层在 `.claude/skills/<name>/`，模型的工作目录是**知识库根**。
skill 内部资源按相对路径解析（挂载时随目录一起复制），外部资源按根相对路径解析。
把内部资源写成根相对路径，换到挂载位置就会断；把外部资源写成 skill 相对路径，永远找不到。

## 2. frontmatter

```yaml
---
name: ai-design-03-db
description: 产出数据库设计：表结构、DDL、索引、回滚脚本。功能详细设计之后、写 Mapper 之前使用。
metadata:
  version: 1.0.0
  stage: 02_概要详细设计
  owner: 待指定
  updated: 2026-10-22
  status: implemented          # implemented | not_implemented
  applicable_stacks: []        # 空=技术中立；非空=仅在这些包下可用，编排层据此跳过（不报错）
  model_tier: medium           # none | small | medium | large，见《模型与工具矩阵》
---
```

**为什么把 `version` / `stage` 等放进 `metadata`**：官方只定义 `name` 与 `description`，
其余字段是我们自己的账本。放在顶层会让"官方格式校验"与"本库账本"混在一起，
将来官方新增字段时无法区分。放进 `metadata` 后，它们照样参与一致性检查。

**`description` 是唯一决定"什么时候用哪个 Skill"的东西**，写法要求：

- 一句话说清 **做什么 + 什么时候用**，写成判据而不是介绍
  （"功能详细设计之后、写 Mapper 之前使用"，而不是"这是一个很强大的数据库设计 Skill"）
- **≤ 800 字符**。运行时把 skill 列表的 `description` 合并截断在 1536 字符，写太长后半段会被切掉
- 不要复述名字。`ai-design-03-db` 这个名字已经说明了一半

## 3. `SKILL.md` 正文骨架

九节，顺序固定（一致性检查按节名核对）：

```markdown
# <name> · <中文名>

## 能力声明        一句话说清做什么，以及**不做什么**
## 何时用 / 何时不用  触发判据。边界情形写清楚，避免被误调用
## 输入契约         | 输入 | 来源 | 必需 | 校验规则 |
## 产出契约         | 产出 | 路径 | 格式 |
## 前置条件         **hard**（不满足则拒绝）/ **soft**（不满足则提示，可继续）
## 执行步骤         编号步骤，写成可照着做的动作
## 独立执行         单独调用时的行为差异（见第 4 节）
## 边界（明确不做）  列出不做的事
## 失败处理         | 失败情形 | 处理 |
## 配套知识         references/ 何时读什么、assets/ 有什么、scripts/ 怎么用
```

**纯脚本 Skill 的例外**：不调模型的 Skill（`ai-spec-build` / `ai-spec-check` / `ai-spec-mount`）
用 `## 执行方式` 替代 `## 执行步骤`——它描述的是"用户说什么 → 脚本做什么"的映射，
不是一串可照做的动作。除此之外九节与顺序不变。

**最重要的三节是「前置条件」「边界」「失败处理」。** 前置条件让编排层判断该不该调用；
边界防止越界（AI 天然倾向"顺手多做一点"，这在流水线里是灾难）；
失败处理决定卡住时是停下还是兜底——**"不确定就停下"优先于"猜一个继续跑"**。

## 4. 前置条件必须分 hard / soft

这是"每阶段可单独执行"的基础。**hard 与 soft 的判据不是"重不重要"，而是"做不了还是没轮到"。**

| 类型 | 含义 | 不满足时 |
|---|---|---|
| **hard** | 缺了就**做不了**（目标项目不存在、目标仓库未挂载、必备输入缺失） | **拒绝执行** |
| **soft** | **顺序性**前置（上一道门禁未过、上一阶段产出物缺失、批次还没走到这一步） | **提示 + 继续**，产出物标注"未经上游确认"，状态记 `partial` |

**soft 不能升级成 hard。** 把它写成 hard，等于宣布"这个 Skill 永远只能在流水线里跑"，
而"只改一个索引注释"这类场景根本不会从第一步开始。反过来，
**hard 也不能降级成 soft**——把产出物落到错误的仓库，比不产出更糟。

## 5. 预算

| 文件 | 预算 | 超了怎么办 |
|---|---|---|
| `SKILL.md` | **≤ 400 行** | 把"为什么这样做"的论证、正反例、长清单挪进 `references/`；不要把步骤挪走 |
| `references/` 单文件 | ≤ 300 行 | 拆文件，在 `INDEX.md` 里各给一条"何时读取" |
| 域 `README.md` | ≤ 150 行 | 拆到该域的 `standards/` |
| 仓库根 `CLAUDE.md` | ≤ 200 行 | 这是最紧张的预算，只放"每次都必须知道"的 |

`SKILL.md` 的 400 行是**合并 `prompt.md` 之后**的上限（原 150 + 300 的合计）。
判断该不该拆 Skill，看**这个步骤能否被单独复用**，不看行数。

## 6. 版本号语义

与软件版本不同，注意各位的含义：

| 位 | 变更含义 | 是否触发下游重跑 |
|---|---|---|
| 主版本 X | **流程步骤变化**（多一步、少一步、顺序变） | 是，需人工确认 |
| 次版本 Y | **产出物结构变化**（模板改字段、编号规则调整） | 是，需重跑下游 |
| 修订 Z | **提示词优化**，产出结构不变 | 否 |

这条规则的实际价值：修订版本升级可以无脑执行；次版本以上升级必须人工确认，
且所有已完成的下游产出物标记为"待重验"。没有这条规则，团队会陷入"每次改措辞就升个版本"的混乱。

**格式标准化（合并 `prompt.md`、frontmatter 迁移）不升版本号**——产出结构与流程步骤都没变。

## 7. 验收标准

一个 Skill 达到可用状态，必须同时满足：

- [ ] 目录名 = `name`，四件套齐全（`assets/`、`scripts/` 可为空，但目录不许出现 `prompt.md`）
- [ ] `SKILL.md` ≤ 400 行，九节齐全（尤其**前置条件分 hard / soft**、**边界**）
- [ ] 资源引用全部相对 skill 目录，且目标存在
- [ ] `description` 说清了"做什么 + 什么时候用"，≤ 800 字符
- [ ] `references/INDEX.md` 存在，每个知识文件都标了"何时读取"
- [ ] `metadata` 里 `version` / `stage` / `owner` / `updated` / `status` 齐全
- [ ] 用**一个真实需求**端到端跑通过至少一次
- [ ] 在信息不足时能正确停下并输出待澄清清单（而不是编造）
- [ ] 重复执行同一输入，产出结构一致（允许措辞差异）
- [ ] 产出物中的每个结构单元都携带编号（`REQ`/`FN`/`TC` 等）

**建议不要一次全建。** 按路线图分批交付，每批都用真实需求验证过再进入下一批。
未经真实批次验证的 Skill 只是"看起来能用"。

## 8. 命名

`ai-<域>-<序号>-<动作>`，域枚举见 `命名与编号规范.md` 第 6 节。
编排类加 `-autopilot`，工具类加 `-runner` / `-convert`。
项目级 Skill（`projects/<码>/skills/`）用描述性名字，不套这套命名——它们不参与挂载。

## 9. 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 留着 `prompt.md`，`SKILL.md` 只当"合同" | 不符合官方格式，且两份指令会分叉 | 合并进 `SKILL.md` |
| `SKILL.md` 里写知识库根路径（`01_需求设计/skills/…/x.md`） | 换到挂载位置读不到 | 改成相对 skill 目录 |
| 把产出模板塞进 `references/` | 该按需读的知识与产出要用的文件混在一起，模板会被"按需跳过" | 模板进 `assets/` |
| 前置条件写成建议（"最好先…"）或全写 hard | 编排层无法判断；或 Skill 永远只能整条流水线跑 | 按第 4 节拆 hard / soft |
| 没有"边界"一节 | AI 顺手多做，产出物互相覆盖 | 明确列出不做什么 |
| 产出物没有编号 | 追溯链断裂，度量无法进行 | 结构单元必须携带编号 |
| 为每个项目分叉一个 Skill | Skill 维护成本随项目数线性增长 | 先问"这个差异能不能放进规范包"，90% 可以 |

**执行方式**：改完任何 Skill 后，重建挂载层并跑一致性检查——调用 `ai-spec-mount` 与 `ai-spec-check`，
它们自己知道该查什么，调用者不需要记任何参数。
