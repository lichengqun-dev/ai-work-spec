# Skill 编写规范

> Skill 不是提示词，是**可编排、可校验的组件**。本规范定义其格式、版本语义与验收标准。

## 1. 三件套结构

| 文件 | 角色 | 谁读 | 变更频率 |
|---|---|---|---|
| `SKILL.md` | **合同**：能力边界、输入输出契约、前置条件、执行步骤 | 编排层（`autopilot`、`gate-runner`）读它判断"能不能调用" | 低 |
| `prompt.md` | **指令**：真正投给模型的可执行提示词 | 模型执行时读 | 高（调优） |
| `references/` | **知识**：领域范本、规则、清单、历史案例 | 模型按需读取（渐进式披露） | 中 |

分开的核心价值是**可以独立演进**：调提示词不影响编排逻辑，补领域知识不串改流程契约。三者混在一个文件里，每次优化提示词都可能不小心改坏流程契约。

## 2. SKILL.md 标准格式

````markdown
---
name: ai-design-03-db
version: 1.0.0
stage: 02_概要详细设计
owner: <负责人>
updated: 2026-10-19
applicable_stacks: []          # 空=技术中立；非空=仅在这些技术栈下可用
---

# 能力声明

一句话说清这个 Skill 做什么，以及**不做什么**。

## 输入契约
| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|

## 产出契约
| 产出 | 路径 | 格式 |
|---|---|---|

## 前置条件（不满足则拒绝执行）
- 批次状态机当前步骤为 `xxx`
- 上一道门禁已通过
- 若目标产出文件已存在 → 走"续做"分支而非覆盖

## 执行步骤
1. …

## 边界（明确不做）
- …

## 失败处理
| 失败情形 | 处理 |
|---|---|
````

**最重要的两节是「前置条件」和「边界」。** 前者让编排层能判断该不该调用（必须写成可判定的布尔条件，不能写成"最好先…"）；后者防止 Skill 越界——AI 天然倾向"顺手多做一点"，这在流水线里是灾难。

## 3. 三条硬性设计原则

**原则一：一个 Skill 只做一件事，做完整的一件事。**
`02-analysis` 负责"原始需求结构化"，就不该顺手把原型也画了。粒度太粗会导致无法复用（迭代场景可能只需要 02，不需要 01）；粒度太细会导致 Skill 间通信成本爆炸。

**原则二：Skill 保持技术中立，技术细节由规范包提供。**
`prompt.md` 里不写 `@Transactional`，写"遵循生效快照中 `STD-SB3-*` 事务条目"。这样换技术栈只需新增一个包，不需要重写 Skill。

需要技术栈专用的 Skill 用 `applicable_stacks` 声明，编排层据此**跳过**（不是报错）不适用的 Skill。

**原则三：不确定就停下，不臆造。**
遇到信息不足时，输出待澄清清单并中止，而不是猜一个答案继续往下跑。流水线里最贵的错误是"看起来跑完了但产出是编的"——错误会逐级放大：需求猜错 → 设计错 → 代码错 → 测试按错的设计写用例且全部通过。

## 4. 版本号语义

与软件版本不同，注意各位的含义：

| 位 | 变更含义 | 是否触发下游重跑 |
|---|---|---|
| 主版本 X | **流程步骤变化**（多一步、少一步、顺序变） | 是，需人工确认 |
| 次版本 Y | **产出物结构变化**（模板改字段、编号规则调整） | 是，需重跑下游 |
| 修订 Z | **提示词优化**，产出结构不变 | 否 |

这条规则的实际价值：修订版本升级可以无脑执行；次版本以上升级必须人工确认，且所有已完成的下游产出物标记为"待重验"。没有这条规则，团队会陷入"每次改措辞就升个版本"的混乱。

## 5. 验收标准

一个 Skill 达到可用状态，必须同时满足：

- [ ] `SKILL.md` ≤ 150 行，且 `inputs` / `outputs` / `preconditions` / 边界四节齐全
- [ ] `prompt.md` ≤ 300 行
- [ ] `references/INDEX.md` 存在，且每个知识文件都标明了"何时读取"
- [ ] 用**一个真实需求**端到端跑通过至少一次
- [ ] 在信息不足时能正确停下并输出待澄清清单（而不是编造）
- [ ] 重复执行同一输入，产出结构一致（允许措辞差异）
- [ ] 产出物中的每个结构单元都携带编号（`REQ`/`FN`/`TC` 等）

**建议不要一次全建。** 按路线图分批交付，每批都用真实需求验证过再进入下一批。未经真实批次验证的 Skill 只是"看起来能用"。

## 6. 命名

`ai-<域>-<序号>-<动作>`，域枚举见 `命名与编号规范.md` 第 6 节。编排类加 `-autopilot`，工具类加 `-runner` / `-convert`。

## 7. 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| `SKILL.md` 超过 400 行，里面做了 5 件事 | 无法复用、无法单独测试、没人敢改 | 按"能否被单独复用"拆 |
| `prompt.md` 里硬编码技术栈写法 | 换栈时整份作废，团队开始复制 Skill | 改为引用规范包条目编号 |
| 没有"边界"一节 | AI 顺手多做，产出物互相覆盖 | 明确列出不做什么 |
| 产出物没有编号 | 追溯链断裂，度量无法进行 | 结构单元必须携带编号 |
| 前置条件写成建议（"最好先…"） | 编排层无法判断，损坏的批次继续往下跑 | 写成可判定的布尔条件 |
| 为每个项目分叉一个 Skill | Skill 维护成本随项目数线性增长 | 先问"这个差异能不能放进规范包"，90% 可以 |
