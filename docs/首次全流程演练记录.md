#### C-01 生效快照的哈希，三个文件三种说法，且 prompt.md 指的那个字段根本不存在

- **现象**：`ai-requirement-00-intake/prompt.md` 写「读 `.ai/spec-effective/<项目码>.json`，填入 `manifest_hash` 或快照哈希」。实测 `taskboard.json` 的顶层键是
  `['project','manifest_hash','built_at','packs','domain_priority','overrides','conflict_resolutions','entries']`——**没有 `snapshot_hash`**。
  真实的 `snapshot_hash` 只写在 `.ai/logs/spec-build.jsonl`（`sha256:087ee1673091b072`），而 `.ai/state/_模板.yaml` 的注释也承认「值取自 `.ai/logs/spec-build.jsonl` 最近一次该项目的记录」。
  SKILL.md 的输入契约又说是 `.ai/spec-effective/<项目码>.md`。
- **位置**：`01_需求设计/skills/ai-requirement-00-intake/prompt.md`（生成批次号之后的「写入批次状态文件」段）；`.../SKILL.md` 输入契约表；`.ai/state/_模板.yaml` 第 17–21 行；`00_工作空间配置/skills/ai-spec-build/scripts/spec_build.py`（`build_snapshot_json`）。
- **为什么算卡点**：批次状态文件的 `spec_snapshot.hash` 是「这个批次用的是哪版规范」的唯一凭证。三个文件三种指引，执行者按 prompt.md 走会拿到 `None` 或 `manifest_hash`（写进去也不报错），于是审计链从第一个文件起就是错的值。
- **影响**：需要人工兜底。
- **建议**：把 `snapshot_hash` 一并写进 `<项目码>.json`；prompt.md 与 SKILL.md 统一指向同一处；`_模板.yaml` 的注释同步改为「取 `<项目码>.json` 的 `snapshot_hash`」。

#### C-02 `ai-design-05-frontend-spec` 声称自己不产出 `design` 类产物，实际会

- **现象**：该 SKILL.md 末尾写「注意：本 Skill **不产出** gate-03 校验的设计产出物类型（`design`），但它属于设计阶段」。但它的产出路径是 `docs/02_设计/前端设计.md`，路径含「设计」；而 `gate_run.py` 的 `PATH_MARKERS["design"] = ("设计", "design")` 是**子串匹配**。因此该文件**是** `design` 类产出物，会被 `fn-coverage-design`、`fn-design-section`、`decision-recorded` 三项检查读到。
- **位置**：`02_概要详细设计/skills/ai-design-05-frontend-spec/SKILL.md`「与其他 Skill 的关系」；`07_质量门禁/skills/ai-gate-runner/scripts/gate_run.py` 第 51–59 行。
- **为什么算卡点**：这句话会让执行者以为「前端设计不参与 gate-03 覆盖率统计」，进而把本该有 FN 小节的文档写成散文。而实际上 `fn-design-section` 会因此报 WARN。
- **影响**：只是别扭（但会诱发真实的 WARN）。
- **建议**：改成「**会**被 gate-03 的 `fn-coverage-design` / `fn-design-section` 读到，因此同样要求每 FN 一个小节」。

#### C-03 检查项数量：README 说 24，实际 25

- **现象**：`07_质量门禁/README.md` 第 59 行「执行器已实现，**24 个检查项全部有实现**」；`--list-checks` 实际输出 `检查项库（共 25 项；门禁定义引用 25 项）`；顶层 `README.md` 第 183 行又写「25 个检查项」。

- **影响**：只是别扭。
- **建议**：把 24 改成 25，并在 README 里加上"数量由 `--list-checks` 输出为准"。

#### C-19 执行器允许用 `--confirm` 越过 BLOCK 级 skip —— 门禁最关键的几项被人工签核架空

- **现象（可复现）**：
  - gate-04 的检查项 1 `commit-format` 是 **BLOCK**，因无 git 仓库记 `skip`；执行器随后输出
    `结果：pending_manual` 并提示 `--confirm --by <你的名字>`。我照做 → `passed`。
  - gate-05 的检查项 2 `testcase-executed`、3 `p0p1-closed` **都是 BLOCK**，都因缺产出物记 `skip`；同样 `--confirm` → `passed`。
  - 也就是说：**「提交信息是否带 FN」「用例都跑完了吗」「P0/P1 都关闭了吗」三件门禁最想守住的事，在零证据的情况下被签成了通过。**
  执行器的 `run_gate()` 里，判定顺序是 `block_fail → waive → confirm → skip/manual`，**`skip` 从未进入阻断判定**。
- **位置**：`gate_run.py` 第 944–957 行（`block_fail` 只看 `result == FAIL`，`skipped` 只影响是否 `pending_manual`）；第 1013–1014 行的输出「⚠️ N 项无法自动校验（skip ≠ pass）。补齐材料或人工确认后再签核。」
- **为什么算卡点**：门禁定义把 BLOCK 定义为"不通过则不可进入下一阶段"，执行器却把 BLOCK+skip 与 WARN+skip 一视同仁，只用一句警告提示，随后给出的建议命令就是"确认通过"。这与门禁自己反复强调的「skip 不等于 pass」**在效果上正好相反**——提示是对的，机制是反的。
- **影响**：**需要人工兜底**（且兜底成了默认路径——本次 6 道门禁里有 4 道走了 `--confirm`）。
- **建议**：① BLOCK 项 skip 时，`--confirm` 应被拒绝，只能走 `--waive --reason --expires`（豁免必须留痕并自动复查）；② 或在 `pending_manual` 的提示里强制列出"哪些 BLOCK 项处于 skip 状态、各自要补什么材料"。

#### C-20 门禁文件承诺的豁免通道，对 BLOCK 项实际不存在，而且不说明原因

  - `ai-design-02-detail` 的异常分支、`ai-test-01-cases` 的用例推导都依赖 `01_需求设计/references/业务场景清单.md`——也是空的（「本文件当前为空，需要由业务方填充」）。
  - `ai-design-03-db` 的输入契约列了「领域模型 | `09_资产库/领域模型/`」，`09_资产库/组件库/后端公共能力清单.md` 等同样为空骨架。
- **位置**：`09_资产库/组件库/前端组件清单.md`、`01_需求设计/references/业务场景清单.md`、`09_资产库/领域模型/业务实体字典.md`。
- **为什么算卡点**：README 已经诚实地说明这些是待填充资产（属 P3），但多个 Skill 把它们写成**必读的第一步**。执行者只能跳过这一步继续，而"跳过"没有任何记录位置——我最终只能把它记成待澄清问题 Q-007 / Q-004。
- **影响**：需要人工兜底。
- **建议**：在 SKILL/prompt 里给这些资产加"**为空时的降级路径**"（如「组件清单为空时，按技术栈包的组件体系搭建，并在问题汇总登记一条待填充项」），把"跳过"变成有记录的合法分支。

## 4. 结论

### 4.1 走通了哪几步

任务里说的"12 步流程"按知识库的实际定义展开是 **23 个阶段 Skill + 6 道质量门禁**（另加 1 次 `ai-spec-build` 前置构建）。结果：

| 分类 | 数量 | 明细 |
|---|---|---|
| **真正走通**（产出齐全、未被拒绝、无兜底） | **15 / 23** | `00-intake`、`01-init`、`02-analysis`、`03-prototype`\*、`04-prd`、`design-01-arch`、`02-detail`、`03-db`、`04-api`、`05-frontend-spec`、`06-review`、`dev-01-scaffold`、`02-backend`、`03-frontend`、`test-01-cases`（\* `03-prototype` 的"先匹配组件"一步被空资产库挡住，产出本身齐全） |
| **部分成功**（产出了但缺件 / 结论不成立） | **2 / 23** | `dev-04-unittest`（用例已写但跑不了，按 SKILL 应拒绝）、`dev-05-codereview`（门禁最终通过，但含 1 个 BLOCK 级 skip） |
| **拒绝执行** | **6 / 23** | `dev-06-docsync`、`test-02-automation`、`test-03-execute`、`test-04-regression`、`test-05-report`、`archive-01-close` |
| **门禁** | **6 / 6** | 全部被真实执行过；gate-02 / gate-05 / gate-06 首次 `failed`，gate-01 / gate-03 / gate-04 首次 `pending_manual`；最终 6 道全部 `passed`（其中 4 道靠 `--confirm --by 演练`，**一次豁免都没用上**，另 1 次触发过「拒绝执行」退出码 2） |
| **附带要求的人工兜底件** | **3** | `docs/04_交付/上线方案.md`、`docs/04_交付/结项报告.md`、`docs/03_测试/拒绝执行的步骤记录.md`——三者都**没有对应的 Skill** |

**一句话**：23 个 Skill 里只有 15 个按契约走通——**测试域 5 个 Skill 只有 1 个（`ai-test-01-cases`）成功**。最终 6 道门禁全部 `passed`，但这个 `passed` 是**人工签核推过去的**：gate-04 在零提交的情况下通过，gate-05 在零执行的情况下通过。

### 4.2 不完整的地方与原因

流程本身走完了（批次已 `archived: true`），但**证据链是空的**：

1. `FN → 提交` 整段为空（3 个 FN 全部无提交），因为流程禁止 git 而门禁只记 skip（C-12）。
2. 25 条测试用例一条未执行，因为 `ai-test-03-execute` 因环境不可用拒绝执行（C-22），两个 BLOCK 项随之 skip 后被签核（C-19）。
3. `ai-test-04-regression` 的回归圈定从未产出，但 gate-05 的 `regression-scoped` 判了 pass（C-06）。

### 4.3 最严重的三个卡点

**第一位 —— C-09：`repo` 一个字段承担四种语义，双仓库模型下必然撞墙。**
这是唯一一个**阻断流程且无法豁免**的卡点（gate-02 `waivable: no`）。根因是 manifest 只有单一 `repo`，而 `ai-requirement-01-init` 强制要求"原型工程仓 = 独立仓库"。它还会连带制造两个更隐蔽的后果：把 `repo` 改指向原型仓后 `fn-coverage-prototype` 变成**假通过**（C-08），以及产出物路径全部解析不到导致下游门禁整体退化。我最终是靠**放弃双仓库**（工作区 W-1）才把流程推下去的。

**第二位 —— C-19：执行器允许 `--confirm` 越过 BLOCK 级 skip。**
这是唯一一个"机制层写反"的卡点。门禁文件把 BLOCK 定义为"不通过则不可进入下一阶段"，执行器的 `run_gate()` 里 `skip` 却根本不参与阻断判定，而 `pending_manual` 的提示语就是"执行 `--confirm`"。结果是本次 **6 道门禁里 4 道走了签核，其中 gate-04 与 gate-05 各自带着 1 个和 2 个 BLOCK 级 skip 通过**——「提交带 FN」「用例跑完了吗」「P0/P1 关闭了吗」这三件门禁最想守住的事，证据都是空的。门禁自己反复强调的「skip 不等于 pass」，在机制上被抵消了。

**第三位 —— C-12：追溯链的最后一环没有产出方，且门禁把它记成 skip 而非 fail。**
`commit-format` 是 BLOCK，但产出"一次合规提交"的动作被 `ai-dev-*` 全部 prompt、`CLAUDE.md` 与 `STD-BASE-005` 三重禁止。更糟的是 gate-06 的 `fn-has-commit` 在"项目仓不是 git 仓库"时记 `skip`——于是**手工断链检测数出来的 3 条断链，在门禁视图里显示为 0**（结项报告 §三的两列数据）。"断链数是目标为 0 的硬指标"这句话，在没有任何提交的批次里会轻松成立。

### 4.4 一个附带的判断

本知识库的**机制设计**（五层规范、构建期合并、编号锚点、skip≠pass、豁免留痕）在本次演练中**基本经受住了检验**——`ai-spec-build` 一次成功、编号体系全程无冲突、gate-03 是唯一一道 8/8 全绿且零 skip 的门禁（设计段的产出契约与检查项咬合得最好）。
问题几乎全部集中在**跨域的接缝处**：`repo` 字段、`artifacts` 路径基准、批次 `steps`、编号登记段、以及"谁负责产出门禁要的那份文件"。设计段的契约之所以严丝合缝，是因为它的输入输出都在同一个域内；一旦跨域（原型仓↔文档仓↔代码仓，测试域↔编码域），契约就没人对齐了。

**这恰好印证了 `docs/设计方案.md` 第 11 节那句"P0 的隐藏关键：老老实实记录卡点"——卡点不在单个 Skill 里，在 Skill 之间的缝里。**
