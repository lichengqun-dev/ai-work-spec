## 为什么这两份要留在仓库里

**因为知识库最容易被改坏的方式，是"善意地改掉一个刻意设计"。**

举两个具体例子，两个都在演练记录里：

- `skip ≠ pass` 这条语义，看起来像是"太严格了"，实际是防"没法校验 = 校验通过"——
  这个 bug 曾经真实发生过：gate-04 在**零提交**下被签核通过
- 挂载层是**生成**的而不是手写的，看起来多此一举，实际是因为手写会产生 39 份需要同步的副本，
  而这个仓库里"副本与源分叉"已经反复出现过

**这两条现在都写进了机制**，但读不懂它们的人依然会想改掉。本目录的作用就是在动手之前拦一下。

## 与提案文档的关系

`ai-spec-check` **不检查本目录**。理由是这两份文档通篇是假设的编号与假想的反例——
它们记录的是"可以长什么样"与"曾经是什么样"，不是当前事实。

**代价要知道**：如果设计文档里用了不存在的编号举例，检查器看不见，
那几个编号会被读者当成真实编号。这是当前已知的取舍。

所以读本目录时请记住：**这里的编号、路径、Skill 名都是示意，不要直接引用。**

## 演练记录的用法

那份记录是按发现顺序写的，不是按重要性排的。**按卡点编号（C-01、C-02…）查**，
每条都写了现象、根因、修没修。末尾有一节"未修复的设计缺口"——那些是需要决策的，
不是遗漏的待办。

> 新增记录时的纪律：**记录卡点原文，不要润色成"一次成功的演练"。**
> 这份记录的价值全部来自它如实记了哪些地方没跑通。
