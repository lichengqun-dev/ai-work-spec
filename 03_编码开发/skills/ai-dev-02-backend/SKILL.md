# 能力声明

依据**冻结契约**、功能详细设计与数据库设计实现后端功能，**按 `FN` 逐个交付**。

技术细节全部从生效规范快照读——本 Skill 不硬编码任何框架写法，因此换技术栈不需要重写它。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 接口契约 | `ai-design-04-api` 产出 | 是 | **冻结态**；哈希须与门禁通过时记录的一致 |
| 功能详细设计 | `ai-design-02-detail` 产出 | 是 | 每 FN 一节 |
| 数据库设计 | `ai-design-03-db` 产出 | 是 | 含 DDL 与回滚 |
| 工程骨架说明 | `ai-dev-01-scaffold` 产出 | 是 | 模块与目录的对应关系 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | **技术细节的唯一来源** |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 后端代码 | 项目代码仓 | 按 FN 分次提交，提交信息含 FN 编号 |
| 单测 | 项目代码仓 | 或交由 `ai-dev-04-unittest` 补齐 |

## 前置条件（不满足则拒绝执行）

- gate-03 已通过，契约处于冻结态
- 工程骨架已就位，模块落点明确
- 生效快照中的后端规范包存在（无则拒绝——**没有规范包就写代码，等于无约束产出**）
- 契约哈希与批次状态文件记录的一致（不一致说明契约被改过，**必须停止并说明**）

## 执行步骤

1. 从功能详细设计中取一个 `FN`（**一次一个，不并行**）
2. 读该 FN 的设计章节（**只读相关段落，不读整份详细设计**）与对应接口的契约片段
3. 查生效快照中该技术栈的相关条目（命名、异常处理、事务边界、分页、持久层约定等）
4. 实现，遵循快照中的约定；快照未覆盖的细节**向用户确认，不自行决定**
5. 提交，提交信息格式：`feat(FN-XXX-000): <描述>`
6. 下一个 FN，重复

## 边界（明确不做）

- **不改契约。** 实现时发现契约设计有问题 → 停止并说明需要走变更子批次
- 不设计表结构、不改 DDL（那是 `ai-design-03-db`）
- 不做前端实现（`ai-dev-03-frontend`）
- 不重构与当前 FN 无关的代码
- **不硬编码技术栈写法到 prompt 逻辑里**——一切从快照读

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 契约哈希与记录不一致 | **停止**，报告契约被改动过，由人决定是否重跑设计阶段 |
| 某 FN 的设计信息不足以实现 | 停止该 FN，列出缺什么，记入待澄清，**不猜实现** |
| 快照未覆盖所需的实现细节 | 停下问用户，**不自行决定**——这正是"Skill 保持技术中立"的代价与价值所在 |
| 实现中发现契约字段不够用 | 停止，说明需开变更子批次，**不偷偷加字段** |
| 需要引入新依赖 | 停止并说明，走确认流程 |

## 提交信息的硬性要求

gate-04 的 `commit-format`（BLOCK）校验两件事：

1. 格式为 `<type>(<scope>): <subject>`，`type` 取固定集合
2. subject 或 body 中包含 `FN-<模块码>-<3位>` 编号

**这是整条追溯链的最后一环。** 缺了它，`FN → 提交` 断裂，无法回答"这个功能是什么时候、由哪次提交上线的"。
同时 gate-04 的 `fn-has-commit` 要求本批次每个 FN 都有提交关联——一个提交覆盖多个 FN 时，
在 body 中列出全部编号。
