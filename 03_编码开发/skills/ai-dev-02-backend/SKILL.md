# ai-dev-02-backend · 后端实现

## 能力声明

依据**冻结契约**、功能详细设计与数据库设计实现后端功能，**按 `FR` 逐个交付**。

技术细节全部从生效规范快照读——本 Skill 不硬编码任何框架写法，因此换技术栈不需要重写它。

**不做什么**：不改契约、不设计表结构、不做前端实现、不重构与当前 FR 无关的代码——见「边界」。

## 何时用 / 何时不用

- **用**：工程骨架就位、契约处于冻结态，要按 FR 逐个实现后端功能时
- **不用**：只补单元测试（走 `ai-dev-04-unittest`）；只做文档回流（走 `ai-dev-06-docsync`）；
  实现时发现契约不够用（先开变更子批次，不是继续写代码）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 接口契约 | `ai-design-04-api` 产出 | 是 | **冻结态**；哈希须与门禁通过时记录的一致 |
| 功能详细设计 | `ai-design-02-detail` 产出 | 是 | 每 FR 一节 |
| 数据库设计 | `ai-design-03-db` 产出 | 是 | 含 DDL 与回滚 |
| 工程骨架说明 | `ai-dev-01-scaffold` 产出 | 是 | 模块与目录的对应关系 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | **技术细节的唯一来源** |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 后端代码 | 项目代码仓 | 按 FR 分次提交，提交信息含 FR 编号 |
| 单测 | 项目代码仓 | 或交由 `ai-dev-04-unittest` 补齐 |

## 前置条件

**hard（不满足则拒绝执行）**

- 接口契约已产出且**处于冻结态**，其**哈希与批次状态文件记录的一致**——
  不一致说明契约在冻结后被改过，继续实现等于基于一份没人确认过的契约写代码
- 功能详细设计已产出（每 FR 一节）
- 工程骨架已就位，模块落点明确
- 生效快照中的后端规范包存在（无则拒绝——**没有规范包就写代码，等于无约束产出**）

**soft（不满足则提示，可继续）**

- gate-03 设计评审已通过（未通过时产出物标注"未经评审"）
- 数据库设计已产出（缺则该 FR 的持久层约定可能不完整，产出物标注）

## 执行步骤

1. 从功能详细设计中取一个 `FR`（**一次一个，不并行**）
2. 读该 FR 的设计章节（**只读相关段落，不读整份详细设计**）与对应接口的契约片段
3. 查生效快照中该技术栈的相关条目（命名、异常处理、事务边界、分页、持久层约定等）
4. 实现，遵循快照中的约定；快照未覆盖的细节**向用户确认，不自行决定**
5. 提交，提交信息格式：`feat(FR-XXX-000): <描述>`
6. 按需重复 1–5，直到本批次的 FR 全部交付
7. 回写批次状态文件：本步骤置 `done`，记录本次实现的 FR 清单

交付节奏：

```
取一个 FR
  → 只读该 FR 的设计章节（不读整份详细设计）
  → 只读该 FR 对应的契约片段
  → 查生效快照中该技术栈的相关条目
  → 实现 → 提交（提交信息带 FR）→ 下一个
```

### 技术细节全部从快照读

**你的 prompt 里没有任何框架写法，这是刻意的。**

```bash
# 先读快照，再写代码
projects/<项目码>/.agent/spec-effective/<项目码>.md
```

快照里的 B 段（按需检索索引）按触发场景列出了条目，例如：

| 你要做的事 | 该读的条目 |
|---|---|
| 写 Service 层 | `STD-SB2-*` / `STD-SB3-*` 的事务与异常条目 |
| 写查询 | `STD-DM8-*` 的方言条目 + 分页条目 |
| 写接口 | `STD-BASE-321/322/323` 的错误码、契约冻结、分页上限 |
| 写配置 | `STD-BASE-104` 密钥外置 |

**快照没覆盖的细节，停下来问。** 自己决定的实现细节会成为团队里的"另一种写法"，
而两种写法并存之后，没人知道哪种是对的。这不是能力不足，是这套体系刻意的边界。

### 提交信息的硬性要求

gate-04 的 `commit-format`（BLOCK）校验两件事：

1. 格式为 `<type>(<scope>): <subject>`，`type` 取
   `feat`/`fix`/`perf`/`refactor`/`test`/`docs`/`chore`/`style`
2. subject 或 body 中包含 `FR-<模块码>-<3位>` 编号

```
feat(FR-CORE-045): 列表页新增导出接口       ← 格式 + FR 编号
```

反例：`update`、`fix bug`、`feat(core-service): 新增导出`（没有 FR 编号）。

**这是整条追溯链的最后一环。** 缺了它，`FR → 提交` 断裂，无法回答"这个功能是什么时候、
由哪次提交上线的"。同时 gate-04 的 `fr-has-commit` 要求本批次每个 FR 都有提交关联——
一个提交覆盖多个 FR 时，在 body 中列出全部编号。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——接一个 FR 就能跑，不必等整个批次排到编码段
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（未接入批次）时：产出物落到指定路径、跳过状态回写并在报告中说明

## 边界（明确不做）

- **不改契约。** 实现时发现契约设计有问题（"这个字段名不合适""少了个参数"）→ 停止并说明需要走变更子批次
- 不设计表结构、不改 DDL（那是 `ai-design-03-db`）
- 不做前端实现（`ai-dev-03-frontend`）
- **不重构与当前 FR 无关的代码**
- 不硬编码密钥（不为了"能跑起来"填一个看起来合理的示例密码）
- **不硬编码技术栈写法到 prompt 逻辑里**——一切从快照读
- 不执行 git 操作（提交由用户确认后执行，或按项目约定）

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 契约哈希与记录不一致 | **停止**，报告契约被改动过，由人决定是否重跑设计阶段 |
| 某 FR 的设计信息不足以实现 | 停止该 FR，列出缺什么，记入待澄清，**不猜实现** |
| 快照未覆盖所需的实现细节 | 停下问用户，**不自行决定**——这正是"Skill 保持技术中立"的代价与价值所在 |
| 实现中发现契约字段不够用 | 停止，说明需开变更子批次，**不偷偷加字段** |
| 需要引入新依赖 | 停止并说明，走确认流程 |
