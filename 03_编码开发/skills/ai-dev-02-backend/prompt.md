# 指令：后端功能实现

## 开始前

确认契约已冻结，且其哈希与批次状态文件记录的一致。**不一致就停下**——
那说明契约在冻结后被改过，继续实现等于基于一份没人确认过的契约写代码。

## 一次一个 FN

```
取一个 FN
  → 只读该 FN 的设计章节（不读整份详细设计）
  → 只读该 FN 对应的契约片段
  → 查生效快照中该技术栈的相关条目
  → 实现 → 提交（提交信息带 FN）→ 下一个
```

**不要并行做多个 FN。** 并行会让"哪个提交对应哪个 FN"变模糊，而 gate-04 的 `fn-has-commit`
依赖这个对应关系。一个提交确实覆盖多个 FN 时，在 body 里列全。

## 技术细节全部从快照读

**你的 prompt 里没有任何框架写法，这是刻意的。**

```bash
# 先读快照，再写代码
.ai/spec-effective/<项目码>.md
```

快照里的 B 段（按需检索索引）按触发场景列出了条目，例如：

| 你要做的事 | 该读的条目 |
|---|---|
| 写 Service 层 | `STD-SB2-*` / `STD-SB3-*` 的事务与异常条目 |
| 写查询 | `STD-DM8-*` 的方言条目 + 分页条目 |
| 写接口 | `STD-BASE-321/322/323` 的错误码、契约冻结、分页上限 |
| 写配置 | `STD-BASE-104` 密钥外置 |

**快照没覆盖的细节，停下来问。** 自己决定的实现细节会成为团队里的"另一种写法"，
而两种写法并存之后，没人知道哪种是对的。这不是能力不足，是这套体系刻意的边界。

## 最常被违反的两条

**一、顺手改契约。**
实现时发现"这个字段名不合适""少了个参数"，很容易顺手改契约——**绝对不要**。
契约已冻结，改它需要开变更子批次并通知前端；而前端此时可能已经按旧契约写了代码。
正确做法：停下，说明需要变更，让用户决定。

**二、顺手重构无关代码。**
改到一半发现旁边的代码写得不顺眼。**不要动。** 无关改动会：

- 让提交信息与实际改动不符
- 让评审者难以判断变更范围
- 在出问题时无法通过 revert 单个提交来撤销

## 提交信息的硬性要求

gate-04 的 `commit-format` 是 **BLOCK** 级，两个要求：

```
feat(FN-CORE-045): 列表页新增导出接口       ← 格式 + FN 编号
```

- 格式：`<type>(<scope>): <subject>`，type 取 `feat`/`fix`/`perf`/`refactor`/`test`/`docs`/`chore`/`style`
- subject 或 body 中必须含 `FN-<模块码>-<3位>`

反例：`update`、`fix bug`、`feat(core-service): 新增导出`（没有 FN 编号）。

**这是追溯链的最后一环。** 没有它就无法回答"这个功能由哪次提交上线"。

## 密钥与配置

`secrets-externalized` 是 BLOCK 级检查项：项目仓里不得出现明文凭据。

- 配置文件里写占位符与配置中心地址
- **不要**为了"能跑起来"填一个看起来合理的示例密码——示例密码常被直接沿用
- 扫描口径是窄的（宁可漏报不误报），所以它通过不等于真的没有硬编码凭据，自己也要留意

## 完成后

回写批次状态文件：本步骤置 `done`，记录本次实现的 FN 清单。

## 你绝对不要做的事

- **不要改契约**（发现不够用 → 停下说明）
- 不要重构与本 FN 无关的代码
- 不要自行决定快照未覆盖的实现细节
- 不要硬编码密钥
- 不要执行 git 操作（提交由用户确认后执行，或按项目约定）

```

设计章节：docs/02_设计/功能详细设计.md §FN-CORE-045
契约片段：POST /api/v1/export（x-fn-id: FN-CORE-045）
遵循的规范条目：STD-SB3-001（jakarta 命名空间）、STD-DM8-001（CLOB 读取）、STD-BASE-323（分页上限）

- src/.../ExportService.java
- src/.../ExportController.java

提交：feat(FN-CORE-045): 列表页新增导出接口
待确认：无

下一个 FN：FN-CORE-046
```
