# 指令：工程骨架与模块划分

## 开始前

确认 **gate-03 已通过、契约已冻结**。没冻结就停下——契约未定就搭骨架，模块划分大概率要返工。

读架构设计、冻结契约、生效快照中的目录组织与构建规范。

## 产出

```
<项目代码仓>/
├── <模块 1>/
├── <模块 2>/
└── <构建配置>
```

**目录风格从生效快照读，不自行发明。** 快照没规定时，**遵循既有工程的风格**——
在骨架说明里记录你观察到的相对一致的约定，不要以"规范"为名重构既有结构。

## 三条纪律

**一、骨架里不写业务逻辑。**
可以有目录、模块声明、构建配置、空的核心类（如启动类、配置类）。
**不应该**有任何业务方法——哪怕"顺手实现一下最简单的那个 FN"。

原因：骨架阶段的实现没有经过"按 FN 逐个交付"的节奏，它会让后续的提交与 FN 对应关系变模糊，
而 `fn-has-commit` 检查项依赖这个对应关系。

**二、只引入架构设计明确需要的依赖。**
不要"顺便"加上常用的工具库、日志库。每个依赖都是一个需要长期维护、需要跟进安全漏洞的外部面。
架构设计里没提到但确实需要的，先问，不要自己加。

**但测试框架要特别处理**：它属于架构设计应当明确的内容，不是"可选的常用库"。
如果设计里没提，**停下询问**，不要跳过——`ai-dev-04-unittest` 的前置条件要求项目仓有可运行的测试命令，
骨架阶段漏掉它，单元测试那一步就没法执行。（这不是把责任推给下游，而是这一步就该问清楚。）

**三、不升级既有技术栈。**
增量开发时，"顺手升个版本"是事故高发区。版本由生效快照锁定；确需升级走独立批次评估。

## 版本约束从快照读

构建配置里最容易出问题的两处（都来自快照）：

| 约束 | 典型值 | 违反后果 |
|---|---|---|
| 编译目标 | Java 8 项目必须 `source/target = 1.8` | 用了 9+ 语法直接编译失败 |
| API 命名空间 | Spring Boot 3 用 `jakarta.*`，2.6 用 `javax.*` | 编译可能通过，运行期 `NoClassDefFoundError` |

这两条在 `09_资产库/规范包/stacks/be-*` 里都有对应条目。

## 骨架说明要写清对应关系

`<需求名>/03_实现/工程骨架说明.md` 里给出模块 ↔ 目录 ↔ 职责的对应表。
下游的 backend / frontend Skill 靠它决定代码该落在哪，
**没有这张表，不同的人会把同一个功能放进不同的模块**。

## 完成后

回写批次状态文件：本步骤置 `done`。

## 你绝对不要做的事

- 不要实现任何业务逻辑（哪怕"最简单的那个"）
- 不要引入架构设计未提及的依赖
- 不要升级既有技术栈
- 不要以"统一风格"为名重构既有目录结构
- 不要执行 git 操作
