# 骨架阶段要点

> 本文件承载**「为什么」**：骨架阶段那三条纪律各自的代价，以及构建配置里最容易出问题的两处。
> 「做什么」在 `SKILL.md` 的执行步骤与边界里，不重复。

## 一、骨架里为什么不写业务逻辑

骨架里可以有目录、模块声明、构建配置、空的核心类（如启动类、配置类），
**不应该**有任何业务方法——哪怕"顺手实现一下最简单的那个 FR"。

原因：骨架阶段的实现没有经过"按 FR 逐个交付"的节奏，它会让后续的提交与 FR 对应关系变模糊，
而 `fr-has-commit` 检查项依赖这个对应关系。追溯链断在第一个提交上，后面补不回来。

## 二、为什么只引入架构设计明确需要的依赖

每个依赖都是一个需要**长期维护、需要跟进安全漏洞**的外部面。骨架阶段"顺便"加上常用的工具库、
日志库，看起来是省事，实际是把这些维护责任悄悄加进来了，而且没人知道是谁加的、为什么要加。

架构设计里没提到但确实需要的，先问，不要自己加。

## 三、为什么不升级既有技术栈

增量开发时，"顺手升个版本"是事故高发区：骨架阶段改动面大、验证最弱，
这个阶段引入的版本变化，要到集成或上线时才暴露。

版本由生效快照锁定；确需升级走独立批次评估，不在骨架里做。

## 四、构建配置里最容易出问题的两处（都来自快照）

| 约束 | 典型值 | 违反后果 |
|---|---|---|
| 编译目标 | Java 8 项目必须 `source/target = 1.8` | 用了 9+ 语法直接编译失败 |
| API 命名空间 | Spring Boot 3 用 `jakarta.*`，2.6 用 `javax.*` | 编译可能通过，运行期 `NoClassDefFoundError` |

这两条在知识库根下 `09_资产库/规范包/stacks/be-*` 里都有对应条目。
**上面的"典型值"只是说明这两处为什么容易出事，不是本 Skill 的默认值**——
实际取值一律以目标项目生效快照里的 C 段为准。
