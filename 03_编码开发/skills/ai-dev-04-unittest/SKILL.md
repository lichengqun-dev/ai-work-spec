# ai-dev-04-unittest · 单元测试

## 能力声明

为已实现的功能生成**单元测试**，并补齐未覆盖的分支。

**本 Skill 只做单元测试。** 接口级、集成级、端到端测试属于 `04_测试验证` 域——两者不是一回事，
混在一起会让"单测覆盖率"这个指标失去意义。

**不做什么**：不写接口级 / 集成级 / E2E 测试、不修实现代码、不为了覆盖率数字写无断言的用例——见「边界」。

## 何时用 / 何时不用

- **用**：某个 FR 的实现已提交，要为它补单元测试与分支覆盖时
- **不用**：接口级 / 集成级 / E2E 测试（`04_测试验证` 域）；实现还没提交（没有可测的对象）
- **前后端可分别补测**：与 `ai-dev-03-frontend` 可并行

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 后端 / 前端代码 | `ai-dev-02-backend` / `03-frontend` 产出 | 是 | 按 FR 提交 |
| 功能详细设计 | `ai-design-02-detail` 产出 | 是 | 每 FR 一节，含异常分支与边界 |
| 单元测试规范 | 知识库根下 `03_编码开发/standards/单元测试规范.md` | 是 | 命名与覆盖要求 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 测试框架与断言风格从这里读 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 单元测试代码 | 项目代码仓 | 与实现同模块 |
| 覆盖率报告 | 由项目侧构建工具生成 | — |

## 前置条件

**hard（不满足则拒绝执行）**

- 对应 FR 的实现已提交
- 功能详细设计中该 FR 的章节存在（含异常分支与边界条件）
- **能确定测试框架**：`test` 维度包或技术栈包内已声明；都没有时向用户确认，**不自行选择**
  （本仓库未预置 `test` 维度包；测试框架约定通常写在技术栈包里）
- 项目仓有可运行的测试命令（无则**拒绝**——无法运行的单测等于没写）

**soft**

- 无。本 Skill 的输入缺任一项都做不了，全部落在 hard 一侧；没有"没轮到"类的前置

## 执行步骤

1. 读功能详细设计中该 FR 的**异常分支与边界条件**——这是用例设计的主要输入，
   **不是实现代码本身**
2. 按分支清单设计用例（见下）
3. 命名表达「场景 + 预期结果」（符合 `STD-BASE-423`）
4. 确认用例**不依赖执行顺序、不依赖真实时间 / 网络 / 外部服务**（符合 `STD-BASE-421`）
5. 确认**每条用例都有断言**
6. 运行测试，报告真实结果
7. 覆盖率不足处补齐；**报告未覆盖的分支而不是凑数字**
8. 回写批次状态文件：本步骤置 `done`，记录新增用例数与覆盖率摘要（真实数字，不美化）

### 从分支出发，不从代码出发

```
功能详细设计中的分支
  ├── 主流程           → 一条用例（可能多条，按关键节点分）
  ├── 异常分支
  │     ├── 参数不合法  → 一条
  │     ├── 无权限      → 一条
  │     ├── 状态冲突    → 一条
  │     └── 并发冲突    → 一条
  └── 边界条件
        ├── 数据为空    → 一条
        ├── 数据量上限  → 一条
        └── 时间范围边界 → 一条
```

照着代码写用例，只能测出"代码做了什么"，测不出"它是否该这么做"。
**功能详细设计里写不出来的分支，说明设计阶段就漏了**——此时报告并停止，不要从代码倒推补上。

### 覆盖率的正确用法

覆盖率是**发现未测分支的线索**，不是目标。

| 用法 | 评价 |
|---|---|
| 看哪条分支没被测到 → 补用例 | ✅ 正确 |
| 看核心模块分支覆盖是否达标 | ✅ 正确 |
| 把行覆盖率刷到 80% 交差 | ❌ 会通过大量无断言调用堆上去 |

核心业务逻辑（状态机、金额计算、权限判断）必须覆盖分支；工具类、DTO、配置类不追求覆盖
——给它们写用例是纯粹的浪费。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——指定一个已提交的 FR 就能补测
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」；
  本 Skill 的 soft 为空，正常不会触发
- 批次状态文件不可写（未接入批次）时：产出物落到指定路径、跳过状态回写并在报告中说明

## 边界（明确不做）

- **不为了覆盖率数字而写无断言的用例。** 行覆盖率可以通过大量无断言调用堆上去，但不验证任何行为
- 不从代码倒推用例（要从设计的分支出发）
- 不写接口级 / 集成级 / E2E 测试（那是 `04_测试验证` 域）
- **不修实现代码。** 发现实现有问题 → 报告并停止，由人决定改实现还是改设计
- 不 mock 掉被测逻辑本身
- 不把测试失败说成"环境问题""偶发失败"
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 测试运行失败 | 报告真实失败信息与定位，**不把失败说成"环境问题"** |
| 某分支无法测（依赖真实外部服务） | 报告并说明，不通过降低断言强度绕过 |
| 实现有问题导致用例失败 | **停止**，报告问题与定位；不修改实现来让测试通过 |
| 无可用测试命令 | 拒绝执行，提示先补齐测试配置（属 `ai-dev-01-scaffold` 的职责） |
| 功能详细设计里写不出该 FR 的分支 | 报告并停止，**不从代码倒推补上**——从代码倒推得到的用例只能验证"现在的实现是这样"，无法发现实现本身错了 |

## 输出格式

```
FR：FR-CORE-045 列表页导出
新增用例：6 条
  - should_export_successfully_when_data_exists
  - should_return_403_when_user_lacks_permission
  - should_handle_empty_dataset
  - should_reject_when_page_size_exceeds_limit
  - should_handle_concurrent_export_of_same_dataset
  - should_exclude_archived_rows_by_default

覆盖率：ExportService 分支覆盖 83%（未覆盖：导出格式异常的兜底分支）
未覆盖说明：该分支需要构造损坏的模板文件，当前测试基础设施无法构造，已记入待办

待确认：无
```
