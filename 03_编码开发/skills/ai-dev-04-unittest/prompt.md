# 指令：生成与补齐单元测试

## 开始前

读功能详细设计中该 FN 的**异常分支与边界条件**——这是用例设计的主要输入，
不是实现代码本身。照着代码写用例，只能测出"代码做了什么"，测不出"它是否该这么做"。

## 用例设计：从分支出发，不从代码出发

```
功能详细设计中的分支
  ├── 主流程           → 一条用例（可能多条，按关键节点分）
  ├── 异常分支
  │     ├── 参数不合法  → 一条
  │     ├── 无权限      → 一条
  │     ├── 状态冲突    → 一条
  │     └── 并发冲突    → 一条
  └── 边界条件
        ├── 数据为空    → 一条
        ├── 数据量上限  → 一条
        └── 时间范围边界 → 一条
```

**功能详细设计里写不出来的分支，说明设计阶段就漏了。** 此时报告并停止，不要从代码倒推补上——
从代码倒推得到的用例只能验证"现在的实现是这样"，无法发现实现本身错了。

## 三条硬性要求

**一、可重复、不依赖执行顺序**（`STD-BASE-421`）。

| 反面 | 正面 |
|---|---|
| 用例 A 依赖用例 B 先创建的数据 | 每个用例自建前置数据 |
| 用 `new Date()` 取当前时间 | 注入时钟 |
| 依赖真实数据库 / 网络 | mock 掉外部依赖 |
| 依赖 Redis / MQ 中间件 | 用内存实现或 mock |

依赖顺序的用例在并行执行或单独运行时失败，团队会开始"整体跑一遍"来绕过——
**最终测试失去定位问题的能力**，而这正是它最大的价值。

**二、命名表达「场景 + 预期结果」**（`STD-BASE-423`）。

```java
should_return_403_when_user_lacks_permission()   ✅
testExport2()                                    ❌
```

用例名是失败报告中唯一可见的信息。名字无意义时，一次 CI 失败的排查要从读代码开始。

**三、每条用例必须有断言。**

```java
// ❌ 无断言——它能提高覆盖率，但不验证任何行为
exportService.export(req);

// ✅
assertEquals(403, response.getCode());
assertThat(result.getRows()).hasSize(10);
```

## 覆盖率的正确心态

覆盖率是**发现未测分支的线索，不是目标**。

行覆盖率可以通过大量无断言的调用堆上去。所以：

- ✅ 看哪条分支没被测到 → 去补
- ✅ 核心模块（状态机、金额计算、权限判断）分支覆盖达标
- ❌ 把行覆盖率刷到 80% 交差

工具类、DTO、配置类**不追求覆盖**——给它们写用例是纯粹的浪费。

## 测试失败时

**报告真实结果，不要润色。**

- 失败就报失败，附完整错误信息与定位
- **不要**把失败说成"环境问题""偶发失败"
- **不要**修改实现代码来让测试通过——发现实现有问题应报告并停止，由人决定改实现还是改设计

技术栈相关的测试写法（JUnit / Vitest / Jest 的断言风格、mock 方式）从生效快照读。

## 完成后

回写批次状态文件：本步骤置 `done`，记录新增用例数与覆盖率摘要（真实数字，不美化）。

## 你绝对不要做的事

- 不要从代码倒推用例（要从设计的分支出发）
- 不要写无断言的用例凑覆盖率
- 不要修改实现代码让测试通过
- 不要写接口级 / 集成级 / E2E 测试（那是 04_测试验证 域）
- 不要把测试失败说成环境问题
- 不要执行 git 操作
