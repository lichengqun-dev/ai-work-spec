# 单元测试要点

> 本文件承载**「为什么」**与**正反例**：三条硬性要求各自的理由。
> 「做什么」在 `SKILL.md` 的执行步骤与边界里，不重复。
>
> 下面的例子用来说明原则，**不是本 Skill 指定的写法**——
> 实际用哪个测试框架、哪种断言风格，由目标项目生效快照里的技术栈包决定。

## 一、可重复、不依赖执行顺序（`STD-BASE-421`）

| 反面 | 正面 |
|---|---|
| 用例 A 依赖用例 B 先创建的数据 | 每个用例自建前置数据 |
| 用 `new Date()` 取当前时间 | 注入时钟 |
| 依赖真实数据库 / 网络 | mock 掉外部依赖 |
| 依赖 Redis / MQ 中间件 | 用内存实现或 mock |

依赖顺序的用例在并行执行或单独运行时失败，团队会开始"整体跑一遍"来绕过——
**最终测试失去定位问题的能力**，而这正是它最大的价值。

## 二、命名表达「场景 + 预期结果」（`STD-BASE-423`）

```java
should_return_403_when_user_lacks_permission()   ✅
testExport2()                                    ❌
```

用例名是失败报告中唯一可见的信息。名字无意义时，一次 CI 失败的排查要从读代码开始。

## 三、每条用例必须有断言

```java
// ❌ 无断言——它能提高覆盖率，但不验证任何行为
exportService.export(req);

// ✅
assertEquals(403, response.getCode());
assertThat(result.getRows()).hasSize(10);
```

## 四、测试失败时怎么报告

**报告真实结果，不要润色。**

- 失败就报失败，附完整错误信息与定位
- **不要**把失败说成"环境问题""偶发失败"
- **不要**修改实现代码来让测试通过——发现实现有问题应报告并停止，由人决定改实现还是改设计
