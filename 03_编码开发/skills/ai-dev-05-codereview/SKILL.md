# ai-dev-05-codereview · 代码评审

## 能力声明

执行 **gate-04（代码评审）**，通过后进入测试阶段。

**本 Skill 不做检查项判断。** 自动检查交给 `ai-gate-runner`，人工项原样列给人。

**不做什么**：不做检查项判断、不放宽检查项、不修复代码、不豁免、不执行 git 操作——见「边界」。

## 何时用 / 何时不用

- **用**：编码段收尾时（scaffold / backend / frontend / unittest 都走完）；需要重跑门禁时；用户要求签核时
- **不用**：想改门禁的检查项定义、或怀疑某个检查项的实现本身有问题——那不是本 Skill 的职责范围
- **用户说"自动化都过了，直接签核吧"时**：本 Skill 的职责是**提醒人工项清单还没核对**，
  把清单再列一遍，让他明确回答每一项的结论——不是照着签核

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 批次状态文件 | `projects/<项目码>/.agent/state/<批次号>.yaml` | 是 | 编码阶段各步骤已 `done` |
| 项目代码仓 | `projects/<项目码>/.agent/project.yaml` 的 `repo` | 是 | 执行器据此读 git log 与扫描密钥 |
| gate-04 定义 | 知识库根下 `07_质量门禁/gates/gate-04-代码评审.md` | 是 | 可解析 |
| 契约哈希记录 | 批次状态文件 | 是 | 用于确认实现基于冻结契约 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 门禁结果 | 批次状态文件 `gates[]` | 由 `ai-gate-runner` 写入 |
| 评审记录 | 项目文档仓 `<需求名>/03_实现/评审记录.md` | 评审结论、参与人、未通过项与处置 |

## 前置条件

**hard（不满足则拒绝执行）**

- `projects/<项目码>/.agent/project.yaml` 的 `repo` **已填真实路径且该路径存在**
  （未填则拒绝——**没填的话密钥扫描与提交检查都会记 `skip`，等于这两项没查**）
- 批次状态文件存在
- gate-04 定义存在且可解析
- `ai-gate-runner` 已实现

**soft（不满足则提示，可继续）**

- gate-03 已通过、契约处于冻结态（未过时门禁照常执行，报告顶部标注「未经上游确认」）
- 编码阶段各步骤（scaffold / backend / frontend / unittest）已 `done`
  （未 done 时照常执行，未通过项本身就是结论；报告标注"未经上游确认"）

## 执行步骤

1. **调用 `ai-gate-runner` 执行 gate-04**（说"跑 gate-04"即可）——本 Skill 不自己做检查项判断
2. **逐条读出执行器输出**，不要总结成"评审已完成"：

   | 输出 | 你该做什么 |
   |---|---|
   | `✅ pass` | 无需处理 |
   | `❌ fail` | **原样读出明细**——执行器已给出提交哈希或文件行号，直接转达 |
   | `⏭️ skip` | 连同"要做什么才能自动校验"一起读出。**`skip` 不是通过** |
   | 人工核对清单 | 原样列出，**不替用户判断** |

3. `failed` → 输出未通过项与定位，**停止**
4. `pending_manual` → 请人核对后签核（把执行器给出的核对清单原样转达给用户）
5. 通过后写评审记录，回写批次状态文件

### 本门禁的两类重点

**自动项（执行器负责）**

| 检查项 | 级别 | 抓什么 |
|---|---|---|
| `commit-format` | BLOCK | 提交格式与 FN 关联——追溯链的最后一环 |
| `secrets-externalized` | BLOCK | 硬编码凭据——进 Git 历史后只能轮换密钥 |
| `fn-has-commit` | WARN | 哪些 FN 没有提交 |
| `lint-passthrough` | BLOCK | **external**：需在项目仓执行 lint。不是"查不了"，是"不归执行器查"——签核时必须用 `--evidence` 说明 lint 结果记在哪 |
| `unit-coverage-report` | WARN | **external**：需项目侧覆盖率报告。签核时用 `--evidence` 说明报告在哪、结论是什么 |

**人工项（本门禁价值最高、也最容易被跳过）**

- **契约一致性**：实际实现的接口签名与冻结契约是否一致。执行器只能校验契约文件自身，
  实现是否遵循契约需要读代码——**这一项是"联调时才发现对不上"的唯一前置拦截点**
- 无 N+1 查询、无循环内远程调用
- 涉及核心数据写入的改动是否走了统一入口（按领域包条目判断）
- 事务内是否发起远程调用（`STD-BASE-402`）
- 异常是否被吞掉（`STD-BASE-403`）

**自动项全绿不代表可以签核。** 自动项只有 5 项，人工项也有 5 项；
如果连契约一致性这一项也跳过，那道门禁就形同虚设。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——指定一个批次就能跑
- soft 不满足时照常执行，并在报告顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（未接入批次）时：报告落到指定路径、跳过状态回写并在报告中说明

## 边界（明确不做）

- **不做检查项判断。** 自动项交给执行器；人工项交给人
- **不放宽检查项。** 不因为"赶进度"就跳过某项
- **不代替人判断人工检查项**，特别是契约一致性那一项
- 不修复代码（发现问题回到 `ai-dev-02-backend` / `03-frontend`）
- 不豁免。豁免由人显式提供批准人与复查日期
- **不要把 `skip` 说成通过**
- 不为让门禁通过而改门禁定义、改状态文件、改提交历史以掩盖问题
- 不建议用 `--no-verify` 绕过 commit hook，不建议把校验从门禁定义里删掉
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 门禁 `failed` | 停止，输出未通过项与定位；**不尝试绕过** |
| `repo` 未填或路径不存在 | 拒绝执行，提示补 manifest 的 `repo` 字段 |
| 提交信息不合规 | 停止；**不要用 `--no-verify` 之类绕过 hook**，改提交信息后重跑 |
| 密钥告警（`secrets-externalized`，BLOCK） | 报出具体文件与行号；值改占位符或配置中心引用。**该值已提交进历史就已泄露**——必须轮换密钥，改当前版本没用（Git 历史、fork、本地副本都还留着）。明确告知这一点，不要说成"改掉就好了" |
| 契约一致性人工项不通过 | 停止，说明需要走变更子批次或改实现 |
| 执行器报"引用了未实现的检查项" | 报错停止，修门禁定义或补实现 |
| 用户说"自动化都过了，直接签核吧" | 提醒他人工项清单还没核对，把清单重新列一遍，请他明确回答每一项的结论；不照此签核 |
