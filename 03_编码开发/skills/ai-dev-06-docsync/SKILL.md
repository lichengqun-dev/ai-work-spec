# ai-dev-06-docsync · 文档回流

## 能力声明

代码变更后，把变更**回流到设计文档**，使文档与实现保持一致。

**这道工序不能省。** 文档一旦被发现不可信，就再也没人会读它——而没人读的文档等于不存在，
还要额外承担维护成本。绝大多数知识库都死在这里：文档只在开始时写一次，之后代码改了文档没改。

**不做什么**：不改设计决策、不通过改文档"对齐"有问题的实现、不因契约或表结构变化而改文档、
不为未实现的代码预先写文档——见「边界」。

## 何时用 / 何时不用

- **用**：本批次有代码变更、且变更可能影响文档描述的行为时；`ai-dev-05-codereview` 之前或之后都可以
- **不用**：代码没变；或变更已被判定为不影响行为（纯重构、格式化、行为不变的性能优化）
- **发现是契约或表结构变了**：停下，走变更子批次——文档同步解决不了

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 变更范围 | 用户提供，或从 `code_repo` 的提交范围**只读**读取 | 是 | 相对上次同步点 |
| 相关设计文档 | 项目文档仓 `<需求名>/02_设计/` | 是 | 功能详细设计 / 数据库设计 / 接口契约 |
| 批次状态文件 | `projects/<项目码>/.agent/state/<批次号>.yaml` | 是 | 记录本批次的 `artifacts` 与哈希 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 文档更新 | 项目文档仓 | 就地更新受影响的章节 |
| 同步说明 | 项目文档仓 `<需求名>/03_实现/文档同步说明.md` | 改了哪些章节、为什么 |
| 更新后的哈希 | 批次状态文件 `artifacts` | **必须同步更新** |

同步说明的结构：

```markdown
# 文档同步说明

同步点：<上次同步的提交> → <本次提交>

| 变更 | 影响行为 | 更新的文档章节 |
|---|---|---|
| 导出改为异步任务 | 是 | 功能详细设计 §FR-CORE-045 |
| 提取导出工具类 | 否 | — |

契约 / 表结构变更：无
```

## 前置条件

**hard（不满足则拒绝执行）**

- **能确定变更范围**：`code_repo` 可读（只读 git 历史，**不做任何 git 变更操作**），
  或由用户直接给出变更清单。**两者都不可用时拒绝**——不知道变了什么就无从回流
- 本批次有代码变更（无变更则无事可做）
- 相关设计文档存在（项目文档仓 `<需求名>/02_设计/`）

**soft（不满足则提示，可继续）**

- 受影响的文档已在 `artifacts` 中登记（未登记说明上游步骤没做完）：照常更新文档，
  但哈希回写会缺失，在同步说明中标注「未经上游确认 —— 文档未在 artifacts 中登记」

## 执行步骤

1. 取代码变更（相对上次同步点的 diff）
2. 判断每处变更**是否影响文档描述的行为**：
   - 影响 → 找到对应文档章节，就地更新
   - 不影响（纯重构、格式调整、性能优化且行为不变）→ 不改文档
3. **区分三类变更**（决定改什么）：

   | 变更性质 | 处理 |
   |---|---|
   | 实现细节变了，行为没变 | 不改文档 |
   | 行为变了（含异常处理、边界） | 更新功能详细设计对应章节 |
   | 契约或表结构变了 | **停止** —— 这需要走变更子批次，不是文档同步能解决的 |

4. 更新受影响的文档哈希到批次状态文件——**这一步不能忘**，顺序是：
   文档改完 → 重新计算文件哈希 → 更新
   `projects/<项目码>/.agent/state/<批次号>.yaml` 的对应条目。
   忘了它，gate-06 的 `artifacts-exist` 会报"产出物被外部修改"——而那个告警是对的，
   它是在说"文档变了但没人登记"
5. 产出同步说明（见「产出契约」的结构）

### 变更范围从哪里来

两种来源，任选其一：

1. **只读 git 历史**（`git -C <code_repo> log` / `diff`）——读历史不算变更操作，
   `STD-BASE-005` 禁止的是 commit / push / rebase / reset / 删分支
2. **用户直接给出变更清单**（改了哪些文件、做了什么）

两者都不可用时**停下**。不要因为"我没有 git 权限"就凭印象改文档——那会把文档改成你记忆里的样子，
而不是代码实际的样子，**比不改更糟**。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——给一段提交范围或一份变更清单就能跑
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（未接入批次）时：产出物落到指定路径、跳过状态回写并在报告中说明

## 边界（明确不做）

- **不改设计决策。** 文档同步是"让文档跟上实现"，不是"让设计迎合实现"。
  发现实现偏离了设计 → 报告并停止
- **不因契约或表结构变化而修改文档** —— 那属于变更子批次的范畴，必须走正式流程
- **不通过改文档来"对齐"有问题的实现** —— 那是把缺陷洗成设计
- 不重写文档（只改受影响章节，不做"顺便优化措辞"）
- 不为未实现的代码预先写文档
- 不忘记更新哈希
- 不凭印象改文档（拿不到变更范围时停下，不照记忆写）
- 不执行 git 变更操作（只读历史可以）

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 实现偏离了设计（不是设计过时，是实现错了） | **停止并报告**，不通过改文档"对齐"——那会把缺陷洗成设计 |
| 检测到契约或表结构变化 | 停止，说明需开变更子批次 |
| 变更影响面判断不了 | 报告并询问，**不猜** |
| 文档未在 `artifacts` 中登记 | 提示先补上游步骤；文档照常更新，同步说明中标注哈希未能回写 |
