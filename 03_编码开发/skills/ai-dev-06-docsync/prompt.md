# 指令：代码变更回流文档

## 这件事为什么不能省

知识库死掉的方式几乎总是同一个：**文档只在开始时写一次，之后代码改了文档没改。**

两周后，有人照着文档做，发现跟实际不符；再两周后，没人再看文档。
于是维护文档的成本还在，价值已经归零。

**这道工序就是防止这件事。** 它很枯燥，但它是知识库"可信"的唯一保证。

## 开始前：先拿到变更范围

两种来源，任选其一：

1. **只读 git 历史**（`git -C <code_repo> log` / `diff`）——读历史不算变更操作，
   `STD-BASE-005` 禁止的是 commit / push / rebase / reset / 删分支
2. **用户直接给出变更清单**（改了哪些文件、做了什么）

**两者都不可用时停下**——不知道变了什么就无从回流。

不要因为"我没有 git 权限"就凭印象改文档——那会把文档改成你记忆里的样子，
而不是代码实际的样子，比不改更糟。

## 判断变更是否影响文档

对每处代码变更问一句：**行为变了吗？**

| 变更性质 | 例子 | 改文档吗 |
|---|---|---|
| 纯重构 | 提取方法、重命名变量、调整类结构 | ❌ 不改 |
| 格式/风格 | 格式化、import 顺序 | ❌ 不改 |
| 性能优化（行为不变） | 加缓存但结果一致 | ❌ 不改 |
| **行为变了** | 异常处理方式改了、边界条件改了、新增了分支 | ✅ 更新功能详细设计对应章节 |
| **契约变了** | 新增/修改接口字段 | ⛔ **停止** |
| **表结构变了** | 加列、改类型 | ⛔ **停止** |

## 契约与表结构变更必须停下

这两种变更的影响面超出本项目：

| 变更 | 谁受影响 |
|---|---|
| 契约变更 | 前端、测试脚本、外部调用方 |
| 表结构变更 | 数据迁移、回滚方案、历史数据兼容 |

**文档同步是单向的"代码 → 文档"回流。** 契约与表结构变更需要的是
"多方确认 → 变更 → 全员同步"，走变更子批次（`<原批次号>-C<n>`）。

把后者塞进文档同步，等于绕过了变更流程——而绕过的那一次，恰恰是前端已经按旧契约写完代码的那一次。

发现这类变更时：停止，明确告知用户需要开变更子批次并通知前后端负责人。

## 最重要的红线：不要让文档迎合实现

有一种情况必须区分清楚：

| 情况 | 特征 | 处理 |
|---|---|---|
| 设计过时了 | 设计写的是旧做法，实现按新共识走了 | ✅ 更新文档 |
| **实现偏离了设计** | 设计是对的，实现做错了 | ⛔ **停止并报告** |

第二种情况下改文档，等于**把缺陷洗成了设计**——它从此消失，再也没人会发现。
而且下一次有人照着"更新后"的文档做，会重复同一个错误。

判断不了时**问用户**：这个改动是有意为之，还是实现走偏了？

## 只改受影响的章节

不要"顺便优化措辞"。文档同步的 diff 应该能一眼看出"哪些行为变了"——
如果 diff 里混着大量措辞调整，评审者无法判断这次同步到底改了什么实质内容。

## 必须同步更新哈希

更新完文档后，把新的哈希写回批次状态文件的 `artifacts`。

**这一步不能忘。** 步骤：
1. 文档改完
2. 重新计算文件哈希
3. 更新 `.ai/state/<批次号>.yaml` 的对应条目

忘了这一步，gate-06 的 `artifacts-exist` 会报"产出物被外部修改"——而那个告警是对的，
它是在说"文档变了但没人登记"。

## 完成后

产出 `docs/03_实现/文档同步说明.md`：

```markdown
# 文档同步说明

同步点：<上次同步的提交> → <本次提交>

| 变更 | 影响行为 | 更新的文档章节 |
|---|---|---|
| 导出改为异步任务 | 是 | 功能详细设计 §FN-CORE-045 |
| 提取导出工具类 | 否 | — |

契约 / 表结构变更：无
```

## 你绝对不要做的事

- **不要通过改文档来"对齐"有问题的实现** —— 那是把缺陷洗成设计
- 不要因为契约或表结构变了就改设计文档 —— 那需要走变更子批次
- 不要重写文档、不要"顺便优化措辞"
- 不要忘记更新哈希
- 不要执行 git 操作
