# 指令：前端实现与联调

## 开始前

确认契约已冻结且哈希一致。读前端设计（页面清单、组件拆分、状态流转、接口映射）与原型工程。

## 迁移，不要重画

原型是**业务方已经确认过的形态**。你的工作是把它落成工程实现，不是重新设计一遍界面。

```
原型页面（带 data-fn 标记）
  → 按前端设计的组件拆分重组
  → 接入契约中的接口
  → 补异常态与空态
```

**从原型迁移时保留布局骨架与交互模式。** 迁移动机是"让它工程化"，不是"让它更好看"。

## 组件复用是第二次机会

`ai-requirement-03-prototype` 阶段已经做过一次"先匹配已有组件"，这里是第二次——
那次是概念层面，这次要落到具体组件。

查 `09_资产库/组件库/前端组件清单.md`。**新组件要写明拆出的理由**，
否则很容易出现"同一个表格在五个页面各写了一遍，每一遍处理方式都稍有不同"。

## 状态归属：最容易出错的地方

前端设计里已经标注了每个状态的归属，照着做。判据回顾：

| 状态类型 | 归属 | 为什么 |
|---|---|---|
| 接口返回的数据 | 请求层（hook / service） | 它是服务端状态，有"一份还是多份"的问题 |
| 跨页面共享的 UI 状态 | 全局 store | 多个页面读同一份 |
| 单页面 UI 开关、tab、表单草稿 | 组件本地 | 离开页面就该丢 |

**不要顺手把接口数据放进全局 store。** 放进去了之后，缓存失效、竞态、重复请求全要手工处理，
而且容易出现"两个页面看到同一份过期数据"——这类问题在测试阶段极难复现。

技术栈相关的状态管理写法（Pinia / Vuex / 自建 hook）从生效快照读。

## 异常态与空态必须实现

前端设计里列了每个页面的三种态，照着做：

| 态 | 常见做法 |
|---|---|
| 无数据 | 空状态提示 vs 空表格（按设计定） |
| 无权限 | 隐藏入口 vs 显示 403（按设计定） |
| 加载失败 | 重试按钮 + 错误提示 |

**不要三个页面三种做法。** 异常态在实现阶段随手写的结果，通常是每个页面各写一套。

## 技术细节从快照读

你的 prompt 里没有框架写法，这是刻意的：

| 你要做的事 | 该读的条目 |
|---|---|
| 写组件 | `STD-VUE3-*` / `STD-REACT-*` 的组件写法条目 |
| 发请求 | `STD-BASE-412` + 对应前端包的请求封装条目 |
| 写文案 | `STD-VUE3-004`（国际化）或 `STD-BASE-413` |
| 写表单 | 对应前端包的校验条目 |

**快照没覆盖的细节，停下来问。**

## 提交：按页面，但带 FN 编号

后端按 FN 交付，前端**按页面交付更自然**——一个页面对应多个 FN 是常态。

但 `commit-format` 是 BLOCK 级检查项，提交信息必须含 FN 编号。一个提交覆盖多个 FN 时列全：

```
feat(FN-CORE-045): 列表页导出入口与结果展示

覆盖 FN-CORE-045（导出入口）、FN-CORE-046（结果下载）
```

## 完成后

回写批次状态文件：本步骤置 `done`，记录本次实现的页面与 FN 清单。

## 你绝对不要做的事

- **不要改契约**（联调发现不够用 → 停下说明）
- 不要重画原型（保留已确认的布局骨架与交互）
- 不要修改原型工程
- 不要把服务端状态塞进全局 store
- 不要自行决定快照未覆盖的组件用法
- 不要执行 git 操作
