# 提交信息与分支规范

## STD-BASE-001 · 分支模型

<!-- meta
tier: indexed
scope: 分支创建与合并
frozen: false
-->

**规则**：长期分支为 `main`（生产就绪，仅从 `release-*` 合并）与 `develop`（日常集成）；短期分支按类型命名：`feat/` `fix/` `perf/` `refactor/` `test/` `docs/` + 简短描述。

**正例**：`feat/FN-CORE-045-export`

**反例**：分支名用 `dev1`、`temp`、`zhangsan` 这类无信息量的名字

**原因**：分支名是变更意图的第一手信息，评审者靠它判断改动范围与风险等级。

---

## STD-BASE-002 · 提交信息格式

<!-- meta
tier: resident
scope: 提交信息
frozen: false
-->

**规则**：提交信息格式为 `<type>(<scope>): <subject>`。`type` 取固定集合：`feat` / `fix` / `perf` / `refactor` / `test` / `docs` / `chore` / `style`，不得自造。

**正例**：`feat(FN-CORE-045): 列表页新增导出能力`

**反例**：`update`、`fix bug`、`修改`、`提交`

**原因**：`type` 决定变更性质，能直接用于生成发布说明；`scope` 决定影响面，能用于圈定回归范围。随意填写的提交信息让这两件事都无法自动化。

---

## STD-BASE-003 · 提交信息必须关联功能编号

<!-- meta
tier: resident
scope: 提交信息
frozen: false
-->

**规则**：涉及功能开发的提交，subject 或 body 中必须包含功能编号（`FN-<模块码>-<3位>`）。

**正例**：`feat(FN-CORE-045): 列表页新增导出能力`

**反例**：`feat(core-service): 新增导出功能` —— 无法回答「这个功能来自哪条需求、覆盖了哪些用例」

**原因**：这是整条追溯链的**最后一环**。缺了它，`FN → 提交` 断裂，无法回答「这个功能是什么时候、由哪次提交上线的」，也无法做「没有对应提交的 FN」这类断链检测。执行方式为 commit hook 校验。

---

## STD-BASE-004 · 禁止直接向长期分支提交

<!-- meta
tier: indexed
scope: 分支操作
frozen: false
-->

**规则**：`main` / `develop` 只接受合并，不接受直接提交；`main` 仅从 `release-*` 合并。

**正例**：功能分支完成后提 PR 合并到 `develop`

**反例**：本地切到 `develop` 后直接 commit 并 push

**原因**：直接提交绕过评审，且无法通过 revert 单个提交来撤销——一次直接提交会污染所有人的基线。

---

## STD-BASE-005 · AI 不得执行未经明确要求的 git 操作

<!-- meta
tier: resident
scope: AI 协作约定
frozen: true
-->

**规则**：AI 助手不得执行任何 git 变更操作（commit / push / rebase / reset / 分支删除等），除非用户在当次对话中明确要求。

**正例**：完成代码修改后告知用户「改动已完成，未提交」

**反例**：改完代码后自动 commit，或为「清理」执行 `git reset --hard`

**原因**：git 是唯一无法通过代码评审拦截的操作层。一次误执行的 `reset --hard` 可能丢失数小时工作。

**例外**：无。
