# 安全基线

> **层级：L0 团队基线**（前缀 `STD-BASE-`）。所有项目无差别适用。
> 平台特有的安全约束（网关鉴权、数据权限模型等）属于**领域包**，放在 `09_资产库/规范包/domains/` 下，
> 不写进基线。

## STD-BASE-101 · 禁止拼接 SQL 字符串

<!-- meta
tier: resident
scope: 持久层与查询
frozen: false
-->

**规则**：SQL 一律使用参数化查询。**禁止任何形式的字符串拼接构造 SQL**，包括 `String.format`、`+` 拼接、`StringBuilder`。动态排序字段必须走白名单校验。

**正例**：
```xml
<select id="query">SELECT * FROM t WHERE name = #{name}</select>
```

**反例**：
```java
String sql = "SELECT * FROM t WHERE name = '" + name + "'";
String order = "ORDER BY " + orderField;   // 未白名单校验 = 注入口
```

**原因**：字符串拼接是 SQL 注入的直接入口。动态排序是其中最容易被忽略的一处——参数化无法覆盖 `ORDER BY`，只能白名单。

## STD-BASE-102 · 敏感信息禁止进入日志

<!-- meta
tier: resident
scope: 日志
frozen: false
-->

**规则**：日志中禁止打印密码、Token、密钥、身份证号、手机号及其他个人敏感信息。打印对象时确认其 `toString` 不包含敏感字段。

**正例**：打印 `userId`、`projectId` 等标识类字段。

**反例**：`log.info("login req: {}", request)` —— `request` 的 `toString` 里带密码。

**原因**：日志的访问面远大于数据库（运维、日志平台、第三方采集）。一次误打印的 Token 等同于凭据泄露，且日志通常长期留存。

**常见踩坑点**：打日志时顺手 `toString()` 整个请求对象；把 `@Data` 对象的 `toString` 直接输出而未排除密码字段。

## STD-BASE-103 · 密码使用 BCrypt 存储

<!-- meta
tier: indexed
scope: 认证与凭据
frozen: false
-->

**规则**：用户密码使用 BCrypt 加密存储，不使用 MD5 / SHA1 / 明文 / 可逆加密。

**正例**：`BCryptPasswordEncoder.matches(raw, encoded)`

**反例**：`DigestUtils.md5Hex(password)`；自实现加盐哈希。

**原因**：MD5 / SHA1 对现代算力已不构成障碍，且无内置盐值，彩虹表可直接命中。BCrypt 自带盐与计算成本参数。

## STD-BASE-104 · 密钥与密码不得进入代码仓库

<!-- meta
tier: resident
scope: 配置与凭据
frozen: false
-->

**规则**：任何密码、密钥、Token 不得写入代码或仓库内的配置文件，必须外置到配置中心。**历史提交中残留的真实密钥视为已泄露，必须轮换。**

**正例**：配置文件中只写占位符与配置中心地址。

**反例**：把数据库密码写在 `application-dev.yml` 里提交。

**原因**：密钥一旦进入 Git 历史，删除当前版本无效——历史提交、fork、本地副本都还留着。唯一补救是轮换。

**AI 协作提醒**：生成配置文件时默认使用占位符，不要为了"能跑起来"填入看起来合理的示例密码——示例密码常被直接沿用。

**对应检查项**：gate-04 的 `secrets-externalized`（BLOCK）。扫描口径是窄的（宁可漏报不误报），通过不等于真的没有硬编码凭据。

## STD-BASE-105 · 入参必须校验

<!-- meta
tier: indexed
scope: 接口入参
frozen: false
-->

**规则**：Controller 入参使用 `@Validated` + JSR-303 注解校验；数字限制范围（`@Min` / `@Max`），字符串限制长度（`@Size`），格式限制用 `@Pattern`。

**正例**：`@Size(max = 64) @Pattern(regexp = "^[a-zA-Z0-9_-]+$") String code`

**反例**：只在 Service 里手写 `if (code == null) throw ...`，且漏掉了长度与格式。

**原因**：手写校验容易遗漏边界（长度、格式、范围），而注解校验是声明式且可被统一审计的。

**命名空间提醒**：Spring Boot 2.6 用 `javax.validation`，Spring Boot 3 用 `jakarta.validation`。写错会编译失败，具体以生效快照中的技术栈包为准。

## STD-BASE-106 · 文件上传限制大小与类型

<!-- meta
tier: indexed
scope: 文件处理
frozen: false
-->

**规则**：文件上传接口必须限制文件大小上限与允许的类型白名单（按扩展名 + MIME 双重校验），不信任前端传入的类型。

**正例**：白名单 `xlsx` / `xls` / `pdf`，大小 ≤ 20MB。

**反例**：只判断扩展名，或完全不限制。

**原因**：无限制的上传是磁盘打满与恶意文件上传的直接入口。仅判扩展名可被改名绕过，因此需要 MIME 双重校验。
