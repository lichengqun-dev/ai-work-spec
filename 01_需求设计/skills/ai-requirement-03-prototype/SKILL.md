# 能力声明

依据需求功能分析产出**原型规划**与**可运行的原型工程**，页面上每个可交互元素带功能编号标记。

原型是 PRD 的**事实源**——PRD 是原型的文字化，不是原型是 PRD 的配图。这个顺序反过来，能消除大量"文档说 A、原型是 B"的扯皮。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 需求功能分析 | `ai-requirement-02-analysis` 产出 | 是 | 每个功能有 `FN` 编号 |
| 批次上下文（L3 CLAUDE.md） | 文档仓 | 是 | 存在 |
| 前端技术栈包 | `.ai/spec-effective/<项目码>.md` | 是 | 用于确认目标技术栈与组件约定 |
| 原型工程仓 | `ai-requirement-01-init` 产出 | 是 | 存在且可运行 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 原型规划 | 文档仓 `docs/01_需求/原型规划.md` | 页面清单 + `PAGE` 编号 + 页面与 FN 的映射 |
| 原型工程页面 | 原型工程仓 | 每个可交互元素带 `data-fn="FN-XXX-000"` |
| 原型与功能映射表 | 文档仓 `docs/01_需求/原型与功能映射.md` | `PAGE` → `FN` 对照 |

## 执行步骤

1. 读需求功能分析，规划页面清单，申请 `PAGE` 编号
2. **先匹配已有组件**：查 `09_资产库/组件库/前端组件清单.md`，能复用的优先复用
3. 再迁移、后调整：基于已有页面的结构改造，优于从零画
4. 完整性检查：每个 `FN` 是否都有页面承载；每个页面是否有明确的 `FN` 归属
5. 生成原型代码，**为每个可交互元素加 `data-fn` 标记**
6. 一致性检查：原型上的字段与需求功能分析是否一致
7. 每批次使用**独立的原型副本**，不覆盖历史批次的原型

## 边界（明确不做）

- 不做视觉设计（配色、图标、精细排版）——原型验证的是**信息结构与交互路径**，不是美术
- 不写业务逻辑（原型用静态数据即可）
- 不产出 PRD（那是 04 的职责）
- 不修改需求功能分析（发现的矛盾记入问题汇总，由人在别处解决）

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 某 FN 无法映射到页面 | 记录到问题汇总，不强行造页面 |
| 原型工程无法启动 | 报告错误但保留已生成代码，由人排查环境问题 |
| 目标技术栈不明确 | 提示先运行 `ai-spec-build`；**不要自行选一个技术栈** |
