# 指令：原型规划与产出

## 执行顺序（顺序很重要）

**先匹配 → 再迁移 → 后调整 → 完整性检查 → 验证修复**

### 1. 先匹配

查 `09_资产库/组件库/前端组件清单.md`，看已有组件能否覆盖需求。

**不要一上来就画新页面。** 项目里大概率已经有 80% 相似的页面或组件——复用它们能让原型与最终实现更接近，也更容易被业务方确认（"哦，跟那个页面一样"比看新设计更容易理解）。

### 2. 再迁移

基于最接近的已有页面改造，而不是从零构造。迁移时保留原有的布局骨架与交互模式。

### 3. 后调整

按需求功能分析调整字段、交互、流程。

### 4. 完整性检查

- 每个 `FN` 是否都有页面承载？
- 每个页面是否有明确的 `FN` 归属？
- 字段与需求功能分析是否一致？

不满足的项**记入问题汇总**，不要强行造页面凑数。

### 5. 验证修复

启动原型工程确认能跑通。主流程要能完整走完。

## 关键要求：`data-fn` 标记

**每个可交互元素必须带 `data-fn="FN-XXX-000"` 标记。**

```html
<button data-fn="FN-CORE-045" class="btn-primary">导出</button>
```

这不是给浏览器看的，是给 `ai-requirement-04-prd` 看的——PRD 靠遍历这些标记来生成功能章节。**没有标记，PRD 就生成不出来，整个"读原型生成 PRD"的机制失效。**

## 每批次独立副本

不要覆盖历史批次的原型。每批次用独立的目录。

理由：历史批次的原型是"当时业务方确认过的东西"。被覆盖后，出了争议就没有依据可查。

## 边界

原型的目的是验证**信息结构与交互路径**，不是美术：

- 不做精细视觉（配色、图标、动效）
- 不写业务逻辑（静态数据即可）
- 不做响应式适配（除非需求明确要求）

**在这些上面花时间是浪费**——它们一定会被真正的实现替换掉，而且会拖慢"业务方确认"这个核心目标的达成。

## 完成后

回写状态文件：`prototype` 步骤置 `done`，登记 `原型规划.md`、原型工程路径、`PAGE` 编号。

## 你绝对不要做的事

- 不要自行选择前端技术栈（从生效规范快照读）
- 不要因为"这样更好看"而偏离目标技术栈的组件体系
- 不要在原型里实现真实接口调用
- 不要执行 git 操作
