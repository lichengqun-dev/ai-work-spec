# ai-requirement-02-analysis · 原始需求结构化

## 能力声明

把原始需求（会议记录 / 工单 / 口头描述）**结构化为标准化的需求文档集**，并为每条需求与每个功能点
分配 `REQ` / `FN` 编号。

**不负责原型产出，不负责 PRD 撰写。** 这两件事属于 03 / 04。

## 何时用 / 何时不用

- **用**：用户提供了原始需求材料，要把它变成带编号的需求条目、功能清单与待澄清问题时
  （需求段的第二步，批次上下文已就位）
- **不用**：要画原型（`ai-requirement-03-prototype` / `ai-figma-axure-convert`）；
  要写 PRD（`ai-requirement-04-prd`）；要做技术方案（选型、数据模型、接口设计——下游域的事）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 原始需求材料 | 用户提供 / 项目文档仓 `inbox/` | 是 | 非空，含业务目标描述 |
| 批次上下文 | `ai-requirement-01-init` 产出（L3 CLAUDE.md） | 是 | 存在 |
| 业务场景清单 | 知识库根下 `01_需求设计/references/业务场景清单.md` | 是 | 存在（可为空骨架） |
| 需求分析规范范本 | 知识库根下 `01_需求设计/references/需求分析规范范本.md` | 是 | 存在 |
| 功能编号总表 | `projects/<项目码>/.agent/index/功能编号总表.md` | 是 | 存在，用于申请 `REQ` / `FN` 编号 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 原始需求格式化 | 文档仓 `<需求名>/01_需求/原始需求格式化.md` | 条目带 `REQ` 编号 |
| 需求功能分析 | 文档仓 `<需求名>/01_需求/需求功能分析.md` | 每个功能有 `FN` 编号，标注来源 `REQ` |

三份文档的产出结构：

```markdown
# 原始需求格式化
REQ-<模块码>-<三位>  <原始材料的原话>
（一个编号只对应一条需求）

# 需求功能分析
## 一、功能清单
| FN 编号 | 功能名称 | 来源 REQ | 优先级 | 备注 |
## 二、功能详情
### FN-XXX-001 <功能名称>
**来源**：REQ-XXX-001　**场景**：<场景名，归类不了填"场景待定"并记入问题汇总>
**前提** / **主流程** / **异常流程** / **边界条件** / **验收要点**

# 需求问题汇总
Q-001 <问题>
      影响：<影响哪些决策、哪些产出物>
      需要回答：<谁>
```

## 前置条件

**hard（不满足则拒绝执行）**

- 批次状态文件 `current_step` 为 `analysis`

**soft（不满足则提示，可继续）**

- gate-01 需求准入尚未通过 / 尚未运行：照常产出，产出物标注「未经上游确认 —— gate-01 未通过」。
  但**不要在需求目标不明的情况下硬做结构化**——信息不足时按「失败处理」停在中途、输出待澄清清单
- 批次上下文（L3 CLAUDE.md）缺失：提示先执行 `ai-requirement-01-init`，
  照常产出并在产出物顶部标注「未经上游确认 —— 批次上下文缺失」
- 目标产出文件已存在 → 走**续做分支**：只补缺失内容，**不覆盖**
- 业务场景清单仍是空骨架 → 照常产出，场景一律填"场景待定"并记入问题汇总，
  **不要硬塞进最接近的场景**

## 执行步骤

1. 读三个东西：原始需求材料、批次上下文（L3 CLAUDE.md）、知识库根下
   `01_需求设计/references/需求分析规范范本.md`。需要判断业务场景时，再读知识库根下
   `01_需求设计/references/业务场景清单.md`（**不要默认读它**）
2. 读原始需求材料，逐条提取需求条目，**向总表申请 `REQ` 编号**
3. 对照业务场景清单归类，识别前提、主流程、异常流程、边界
4. 推导功能清单，**申请 `FN` 编号**，逐条标注来源 `REQ`
5. 无法确定的信息 → 记入待澄清清单，**不臆造**
6. 校验产出完整性（FN 是否都有来源、编号是否都已登记）
7. 回写状态文件：`analysis` 步骤置 `done`，`artifacts` 段登记三份产出物及其哈希，
   `pending_questions` 段登记待澄清问题

### 三份文档怎么写

**一、原始需求格式化.md**：把非结构化的原始材料（会议记录、工单、口头描述）转成条目，
逐条分配 `REQ-<模块码>-<三位>` 编号，向 `projects/<项目码>/.agent/index/功能编号总表.md` 申请。

**一个编号只对应一条需求。** 不要把"导出相关需求"下面再列三条——那样三条都无法被单独追踪。
保留原始材料的原话，不要在这一步就"优化表述"：原话是后续争议时的依据。

**二、需求功能分析.md**：每个功能点分配 `FN-<模块码>-<三位>`，并**标注来源 `REQ`**。
对每个功能点写清四件事：

| 项 | 要求 |
|---|---|
| 前提 | 什么状态下这个功能才可用 |
| 主流程 | 正常路径的步骤 |
| 异常流程 | 失败、无权限、状态冲突时怎么办 |
| 边界 | 数据量上限、时间范围、并发等边界条件 |

**异常流程与边界写不出来时，说明需求信息不足——记入待澄清，不要编。**

**三、需求问题汇总.md**：每条问题写清编号、问题、影响什么、需要谁回答。

```
Q-001 导出是否包含已归档数据？
      影响：数据量估算、权限判断、性能验收标准
      需要回答：业务方
```

### 编号纪律

- **不得自行生成编号。** 一律向 `projects/<项目码>/.agent/index/功能编号总表.md` 申请，并回写该表
- 编号冲突时**报错退出**，不要自动重新编号——自动重编会让已经写在别处的引用失效
- 删除的需求条目保留编号并标记 `[已废弃]`，不回收

### 这一阶段最重要的一条纪律

**信息不足时停下，不要臆造。** 停下与臆造的代价对比见 `references/需求分析要点.md`。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始（补一条需求、重出一份功能清单都成立）
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：三份文档落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- 不生成原型、不撰写 PRD
- 不做技术方案设计（不选技术栈、不定数据模型、不写接口设计）
- **不在需求功能分析里写实现方式**
- 不修改已归档的历史批次文档
- 不评估工作量
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 原始需求信息量不足以识别功能 | **停在中途**，输出待澄清清单，等待人工补充 |
| 功能编号冲突 | 报错退出，**不自动重新编号** |
| 业务场景无法归类 | 标为"场景待定"，记入问题汇总（不要硬塞进最近的场景） |
| 批次上下文缺失 | 提示先执行 `ai-requirement-01-init` |
