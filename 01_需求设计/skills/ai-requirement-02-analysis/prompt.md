# 指令：原始需求结构化

## 开始前

读三个东西：原始需求材料、批次上下文（L3 CLAUDE.md）、`references/需求分析规范范本.md`。
需要判断业务场景时再读 `references/业务场景清单.md`（**不要默认读它**）。

## 产出三份文档

### 一、原始需求格式化.md

把非结构化的原始材料（会议记录、工单、口头描述）转成条目。**逐条分配 `REQ-<模块码>-<三位>` 编号，向 `projects/<项目码>/.agent/index/功能编号总表.md` 申请。**

**一个编号只对应一条需求。** 不要把"导出相关需求"下面再列三条——那样三条都无法被单独追踪。

保留原始材料的原话，不要在这一步就"优化表述"。原话是后续争议时的依据。

### 二、需求功能分析.md

每个功能点分配 `FN-<模块码>-<三位>`，并**标注来源 `REQ`**。

对每个功能点写清四件事：

| 项 | 要求 |
|---|---|
| 前提 | 什么状态下这个功能才可用 |
| 主流程 | 正常路径的步骤 |
| 异常流程 | 失败、无权限、状态冲突时怎么办 |
| 边界 | 数据量上限、时间范围、并发等边界条件 |

**异常流程与边界写不出来时，说明需求信息不足——记入待澄清，不要编。**

### 三、需求问题汇总.md

每条问题写：编号、问题、影响什么、需要谁回答。

例：
```
Q-001 导出是否包含已归档数据？
      影响：数据量估算、权限判断、性能验收标准
      需要回答：业务方
```

## 这一阶段最重要的一条纪律

**信息不足时停下，不要臆造。**

你的默认倾向是补全合理猜测让产出看起来完整。在这个流水线里，这是最贵的错误，因为错误会逐级放大：

需求猜错 → 设计按错的做 → 代码按错的设计写 → 测试按错的设计编用例 → **全部通过** → 上线才发现。

停下来问，比跑完返工便宜一个数量级。

## 编号纪律

- **不得自行生成编号。** 一律向 `projects/<项目码>/.agent/index/功能编号总表.md` 申请，并回写该表。
- 编号冲突时**报错退出**，不要自动重新编号——自动重编会让已经写在别处的引用失效。
- 删除的需求条目保留编号并标记 `[已废弃]`，不回收。

## 完成后

回写批次状态文件：`analysis` 步骤置 `done`，`artifacts` 段登记三份产出物及其哈希，`pending_questions` 段登记待澄清问题。

## 你绝对不要做的事

- 不要生成原型或 PRD
- 不要做技术方案（选型、数据模型、接口设计）
- 不要在需求功能分析里写实现方式
- 不要执行 git 操作
