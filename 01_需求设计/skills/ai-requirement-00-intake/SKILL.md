# 能力声明

判定一个新进来的需求该走哪条流程（新建 / 续做 / 变更），并创建或恢复批次状态文件。

**不产出任何业务文档。** 它只做一件事：把"来了个需求"变成"有了一个批次，走哪条路"。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 需求描述 | 用户提供 | 是 | 非空；若过于模糊（无法判断项目归属）则进入澄清流程 |
| 项目码 | `projects/<项目码>/` | 是 | 目录存在，manifest 可解析 |
| 已有批次状态 | `.ai/state/*.yaml` | 否 | 存在同项目活跃批次时进入续做判定 |
| 生效规范快照 | `.ai/spec-effective/<项目码>.md` | 是 | 不存在则提示先运行 `ai-spec-build` |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 批次状态文件 | `.ai/state/<批次号>.yaml` | 按 `.ai/state/_模板.yaml` |
| 判定结论 | 输出给用户 | 路径类型 + 理由 + 下一步 |

## 前置条件（不满足则拒绝执行）

- `projects/<项目码>/project.yaml` 存在且可解析
- `.ai/spec-effective/<项目码>.md` 存在（规范快照未生成时拒绝，避免在无规范状态下开工）
- 需求描述可判断归属项目（判断不了则先澄清，不要猜）

## 执行步骤

1. 确认项目码；无法确认则向用户澄清，**不猜**
2. 扫描 `.ai/state/` 中该项目的历史批次
3. 按下表判定路径类型
4. 生成批次号 `<项目码大写>-<YYYYMMDD>-<三位序号>`
5. 写入批次状态文件（`steps` 填本路径要走的具体步骤）
6. 输出判定结论与理由

## 路径判定规则

| 条件 | 判定 | 理由 |
|---|---|---|
| 该项目无任何已归档批次 | **新建（new）** | 尚无基线，需走完整流程 |
| 存在 `status: in_progress` 的批次 | **续做（resume）** | 同一需求不应开两个批次 |
| 存在已归档批次，本次是改行为 | **变更（change）** | 开 `<原批次号>-C<n>` 子批次，原批次保持不可变 |
| 存在已归档批次，本次是加功能 | **新建（new）** | 新增功能是独立批次，不挂在历史批次下 |

**判定必须给出理由。** 判断错误的代价是追溯链挂错位置，事后很难发现。

## 边界（明确不做）

- 不产出需求分析、原型、PRD（那是 01/02/03/04 的职责）
- 不判定"这个需求值不值得做"——那是 gate-01 人工决策
- 不修改历史批次状态文件
- 不生成 `FN` / `REQ` 编号（编号在 02-analysis 阶段申请）

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 项目码无法确定 | 输出澄清问题，中止 |
| 需求描述不足以判断路径类型 | 输出澄清问题，中止（不默认按新建处理） |
| 规范快照不存在 | 提示先运行 `ai-spec-build --project <项目码>` |
| 批次号冲突 | 序号 +1 重试；连续冲突 3 次则报错退出 |
