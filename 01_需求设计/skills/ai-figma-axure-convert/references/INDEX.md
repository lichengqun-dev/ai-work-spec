# 知识索引 · ai-figma-axure-convert

> `references/` 默认**只加载本文件**。按下方「何时读取」按需读取，单次不超过 3 个文件、合计 1500 行。
> **本文件内的路径**：`references/` 开头的是本 Skill 内的资源；「知识库根下」开头的是 Skill 之外的资源。

| 知识 | 位置 | 何时读取 |
|---|---|---|
| 设计稿转换要点（不做像素级复刻 / 必须同构 / 不猜 `data-fr`） | `references/设计稿转换要点.md` | 动手前 |
| **格式基准** | 知识库根下 `01_需求设计/skills/ai-requirement-03-prototype/SKILL.md` 的产出契约 | **动手前必读** |
| 功能编号规则 | 知识库根下 `00_工作空间配置/命名与编号规范.md` | 申请 `PAGE` 编号时 |
| 功能编号总表 | `projects/<项目码>/.agent/index/功能编号总表.md` | `PAGE` 编号在这里登记 |
| 需求功能分析 | 项目文档仓 `<需求名>/01_需求/需求功能分析.md` | 补 `data-fr` 时 |
| 前端技术栈 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 生成原型代码前 |

## 为什么这里几乎没有格式知识

格式要求**全部来自格式基准**（`ai-requirement-03-prototype` 的产出契约）与需求功能分析。
把格式要求抄一份到这里，等于制造一个会与基准分叉的副本——而这个格式恰恰是
`ai-requirement-04-prd` 按它解析的，分叉的后果是 PRD 生成不出来。

## 什么时候该在本目录新增文件

出现**只有这个 Skill 用得上、且不适合留在 SKILL.md 里**的知识时，例如：

- **设计稿导出物的解析要点**（Figma JSON 的结构、Axure HTML 导出的特征、切图标注怎么读）
- 历次「设计稿与需求冲突」的处置记录——这类冲突的处理方式值得复用过
- 常见的设计稿元素到 `FR` 的映射模式（按钮 → 动作类 FR，列表 → 查询类 FR）

**第一类最实用**：设计稿导出格式的坑（图层命名混乱、组件实例展开不完整）
每个项目都要重新踩一遍，而它和业务无关，完全可以沉淀成通用知识。

**判据**：同域其他 Skill 会不会用到？会 → 放域级 `references/`（知识库根下 `01_需求设计/references/`），
不要在这里重复一份。共用知识在每个 Skill 下各存一份，是知识库腐化的典型起点——改一处忘另一处。
