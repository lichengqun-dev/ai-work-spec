# 指令：设计稿转原型

## 唯一的目标：信息结构与交互路径可验证

**不是像素级复刻。** 配色、圆角、阴影、动效的实现成本高，而且一定会被真实实现替换掉——
在原型阶段做它们是纯浪费。

判断标准只有一条：**业务方能否通过它确认「这就是我要的」**。

## 硬要求：与 `ai-requirement-03-prototype` 同构

这条比"好看"重要得多。`ai-requirement-04-prd` 靠遍历原型的 `data-fn` 标记生成 PRD——

```
04-prd 读原型 → 提取 data-fn → 逐个 FN 生成 PRD 章节
```

**两条路径（自画原型 / 外部设计稿）的产出必须格式一致**，否则 04-prd 只认其中一条。
所以动手前先读 `01_需求设计/skills/ai-requirement-03-prototype/SKILL.md` 的产出契约，
以它为格式基准。

产出后逐项自检：

| 项 | 要求 |
|---|---|
| 可运行 | 能启动、主流程能走通 |
| `data-fn` 标记 | 每个可交互元素带，取值是合法 `FN` 编号 |
| 目录结构 | 与 03-prototype 同构，不新造一套风格 |
| 页面清单 | 已在 `原型规划.md` 登记 `PAGE` 编号 |

**任一项不满足就报告**，不要说"先这样，反正能看"。格式不一致的后果是 PRD 生成不出来，
而那时已经过了原型确认这道门禁——返工要从头来。

## 补 `data-fn`：不能猜

设计稿里没有功能编号信息，要对照 `需求功能分析.md` 补齐。

```
设计稿元素                            → 需求功能分析
「导出」按钮                          → FN-CORE-045（列表页导出）
「筛选」下拉                          → FN-CORE-046（按分组筛选）
右上角「设置」图标                    → ❓ 需求功能分析里没有对应项
```

最后一类**列入「待人工确认」清单，不要猜**。

猜错的标记会让 04-prd 生成错误的功能章节，而错误会被下游一路放大：
需求错 → 设计错 → 代码错 → 测试按错的设计编用例且全部通过。

## 设计稿与需求冲突时，停下来

如果设计稿里出现了需求功能分析中没有的功能：

**停止并报告**，说清两种情况都有可能：

| 可能 | 该谁处理 |
|---|---|
| 需求分析漏了这一块 | 回 `ai-requirement-02-analysis` 补 |
| 设计稿画多了 / 画的是旧版本 | 找设计方确认 |

**不要自行取舍**。自行取舍的结果是原型里有一个"没人认领"的功能页，
而它会一路走到 PRD、设计、代码——直到有人问"这个功能谁提的"。

## 技术栈从快照读

不要自己选前端框架。从 `.ai/spec-effective/<项目码>.md` 读目标技术栈；
快照不存在就停下，提示先运行 `ai-spec-build`。

## 完成后

1. 回写批次状态文件：本步骤 `done`，登记原型工程路径、页面清单与哈希
2. 输出标记补齐说明（含待人工确认清单）

## 你绝对不要做的事

- 不要做像素级复刻（重点是结构与交互）
- 不要猜测 `data-fn` 归属
- 不要在设计稿与需求冲突时自行取舍
- 不要自行选择前端技术栈
- 不要修改 `ai-requirement-03-prototype` 的产出
- 不要产出 PRD
- 不要执行 git 操作

## 输出格式

```
设计稿：Figma 导出（3 个页面）
目标技术栈：fe-vue3-elementplus（来自生效快照）

产出页面：3 个
  PAGE-CORE-001 列表页    data-fn 标记 7 处
  PAGE-CORE-002 详情页    data-fn 标记 4 处
  PAGE-CORE-003 设置页    data-fn 标记 2 处

同构性自检：✅ 可运行 · ✅ 标记合法 · ✅ 目录同构 · ✅ 已登记 PAGE 编号

待人工确认：
  - 设置页「高级选项」折叠区，无对应 FN —— 需求功能分析中未列出
  - 列表页「批量操作」按钮，可能对应 FN-CORE-047（未确认）

冲突提示：
  - 设计稿含「报表订阅」入口，需求功能分析中无此项 —— 是需求遗漏还是设计稿版本较旧？
```
