# 指令：读原型生成 PRD

## 核心机制

**原型是事实源，PRD 是原型的文字化。**

不要从需求功能分析"重新写一遍需求"——那样会写出一份与原型不一致的文档。正确做法是**遍历原型**，把页面上实际存在的东西描述出来。

顺序绝不能反过来（先写 PRD 再画原型）。反过来必然产生"文档说 A、原型是 B"的扯皮，而且没人能判定哪个对。

## 步骤

### 1. 遍历原型，提取标记

遍历原型工程页面，收集全部 `data-fn` 标记及其所在的元素、位置、上下文。

### 2. 逐个 FN 生成 PRD 章节

每个 `FN` 一节，写清：

| 项 | 内容 |
|---|---|
| 功能描述 | 这个功能做什么（一句话） |
| 入口 | 从哪个页面/按钮进入 |
| 交互说明 | 操作步骤、页面反馈 |
| 字段说明 | 每个字段的名称、类型、必填、校验规则、默认值 |
| 异常提示 | 失败、无权限、数据为空时页面显示什么 |
| 验收要点 | 可客观判定的验收标准（不能写"显示正常"） |

### 3. 生成页面原型映射表

`PAGE` ↔ `FN` ↔ PRD 章节号，三方对照。

### 4. 交叉校验

- PRD 里的每个 `FN`，原型中有对应页面吗？
- 原型里的每个 `data-fn`，PRD 中都有章节吗？

两边不一致时：**以原型为准**，并把不一致处单独列出供人复核。

### 5. 待确认事项原样带入

`需求问题汇总.md` 里的未解决问题，**原样列进 PRD 的"待确认事项"节**。

**不要自行填补，也不要删掉它们。** 一份"看起来很完整"的 PRD 比一份明确写着"这里还没确定"的 PRD 危险得多——前者会让人以为都想清楚了。

## 你绝对不要做的事

- 不要写技术方案、接口设计、数据模型
- 不要修改原型（发现问题回到 03）
- 不要因为某个 `FN` 在原型中体现不清就跳过它——列出来让人确认
- 不要执行 git 操作
