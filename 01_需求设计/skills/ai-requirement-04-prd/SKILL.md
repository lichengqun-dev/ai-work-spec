# ai-requirement-04-prd · PRD 生成

## 能力声明

**读取原型工程**，生成 PRD 与页面原型映射表。

核心机制是"AI 读原型生成 PRD"——因为原型里带着 `data-fn` 标记，它比任何文字描述都更接近需求的事实。

**不做什么**：不做技术方案、不写接口设计、不定数据模型、不修改原型——见「边界」。

## 何时用 / 何时不用

- **用**：原型已经业务方确认（gate-02 通过），要把原型文字化成 PRD 与页面原型映射表时
- **不用**：要从需求画原型（`ai-requirement-03-prototype` / `ai-figma-axure-convert`）；
  要写技术方案、接口设计、数据模型（设计域）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 原型工程 | `ai-requirement-03-prototype` 产出 | 是 | 页面元素带 `data-fn` 标记 |
| 需求功能分析 | `ai-requirement-02-analysis` 产出 | 是 | 每个功能有 `FN` 编号 |
| PRD 模板 | 知识库根下 `01_需求设计/templates/PRD 模板.md` | 是 | 存在 |
| 需求问题汇总 | `ai-requirement-02-analysis` 产出 | 是 | 存在 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| PRD | 文档仓 `<需求名>/01_需求/PRD.md` | 按模板；每个功能一节，标注 `FN` |
| 页面原型映射表 | 文档仓 `<需求名>/01_需求/页面原型映射表.md` | `PAGE` ↔ `FN` ↔ PRD 章节 |

PRD 的产出结构：

```markdown
# 需求规格说明书（PRD）

## 一、批次概述
## 二、功能需求
### FN-XXX-001 <功能名称>
| 来源需求 | REQ-XXX-001 |
| 对应原型页面 | PAGE-XXX-001 |

**功能描述** / **入口** / **交互说明** / **字段说明** / **异常提示** / **验收要点**

## 三、页面原型映射表
| PAGE 编号 | 页面名称 | 对应 FN | PRD 章节 |

## 四、待确认事项
| 问题编号 | 问题 | 影响 | 需要谁回答 |

## 五、非功能需求
```

每个 `FN` 一节要写清的六项：

| 项 | 内容 |
|---|---|
| 功能描述 | 这个功能做什么（一句话） |
| 入口 | 从哪个页面 / 按钮进入 |
| 交互说明 | 操作步骤、页面反馈 |
| 字段说明 | 每个字段的名称、类型、必填、校验规则、默认值 |
| 异常提示 | 失败、无权限、数据为空时页面显示什么 |
| 验收要点 | 可客观判定的验收标准（不能写"显示正常"） |

## 前置条件

**hard（不满足则拒绝执行）**

- 原型工程存在（本 Skill 的事实源就是原型，不以需求功能分析作为替代来源）
- 需求功能分析存在，且每个功能有 `FN` 编号
- PRD 模板存在（知识库根下 `01_需求设计/templates/PRD 模板.md`）
- 需求问题汇总存在（未解决的问题要原样带入 PRD 的「待确认事项」节）

**soft（不满足则提示，可继续）**

- gate-02 原型确认尚未通过 / 尚未运行：照常产出，产出物标注「未经上游确认 —— gate-02 未通过」。
  **原型还没被业务方确认，据此生成的 PRD 会白写**
- 原型中 `data-fn` 标记未覆盖全部 `FN`：列出缺失清单，询问用户是否继续；
  继续时对应章节标注"原型未体现"

## 执行步骤

1. **遍历原型，提取标记**：收集全部 `data-fn` 标记及其所在的元素、位置、上下文
2. **逐个 `FN` 生成 PRD 章节**：功能描述、入口、交互说明、字段说明、异常提示、验收要点
3. **生成页面原型映射表**：`PAGE` ↔ `FN` ↔ PRD 章节号，三方对照
4. **交叉校验**：PRD 里的每个 `FN`，原型中有对应页面吗？原型里的每个 `data-fn`，PRD 中都有章节吗？
   - 两边不一致时：**以原型为准**，并把不一致处单独列出供人复核
   - 某个 `FN` 在原型中体现不清 → 列出来让人确认，**不要跳过它**
5. **待确认事项原样带入**：`需求问题汇总.md` 里的未解决问题，**原样列进 PRD 的「待确认事项」节**，
   **不自行填补，也不删掉它们**

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始（原型更新后重出一版 PRD 是常见场景）
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：产出物照常落到指定路径，在报告中说明即可

## 边界（明确不做）

- 不做技术方案、不写接口设计、不定数据模型
- 不修改原型（发现原型有问题应回到 `ai-requirement-03-prototype`）
- **不解决待澄清问题**——把它们原样带入 PRD 的「待确认事项」节
- 不要因为某个 `FN` 在原型中体现不清就跳过它——列出来让人确认
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 原型中 `data-fn` 标记缺失 | 列出缺失清单，询问用户是否继续（继续则对应章节标注"原型未体现"） |
| PRD 与原型不一致 | 以**原型**为准，并在报告中标出不一致处供人复核 |
| 待澄清问题仍存在 | 不阻断，但必须在 PRD 中列为待确认事项 |
