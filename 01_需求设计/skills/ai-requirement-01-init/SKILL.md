# ai-requirement-01-init · 双仓库初始化

## 能力声明

初始化**项目文档双仓库**骨架与批次上下文（L3 CLAUDE.md）。

双仓库 = **项目文档仓**（人读为主：PRD、设计、测试报告）+ **原型工程仓**（机器读为主：可运行的原型代码）。

**不做什么**：不覆盖已存在的仓库或文件、不产出需求分析 / 原型页面 / PRD、不初始化业务代码仓——见「边界」。

## 何时用 / 何时不用

- **用**：批次已创建、批次状态文件里 `current_step` 为 `init` 时（本路径的第一步）
- **不用**：目标仓库已初始化过 → 走**续做分支**，只补缺失文件，不重建；
  要初始化**业务代码仓** → `ai-dev-01-scaffold`

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 批次状态文件 | `ai-requirement-00-intake` 产出 | 是 | `current_step` 为 `init` |
| 项目 manifest | `projects/<项目码>/.agent/project.yaml` | 是 | 含 `repo` 字段 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 存在 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 文档仓目录骨架 | 项目文档仓 | `<需求名>/00_批次` ~ `<需求名>/05_交付` |
| 批次上下文 | 项目文档仓 `CLAUDE.md`（L3） | ≤ 80 行 |
| 原型工程仓骨架 | 独立仓库 | 最小可运行工程 |
| 更新后的状态文件 | `projects/<项目码>/.agent/state/<批次号>.yaml` | `init` 步骤置 done |

### 文档仓骨架（产出结构）

```
<文档仓>/
├── CLAUDE.md              ← 批次上下文（L3）
├── README.md              ← 索引
└── docs/
    ├── 00_批次/
    ├── 01_需求/
    ├── 02_设计/
    ├── 03_实现/           ← 编码阶段的产出物
    ├── 04_测试/           ← 测试阶段的产出物
    ├── 05_交付/           ← 上线步骤、发布说明、结项报告
    └── 迭代/              ← 影响面分析、增量设计、变更登记（迭代批次才用）
```

**序号固定，逐字照抄，不要自造。** 这份清单与知识库根下 `projects/README.md` 的
「项目文档仓的目录约定」必须**完全一致**——各阶段 Skill 的产出契约里写死了这些路径，
名称对不上就是"建了目录但没人往里写"（教训见 `references/双仓库与批次上下文要点.md`）。

### L3 CLAUDE.md（产出结构，≤ 80 行）

```markdown
# 当前批次上下文

批次号：<批次号>
当前步骤：<current_step>
项目：<项目名>（<项目码>）
生效规范快照：projects/<项目码>/.agent/spec-effective/<项目码>.md @ <hash>

## 本批次范围
<一句话说明这个批次做什么>

## 已完成
- （随流程回写）

## 待澄清问题
- （见 <需求名>/01_需求/需求问题汇总.md）

## 本批次禁止
- （如：禁止修改某张表的既有字段，迁移成本高）
```

## 前置条件

**hard（不满足则拒绝执行）**

- 批次状态文件中 `current_step` 为 `init`
- 规范快照存在（`projects/<项目码>/.agent/spec-effective/<项目码>.md`）
- 项目 manifest 含 `repo` 字段——**不知道往哪建就做不了**

**soft（不满足则提示，可继续）**

- 目标文档仓路径已存在且非空 → **走续做分支**：逐个比对缺哪些文件，只补缺失的，报告补了什么。
  **绝不覆盖已有文件**——那可能包含已确认的需求变更

## 执行步骤

1. 确认仓库路径；两仓都存在则提示"已初始化"，只补缺失部分
2. 创建文档仓骨架（目录 + README + 索引）
3. 生成 L3 `CLAUDE.md`（批次上下文，≤ 80 行）
4. 建原型工程仓骨架（**先确认本项目是否需要**，见下）
5. 回写状态文件：`init` 步骤置 `done`，记录时间

### 第 4 步的判据：本项目要不要建原型工程仓

最小可运行工程即可。**技术栈从生效规范快照里读**，不要自己选。但**先判断这一步是否适用**：

| 情况 | 处理 |
|---|---|
| **原型由需求方外部提供**（客户已给精确原型、存量系统的功能增强） | **跳过本步**，并在状态文件里注明"原型外部提供，不建原型工程仓"。此时 manifest 不填 `prototype_repo`，gate-02 的两项原型检查会记 `external`（需人工核对覆盖情况并附证据） |
| 项目已存在原型工程仓（续做批次） | 走续做分支，只补缺的，不重建 |

建仓前先看 `projects/<项目码>/.agent/project.yaml`：**如果本来就没打算配 `prototype_repo`，就不要建仓**——
建了空仓反而会在 gate-02 里造成一次 `fail`（有仓但无 `data-fn` 标记），比如实记 `external` 更糟。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常执行（续做分支），并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：目录骨架与 L3 `CLAUDE.md` 照常落到指定路径，
  跳过状态回写并在报告中说明

## 边界（明确不做）

- **不覆盖已存在的仓库或文件**
- **不要自己选技术栈。** 快照里写的是什么就用什么；快照不存在就先跑 `ai-spec-build`
- **不要让 L3 CLAUDE.md 超过 80 行**
- 不产出需求分析、原型页面、PRD
- 不初始化业务代码仓（那是 `ai-dev-01-scaffold` 的职责）
- 不执行 git 操作——仓库初始化只建目录和文件，不 `git init`、不 commit

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 目标目录非空 | 走续做分支：只补缺失文件，逐个报告补了什么 |
| 原型工程仓创建失败 | 文档仓照常完成，标注原型仓待建；**不因为一个仓库失败就回滚全部** |
