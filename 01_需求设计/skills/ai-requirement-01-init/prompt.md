# 指令：初始化项目文档双仓库

## 双仓库是什么

| 仓库 | 内容 | 谁读 |
|---|---|---|
| **项目文档仓** | PRD、设计文档、测试报告、上线手册 | 人 |
| **原型工程仓** | 可运行的原型代码（带 `data-fn` 标记） | 机器（04-prd 要读它） |

分开的理由：原型是可运行的代码（有构建产物、有依赖），文档是结构化文本。混在一个仓会互相干扰，而且两者的评审节奏不同。

## 步骤

### 1. 检查现状

目标路径存在且非空？→ **走续做分支**：逐个比对缺哪些文件，只补缺失的，报告补了什么。**绝不覆盖已有文件**——那可能包含已确认的需求变更。

### 2. 建文档仓骨架

```
<文档仓>/
├── CLAUDE.md              ← 批次上下文（L3）
├── README.md              ← 索引
└── docs/
    ├── 00_批次/
    ├── 01_需求/
    ├── 02_设计/
    ├── 03_实现/           ← 编码阶段的产出物
    ├── 04_测试/           ← 测试阶段的产出物
    ├── 05_交付/           ← 上线步骤、发布说明、结项报告
    └── 迭代/              ← 影响面分析、增量设计、变更登记（迭代批次才用）
```

**序号固定，逐字照抄，不要自造。** 这份清单与 `projects/README.md` 的「项目文档仓的目录约定」
必须**完全一致**——各阶段 Skill 的产出契约里写死了这些路径，名称对不上就是"建了目录但没人往里写"。

> 曾经这里是 `03_测试 / 04_交付`，与下游全部 Skill 的产出路径（`03_实现 / 04_测试 / 05_交付`）
> 对不上。**症状很有欺骗性**：init 跑完看起来成功，直到编码阶段才发现产出物写不进去。

### 3. 生成 L3 CLAUDE.md（≤80 行）

这是整套体系的效率杠杆——让每次 Skill 执行只读一个 80 行文件就知道该做什么。**必须严格控制在 80 行以内，超了就要删减。**

```markdown
# 当前批次上下文

批次号：<批次号>
当前步骤：<current_step>
项目：<项目名>（<项目码>）
生效规范快照：projects/<项目码>/.agent/spec-effective/<项目码>.md @ <hash>

## 本批次范围
<一句话说明这个批次做什么>

## 已完成
- （随流程回写）

## 待澄清问题
- （见 <需求名>/01_需求/需求问题汇总.md）

## 本批次禁止
- （如：禁止修改某张表的既有字段，迁移成本高）
```

### 4. 建原型工程仓骨架（**先确认本项目是否需要**）

最小可运行工程即可。**技术栈从生效规范快照里读**，不要自己选。

**但先判断这一步是否适用。** 有两种情况**不需要**建原型工程仓：

| 情况 | 处理 |
|---|---|
| **原型由需求方外部提供**（客户已给精确原型、存量系统的功能增强） | **跳过本步**，并在状态文件里注明"原型外部提供，不建原型工程仓"。此时 manifest 不填 `prototype_repo`，gate-02 的两项原型检查会记 `external`（需人工核对覆盖情况并附证据） |
| 项目已存在原型工程仓（续做批次） | 走续做分支，只补缺的，不重建 |

建仓前先看 `projects/<项目码>/.agent/project.yaml`：**如果本来就没打算配 `prototype_repo`，就不要建仓**——
建了空仓反而会在 gate-02 里造成一次 `fail`（有仓但无 `data-fn` 标记），比如实记 `external` 更糟。

### 5. 回写状态文件

`init` 步骤置 `done`，记录时间。

## 你绝对不要做的事

- **不要覆盖已存在的文件。**
- **不要自己选技术栈。** 快照里写的是什么就用什么；快照不存在就先跑 `ai-spec-build`。
- **不要让 L3 CLAUDE.md 超过 80 行。**
- **不要执行 git 操作。** 仓库初始化只建目录和文件，不 `git init`、不 commit。
