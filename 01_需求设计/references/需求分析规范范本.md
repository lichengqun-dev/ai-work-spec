# 需求分析规范范本

> `ai-requirement-02-analysis` 的产出标准。**每个需求开始分析时必读。**

## 一、需求条目的合格标准

一条合格的需求条目包含五个要素，缺任何一个都说明信息不足：

| 要素 | 说明 | 不合格的样子 |
|---|---|---|
| 角色 | 谁在用 | "系统需要支持导出" |
| 场景 | 什么情况下用 | 同上——没说谁在什么情况下要导出 |
| 行为 | 要做什么 | — |
| 结果 | 期望得到什么 | — |
| 验收 | 怎么判断做对了 | "导出功能好用" |

合格示例：

```
REQ-CORE-012 角色：项目管理员
             场景：需要把列表数据交给线下评审
             行为：按当前筛选条件导出为 Excel
             结果：得到一个包含 12 列数据的 xlsx 文件
             验收：1 万条数据导出耗时 ≤ 30 秒；列与页面列表一致
```

## 二、功能点的拆解粒度

**判据：这个功能点能否被单独验收。**

如果"导出"和"导出后的下载"无法分别验收（一个做完另一个一定也做完了），它们就是一个功能点。如果能分别验收，就是两个。

粒度太粗：一个 `FN` 对应了 5 个可独立验收的能力 → 追踪时无法定位是哪个没做完。
粒度太细：20 个 `FN` 对应一个 10 分钟就能做完的改动 → 管理成本超过收益。

## 三、异常流程必须写出来

每条功能都要回答：

- 参数不合法怎么办？
- 无权限怎么办？
- 目标数据为空怎么办？
- 数据量超预期怎么办？
- 并发操作（两人同时改同一条）怎么办？

**写不出来就不写，记入待澄清清单。** 凭空编一个异常处理方式，比留着空白更糟——它会被当成确定的需求往下实现。

## 四、待澄清问题的写法

每条问题必须包含三部分：

```
Q-<三位编号> <问题本身>
影响：<影响哪些决策、哪些产出物>
需要回答：<谁>（业务方 / 技术负责人 / 客户）
```

**不写"影响"的问题等于没提**——接收者无法判断该多重视它，最终会拖到最后一刻。

## 五、常见歧义与处理

| 歧义表述 | 问题 | 处理 |
|---|---|---|
| "支持批量操作" | 批量上限是多少？失败一条怎么办？ | 记入待澄清 |
| "性能要好" | 什么指标、什么量级 | 记入待澄清，要求量化 |
| "跟原来一样" | 原来的哪一部分？只可意会 | 要求指认具体页面/功能 |
| "先简单做一版" | 简单在哪？砍掉什么 | 记入待澄清——"简单版"是最容易失控的需求 |
| "加个导出" | 导什么、给谁、什么格式 | 记入待澄清 |

**"跟原来一样"和"先简单做一版"是最危险的两类需求**：它们听起来明确，实际没有边界，实现出来大概率不是对方想要的。

## 六、场景归类

对照 `业务场景清单.md` 归类。**场景判断错了，后面推导出的功能点与验收标准都会偏。**

例：「导出」在**报表场景**下要求格式与完整性；在**数据集成场景**下要求接口稳定与幂等。同一个词，两个场景下是完全不同的需求。

归类不了时标为"场景待定"，记入问题汇总——**不要硬塞进最接近的场景**。
