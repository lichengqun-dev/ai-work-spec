# AI产品PRD与原型评审规范

本规范**仅定义 AI 自动初评**的全部核查维度与判定规则。评审对象为依据《产品PRD与原型图约束规范》产出的产品 PRD（产品需求文档）与原型图。评审目标：AI 初评确保 PRD 与原型图章节完整、数据真实、编号可追溯、原型与 PRD 一致、UI/UE 设计符合《岚图内部系统 UI/UE 设计规范 V1\.0》、验收标准可测试，检出明显数据造假和逻辑矛盾的问题，作为需求冻结前的自动化门禁。人工评审属于线下行为，不在本规范范围内。

本规范与以下规范共同构成"测试左移质量保障"链路：

- 《AI测试用例评审规范》

- 《AI测试报告评审规范》

# 一、概述与适用范围

## 1\.1 规范定位

基础规范定义"PRD 与原型图长什么样"，本规范定义"长成那样才算合格"。两者关系：

|文档|定位|核心问题|
|---|---|---|
|《产品PRD与原型图约束规范》（基础规范，11 章）|PRD 与原型图生成标准|PRD / 原型图应包含哪些章节、哪些必填项、什么质量标准|
|本规范（评审规范）|PRD 与原型图验收标准|AI 产出的 PRD \+ 原型图质量是否达标、可否进入开发与测试设计阶段|

## 1\.2 适用范围

本规范适用于依据《产品PRD与原型图约束规范》产出的**所有产品 PRD 与原型图**的评审，覆盖从文档元数据、业务目标、功能需求到原型 UI/UE 合规的完整需求产物。

- **评审对象**：AI 生成的产品 PRD（含基础规范 11 章内容）与原型图产物（含 AI 生成原型），两者作为整体送审

- **覆盖范围**：需求生成完成后、需求冻结前的评审，评审结论是需求进入开发阶段与测试用例设计阶段的门禁依据

- **不适用**：人工撰写 PRD 可参照执行，但以人工评审为主；纯开发技术方案文档由《AI开发技术方案评审规范》覆盖；纯视觉设计稿（不含交互与需求映射）不在本规范范围

## 1\.3 评审对象

评审的对象是 AI 生成的**产品 PRD 与原型图产物本身**，不是需求生成过程、也不是最终产品质量。评审关注：

- 章节完整性——基础规范 11 章全部具备，必填项无缺失

- 数据真实性——指标基线值、编号引用、关联文档真实可追溯，无 AI 幻觉与编造

- 内部一致性——章节之间无自相矛盾，原型图与 PRD 一致

- UI/UE 合规性——原型图符合《岚图内部系统 UI/UE 设计规范 V1\.0》硬性指标

- 是否满足需求冻结门禁条件

# 二、评审角色与职责

## 2\.1 角色定义

|角色|职责|阶段|
|---|---|---|
|**AI 初评员**|自动化 AI 系统担任，产品提交 PRD \+ 原型图后自动执行初评，核查章节完整性、数据真实性、逻辑自洽性、原型\-PRD 一致性以及 UI/UE 合规性，作为需求冻结的自动化门禁|AI 初评|

注：产品评审员、开发代表、测试代表、质量终审员属于人工线下环节，不在本规范范围内。

## 2\.2 角色分工原则

AI 初评员由自动化 AI 系统担任，在 PRD 与原型图提交后自动执行初评，核查章节完整性、数据真实性和原型\-PRD 一致性，作为需求冻结的自动化门禁。AI 初评员只输出核查事实与质疑清单，不做主观取舍：原型图与 PRD 不一致时只列差异，裁定权在人工线下环节。

# 三、评审流程

## 3\.1 流程总览

评审流程分为 4 个阶段，按顺序执行：

1. **提交阶段**：产品经理按《产品PRD与原型图约束规范》完成 PRD 与原型图生成，产品完成自查（11 章完整性 / 必填项 / 编号一致性自查清单）并签字确认。提交后自动触发 AI 初评（见第四章），AI 对 PRD 与原型图进行全维度自动化核查。

2. **AI 初评阶段**：AI 系统自动完成 12 个维度的合规性核查（含事实层真实性、逻辑层合理性、原型\-PRD 差异核验、UI/UE 硬性指标核验与原型图格式准入核查），输出初评报告（见第四章、第五章），通过则进入需求冻结流程，不通过则退回产品修正。

3. AI 初评不通过阶段：若任一强制一票否决项触发，PRD 与原型图直接退回产品修正，修正后重新提交触发 AI 初评。

4. **AI 初评完成**：AI 输出初评报告 HTML 文件，作为需求冻结门禁的自动化凭证，AI 初评通过的 PRD 与原型图可进入后续线下流程（开发启动与测试用例设计）。

## 3\.2 流程规则

- AI 初评须在 PRD \+ 原型图提交后 **30 分钟内**自动完成；若发现任一严重级不达标项，PRD 与原型图直接退回产品修正，AI 初评不通过不进入需求冻结流程。

- 每项检查项 AI 系统必须给出明确的初评结论和具体说明，不得留空。

- "不达标"项必须给出具体缺陷描述和改进建议。

- 整改后重新提交 AI 初评时，系统须重新核查对应项及关联影响。

- 原型图与 PRD 的差异须全部列入差异清单并裁定关闭后，方可生成下游产物（技术方案、测试用例）。

- AI 初评记录须归档，作为需求冻结门禁的审计凭证。

# 四、AI 初评 · 12 维度自动化核查

本章定义 AI 初评的 12 个自动化核查维度，其中维度一至维度十一为计分维度，维度十二为格式准入一票否决维度（不占评分权重），全部由 AI 系统自动执行，无需人工介入。覆盖从基础规范 11 章结构合规、事实层真实性核查、逻辑层合理性核查、原型\-PRD 差异核验、UI/UE 硬性指标完整校验到原型图格式准入核查的全链路验证。任一「不真实项」（编造数据、虚构引用、虚构依赖等）与任一维度十二格式核查不通过，均触发强制一票否决。

## 4\.1 维度一：文档基础信息完整性

对应基础规范 §1（1\.1 文档元数据、1\.2 术语与缩写定义）。

|检查项|核查要点|严重程度|单项分值|
|---|---|---|---|
|元数据必填项完整|文档编号、文档名称、版本号、作者、审核人、批准人、创建日期、最后更新日期、文档状态 9 项必填字段无空缺；文档状态为草稿 / 评审中 / 已批准 / 已发布 / 已废弃之一；关联文档清单完整可追溯|严重|0\.71 分|
|版本号格式合规|采用语义化版本（主版本\.次版本，如 v1\.2）|一般|0\.71 分|
|术语表完整|正文开始前提供术语与缩写定义表，含通用术语基线并补充项目特有术语|一般|0\.71 分|
|责任链明确|作者、审核人、批准人三个角色均已指定且不空缺|严重|0\.71 分|
|术语与定义真实性（事实层）|§1\.2 术语表中引用的外部概念定义与权威出处一致，歪曲权威定义 = 不真实项|严重|0\.71 分|
|引用规范真实性（事实层）|引用的国家标准、行业标准、企业内部规范真实存在，编号与名称准确，引用不存在或张冠李戴 = 不真实项|严重|0\.71 分|
|术语一致性（逻辑层）|全文统一使用 §1\.2 定义的术语，无同义异名、同名异义|一般|0\.71 分|

## 4\.2 维度二：业务背景与目标明确性

对应基础规范 §2（2\.1 业务背景、2\.2 业务目标与成功指标）。

|检查项|核查要点|严重程度|单项分值|
|---|---|---|---|
|业务背景四要素齐全|业务痛点/机会、现状分析、行业趋势、战略关联四要素均有论述，痛点/机会有数据或案例说明影响范围|严重|1\.43 分|
|业务目标明确|用 1\-3 句话描述核心业务目标，且与背景章节的痛点/机会一一对应|严重|1\.43 分|
|KPI 可量化|至少定义 2 个可量化的成功指标，每个指标均含当前基线值、目标值、度量方式、度量周期四项|严重|1\.43 分|
|指标设计原则|指标可度量（能通过系统数据/业务报表/人工统计获得）、有基线、有时限、业务导向（不以接口响应时间等技术指标充当业务 KPI）|一般|1\.43 分|
|原型背景标注（原型适用）|原型图精简引用相关 PRD 的业务背景，并补充产品视角的分析|一般|1\.43 分|
|业务数据真实性（事实层）|§2 引用的现状基线、目标值均标注数据来源，来源真实存在、可访问、口径一致，无来源或来源不可追溯 = 不真实项|严重|1\.43 分|
|数值一致性（逻辑层）|同一指标在不同章节的取值一致；合计与分项之和吻合；目标值与成功指标口径对得上|严重|1\.43 分|

量化成功指标缺失为强制一票否决项——若本维度不达标（少于 2 项可度量指标，或缺基线值 / 目标值 / 度量方式 / 度量周期），无论其他维度表现如何，AI 初评直接判定不通过。

## 4\.12 维度十二：原型图格式（必须为 HTML，一票否决）

对应基础规范《产品PRD与原型图约束规范》§8\.8「[原型图格式约束（必须为 HTML）](https://hav4xarv6k.feishu.cn/docx/BvKXdD5osogZWnxL56aca8mNnUh)」，与生成端格式约束衔接并保持一致，格式口径以基础规范为准。本维度是原型图的格式准入核查，为 AI 初评最先执行的检查项：先完成本维度核查，再进入维度一至维度十一的评分核查。

**一票否决机制：**本维度 9 项 Checklist 任一不通过 → AI 初评直接判定不通过、评审打回（退回产品修正，备注不通过的具体检查项及"不符合基础规范 8\.8 原型图格式约束"），不进入后续评分维度核查。本维度不占 100 分制评分权重、不参与 §5\.3 得分计算，维度一至维度十一的权重与得分保持原样不变（见 §5\.2）。整改后重新提交时，须重新核查对应项及关联影响（流程规则见 §3\.2）。

**检查项 1：HTML 单文件**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|通过：原型图为单个 \.html 文件，浏览器直接打开即可完整渲染原型内容（含全部页面、组件与交互效果）。不通过：提交 Figma / Sketch / MasterGo 等设计源文件或设计稿截图，PNG / JPEG / GIF 等图片格式，PDF，PPT / PPTX，Axure \.rp 源文件，或仅提供在线原型平台链接（Figma 云端、蓝湖、墨刀等）。|
|**例外处理**|多页面原型允许合并在一个 HTML 内，通过页内导航（锚点 / JS 切换）实现页面跳转；确有多个独立 HTML 原型文件时，每个文件分别按本维度 9 项核查，且每个文件的链接均须嵌入 PRD（见检查项 9）。|
|**错误示例**|① 用 Figma 截图拼成的 PNG 图集充当原型；② 提交包含 HTML \+ 外置 css / js / 图片文件夹的 zip 压缩包；③ 只给设计工具在线预览链接、无任何 HTML 文件。|
|**整改建议**|重新以单文件 HTML 形式产出原型（样式与脚本全部内联，见检查项 3）；设计源文件与截图可作为辅助材料保留，但不得替代 HTML 原型作为送审对象。|

**检查项 2：HTML5 标准**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|三项必查点全部满足方为通过，缺一即不通过：① 文件首行为 `<!DOCTYPE html>` 声明，且其前无任何字符、空行或 BOM 标记；② `<head>` 内含字符集声明 `<meta charset="UTF-8">`；③ `<head>` 内含视口声明 `<meta name="viewport" content="width=device-width, initial-scale=1.0">`。|
|**例外处理**|字符集声明允许 `charset="utf-8"` 等等价写法（大小写不敏感），但不得缺失、不得以 gb2312 / gbk 等非 UTF\-8 编码替代；旧式 HTML4 / XHTML 文档类型声明（如 `<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Transitional//EN" …>`）一律判定不符合 HTML5 标准。|
|**错误示例**|① 文件直接以 `<html>` 开头、无 DOCTYPE 声明；② 缺 viewport 声明，页面被按虚拟宽视口渲染；③ 声明 gb2312 编码，原型中文出现乱码。|
|**整改建议**|补齐文档头三件套：`<!DOCTYPE html>` \+ `<meta charset="UTF-8">` \+ viewport 声明；提交前确认文件以 UTF\-8 编码保存。|

**检查项 3：单文件交付（禁止外链资源）**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|通过：全部样式内联于 `<style>` 标签、全部脚本内联于 `<script>` 标签；文件中不出现 `<link href="…">`、`<script src="…">`、`@import`、`url(http…)` 等外链引用；不引用 CDN、外链字体或外链图片地址（含 `//cdn.xxx.com` 协议相对路径）。|
|**例外处理**|允许 HTML 内以 Base64 Data URI 内联图片；允许页内锚点导航与页内 JS 交互。外链资源无论当前是否可访问，一律判定不通过——在线显示正常但离线打开即失效的，同样不通过。|
|**错误示例**|① `<script src="https://code.jquery.com/jquery.min.js">` 引入外部库；② `<link rel="stylesheet" href="./style.css">` 引同目录外置样式文件；③ 背景图 `url(https://xxx.com/bg.png)` 引外部图床图片。|
|**整改建议**|将外置 CSS / JS 内容移入文件内 `<style>` / `<script>` 标签；小体积图片转为 Base64 Data URI；确需第三方库的，把库源码内联进文件或改用原生 HTML / CSS / JS 实现。|

**检查项 4：中文字体**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|通过：页面全局样式（body 或等效选择器）的 `font-family` 字体栈中包含 Microsoft YaHei（微软雅黑）或 PingFang SC（苹方），如 `font-family: "Microsoft YaHei", "PingFang SC", sans-serif;`；中文文本渲染为中文黑体，而非回退到浏览器默认衬线字体。不通过：字体栈中无任何中文字体。|
|**例外处理**|代码展示区等特殊区域可前置 Consolas / Menlo 等等宽字体，但字体栈仍须保留 Microsoft YaHei / PingFang SC 作中文回退；使用自定义品牌字体的，仍须将 Microsoft YaHei 或 PingFang SC 列为回退字体。|
|**错误示例**|① `font-family: Arial, Helvetica, sans-serif;` 仅声明西文字体，中文回退为默认宋体样式；② 仅写 `sans-serif` 泛型族、无具体中文字体名；③ 通过外链 CDN 加载 web 字体（同时违反检查项 3）。|
|**整改建议**|在全局样式补上 `"Microsoft YaHei", "PingFang SC", sans-serif` 字体栈；两款字体分别覆盖 Windows / macOS 主流环境，无需附带字体文件。|

**检查项 5：响应式（支持最小宽度 1280px）**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|通过：页面在 1280px 视口宽度下显示正常——无整页横向滚动条、无模块被截断、无文字重叠或元素错位；布局采用 % / flex / grid 等弹性方式，或最小宽度不低于 1280px 的居中容器。不通过：1280px 宽度下出现整页横向滚动、大面积内容截断或布局崩坏。|
|**例外处理**|列数较多的宽表格允许在表格容器内部横向滚动，但页面整体不得出现横向滚动条；允许额外适配更窄宽度，但不得因此破坏 1280px 下的显示；允许定宽布局，但设计宽度不得低于 1280px 且页面居中。|
|**错误示例**|① 页面仅按 1920px 宽屏设计，1280px 下出现大面积截断或整页横向滚动条；② 弹窗 / 浮层定位在 1280px 视口之外，无法正常打开或查看。|
|**整改建议**|将布局改为 flex / grid 或百分比宽度，外层容器设置 `min-width: 1280px` 并居中；提交前逐页在 1280px 宽度下自查。|

**检查项 6：HTML 注释**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|通过：文件含 HTML 注释（`<!-- … -->`），注释覆盖每屏（页面 / Tab）与每个核心交互区域（弹窗、抽屉、下拉面板、状态切换区等）；注释内容清晰可读，能说明屏名称或交互的触发条件 / 状态变化，且与实际内容一致。不通过：无注释、注释未覆盖、或注释为无意义占位。|
|**例外处理**|单屏包含多个交互区域时，允许合并注释或拆分注释，但必须覆盖；构建工具自动生成的注释不计为有效注释；因压缩 / 混淆流程导致注释全部丢失的，按无注释判定不通过。|
|**错误示例**|① 整份文件无任何 HTML 注释；② 仅有 `<!-- 1 -->`、`<!-- aaa -->` 之类无意义占位注释；③ 注释与内容不符（如注释写"订单列表"，实际代码是"用户中心"）。|
|**整改建议**|按"每屏头部 `<!-- 屏：xxx -->`、每个核心交互区域 `<!-- 交互：xxx（触发条件 / 状态变化）-->`"补齐注释，并确保注释与实际内容一致。|

**检查项 7：元素语义化**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|通过：页面结构使用语义化标签——页面骨架使用 header / nav / main / footer / section / aside，列表使用 ul / ol，数据表格使用 table / thead / tbody，按钮使用 button，链接使用 a；未全篇滥用 div / span 承载结构与交互。不通过：全篇 div / span 堆叠、无语义化标签。|
|**例外处理**|复杂自定义组件（自定义下拉、拖拽容器等）允许用 div 搭建，但应通过 role / aria\-\* 属性或注释补充语义；纯装饰性图形（div \+ CSS 实现）不要求语义化标签。|
|**错误示例**|① 用 `<div onclick>` 实现导航菜单与按钮，未使用 nav / button / a；② 用 div 模拟数据表格，未使用 table 结构；③ 整页 20 层以上 div 嵌套、无任何语义化标签。|
|**整改建议**|按语义重构：页面骨架改用 header / nav / main / footer，可操作元素改用 button 或 a，列表改用 ul / ol，数据表格改用标准 table 结构。|

**检查项 8：交互元素完整**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|通过：交互元素（按钮、输入框、下拉框、标签页、列表行等）覆盖 hover / click（active）/ disabled 三类状态——hover 有视觉反馈，disabled 有置灰样式且不可点击，核心按钮有点击结果反馈（状态变化、弹窗或跳转说明）；状态通过 CSS 伪类（:hover / :active / :disabled）或 JS 实现，而非仅文字描述。不通过：交互状态缺失或仅口头描述。|
|**例外处理**|纯展示型元素（徽标、标签墙、静态统计卡片等）不要求交互状态；确无 disabled 业务场景的元素（如始终可用的提交按钮），在注释中说明"无 disabled 场景"即可。|
|**错误示例**|① 按钮只有默认态，hover、click 无任何视觉反馈；② disabled 状态与正常态无区分、仍可点击；③ 交互状态仅写在 PRD 文字里，原型未实现对应样式或行为。|
|**整改建议**|为交互元素补齐 `:hover`、`:active`、`:disabled` 样式，并用 JS 实现点击 → 弹窗 / 跳转 / 状态切换流程，确保每个核心交互可感知。|

**检查项 9：PRD 嵌入链接**

|方面|内容|
|---|---|
|**通过 / 不通过判定**|通过：PRD 文档的原型图章节（或对应位置）嵌入 HTML 原型文件的访问链接，链接可点击、能跳转到实际存放的文件（云盘或内部平台地址），且链接对应文件与本次送审版本一致。不通过：无链接、链接不可访问、或链接指向非本次送审文件。|
|**例外处理**|原型以评审系统附件形式提交而非链接的，PRD 对应位置须注明附件文件名与版本号；存在多个原型文件的，须逐一列明并分别嵌入链接，缺任何一个按不通过处理。|
|**错误示例**|① PRD 仅写"原型见附件"，无可点击链接；② 链接指向历史旧版本，与本次送审文件不一致；③ 使用 `file://C:\xxx.html` 之类本地路径，他人无法访问。|
|**整改建议**|将 HTML 文件上传至云盘或指定内部平台，获取可分享链接嵌入 PRD 原型图章节；提交前点击验证链接可访问、版本与送审文件一致。|

# 五、AI 初评 · 判定与评分机制

## 5\.1 判定结论

本章在三种判定结论的基础上引入满分 100 分的量化评分体系，将定性判定升级为可度量的质量分值，用于横向对比不同项目需求文档产出质量、识别团队内优秀 PRD 实践、以及驱动需求质量持续改进。分值与判定结论完全兼容：100 分对应「直接通过」，100 分以下（不含免检）对应「待人工确认」，70 分以下或触发一票否决对应「退回重写」。

AI 初评是自动化门禁，输出三种结论。只有 100 分才能自动判定通过；有严重违规可自动判定退回；介于两者之间的转人工确认。所有 12 个维度自动核查完毕后按分值、严重级检查项计数与一票否决核查结果（含维度十二原型图格式）综合判定：

|结论|判定条件|后续动作|
|---|---|---|
|**✅ 直接通过**|100 分，全部检查项通过，无「不真实」项，无 UI/UE 硬性指标不达标，原型\-PRD 无差异或差异均有合理说明|免检直接冻结，AI 初评记录自动归档|
|**⚠️ 待人工确认**|100 分以下（不含免检），无「不真实」项，无 UI/UE 硬性指标不达标，但存在其他不达标项或未决的原型\-PRD 差异|转人工评审，24 小时内综合研判，决定是正常冻结、带条件冻结或退回重写|
|**❌ 退回重写**|存在任一「不真实」项；或严重级检查项累计不达标 ≥ 3 项；或任一 UI/UE 硬性指标不达标；或原型与 PRD 严重脱节；或维度十二原型图格式核查不通过（一票否决）|PRD 与原型图退回产品修正，附带 AI 质疑清单，修正后重新提交触发 AI 初评|

AI 初评输出 HTML 模板复用《AI测试报告评审规范》§5\.11 的视觉风格和区块结构，评审对象替换为「产品 PRD 与原型」即可。

## 5\.3 得分计算公式

AI 自动初评完成全部 12 个维度核查后，按以下公式对维度一至维度十一（计分维度）计算最终得分（维度十二为一票否决项，不参与计分）：

`最终得分 = 总和(维度 i 权重分 × 维度 i 达标率) - 扣分项`

**公式说明：**

- **维度 i 权重分**：第 i 个维度的分配权重分值，11 个计分维度（维度一至维度十一）权重之和为 100 分；维度十二为一票否决维度，不占权重、不参与得分计算

- **维度 i 达标率**：维度 i 下已通过检查项数 ÷ 维度 i 下总检查项数，取值范围 0\.0 \~ 1\.0；标记为"不适用"的检查项从分母中剔除，不参与达标率计算。**注意：达标率已通过比例自动分摊该维度内的所有不达标项扣分（维度 i 权重分 × 不达标项比例），无需在扣分项中重复扣减。**

- **扣分项**：仅含同一问题复现扣分（\-5 分/处）；常规不达标已由达标率机制覆盖，严重级溢出扣分见 §5\.5 扣分规则明细，勿重复计入

- **一票否决强制归零**：若触发 4\.2 节量化成功指标缺失、4\.8 节验收标准缺失、4\.9 节风险依赖章节整体缺失、4\.10 节 UI/UE 硬性指标不达标（含原型与 PRD 严重脱节）、4\.12 节原型图格式核查不通过（非 HTML 或 9 项 Checklist 任一不通过）任一否决项，或存在任一「不真实项」，最终得分直接归零为 0 分，判定不合格（一票否决为最高优先级，先于得分计算执行，不进入公式）

- **原型图未提交**：原型图未随 PRD 提交时，维度十整体按 0 分计，并记录为严重缺失

## 5\.4 等级判定标准

按最终得分划分 5 个质量等级，对应不同的冻结决策：

|等级|分数段|质量描述|冻结状态|
|---|---|---|---|
|⭐⭐⭐⭐⭐ 卓越|100 分|所有检查项全部通过，PRD 与原型质量接近完美，可作为团队标杆需求文档样板|免检直接冻结|
|⭐⭐⭐⭐ 优秀|90 \~ 99 分|严重级检查项 100% 通过，仅少量一般级检查项有优化空间|正常冻结|
|⭐⭐⭐ 良好|80 \~ 89 分|严重级检查项 100% 通过，一般级检查项存在部分不达标，整体质量合格|正常冻结|
|⭐⭐ 合格|70 \~ 79 分|严重级检查项 100% 通过，一般级检查项存在部分不达标，整体满足最低冻结门禁要求，需补充小范围修正|带条件冻结，限期 24h 内补全|
|⭐ 不合格|小于 70 分|严重级检查项累计不达标 3 项及以上，或触发一票否决（硬性指标不达标 / 业务目标缺失 / 验收标准缺失 / 风险依赖缺失 / 原型图格式不合规 / 不真实项），需求文档质量不满足基本要求|退回重写，不进入开发流程|

## 5\.5 扣分规则明细

按不达标项的严重程度执行对应扣分：

|不达标类型|单次扣分值|备注说明|
|---|---|---|
|严重级溢出（维度权重分扣完后仍有严重级不达标项）|额外追加 5 分/项|该维度内的严重级不达标已由达标率机制扣至 0 分，但仍有惩戒必要，故跨维度追加惩罚性扣分，保持与评审规范体系一致|
|一票否决触发|直接归零 100 分|无论其他维度表现如何，最终得分强制归零判定为不合格，一票否决|
|同一问题整改后复现（复审不通过）|\-5 分/处|整改后复审发现同一检查项再次不达标，说明整改未真正落实，追加惩罚性扣分；同一问题第三次出现则累计追加|

**扣分计算优先级：** 达标率扣分（通过比例自动计算）→ 严重级溢出（5 分/项）→ 特殊行为惩罚（\-5 分/处）；一票否决强制归零为最高优先级，在得分计算前执行。**严禁将达标率已覆盖的扣分重复计入扣分项。**

- 扣分明细清单（每条扣分对应不达标项、扣分值、改进建议）

- 与历史基线平均分的对比趋势线
