## 用法

```bash
S=07_质量门禁/skills/ai-gate-runner/scripts/gate_run.py

python3 $S --list-checks                       # 列出检查项库与实现状态
python3 $S --project <码> --batch <批次号> --gate gate-03          # 执行一道门禁
python3 $S --project <码> --batch <批次号> --gate gate-03 --check   # 只校验不回写
python3 $S --project <码> --batch <批次号> --all                    # 按顺序跑到第一个未通过
python3 $S --project <码> --batch <批次号> --gate gate-03 --confirm --by 张三
python3 $S --project <码> --batch <批次号> --gate gate-03 --waive --by 张三 \
        --reason "客户要求当日上线" --expires 2027-06-30
```

退出码：`0` 通过 ｜ `1` 未通过或待人工确认 ｜ `2` 执行器自身错误（含拒绝执行）。

## 执行器的三条不能破的语义

**一、找不到检查项实现 → 整道门禁拒绝执行。** 不是跳过那一项。静默跳过等于门禁失效——而失效的门禁比没有门禁更糟，因为它让人以为已经检查过了。

**二、`skip` 不等于 `pass`。** 缺少校验材料（项目仓未挂载、依赖尚未实现的 Skill）时记为 `skip`，转入人工确认，并在输出里说明"要做什么才能自动校验"。把"没法校验"当成"校验通过"，是门禁最容易失效的方式。

**三、执行器不代替人做判断。** 标注 `人` 的检查项原样列出等人工核对；门禁不会自动变成 `passed`——需要 `--confirm --by <名字>` 显式签核。理由不是 AI 能力不足，而是**责任必须有人承担**。

## 门禁设计的三个要点

**自动检查优先，人工检查兜底。** 每个检查项先问"能不能写成脚本"。能写的一律自动化——因为人工检查会随时间推移变成走过场。只有真正需要判断力的（技术方案是否合理、索引设计是否恰当）才留给人。

**区分 BLOCK 与 WARN。** 如果所有检查项都是阻断项，团队会在第一次被卡住后要求关闭整道门禁。区分级别让门禁具备"可存活"性——WARN 项生成待办但不阻断。

**豁免要留痕且自动复查。** 豁免写入批次状态文件的 `waivers` 段（含批准人与复查日期），**不自动续期**。`waivable: no` 的门禁（gate-02 / gate-06）直接拒绝豁免——它们守着跳过就无法补救的东西。

## 现状

执行器已实现，**24 个检查项全部有实现**（`--list-checks` 可核对），并已用夹具逐条验证拦截行为。

其中 5 项固定返回 `skip`，因为它们本质上要在项目仓或依赖尚未实现的 Skill 下完成：

| 检查项 | 为什么 skip |
|---|---|
| `lint-passthrough` | 静态检查需按项目自己的配置执行，不在执行器职责内 |
| `unit-coverage-report` | 需项目侧生成覆盖率报告（`ai-dev-04-unittest`，P1） |
| `testcase-executed` | 需测试报告（`ai-test-03/05`，P2） |
| `p0p1-closed` | 需缺陷台账（`ai-test-03-execute`，P2） |
| `secrets-externalized`（无项目仓时） | 需要项目仓路径 |

**这类 skip 是有意保留的**：执行器宁可明确说"我查不了，需要你做 X"，也不猜一个结论。
