# 07_质量门禁

> 六道门禁的定义与统一执行器。门禁横跨所有阶段，因此独立成域，而不是挂在某个阶段下。

## 这个域有什么

| 内容 | 位置 | 说明 |
|---|---|---|
| 门禁定义 | `gates/gate-01…06.md` | 每道门禁的入口条件、检查项、通过标准、豁免机制 |
| **执行器** | `skills/ai-gate-runner/scripts/gate_run.py` | 读取门禁定义并执行，纯脚本，不调用模型 |

**自动检查项不单独放脚本。** 最初的设计是"每个 `auto` 检查项对应一个独立脚本"，
实现时改成了**单文件检查项库**，三个理由：

- **共享上下文**：绝大多数检查项要读同一批东西（批次状态文件、编号总表、产出物文本、git log）。
  独立脚本意味着每个都自己解析一遍，或依赖一个共享中间产物（多一层失败点）。
- **一致性**：读取产出物、解析编号、判断路径归属这些逻辑必须完全一致，否则同一个 FN
  在覆盖率检查里算"存在"、在断链检查里算"缺失"。放在一起才不可能分叉。
- **`skip` 语义统一**："缺材料时记 skip 而不是 fail"是执行器级别的语义，散落各处无法保证一致。

**人工检查清单也不单独放文件。** `方式=人` 的项已内联在 `gates/*.md` 的检查项表格里，
执行时会原样摆到人面前。只有真正需要**额外说明**（如"技术方案是否符合分层架构规范"需要配一张禁止依赖矩阵图）
的项，才值得单独写清单——不要为了"内容完整"而复制 gates 里已有的清单。

## 用法

**调用 `ai-gate-runner` 即可**，说"跑 gate-03"或"这个批次过一下门禁"。
它自己知道去哪读门禁定义、该跑哪些检查项、结果写回哪个文件。

**使用者不需要记参数，也不需要知道检查项有几项。** 会需要他出场的只有三种情况：

| 它说 | 你要做 |
|---|---|
| 有待人工核对的项 | 照它列出的清单核对，核对完给它**真实姓名**去签核 |
| 某检查项缺材料，记了 `skip` | 按它说明的"要做什么才能自动校验"补材料，然后重跑 |
| 确实要带风险上线 | 给它**原因**和**复查日期**，走豁免 |

结果只有三种：**通过** ｜ **未通过或待人工确认** ｜ **执行器自身错误（含拒绝执行）**。
第三种不是"检查没做"，是"这道门禁根本没跑起来"——它一定会说明原因，且不会被算作通过。

## 执行器的五条不能破的语义

**一、找不到检查项实现 → 整道门禁拒绝执行。** 不是跳过那一项。静默跳过等于门禁失效——而失效的门禁比没有门禁更糟，因为它让人以为已经检查过了。

**二、`skip` 不等于 `pass`。** 缺少校验材料时记为 `skip`，转入人工确认，并在输出里说明"要做什么才能自动校验"。把"没法校验"当成"校验通过"，是门禁最容易失效的方式。

**三、执行器不代替人做判断。** 标注 `人` 的检查项原样列出等人工核对；门禁不会自动变成 `passed`——
需要**带真实人名的显式签核**。理由不是 AI 能力不足，而是**责任必须有人承担**。

**四、BLOCK 级 skip 不能用签核越过，只能豁免。** 签核的前提是「有人核对过了」；
当 BLOCK 项因为**校验材料根本不存在**而 skip 时（无代码仓、无测试报告），没有人能核对它。

**五、`external` 不等于 `skip`——不在执行器职责内的项可以签核，但必须附证据。**
`skip` 是"缺材料"（补了就能自动校验），`external` 是"不归它查"（补材料没用，必须人做）。
判据是**有没有人的判断可依赖**：材料不存在 → 没人核对过 → 不能签核；
人真能去跑 lint、看覆盖率报告 → 判断有依据 → 可以签核，但要用 `--evidence` 把依据写下来。

> 第五条是分两批补的，它解的是两个死结：`lint-passthrough` 是 BLOCK 级却无条件 skip，
> 而它没有任何可补齐的材料 → `--confirm` 永远被拒 → **gate-04 结构上无法通过**，
> 每次都必须 `--waive`，**豁免从"例外通道"变成了"常规通道"**。
>
> 更严重的是 `fn-coverage-prototype` / `data-fn-markers`：**原型由需求方外部提供**时，
> 本项目根本不存在带 `data-fn` 的可运行原型，补也补不出来；而 **gate-02 是 `waivable: no`**，
> 连豁免都不许——**整条流程卡死在原型确认**。
>
> 引入 `external` 后两道门禁都回到可签核，而证据要求比原来更严——**这不是放宽，是把它挪到了对的位置上。**

早期实现允许 `--confirm` 直接越过这类 skip，后果是实测中 gate-04 在**零提交**下通过、
gate-05 在**零用例执行**下通过——「提交带 FN」「用例跑完了吗」「P0/P1 关闭了吗」三件最想守住的事，
证据全是空的。现在 `--confirm` 遇到 BLOCK 级 skip 会**拒绝并说明**，两条出路：补齐材料后重跑，
或用 `--waive` 带批准人与复查期豁免。

## 门禁设计的三个要点

**自动检查优先，人工检查兜底。** 每个检查项先问"能不能写成脚本"。能写的一律自动化——因为人工检查会随时间推移变成走过场。只有真正需要判断力的（技术方案是否合理、索引设计是否恰当）才留给人。

**区分 BLOCK 与 WARN。** 如果所有检查项都是阻断项，团队会在第一次被卡住后要求关闭整道门禁。区分级别让门禁具备"可存活"性——WARN 项生成待办但不阻断。

**豁免要留痕，且复查日期受机器约束。** 豁免写入批次状态文件的 `waivers` 段（含批准人与复查日期），**不自动续期**。
执行器校验复查日期：**必须晚于今天、且在 90 天以内**——填 9999-12-31 这类会被直接拒绝。
`waivable: no` 的门禁（gate-02 / gate-06）连豁免都拒绝——它们守着跳过就无法补救的东西。

> ⚠️ **但"到期自动提醒"这一半还没实现。** 复查日期会被如实记录下来，
> 却没有任何代码会在到期时提醒任何人。所以现阶段**复查看排期，靠人**——
> 排期时把已豁免的项纳入常规巡检，否则这条豁免会安静地变成永久遗忘。
>
> 这条机制的意义正是防止"临时豁免变成永久遗忘"。**在它实现之前，
> 那句"没有自动复查的豁免机制等于没有门禁"，说的就是本仓库自己。**

## 现状

执行器的 **25 个检查项全部有实现**（可用"列出检查项库"模式核对，它会标出哪些被门禁引用、哪些没有）。

**4 项不在执行器职责内（`external`）**，另有 **1 项有条件 skip**：

| 检查项 | 结果 | 为什么 |
|---|---|---|
| `lint-passthrough` | **`external`** | 静态检查需按项目自己的配置执行。执行器不跑任意命令、不假设项目的构建工具 |
| `unit-coverage-report` | **`external`** | 需项目侧生成覆盖率报告，格式因工具而异，无稳定约定 |
| `fn-coverage-prototype` | **`external`** | 未配置原型工程仓时（**原型由需求方外部提供**是合法情形），无常 `data-fn` 标记可扫 |
| `data-fn-markers` | **`external`** | 同上 |
| `secrets-externalized` | **项目仓未挂载时 `skip`** | 有代码仓时正常校验，不是"永远查不了" |

前四项原先挂 `skip`，卡死了两道门禁（见上文第五条语义）：
`lint-passthrough` 让 **gate-04** 每次都得豁免；`fn-coverage-prototype` 让 **gate-02** 彻底走不通
（它是 `waivable: no`，连豁免都不许）。现在它们是 `external`：
**可以签核，但必须用 `--evidence` 说明依据在哪**——比原来更麻烦，
但那是它们该有的位置：不是"查不了"，是"不归执行器查，得由人查并留痕"。

**另有一组检查项的准确性取决于产出物的格式约定**——`testcase-executed`、`p0p1-closed`、
`rollout-plan-present`、`regression-scoped` 解析测试报告、缺陷台账与交付类产出物。
格式约定写在各 Skill 的产出契约里并标注了「不可改」；字段名一改，检查项只会报"无法解析"，
于是"用例都跑完了吗""P0/P1 都关闭了吗"又回到了"靠人说"的状态。

**这类明确说"我查不了，需要你做 X"是有意保留的**：执行器宁可如实说查不了，也不猜一个结论。

> 关于验证：执行器的拦截行为在开发期用夹具逐条验证过（通过路径 + 失败路径），
> 但**仓库内没有保留这些夹具**，所以这个说法现在不可复核。
> 要让它可信，需要把夹具入库并纳入常规验证；在那之前，请以实际运行为准。
