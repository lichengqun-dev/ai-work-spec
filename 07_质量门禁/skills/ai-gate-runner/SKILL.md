# ai-gate-runner · 门禁执行

## 能力声明

统一的门禁执行器。读取 `07_质量门禁/gates/*.md` 的定义，执行其中标注 `auto:<检查项 ID>` 的检查项，
把结果写回批次状态文件。

**纯脚本，不调用模型。** 门禁结论必须可复现、可 diff、可审计——这些性质与"让模型判断一下"互斥。

实现是 `scripts/gate_run.py`，参数说明见脚本自身的 docstring——**使用者不需要记参数**。
依赖 Python 3.8+ 与 PyYAML。结果只有三种（对应脚本退出码 `0` / `1` / `2`）：
**通过**（`passed` / `waived`） ｜ **未通过或待人工确认**（`failed` / `pending_manual`） ｜
**执行器自身错误（含拒绝执行）**。第三种不是"检查没做"，是"这道门禁根本没跑起来"。

**不做什么**：不自动修复、不替人判断人工项、不自动豁免、不改门禁定义——见「边界」。

## 何时用 / 何时不用

- **用**：进入下一阶段前；用户说"跑门禁""检查一下能不能进下一步""归档前校验"；
  用户人工核对完了要签核；用户确实要带风险上线要豁免
- **不用**：要修的是项目代码或文档（本 Skill 只报告，不修复）；
  要改的是门禁定义本身（先读 `references/门禁格式约定.md`，改完再跑门禁）
- 不确定批次号就查 `projects/<项目码>/.agent/state/`；不确定门禁 id 就用"按顺序跑"那个模式

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 门禁定义 | `07_质量门禁/gates/gate-*.md` | 是 | 元信息含 `stage`/`blocking`/`auto_check`/`waivable`；检查项表格可解析 |
| 批次状态文件 | `projects/<项目码>/.agent/state/<批次号>.yaml` | 是 | 含 `steps` 与 `artifacts`；`current_step` 必须在 `steps` 中 |
| 项目 manifest | `projects/<项目码>/.agent/project.yaml` | 是 | `repo` 字段指向项目文档仓或代码仓（未填则相关检查项记 skip） |
| 功能编号总表 | `projects/<项目码>/.agent/index/功能编号总表.md` | 是 | 断链与覆盖率检查依赖它 |
| 上一道门禁状态 | 同一批次状态文件 | 是 | 必须为 `passed` / `waived`，否则拒绝执行 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 门禁结果 | 批次状态文件 `gates[]` | status / at / by / note / checks / manual_pending / block_skip / external_pending / external_evidence |
| 豁免记录 | 批次状态文件 `waivers[]` | gate / reason / approved_by / at / review_at |
| 执行日志 | `projects/<项目码>/.agent/logs/<批次号>.jsonl` | 每次执行追加一行 JSON |

## 前置条件

**hard（不满足则拒绝执行）**

- 门禁定义文件可解析，且**每个 `auto:` 引用的检查项都已实现**——引用到未实现的检查项时，
  整道门禁拒绝执行，而不是跳过那一项
- 批次状态文件存在，`current_step` 在 `steps` 中
- **上一道门禁为 `passed` / `waived`**（门禁不允许跳步）
- `--confirm` / `--waive` 必须提供 `--by`；`--waive` 还必须提供 `--reason` 与 `--expires`
- 目标门禁的 `waivable` 不为 `no`
- 输入契约中标注「必需」的各项存在（门禁定义、批次状态文件、项目 manifest、功能编号总表）

**soft**

- 无。纯脚本 Skill，不依赖批次进度，任何时刻都可单独运行

## 执行步骤

1. 判断用户要做什么，并**把用户意图翻译成脚本要的参数**：

   | 用户说的 | 本 Skill 的行为（= 该给脚本什么） |
   |---|---|
   | 点名了一道门禁（"跑 gate-03"） | **执行那一道**，写回批次状态文件 |
   | "全过一遍""按顺序跑" | **依次执行**全部门禁，跑到第一个未通过为止 |
   | "只看结果，别改状态"（CI 场景） | **只校验**，不回写 |
   | "我核对完了，签核通过" | **签核通过**（须提供用户给的真实人名） |
   | "这次带风险上线" | **豁免**（须提供人名、原因、复查日期） |
   | "有哪些检查项" | **列出检查项库与实现状态** |

   参数写法见脚本自身的 docstring——**不需要向用户展示参数，更不要教他记参数。**
   调用本 Skill 的意图本身已经足够。
2. 执行 `scripts/gate_run.py`，把结果写回批次状态文件
3. **逐条读出脚本输出，不要总结成"已完成"。** 输出里有五类信息，都要如实转达：

   1. **自动检查结果**：`✅ pass` / `❌ fail` / `⏭️ skip` / `🔧 external`
      - `fail` 要把明细原文读出来（脚本已经给出了具体对象，如"缺失 FN-XXX-045"）
      - `skip` 要把"要做什么才能自动校验"这句话一起读出来——**skip 不是通过**
      - `external` 要**把"这件事归谁做、人该做什么"读出来**——它也不是通过，
        但和 skip 不同：**补材料没用**，必须人在执行器之外做完
   2. **需人工核对的清单**：原样列出。**不要替用户判断这些项过不过**——
      这是执行器刻意留给人的，你替人拍板会让门禁失去意义，而且没人知道它其实没被真正检查过
   3. **结果状态**：
      - `failed` → 明确说"不可进入下一阶段"，并给出修正方向
      - `pending_manual` → 说明还差人工确认，把执行器输出的核对清单与签核方式一并转达
      - `passed` / `waived` → 说明可以继续
   4. **执行器自身错误**（拒绝执行）不是"检查没做"，是"这道门禁根本没跑起来"，
      **绝不能算作通过**。它一定会说明原因，原样转达
   5. **`skip` 与 `external` 的区别不要讲混。** 一句话版本：
      **skip 是"缺材料"（补了就能自动查），external 是"不归它查"（得人做完并留证据）。**
      讲混了会让用户去补一堆永远补不齐的材料
4. **用户要求"签核通过"时：不要自己替用户签核。** 先确认：

   - 人工核对的那几项，用户是否**真的核对过了**？如果用户只是说"差不多行吧"，
     提醒他这些项的实际含义，让他给出明确结论
   - **有没有 BLOCK 项是 `skip` 的？** 如果有，签核会被执行器**拒绝**。
     这不是障碍，是设计：签核的前提是「有人核对过了」，而材料不存在时无从核对。
     此时应引导用户补齐材料后重跑，或走豁免（须给人名 / 原因 / 复查日期）

     典型场景：项目仓不是 git 仓库 → `commit-format`（BLOCK）skip。
     在零提交的情况下「签核通过」，等于承认一次没有任何提交的代码通过了代码评审。

   - **有没有 `external` 项（🔧）？** 有的话签核**必须附证据**（`--evidence`），否则执行器会拒绝。
     这时候要问用户一个具体问题：**"lint 结果 / 覆盖率报告记在哪个文件？"**
     ——不要接受"跑过了"这种回答。不要求证据的话，它跟没查是一样的。

   确认后再让脚本执行签核，并带上**用户提供的真实人名**（以及 external 项的证据说明）。

   **人名必须是真实的。** 门禁记录要能回答"谁在什么时候确认的"，填 `auto`、`admin` 之类等于没留痕。
5. **用户要求"豁免"时**：豁免不是"放行"，是**在留痕的前提下带风险上线**。要求用户提供三样东西：

   | 要什么 | 要求 |
   |---|---|
   | 原因 | 具体原因。反例："赶工期"；正例："客户要求当日上线，契约变更待下个批次补" |
   | 批准人 | 真实姓名 |
   | 复查日期 | `YYYY-MM-DD`。**执行器会校验**：必须晚于今天、且在 **90 天**以内。填很远的日期（如 9999-12-31）会被直接拒绝——那等于把"临时豁免"变成"永久遗忘" |

   如果目标是 `waivable: no` 的门禁（gate-02 / gate-06），**执行器会拒绝并说明理由**。
   此时不要试图绕过，向用户解释：这道门禁守着一个跳过就无法补救的东西
   （gate-02 是需求理解的唯一验证点，gate-06 是追溯链的完整性）。

### 不能破的语义

**一、找不到检查项实现 → 整道门禁拒绝执行。**
静默跳过等于门禁失效，而失效的门禁比没有门禁更糟——它让人以为已经检查过了。

**二、`skip` 不等于 `pass`。**
缺少校验材料时记为 `skip`，转入人工确认，并说明"要做什么才能自动校验"。
把"没法校验"当成"校验通过"，是门禁最容易失效的方式。

**三、不代替人做判断。**
标注 `人` 的检查项原样列出等人工核对；门禁不会自动变成 `passed`，需要 `--confirm --by <名字>` 显式签核。
不是能力不足，而是**责任必须有人承担**。

**四、BLOCK 级 skip 不能用签核越过。**
签核的前提是「有人核对过了」；材料根本不存在时（无代码仓、无测试报告）无从核对。
这类项只能走 `--waive`（带批准人与复查期），不能走 `--confirm`。
否则门禁记录会显示「已通过」，而它其实什么都没查——这比没有门禁更糟。

## 独立执行

纯脚本 Skill，不依赖批次状态：**任何时刻都可单独运行**。
最安全的单独执行形态是"只校验、不回写状态"（CI 场景那个模式）——它在任何仓库状态下都不会改动任何东西。
（门禁自身的前置条件仍然生效：引用到未实现的检查项、或上一道门禁未通过时，执行器会拒绝执行并说明原因。）

## 边界（明确不做）

- **不自动修复。** 检查失败只报告，不改代码或文档——否则门禁会变成"自动掩盖问题的工具"
- **不要修改项目代码或文档来消除失败项**——那会让门禁变成掩盖问题的工具。只报告，不修复
- 不代替人做 `人` 项的判断，只负责把清单摆出来
- 不自动豁免。豁免必须由人显式提供批准人与复查日期
- **不把 `skip` 说成通过**
- **不为让门禁通过而改门禁定义、改状态文件或放宽检查项。** 门禁的价值全部来自"它说了真话"
- 不修改门禁定义文件
- 不调用模型
- 不执行 git 操作

## 失败处理

门禁结果的处置：

| 失败情形 | 处理 |
|---|---|
| BLOCK 项 `fail` | 门禁置 `failed`，输出明细与定位，不可进入下一阶段 |
| WARN 项 `fail` | 记入待办，门禁可继续（状态为 `pending_manual`） |
| 存在 `人` 项或 `skip` 项 | 门禁置 `pending_manual`，输出人工清单与签核命令 |
| BLOCK 项 skip 且用户要求签核 | **拒绝签核**，说明需补齐材料或改用豁免（状态保持 `pending_manual`） |
| 检查项抛异常 | 记为 `fail` 并附异常信息——**不允许把异常当成通过** |
| 门禁定义格式错误 | 拒绝执行（不跳过无法解析的检查项） |
| 上一道门禁未通过 | 拒绝执行，提示先完成上一道 |

执行器报错与正确应对：

| 输出 | 含义 | 正确应对 |
|---|---|---|
| `引用了未实现的检查项` | 门禁定义里的 `auto:<id>` 在执行器里不存在 | 用"列出检查项库"那个模式核对；改门禁定义或补实现。**不要**私自从定义里删掉那一项 |
| `上一道 gate-0X 的状态为 pending` | 门禁不允许跳步 | 先完成上一道。**不要**绕过顺序硬跑后面的 |
| `repo 未填或路径不存在` | 项目 manifest 的 `repo` 是占位值 | 填上项目文档仓/代码仓路径，或接受相关检查项记 `skip` 并人工确认 |
| `批次状态文件 ... current_step 不在 steps 中` | 状态文件不完整 | 让上游 Skill 修正状态文件；不要手工改数字蒙过去 |
| `产出物哈希与登记值不一致` | 产出物在确认后被改过 | 查是谁改的、改了什么，再决定是否重跑上游 |

## 已知限制

- **4 个检查项不在执行器职责内（`external`）**：静态检查、单元覆盖率、原型 FN 覆盖、`data-fn` 标记统计。
  前两个执行器不跑命令、不解析五花八门的覆盖率格式；后两个在**原型由需求方外部提供**时无从扫描
  （那是合法情形，不是配置疏漏）。四项都**补材料没用**，必须由人核对并用 `--evidence` 交代依据。
  另 **1 个有条件 skip**（密钥扫描：项目仓未挂载时，补上路径即可自动校验）。
  四态语义与判据见 `references/检查项清单.md` §八 / §十。
- **豁免的"到期自动复查"未实现。** 复查日期会被记录（且受 90 天上限约束），
  但没有任何代码会在到期时提醒。现阶段豁免的复查靠人记。
- `repo` 是兜底字段；文档仓 / 原型仓 / 代码仓分离时用 `docs_repo` / `prototype_repo` / `code_repo` 分别指定，
  否则原型覆盖率、密钥扫描、提交检查会互相污染（详见 `references/检查项清单.md`）
- `openapi-valid` 只做结构校验，完整规范校验建议在 CI 中追加 `@redocly/cli lint`
- `fn-coverage-design` 是"FN 出现在设计类产出物中"的**下限**检查；
  更严格的"每个 FN 有专属小节"由 `fn-design-section`（WARN）承担，分两级是为了避免误报阻断交付
