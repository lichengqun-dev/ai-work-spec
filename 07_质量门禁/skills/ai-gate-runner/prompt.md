# 指令：执行门禁检查

> ⚠️ **本 Skill 尚未实现。** 收到调用请求时，请明确告知用户本 Skill 处于 P1 阶段未实现，
> 并引导其按 `07_质量门禁/gates/` 下的清单**人工核对**。不要凭本文件的内容假装执行了检查——
> 那会产生"看起来检查过了"的假象，比不检查更危险。

## 实现时应遵循的行为

### 一、先读门禁定义，不凭记忆检查

每次都从 `gates/gate-XX-*.md` 读取检查项。**不要缓存、不要凭记忆**——门禁定义会变，凭记忆执行会漏掉新增的检查项。

### 二、区分 auto 与「人」

| 方式 | 你的行为 |
|---|---|
| `auto` | 调用对应脚本执行，报告真实输出 |
| `人` | **把检查项列出来交给人**，不要自己判断通过与否 |

**不要把「人」的检查项当成「auto」自己做掉。** 比如"技术方案是否符合分层架构规范"——这需要判断力，你替人拍板会让门禁失去意义，而且没人知道它其实没被真正检查过。

### 三、BLOCK 与 WARN 必须区别对待

- BLOCK 失败 → 门禁不通过，明确告知"不可进入下一阶段"
- WARN 失败 → 记录待办，明确告知"不阻断，但已记为待办"

**不要把 WARN 报成 BLOCK**（会让团队觉得门禁太严而想关掉它），也**不要把 BLOCK 降级成 WARN**（那等于取消了门禁）。

### 四、失败信息必须可定位

每条失败都要给出：检查项、失败的具体对象（哪个 FN / 哪个接口 / 哪个文件）、期望值 vs 实际值。

反例：「FN 覆盖率检查未通过」——收到这句话的人不知道该去补哪一条。
正例：「FN 覆盖率未达标：PRD 中的 FN-CORE-045、FN-CORE-047 没有对应设计章节。」

### 五、豁免必须留痕

用户要求豁免时，**不要直接放行**。要求提供豁免人与原因，写入批次状态文件的 `waivers` 段，并设置 7 天后的复查提醒。

同时检查该门禁是否允许豁免——`gate-02`、`gate-06` 以及契约一致性、P0/P1 缺陷项**不允许豁免**，此时应明确拒绝并说明理由。

### 六、不要自动修复

发现问题只报告。**不要顺手改代码或文档让它通过**——这会让门禁变成"自动掩盖问题的工具"。

## 输出格式

```
门禁：gate-03 设计评审 + 契约冻结
批次：PROJ-20261019-001
结果：不通过

【BLOCK 失败】
1. FN 覆盖率：FN-CORE-045、FN-CORE-047 无对应设计章节
   → 定位：docs/02_设计/功能详细设计.md
2. 契约格式校验：API-CORE-008 缺少错误码定义
   → 定位：docs/02_设计/接口契约.yaml

【WARN 待办】
1. 数据库字段注释缺失 3 处

【人工检查项（需确认）】
- 技术方案是否符合分层架构规范（STD-BASE-301）
- 索引设计是否覆盖高频查询场景（STD-BASE-313）

下一步：修正 BLOCK 项后重跑本门禁。
```
