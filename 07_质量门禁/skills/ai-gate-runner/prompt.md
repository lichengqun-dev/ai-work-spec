# 指令：执行门禁检查

## 你要做的事

当用户要求"跑门禁""检查一下能不能进下一步""归档前校验"时，
**执行本 Skill 的实现脚本**（位于本 Skill 目录下的 `scripts/gate_run.py`），
把用户意图翻译成脚本要的参数：

| 用户说的 | 该给脚本什么 |
|---|---|
| 点名了一道门禁（"跑 gate-03"） | 执行那一道 |
| "全过一遍""按顺序跑" | 依次执行，跑到第一个未通过为止 |
| "只看结果，别改状态"（CI 场景） | 只校验，不回写 |
| "我核对完了，签核通过" | 带上用户给的真实人名，签核 |
| "这次带风险上线" | 带上人名、原因、复查日期，豁免 |
| "有哪些检查项" | 列出检查项库与实现状态 |

参数写法见脚本自身的 docstring——**不需要向用户展示参数，更不要教他记参数。**
调用本 Skill 的意图本身已经足够。

不确定批次号就查 `projects/<项目码>/.agent/state/`；不确定门禁 id 就用"按顺序跑"那个模式。

## 执行后必须做的事

**逐条读出脚本输出，不要总结成"已完成"。** 输出里有五类信息，都要如实转达：

1. **自动检查结果**：`✅ pass` / `❌ fail` / `⏭️ skip` / `🔧 external`
   - `fail` 要把明细原文读出来（脚本已经给出了具体对象，如"缺失 FN-XXX-045"）
   - `skip` 要把"要做什么才能自动校验"这句话一起读出来——**skip 不是通过**
   - `external` 要**把"这件事归谁做、人该做什么"读出来**——它也不是通过，
     但和 skip 不同：**补材料没用**，必须人在执行器之外做完

2. **需人工核对的清单**：原样列出。**不要替用户判断这些项过不过**——
   这是执行器刻意留给人的，你替人拍板会让门禁失去意义，而且没人知道它其实没被真正检查过。

3. **结果状态**：
   - `failed` → 明确说"不可进入下一阶段"，并给出修正方向
   - `pending_manual` → 说明还差人工确认，把执行器输出的核对清单与签核方式一并转达
   - `passed` / `waived` → 说明可以继续

4. **执行器自身错误**（拒绝执行）不是"检查没做"，是"这道门禁根本没跑起来"，
   **绝不能算作通过**。它一定会说明原因，原样转达。

5. **`skip` 与 `external` 的区别不要讲混。** 一句话版本：
   **skip 是"缺材料"（补了就能自动查），external 是"不归它查"（得人做完并留证据）。**
   讲混了会让用户去补一堆永远补不齐的材料。

## 用户要求"签核通过"时

**不要自己替用户签核。** 先确认：

- 人工核对的那几项，用户是否**真的核对过了**？如果用户只是说"差不多行吧"，提醒他这些项的实际含义，让他给出明确结论
- **有没有 BLOCK 项是 `skip` 的？** 如果有，签核会被执行器**拒绝**。
  这不是障碍，是设计：签核的前提是「有人核对过了」，而材料不存在时无从核对。
  此时应引导用户补齐材料后重跑，或走豁免（须给人名 / 原因 / 复查日期）

  典型场景：项目仓不是 git 仓库 → `commit-format`（BLOCK）skip。
  在零提交的情况下「签核通过」，等于承认一次没有任何提交的代码通过了代码评审。

- **有没有 `external` 项（🔧）？** 有的话签核**必须附证据**（`--evidence`），否则执行器会拒绝。
  这时候要问用户一个具体问题：**"lint 结果 / 覆盖率报告记在哪个文件？"**
  ——不要接受"跑过了"这种回答。不要求证据的话，它跟没查是一样的。

确认后再让脚本执行签核，并带上**用户提供的真实人名**（以及 external 项的证据说明）。

**人名必须是真实的。** 门禁记录要能回答"谁在什么时候确认的"，填 `auto`、`admin` 之类等于没留痕。

## 用户要求"豁免"时

豁免不是"放行"，是**在留痕的前提下带风险上线**。要求用户提供三样东西：

| 要什么 | 要求 |
|---|---|
| 原因 | 具体原因。反例："赶工期"；正例："客户要求当日上线，契约变更待下个批次补" |
| 批准人 | 真实姓名 |
| 复查日期 | `YYYY-MM-DD`。**执行器会校验**：必须晚于今天、且在 **90 天**以内。填很远的日期（如 9999-12-31）会被直接拒绝——那等于把"临时豁免"变成"永久遗忘" |

如果目标是 `waivable: no` 的门禁（gate-02 / gate-06），**执行器会拒绝并说明理由**。
此时不要试图绕过，向用户解释：这道门禁守着一个跳过就无法补救的东西
（gate-02 是需求理解的唯一验证点，gate-06 是追溯链的完整性）。

## 常见错误与正确应对

| 输出 | 含义 | 正确应对 |
|---|---|---|
| `引用了未实现的检查项` | 门禁定义里的 `auto:<id>` 在执行器里不存在 | 用"列出检查项库"那个模式核对；改门禁定义或补实现。**不要**私自从定义里删掉那一项 |
| `上一道 gate-0X 的状态为 pending` | 门禁不允许跳步 | 先完成上一道。**不要**绕过顺序硬跑后面的 |
| `repo 未填或路径不存在` | 项目 manifest 的 `repo` 是占位值 | 填上项目文档仓/代码仓路径，或接受相关检查项记 `skip` 并人工确认 |
| `批次状态文件 ... current_step 不在 steps 中` | 状态文件不完整 | 让上游 Skill 修正状态文件；不要手工改数字蒙过去 |
| `产出物哈希与登记值不一致` | 产出物在确认后被改过 | 查是谁改的、改了什么，再决定是否重跑上游 |

## 你绝对不要做的事

- **不要替人判断 `人` 标注的检查项。**
- **不要把 `skip` 说成通过。**
- **不要为让门禁通过而改门禁定义、改状态文件或放宽检查项。** 门禁的价值全部来自"它说了真话"。
- **不要修改项目代码或文档来消除失败项**——那会让门禁变成掩盖问题的工具。只报告，不修复。
- **不要执行 git 操作。**

```
门禁：gate-03 设计评审 + 契约冻结
批次：PROJ-20261020-001
结果：failed

【自动检查】
✅ [1] FN 覆盖率
❌ [5] 数据库设计包含 DDL 与回滚脚本 —— 有 DDL 但未见回滚方案，要求补齐
⏭️  [9] 编码静态检查 —— skip（需在项目仓执行 lint）

【需人工核对】3 项，执行器不替你拍板
- [8] 是否引入新的中间件或第三方依赖
- [10] 技术方案符合分层架构规范
- [11] 索引设计覆盖高频查询场景

下一步：修正第 5 项（补回滚脚本）后重跑本门禁。
```
