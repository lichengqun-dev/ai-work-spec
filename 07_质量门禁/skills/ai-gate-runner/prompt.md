# 指令：执行门禁检查

## 你要做的事

当用户要求"跑门禁""检查一下能不能进下一步""归档前校验"时，执行：

```bash
S=07_质量门禁/skills/ai-gate-runner/scripts/gate_run.py
python3 $S --project <项目码> --batch <批次号> --gate <门禁 id>
```

不确定批次号就查 `.ai/state/`；不确定门禁 id 用 `--all`（按顺序跑到第一个未通过）。

## 执行后必须做的事

**逐条读出脚本输出，不要总结成"已完成"。** 输出里有四类信息，都要如实转达：

1. **自动检查结果**：`✅ pass` / `❌ fail` / `⏭️ skip`
   - `fail` 要把明细原文读出来（脚本已经给出了具体对象，如"缺失 FN-XXX-045"）
   - `skip` 要把"要做什么才能自动校验"这句话一起读出来——**skip 不是通过**

2. **需人工核对的清单**：原样列出。**不要替用户判断这些项过不过**——
   这是执行器刻意留给人的，你替人拍板会让门禁失去意义，而且没人知道它其实没被真正检查过。

3. **结果状态**：
   - `failed` → 明确说"不可进入下一阶段"，并给出修正方向
   - `pending_manual` → 说明还差人工确认，给出签核命令（脚本已输出）
   - `passed` / `waived` → 说明可以继续

4. **退出码**：`1` 和 `2` 都不是成功，不要当成通过。

## 用户要求"签核通过"时

**不要直接执行 `--confirm`。** 先确认：

- 人工核对的那几项，用户是否**真的核对过了**？如果用户只是说"差不多行吧"，提醒他这些项的实际含义，让他给出明确结论
- **有没有 BLOCK 项是 `skip` 的？** 如果有，`--confirm` 会被执行器**拒绝**。
  这不是障碍，是设计：签核的前提是「有人核对过了」，而材料不存在时无从核对。
  此时应引导用户走 `--waive`（带 `--by` / `--reason` / `--expires`），或补齐材料后重跑

  典型场景：项目仓不是 git 仓库 → `commit-format`（BLOCK）skip。
  在零提交的情况下「签核通过」，等于承认一次没有任何提交的代码通过了代码评审。

确认后再执行：

```bash
python3 $S --project <项目码> --batch <批次号> --gate <门禁 id> --confirm --by <用户提供的名字>
```

**`--by` 必须是真实的人名。** 门禁记录要能回答"谁在什么时候确认的"，填 `auto`、`admin` 之类等于没留痕。

## 用户要求"豁免"时

豁免不是"放行"，是**在留痕的前提下带风险上线**。要求用户提供三样东西：

| 参数 | 要求 |
|---|---|
| `--reason` | 具体原因。反例："赶工期"；正例："客户要求当日上线，契约变更待下个批次补" |
| `--by` | 批准人姓名 |
| `--expires` | 复查日期 `YYYY-MM-DD`。**不允许填很远**（如 9999-12-31）——那等于没填 |

如果目标是 `waivable: no` 的门禁（gate-02 / gate-06），**执行器会拒绝并说明理由**。
此时不要试图绕过，向用户解释：这道门禁守着一个跳过就无法补救的东西
（gate-02 是需求理解的唯一验证点，gate-06 是追溯链的完整性）。

## 常见错误与正确应对

| 输出 | 含义 | 正确应对 |
|---|---|---|
| `引用了未实现的检查项` | 门禁定义里的 `auto:<id>` 在执行器里不存在 | 用 `--list-checks` 核对；改门禁定义或补实现。**不要**私自从定义里删掉那一项 |
| `上一道 gate-0X 的状态为 pending` | 门禁不允许跳步 | 先完成上一道。不要用 `--gate` 硬跑后面的 |
| `repo 未填或路径不存在` | 项目 manifest 的 `repo` 是占位值 | 填上项目文档仓/代码仓路径，或接受相关检查项记 `skip` 并人工确认 |
| `批次状态文件 ... current_step 不在 steps 中` | 状态文件不完整 | 让上游 Skill 修正状态文件；不要手工改数字蒙过去 |
| `产出物哈希与登记值不一致` | 产出物在确认后被改过 | 查是谁改的、改了什么，再决定是否重跑上游 |

## 你绝对不要做的事

- **不要替人判断 `人` 标注的检查项。**
- **不要把 `skip` 说成通过。**
- **不要为让门禁通过而改门禁定义、改状态文件或放宽检查项。** 门禁的价值全部来自"它说了真话"。
- **不要修改项目代码或文档来消除失败项**——那会让门禁变成掩盖问题的工具。只报告，不修复。
- **不要执行 git 操作。**

```
门禁：gate-03 设计评审 + 契约冻结
批次：PROJ-20261020-001
结果：failed

【自动检查】
✅ [1] FN 覆盖率
❌ [5] 数据库设计包含 DDL 与回滚脚本 —— 有 DDL 但未见回滚方案，要求补齐
⏭️  [9] 编码静态检查 —— skip（需在项目仓执行 lint）

【需人工核对】3 项，执行器不替你拍板
- [8] 是否引入新的中间件或第三方依赖
- [10] 技术方案符合分层架构规范
- [11] 索引设计覆盖高频查询场景

下一步：修正第 5 项（补回滚脚本）后重跑本门禁。
```
