# 门禁格式约定

> 新增或修改门禁定义时**必读**。改了格式执行器就解析不了——这是唯一的硬约束。

## 一、文件位置与命名

```
07_质量门禁/gates/gate-<两位序号>-<名称>.md
```

文件名前缀 `gate-NN-` 直接决定门禁 id 与**执行顺序**（执行器按 id 排序）。**跳步保护靠这个顺序**：
执行 gate-NN 前会检查 gate-(NN-1) 的状态是否为 `passed` / `waived`。

新增门禁时不要插入序号中间（会让已有批次的记录对不上），追加到末尾。

## 二、文件结构

````markdown
# gate-03 设计评审 + 契约冻结          ← 第一行是标题，执行器从中取名称

```
stage: 02_概要详细设计                 ← 必填：本门禁属于哪个阶段
blocking: true                        ← 必填：是否阻断
auto_check: 是                        ← 必填：是否可自动执行
waivable: partial                     ← 必填：yes | no | partial
```

> （说明段）

## 入口条件（进入本门禁前的必要条件）

- [ ] ...                             ← 人读；执行器不解析这里

## 检查项

| # | 检查内容 | 方式 | 阻断级别 | 失败处理 |
|---|---|---|---|---|
| 1 | ... | auto:fn-coverage-design | BLOCK | ... |
| 9 | ... | 人 | BLOCK | ... |

## 方式说明
## 通过标准
## 豁免机制
````

**元信息块必须是文件里第一个 ``` 围栏**，字段名固定。执行器缺任一字段就报错退出。

### `waivable` 的取值

| 值 | 含义 | 执行器的行为 |
|---|---|---|
| `yes` | 允许豁免 | 正常记录豁免 |
| `partial` | 部分可豁免 | 允许豁免，但打印提醒 |
| `no` | 不允许豁免 | **拒绝豁免请求** |

`no` 只用在该门禁守着"跳过就无法补救"的东西时——目前是 gate-02（需求理解的唯一验证点）
与 gate-06（追溯链完整性）。**不要滥用 `no`**：门禁全是死结时，团队会整体关掉它们。

## 三、检查项表格

必须五列，`方式` 列只允许两种取值：

| 取值 | 含义 |
|---|---|
| `auto:<检查项 ID>` | 脚本自动校验。ID 必须在执行器的检查项库里存在 |
| `人` | 人工核对。执行器只列出清单 |

`阻断级别` 只允许 `BLOCK` 或 `WARN`。

**加检查项的规则**：

1. 先问"这件事能不能写成脚本"——能写的一律 `auto`，因为人工检查会随时间推移变成走过场
2. 写出检查项 ID，在 `scripts/gate_run.py` 里用 `@check("<id>", "<描述>")` 注册实现
3. **ID 一旦被门禁引用就不要再改名**——改了会让历史批次的 `checks` 记录对不上
4. 跑 `--list-checks` 确认没有"被引用但未实现"的项
5. 用真实夹具验证一遍：既验证通过路径，也验证失败路径

**不要写没有实现的 `auto:<id>`。** 执行器会拒绝执行整道门禁——这是刻意的，
因为静默跳过等于门禁失效，而失效的门禁比没有门禁更糟。

## 四、BLOCK 还是 WARN

判据是**误报的代价**：

| 情况 | 用 |
|---|---|
| 客观可判定，误报几乎不可能（编号缺失、文件不存在、哈希不一致） | `BLOCK` |
| 启发式判断，可能漏判或误判（验收标准是否"可量化"、FN 是否有"专属小节"） | `WARN` |
| 涉及安全红线（硬编码凭据） | `BLOCK`，但扫描口径要收窄以避免误报 |

**误报阻断交付的代价远大于漏放一项。** 一次错误阻断就会让团队开始要求关掉门禁，
而门禁一旦被关掉，所有检查项一起失效。

## 五、为什么门禁不能全自动

执行器**不会**自己把门禁置为 `passed`。自动校验全通过、且没有 `人` 项与 `skip` 项时才自动通过；
否则置为 `pending_manual`，要求 `--confirm --by <名字>` 显式签核。

原因不是 AI 能力不足，而是**责任必须有人承担**——门禁记录要能回答"谁在什么时候确认的"。

## 六、修改已有门禁时的注意

| 改动 | 影响 |
|---|---|
| 加/删检查项 | 安全。历史批次的 `checks` 记录保留原样 |
| 改检查项 ID | ⚠️ 历史记录对不上。**不要做** |
| 改 `waivable` | 谨慎：从 `no` 改 `yes` 等于给某道门禁开了口子，需要在设计文档里说明理由 |
| 改文件名里的序号 | ⚠️ 会改变执行顺序，破坏跳步保护与历史记录。**不要做** |
| 改门禁含义但保留 id | 需要提升版本并在批次状态里留痕，否则"当时为什么通过"无法回答 |
