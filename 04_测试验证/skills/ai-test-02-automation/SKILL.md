# ai-test-02-automation · 接口自动化脚本生成

## 能力声明

从**冻结的 OpenAPI 契约**生成接口自动化测试脚本，并覆盖契约声明的每个错误码。

**契约的规范程度直接决定自动化覆盖率。** 契约里写了 `x-fn-id` 与错误响应，脚本就能自动生成；
没写就只能手工补——这是"契约写得细"的实际收益之一。

**不做什么**：不自动化 UI / E2E 测试、不执行脚本（`ai-test-03-execute`）、不修实现代码、
不改契约——见「边界」。

## 何时用 / 何时不用

- **用**：测试用例已产出，要把契约里每个 operation 与每个错误码落成可执行的接口脚本时
- **不用**：自动化 UI / E2E（那需要稳定的选择器与测试数据管理，是独立工作）；执行脚本并登记结果（`ai-test-03-execute`）
- **契约信息不足时**：仍走本 Skill，但按「契约信息不足时」的处理分档报告，**不生成"差不多的脚本"**

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 接口契约 | `ai-design-04-api` 产出 | 是 | 冻结态；每 operation 带 `responses` |
| 测试用例 | `ai-test-01-cases` 产出 | 是 | 编号挂载到 FN |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 测试框架与断言风格从这里读 |
| 测试环境信息 | 项目文档仓 | 是 | 环境地址与账号（**不写入脚本，走配置**） |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 自动化脚本 | 项目代码仓 | 接口级测试，用例编号与 `TC` 对应 |
| 覆盖率说明 | 项目文档仓 `<需求名>/04_测试/自动化覆盖说明.md` | 哪些契约 operation 已自动化、哪些需人工 |

产出结构：

```markdown
# 自动化覆盖说明

| operation | 对应 TC | 状态 |
|---|---|---|
| POST /api/v1/export | TC-FN-CORE-045-01 | 已自动化 |
| GET /api/v1/export/{id} | — | 需人工：契约缺 `responses` |

生成 24 个脚本
已执行验证：18 个（环境可达）
未验证：6 个 —— 测试环境 10:30 起不可达，脚本已生成但未跑通
```

**断言强度是这套脚本的唯一价值。** 自动化测试最容易退化成"跑一遍看有没有报错"——
这种脚本通过率高、价值接近于零：**它只能发现 500，发现不了返回了错误的 200**。

- 每条脚本至少断言 **HTTP 状态码、业务错误码、响应结构的关键字段** 三样
- 错误码用例要断言**具体的错误码**，不是"4xx 即可"

反例 / 正例与追溯链（`代码 diff → FN → TC → 脚本`）见 `references/断言强度与追溯链.md`。

## 前置条件

**hard（不满足则拒绝执行）**

- 契约处于**冻结态，且哈希与记录一致**
- 测试用例已产出（编号挂载到 FN）
- **能确定测试框架**：来自生效快照的 `test` 维度包或技术栈包；两者都没有时**向用户确认，不自行选择**
  （本仓库目前没有预置 `test` 维度包——这不是缺陷，测试框架约定通常写在技术栈包里）

**soft（不满足则提示，可继续）**

- 测试环境可达（不可达时照常产出脚本并标注「未验证」，**不谎报"已跑通"**）

## 执行步骤

1. 遍历契约，为每个 operation 生成基础脚本：正常路径 + **每个声明的错误码一条**
2. 把脚本与 `TC` 编号对应（**脚本可追溯到用例，用例可追溯到 FN**）
3. 参数组合与边界值从 `ai-test-01-cases` 的用例取，**不在此重复推导**
4. 环境信息与账号**从配置读取，不写进脚本**（符合 `STD-BASE-104`）
5. 产出覆盖说明：哪些 operation 已自动覆盖、哪些因契约信息不足需人工补
6. 回写批次状态文件：本步骤置 `done`，登记自动化脚本位置与覆盖说明

### 两件事分开做

| 来源 | 生成什么 |
|---|---|
| 契约 | 每个 operation 的基础脚本骨架：请求构造、**每个声明错误码一条** |
| 测试用例 | 参数组合、边界值、业务场景的具体取值 |

这样分工的理由：契约保证**接口层面**的覆盖完整（不会漏掉某个错误码），用例保证**业务层面**的覆盖完整。
两者都不做就会漏掉其中一面。

### 契约信息不足时

| 情况 | 处理 |
|---|---|
| operation 缺 `responses` | 标记"无法自动化"，说明原因。**不生成只调不断言的脚本** |
| operation 缺 `x-fn-id` | 报告——通常是设计阶段漏了标注；脚本无法挂载到用例 |
| 错误码只有 200 | 报告——没有错误响应就无法生成异常用例 |

**不要自己补一个 xxx 错误码**。契约是冻结的，脚本必须按契约来——如果契约缺了，
那说明 gate-03 有东西没查出来，值得回头看一眼。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不自动化 UI / E2E 测试**——那需要稳定的选择器与测试数据管理，是独立工作，不在本 Skill 内
- 不执行脚本（`ai-test-03-execute`）
- **不为了覆盖率而生成空脚本**（调用接口但不做断言）
- 不修实现代码
- 不改契约。契约信息不足以生成脚本时**报告并停止**
- 不要生成无断言的脚本凑覆盖率
- 不要把环境地址 / 账号写进脚本
- 不要自己给契约补错误码
- 不要谎报"已跑通"
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 契约某 operation 缺 `responses` | 该 operation 标记为"无法自动化"并说明原因，**不生成只调不断言的脚本** |
| 契约缺 `x-fn-id` | 对应脚本无法挂载到用例，报告——**这通常是设计阶段漏了标注** |
| 契约错误码只有 200 | 报告——没有错误响应就无法生成异常用例；不自行补错误码 |
| 测试环境不可用 | 生成脚本但标注「**未验证**」，**不谎报"已跑通"** |
| 无可用测试框架 | **拒绝执行**，提示先补齐（属工程骨架职责）；不自行选一套 |
