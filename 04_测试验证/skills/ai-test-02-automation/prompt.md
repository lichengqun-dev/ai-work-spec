# 指令：自动化测试脚本生成

## 开始前

读冻结契约、测试用例、生效快照中 `test` 维度的框架约定。

**没有可用的测试框架就停下。** 不知道用什么框架就不要自己选一套——那会变成团队里的"另一种写法"。

## 从契约生成骨架，从用例取细节

两件事分开：

| 来源 | 生成什么 |
|---|---|
| 契约 | 每个 operation 的基础脚本骨架：请求构造、**每个声明错误码一条** |
| 测试用例 | 参数组合、边界值、业务场景的具体取值 |

这样分工的理由：契约保证**接口层面**的覆盖完整（不会漏掉某个错误码），用例保证**业务层面**的覆盖完整。
两者都不做就会漏掉其中一面。

## 断言强度决定这套脚本有没有价值

自动化测试最容易退化成"跑一遍看有没有报错"。这种脚本通过率很高、价值接近于零——
**它只能发现 500，发现不了"返回了错误的 200"。**

```java
// ❌ 只调用不断言
client.post("/api/v1/export", req);

// ✅
ResponseEntity<ExportResp> resp = client.post("/api/v1/export", req);
assertEquals(HttpStatus.OK, resp.getStatusCode());
assertEquals(0, resp.getBody().getCode());
assertNotNull(resp.getBody().getData().getFileId());
```

**每条脚本至少断言三样**：HTTP 状态码、业务错误码、响应结构的关键字段。

错误码用例要断言**具体的错误码**，不是"4xx 即可"：

```java
// ❌
assertTrue(resp.getStatusCode().is4xxClientError());

// ✅
assertEquals(403, resp.getStatusCode().value());
assertEquals(40301, resp.getBody().getCode());   // 契约里声明的具体码
```

## 脚本必须能追溯到用例

每个脚本与 `TC` 编号对应，`TC` 又挂载到 `FN`。这样：

```
代码 diff → FN → TC → 脚本
```

这条链让 `ai-test-04-regression` 能自动圈定回归范围。断了就退化成"全量跑一遍"或"凭经验挑"。

## 环境信息不写进脚本

环境地址、账号、token 一律从配置读取。写进脚本会有两个后果：

1. `secrets-externalized` 检查项（BLOCK）会失败
2. 更实际的问题：脚本无法在不同环境跑

## 契约信息不足时

不要"生成一个差不多的脚本"。三种情况分开处理：

| 情况 | 处理 |
|---|---|
| operation 缺 `responses` | 标记"无法自动化"，说明原因。**不生成只调不断言的脚本** |
| operation 缺 `x-fn-id` | 报告——通常是设计阶段漏了标注；脚本无法挂载到用例 |
| 错误码只有 200 | 报告——没有错误响应就无法生成异常用例 |

**不要自己补一个 xxx 错误码**。契约是冻结的，脚本必须按契约来——如果契约缺了，
那说明 gate-03 有东西没查出来，值得回头看一眼。

## 测试环境不可用时

生成脚本，但标注"**未验证**"。**不要谎报"已跑通"。**

```
生成 24 个脚本
已执行验证：18 个（环境可达）
未验证：6 个 —— 测试环境 10:30 起不可达，脚本已生成但未跑通
```

## 完成后

回写批次状态文件：本步骤置 `done`，登记自动化脚本位置与覆盖说明。

## 你绝对不要做的事

- 不要生成无断言的脚本凑覆盖率
- 不要把环境地址 / 账号写进脚本
- 不要自己给契约补错误码
- 不要自动化 UI / E2E（独立工作，不在本 Skill 内）
- 不要谎报"已跑通"
- 不要执行 git 操作
