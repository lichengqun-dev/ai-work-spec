# 指令：测试报告与上线建议

## 结论放最前面

```
# 测试报告

## 一、结论
**不建议上线。** 依据：存在 1 个未关闭 P0 缺陷（导出产生错误行数），
且 3 条核心路径用例因第三方沙箱不可用而未执行。

## 二、执行概览
## 三、缺陷汇总
## 四、遗留风险
## 五、回归覆盖情况
## 六、附录（明细）
```

**最容易犯的错是把遗留风险写在最后。** 一份把风险埋在附录里的报告，
读者（往往是没时间细看的人）会直接看结论和通过率，然后决定上线。

结论必须在第一屏。

## 执行率必须可机械解析

两种写法任选，**字段名不能改**：

```markdown
用例执行率：100%
```

```markdown
| 项 | 值 |
|---|---|
| 用例执行率 | 100% |
```

gate-05 的 `testcase-executed` 检查项按这两种形式解析。改字段名它报"无法解析"——
那个告警是对的：**"用例都跑完了吗"这件事必须能被机械判定**，否则只能靠人说，而人说的会被打折。

## 数字不许美化

执行率 93% 就写 93%。通过率 84% 就写 84%。

美化有两个直接后果：

- `testcase-executed` 是 BLOCK 级检查项，真实数字会让门禁拦住你——**而它拦住是对的**
- 更实际的：上线后出问题时，没人能相信这份报告里的其他数字

## 缺陷汇总要把未关闭项顶到前面

```markdown
## 三、缺陷汇总

| 级别 | 总数 | 已关闭 | 未关闭 |
|---|---|---|---|
| P0 | 1 | 0 | **1** |
| P1 | 1 | 1 | 0 |
| P2 | 2 | 1 | 1 |
| P3 | 0 | 0 | 0 |

**未关闭的阻塞项**
- BUG-PROJ-20261020-001-001（P0）导出产生错误行数 —— 负责人张三，预计 10-21 修复
```

## 上线建议必须带条件

| 结论 | 条件 |
|---|---|
| 建议上线 | 执行率 100%、无未关闭 P0/P1、遗留风险已列明且可接受 |
| **有条件上线** | **必须写明具体条件与后续动作** |
| 不建议上线 | 有未关闭 P0/P1，或执行率缺口涉及核心路径 |

**"有条件上线"最容易写虚。** 反例："建议在注意风险的前提下上线"——
这句话没有任何信息量。正例："建议上线，条件：P2 缺陷 3 条转入下批次（已登记到快车道台账），
需在发布说明中标注；受限的 3 条第三方沙箱用例在沙箱恢复后 24 小时内补测。"

条件要能被验收：谁、在什么时候、做什么。

## 遗留风险要具体

| 反例 | 正例 |
|---|---|
| 存在少量未覆盖路径 | 3 条用例未执行（TC-FN-CORE-047-03~05），涉及第三方存储对接；沙箱不可用 |
| 性能待观察 | 未做压测；导出 1 万条在测试环境耗时 12 秒，生产数据量为 10 倍 |

## 存在未关闭的 P0/P1 时

**正常产出报告**，但上线建议必须是"不建议上线"，并列出未关闭项。

不要因为"负责人说今天能修好"就写成"建议上线"。修好了再跑一次门禁，
这份报告的价值恰恰在于它记录的是**当时的事实**。

## 完成后

回写批次状态文件：本步骤置 `done`，登记测试报告与哈希。

## 你绝对不要做的事

- 不要美化执行率或通过率
- 不要把遗留风险埋在报告末尾
- 不要写没有具体条件的"有条件上线"
- 不要在存在未关闭 P0/P1 时给"建议上线"
- 不要改「用例执行率」字段名
- 不要修缺陷或补测
- 不要执行 git 操作
