# 能力声明

从 **PRD + 接口契约 + 功能详细设计**三者生成测试用例。

三份输入缺一不可：PRD 提供业务场景与验收标准、契约提供参数组合与错误码、详细设计提供异常分支。
只从其中一份生成，会漏掉另外两个维度的问题。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| PRD | `ai-requirement-04-prd` 产出 | 是 | 每个功能有 `FN` 编号与验收要点 |
| 接口契约 | `ai-design-04-api` 产出 | 是 | 冻结态；每 operation 带 `x-fn-id` 与错误码 |
| 功能详细设计 | `ai-design-02-detail` 产出 | 是 | 每 FN 一节，含异常分支与边界 |
| 原型工程 | `ai-requirement-03-prototype` 产出 | 否 | 用于 UI 路径类用例 |
| 测试用例设计规范 | `04_测试验证/standards/测试用例设计规范.md` | 是 | 编号挂载规则、优先级 |
| 缺陷分级标准 | `04_测试验证/standards/缺陷分级标准.md` | 是 | 用于标注用例严重程度 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 测试用例 | 项目文档仓 `docs/04_测试/测试用例.md` | **编号格式 `TC-<FN编号>-<两位序号>`** |
| 用例登记 | `.ai/index/功能编号总表.md` 功能点段的「覆盖用例」列 | 回填 `TC` 编号 |

## 前置条件（不满足则拒绝执行）

- gate-04 已通过
- 契约处于冻结态，且哈希与记录一致
- 功能详细设计中每个 FN 都有异常分支章节（缺失时**拒绝**——异常分支是用例设计的主要输入）

## 执行步骤

1. 取本批次范围内全部 `FN`
2. **每个 FN 至少一条用例**（gate-05 的 `fn-has-testcase` 是 BLOCK 级）
3. 按三个来源分别推导：

   | 来源 | 推导什么 |
   |---|---|
   | PRD 验收要点 | 正常路径与验收判定 |
   | 契约 | 参数组合、边界值、每个错误码一条 |
   | 详细设计的异常分支 | 状态冲突、并发冲突、权限不足、数据为空 |

4. 编号 `TC-<FN编号>-<两位序号>`，两位序号在同一 FN 下递增
5. 每条用例写清：前置条件、步骤、**可判定的预期结果**
6. 回填编号总表的「覆盖用例」列
7. 回写批次状态文件

## 边界（明确不做）

- **不写自动化脚本**（那是 `ai-test-02-automation`）
- 不执行用例（`ai-test-03-execute`）
- 不修实现代码。用例与实现不符时**先确认是用例错了还是实现错了**，不要直接改用例迁就实现
- 不设计性能测试方案（那是另一类工作）

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 某 FN 的详细设计缺异常分支章节 | **拒绝执行**，回到 `ai-design-02-detail` 补齐——凭空想象异常分支会漏掉真实的分支 |
| 某 FN 找不到对应接口 | 列出——**通常意味着设计阶段漏了接口，或该 FN 不需要接口但设计没说清** |
| 验收要点不可判定 | 列出并记入待澄清，**不自行编造判定标准** |
| 契约哈希不一致 | 停止，报告契约被改动过 |

## 用例编号为什么必须挂载到 FN

`TC-FN-CORE-045-01` 而不是 `TC-001`。

| 挂载形式 | 能回答的问题 |
|---|---|
| `TC-FN-CORE-045-01` | 每个 FN 有多少用例覆盖？哪些 FN 没有用例？回归时该跑哪些？ |
| `TC-001` | 只有"一共有多少条用例" |

**功能覆盖率**（按 FN 统计）与**回归范围圈定**（`ai-test-04-regression`）都依赖这条挂载关系。
游离编号会让这两个机制同时失效。
