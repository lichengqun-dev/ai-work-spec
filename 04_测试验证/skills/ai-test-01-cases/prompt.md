# 指令：测试用例生成

## 开始前

读三份输入，**缺一不可**：

| 输入 | 提供什么 | 只读它一份会漏什么 |
|---|---|---|
| PRD | 业务场景、验收要点 | 漏掉参数组合与错误码 |
| 接口契约 | 参数定义、错误码、必填性 | 漏掉业务规则与异常流程 |
| 功能详细设计 | 异常分支、边界条件、状态流转 | 漏掉参数边界与接口层错误 |

**三份都读，然后交叉推导。** 只从 PRD 生成会得到一堆"能跑通就行"的用例。

## 编号必须挂载到 FN

```
TC-FN-CORE-045-01      ✅
TC-001                 ❌
导出测试1               ❌
```

格式 `TC-<FN编号>-<两位序号>`，两位序号在同一 FN 下递增。

**这不是命名偏好**，有两个机制依赖它：

- `fn-has-testcase` 检查项（gate-05 的 BLOCK 级）按 FN 统计覆盖
- `ai-test-04-regression` 圈定回归范围时，走的是 `代码 diff → FN → 用例集合`

游离编号会让这两个机制同时失效。

## 按三个来源推导

对每个 FN：

**从 PRD 验收要点** → 正常路径 + 验收判定用例

**从契约** → 每个参数组合、每个边界值、**每个错误码一条**。
契约里声明了 403/409 却没有对应用例，等于声明了不测。

**从详细设计的异常分支** → 状态冲突、并发冲突、权限不足、数据为空、数据量上限。

**详细设计里没写异常分支的 FN，拒绝执行并回到 `ai-design-02-detail`。**
凭空想象的异常分支会漏掉真实的分支——而异常分支正是缺陷最集中的地方。

## 每条用例的三个要素

```markdown
### TC-FN-CORE-045-01 正常导出

**前置**：存在 100 条未归档数据，当前用户有导出权限
**步骤**：
1. 打开列表页
2. 点击导出
3. 等待完成

**预期**：下载到 xlsx 文件；行数 = 100；列与页面列表一致；耗时 ≤ 30 秒
```

**预期结果必须可判定。** 反例：「页面正常显示」「导出成功」。

不可判定的预期结果使用例执行变成主观判断——不同人执行结果不同，也无法自动化。

## 覆盖检查

产出后自查：

- 每个 FN 都有用例吗？（gate-05 的 BLOCK 项）
- 契约里每个错误码都有对应用例吗？
- 详细设计里每条异常分支都有对应用例吗？

**第三条最容易漏。** 详细设计写了 5 条异常分支，用例里只覆盖了 2 条——这是"覆盖率高但漏测多"的典型形态。

## 用例与实现不符时

先确认是**用例错了**还是**实现错了**，不要直接改用例迁就实现。

改用例迁就实现，等于用手中的笔把缺陷擦掉。这种情况应该报告并停止，由人判断。

## 完成后

1. 回填 `.ai/index/功能编号总表.md` 功能点段的「覆盖用例」列
2. 回写批次状态文件：本步骤置 `done`，登记 `docs/03_测试/测试用例.md` 与哈希

## 你绝对不要做的事

- 不要写不挂载 FN 的游离编号
- 不要写不可判定的预期结果
- 不要只从 PRD 生成（会漏参数与错误码维度）
- 不要直接改用例迁就实现
- 不要写自动化脚本（那是 `ai-test-02-automation`）
- 不要执行 git 操作
