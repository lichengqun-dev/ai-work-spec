# ai-test-03-execute · 执行测试与缺陷登记

## 能力声明

执行测试用例、登记缺陷、给出真实结果。

**本 Skill 的核心纪律是"报告真实结果"**——这条纪律压过其他所有条。
测试环节一旦开始美化数据，整套质量机制就失去了唯一的输入源：门禁、度量、技术债识别
全部建立在"测试结果是真的"这个前提上。它倒了，后面所有东西都是空转。

具体表现：

- 环境不可用 → 说环境不可用，**不要说"先标记通过"**
- 不确定是用例问题还是实现问题 → **停下来问**，不要归类成前者（归类成用例问题会掩盖真实缺陷）
- 用例失败 → 记录失败，**不要改用例迁就实现**
- 覆盖率不够 → 说不够，不要用无断言的调用凑

**不做什么**：不修实现代码、不改测试用例使其通过、不写测试报告（那是 `ai-test-05-report`）——见「边界」。

## 何时用 / 何时不用

- **用**：用例集已产出（且通常已有自动化脚本），要跑出真实结果、登记缺陷时
- **不用**：写测试报告（`ai-test-05-report`）；修缺陷（开发职责）；补测用例（回到 `ai-test-01-cases`）
- **环境不可用时**：仍走本 Skill，但**拒绝执行**，不用"先记成通过，回头再补测"的方式推进

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 测试用例 | `ai-test-01-cases` 产出 | 是 | 编号挂载到 FN |
| 自动化脚本 | `ai-test-02-automation` 产出 | 否 | 存在则先跑，手工用例补充 |
| 缺陷分级标准 | 知识库根下 `04_测试验证/standards/缺陷分级标准.md` | 是 | 定级依据 |
| 测试环境 | 项目文档仓 | 是 | 环境信息从配置读，不写进脚本 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 缺陷台账 | 项目文档仓 `<需求名>/04_测试/缺陷台账.md` | 编号 `BUG-<批次号>-<三位>`，含级别与状态列 |
| 执行结果 | 项目文档仓 `<需求名>/04_测试/执行结果.md` | 每条用例的执行结论 |

**缺陷台账的表头固定为**：`| 编号 | 级别 | 描述 | 状态 | 发现时间 | 负责人 |`
状态取值：`待修复` / `修复中` / `已关闭` / `已转待办`。
**只有 `已关闭` 和 `已转待办` 算关闭**（后者需在描述里写明转待办的理由）。
gate-05 的 `p0p1-closed` 检查项按这个表头解析，**改了表头它会报"无法解析"**——
那不是检查项太死板，而是"存在 P0/P1 未关闭"这件事必须能被机械判定，否则门禁形同虚设。

产出结构：

```markdown
| 编号 | 级别 | 描述 | 状态 | 发现时间 | 负责人 |
|---|---|---|---|---|---|
| BUG-PROJ-20261020-001-007 | P1 | 导出偶发超时 | 待修复 | 2026-10-20 | 张三 |
```

## 前置条件

**hard（不满足则拒绝执行）**

- 测试用例已产出（编号挂载到 FN）
- **测试环境可用**（不可用时拒绝执行，不要"先记成通过，回头再补测"）

**soft（不满足则提示，可继续）**

- gate-04 已通过（未通过时产出物标注「未经上游确认 —— gate-04 未通过」）
- 自动化脚本已产出（缺则全部走手工，产出物标注覆盖来源）

## 执行步骤

1. **先跑自动化脚本**，保留脚本的真实输出：

   ```bash
   # 自动化脚本的真实输出要保留
   <项目测试命令>
   ```

   手工用例补充自动化覆盖不到的部分（业务场景、跨模块串联、UI 交互）。

2. 执行手工用例，逐条记录结论
3. 失败的用例登记为缺陷：编号 `BUG-<批次号>-<三位>`
4. **按 `STD-BASE-511` 定级**，定级有争议的标为"待裁决"，不由单方决定
5. **P0/P1 缺陷修复后必须补回归用例**（`STD-BASE-512`）
6. 回写批次状态文件：本步骤置 `done`，登记缺陷台账、执行结果与缺陷统计

### 定级按标准，不按感觉

| 级别 | 定义 | 典型 |
|---|---|---|
| P0 | 阻塞：核心功能不可用 / **数据错误** | 导出产生错误数据 |
| P1 | 严重：主流程受阻但有绕行 | 导出偶发失败 |
| P2 | 一般：非主流程异常 | 提示文案错误 |
| P3 | 轻微：文案、样式 | — |

两个常见的定级错误：

**把数据错误标成 P1。** 功能不可用会被立刻发现，数据错误不会——它会被带进生产，
影响面比"功能挂了"大得多。**数据错误一律 P0。**

**定级争议由单方决定。** 开发说 P2、测试说 P0 时，应由双方负责人共同裁决，
**不由任何一方自己拍板**。你可以把争议项标为"待裁决"并列出双方理由。

**定级随意会让分级机制失效**：全部标 P0 则 P0 不再意味着"必须马上修"；
全部标一般则没有东西会阻断上线。

### P0/P1 修复后必须补回归用例

`STD-BASE-512`：P0/P1 缺陷修复后必须补充对应的回归测试用例。

理由：缺陷修复只保证"这一次修好了"。同一模块的下一次改动很容易重新引入同类问题，
而那时已经没人记得曾经踩过这个坑。

补的用例编号续在该 FN 下：`TC-FN-CORE-045-06`。

### 用例有问题时

先判断是**用例错了**还是**实现错了**：

| 判断 | 处理 |
|---|---|
| 用例步骤写错、预期不对 | 登记为用例缺陷，回到 `ai-test-01-cases` |
| 实现与设计不符 | 登记为产品缺陷 |
| **判断不了** | **停下来问** |

第三种情况下自行归类的成本很高：归成用例问题 → 真实缺陷被掩盖；归成产品缺陷 → 开发排查半天
发现是用例写错了，几次之后就不再信任测试报上来的问题。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不修实现代码。** 发现缺陷只登记，修复由开发执行
- 不降低用例标准（"这个用例其实不重要"不是跳过它的理由）
- 不改测试用例使其通过
- 不写测试报告（那是 `ai-test-05-report`）
- **不美化结果**：不通过就是不通过
- 不要改用例迁就实现
- **不要改缺陷台账的表头**
- 不要把数据错误定成 P1
- 不要在判断不了时自行归类
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 测试环境不可用 | **拒绝执行**。不要用"先标记通过"的方式推进 |
| 用例本身有问题（步骤写错、预期不对） | 登记为用例缺陷而非产品缺陷，回到 `ai-test-01-cases` |
| 无法判断是用例问题还是实现问题 | **停下来问**，不要自行归类——归类错了会掩盖真实缺陷 |
| 定级有争议 | 标为"待裁决"并列出双方理由，交测试与开发负责人共同裁决，不由单方决定 |
| P0/P1 缺陷未修复 | 记录为未关闭，gate-05 会阻断 |

```
通过：38　失败：4

新增缺陷：4 条

- BUG-PROJ-20261020-001-003  P2  空数据时提示文案错误

待裁决定级：无
```
