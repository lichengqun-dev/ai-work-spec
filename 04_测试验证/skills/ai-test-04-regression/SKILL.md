# 能力声明

从**代码变更**出发圈定回归范围：`代码 diff → FN → 依赖图遍历 → 用例集合`。

**这是测试环节里 AI 增值最大的一步。** 传统做法只有两种，都不好：全量回归（慢）或凭经验选（漏）。
把回归范围从"人的记忆"变成"图的遍历"，既快又不容易漏。

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 代码变更 | 项目代码仓 git diff | 是 | 相对本批次基线的 diff |
| 依赖关系图 | `.ai/index/依赖关系图.md` | 是 | 记录 FN 之间的依赖；**为空时拒绝**（见失败处理） |
| 功能编号总表 | `.ai/index/功能编号总表.md` | 是 | FN ↔ 用例的挂载关系 |
| 测试用例 | `ai-test-01-cases` 产出 | 是 | 编号挂载到 FN |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 回归范围 | 项目文档仓 `docs/04_测试/回归范围.md` | 受影响 FN 清单 + 用例清单 + 排除理由 |
| 依赖图更新 | `.ai/index/依赖关系图.md` | 本批次新增的 FN 依赖关系回填 |

## 前置条件（不满足则拒绝执行）

- 代码变更已提交（本批次有 commit）
- 测试用例已产出（无用例则"圈定范围"没有意义）
- **依赖关系图非空**（空图无法遍历，见失败处理）

## 执行步骤

1. 取代码 diff，按提交信息与文件路径映射到 `FN`（提交信息带 FN 编号，这是可映射的前提）
2. 从这些 FN 出发，按依赖关系图**双向遍历**：找它的上游（谁依赖它）与下游（它依赖谁）
3. 得到受影响 FN 集合
4. 映射到用例集合：每个受影响 FN 对应的全部 `TC`
5. **排除项要写明理由**，不是静默丢掉
6. 回填本批次新增的依赖关系到依赖图
7. 回写批次状态文件

## 边界（明确不做）

- **不执行回归**（那是 `ai-test-03-execute`）
- 不判定某条用例"不重要"而排除——排除必须写明理由并由人确认
- 不修改依赖关系图里已有的关系（只追加）
- 不做性能回归（那是另一类测试）

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 依赖关系图为空 | **拒绝执行**并说明：无依赖图只能做全量回归或凭经验选，而两者都不该由本 Skill 默默决定。给出两条路：① 补维护依赖图；② 由人显式指定回归范围 |
| 代码 diff 无法映射到 FN（提交信息没带编号） | **拒绝执行**，列出无法映射的提交——这是 `commit-format` 漏查的后果 |
| 某 FN 在上游被改动但依赖图无对应边 | 列入"疑似受影响"，标注"依赖图可能不完整"，不静默忽略 |
| 受影响范围过大（超过全部 FN 的 70%） | 提示"接近全量回归"，但仍输出范围——**不因为范围大就自行缩小** |

## 双向遍历为什么必要

只往下游走（"我改的 FN 依赖谁"）会漏掉**上游**：改了底层能力，所有依赖它的功能都受影响。

| 方向 | 含义 | 漏掉的后果 |
|---|---|---|
| 下游 | 我依赖的功能 | 我改了它，被改的功能需回归 |
| **上游** | 依赖我的功能 | **我改了底层，上层全部受影响——这是最容易漏的方向** |

实践中"改了 A 崩了 C"绝大多数是上游方向没遍历到。
