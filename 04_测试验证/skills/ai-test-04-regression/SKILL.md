# ai-test-04-regression · 回归范围智能圈定

## 能力声明

从**代码变更**出发圈定回归范围：`代码 diff → FR → 依赖图遍历 → 用例集合`。

**这是测试环节里 AI 增值最大的一步。** 把回归范围从"人的记忆"变成"图的遍历"，既快又不容易漏，
而且**范围是怎么来的可以复核**——这是最关键的一点。

**不做什么**：不执行回归（那是 `ai-test-03-execute`）、不做性能回归、
不判定某条用例"不重要"而排除、不修改依赖关系图里已有的关系——见「边界」。

## 何时用 / 何时不用

- **用**：本批次有代码改动，需要确定"这次要测哪些"时
- **不用**：执行回归并登记结果（`ai-test-03-execute`）；只做性能回归（另一类测试）
- **范围过大时仍走本 Skill**：提示"接近全量回归"，但**不因为范围大就自行缩小**

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 代码变更 | 项目代码仓 git diff | 是 | 相对本批次基线的 diff |
| 依赖关系图 | `projects/<项目码>/.agent/index/依赖关系图.md` | 是 | 记录 FR 之间的依赖；**为空时拒绝**（见失败处理） |
| 功能编号总表 | `projects/<项目码>/.agent/index/功能编号总表.md` | 是 | FR ↔ 用例的挂载关系 |
| 测试用例 | `ai-test-01-cases` 产出 | 是 | 编号挂载到 FR |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 回归范围 | 项目文档仓 `<需求名>/04_测试/回归范围.md` | 受影响 FR 清单 + 用例清单 + 排除理由 |
| 依赖图更新 | `projects/<项目码>/.agent/index/依赖关系图.md` | 本批次新增的 FR 依赖关系回填 |

产出结构：

```markdown
## 受影响 FR 与用例
| FR | 用例 | 方向 |
|---|---|---|
| FR-CORE-045 | TC-FR-CORE-045-01~05 | 直接改动 |

## 疑似受影响（依赖图可能不完整）
| FR | 依据 | 建议 |
|---|---|---|
| FR-CORE-052 | 与 FR-CORE-045 共用同一张表的读写 | 建议一并回归；若确认无影响，请补依赖图 |

## 已排除
| FR | 用例 | 排除理由 |
|---|---|---|
| FR-CORE-031 | TC-FR-CORE-031-01~03 | 该 FR 的代码未在本批次 diff 中出现，且依赖图中无路径可达 |

## 依赖图回填
| FR 编号 | 依赖的 FR | 依赖类型 | 说明 |
|---|---|---|---|
| FR-CORE-045 | FR-CORE-001 | 数据依赖 | 读取 001 产生的基础数据 |
```

依赖类型取 `数据依赖` / `流程依赖` / `状态依赖`。

## 前置条件

**hard（不满足则拒绝执行）**

- 代码变更已提交（本批次有 commit，可读到相对本批次基线的 diff）
- 测试用例已产出（无用例则"圈定范围"没有意义）
- **依赖关系图非空**（空图无法遍历，见失败处理）

**soft**

- 无。本 Skill 的前置都是"缺了做不了"——依赖图为空、diff 无法映射到 FR 时都拒绝执行，
  不会降级成"凭经验圈一个范围"

## 执行步骤

1. 取代码 diff，按提交信息与文件路径映射到 `FR`（提交信息带 FR 编号，这是可映射的前提）
2. 从这些 FR 出发，按依赖关系图**双向遍历**：找它的上游（谁依赖它）与下游（它依赖谁）
   ——**上游方向最容易漏**（见 `references/回归圈定原理.md`）
3. 得到受影响 FR 集合
4. 映射到用例集合：每个受影响 FR 对应的全部 `TC`
5. **排除项要写明理由**，不是静默丢掉（「已排除」表的格式见「产出契约」）
   **静默排除是这一步最容易出的问题**：范围看起来收窄了、跑得快了，但没人知道漏了什么。

6. 回填本批次新增的依赖关系到依赖图（**只追加，不修改已有关系**——那些关系是历史批次积累的，
   改它们需要单独确认）
7. 回写批次状态文件：本步骤置 `done`，登记回归范围文件与哈希

### 依赖图不完整时

遍历完如果发现"某 FR 在上游被改动，但依赖图里没有对应边"，列入**疑似受影响**并标注
（「疑似受影响」表的格式见「产出契约」）。

**不要静默忽略，也不要擅自扩大范围。** 摆出来让人决定——同时也是在提示"依赖图该补了"。

### 范围过大时

受影响 FR 超过全部 FR 的 70% 时，提示这是"接近全量回归"——
**但仍原样输出范围，不因为范围大就自行缩小。**
自行缩小范围是最危险的动作：它把"成本问题"变成了"漏测问题"，而后者要到线上才发现。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不执行回归**（那是 `ai-test-03-execute`）
- 不判定某条用例"不重要"而排除——排除必须写明理由并由人确认
- 不修改依赖关系图里已有的关系（只追加）
- 不做性能回归（那是另一类测试）
- 不要在依赖图为空时凭经验圈一个范围
- 不要只遍历下游
- 不要静默排除
- 不要因为范围大就自行缩小
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 依赖关系图为空 | **拒绝执行**并说明：无依赖图只能做全量回归或凭经验选，而两者都不该由本 Skill 默默决定。给出两条路：① 补维护依赖图；② 由人显式指定回归范围 |
| 代码 diff 无法映射到 FR（提交信息没带编号） | **拒绝执行**，列出无法映射的提交——这是 `commit-format` 漏查的后果 |
| 某 FR 在上游被改动但依赖图无对应边 | 列入"疑似受影响"，标注"依赖图可能不完整"，不静默忽略 |
| 受影响范围过大（超过全部 FR 的 70%） | 提示"接近全量回归"，但仍输出范围——**不因为范围大就自行缩小** |

## 输出格式

```
代码变更：12 个提交 → 映射到 4 个 FR
  - FR-CORE-045（导出入口）
  - FR-CORE-046（结果下载）
  - FR-CORE-001（基础字典读取）    ← 底层改动，需重点看上游
  - FR-CORE-020（列配置）

依赖图遍历：
  上游（依赖上述 FR 的）：FR-CORE-052、FR-CORE-061、FR-CORE-070
  下游（上述 FR 依赖的）：FR-CORE-001、FR-CORE-010

受影响 FR：共 7 个
回归用例：23 条（占全部 45 条的 51%）

疑似受影响：无
已排除：2 个 FR（无路径可达，理由见文件）
依赖图回填：新增 3 条关系
```
