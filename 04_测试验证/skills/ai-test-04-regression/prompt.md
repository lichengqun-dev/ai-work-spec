# 指令：回归范围智能圈定

## 为什么这一步值得单独做一个 Skill

回归测试的传统做法只有两种，都不好：

| 做法 | 问题 |
|---|---|
| 全量回归 | 慢。改动一行也要跑完全部用例，团队会开始跳过回归 |
| 凭经验选 | 漏。"我觉得这块不影响"——直到线上出问题 |

本 Skill 把它变成**图的遍历**：从代码变更出发，沿依赖关系走一遍，得出范围。
比全量快，比经验准，而且**范围是怎么来的可以复核**——这是最关键的一点。

## 走这条链

```
代码 diff
  → 提交信息里的 FN 编号
    → 依赖关系图双向遍历
      → 受影响 FN 集合
        → 每个 FN 挂载的 TC 集合
          → 回归范围
```

**每一跳断了都会退化成"凭经验"**：

| 断点 | 后果 |
|---|---|
| 提交信息没带 FN | 无法映射，只能按文件路径猜 |
| 依赖图为空 | 无法遍历，只能全量或凭经验 |
| 用例没挂 FN | 圈出 FN 也找不到对应用例 |

遇到断点**拒绝执行并说明**，不要猜一个范围。猜出来的范围看起来合理，但没人能复核它。

## 双向遍历，尤其是上游

```
        ┌─ 上游：依赖我的功能  ← 最容易漏
我改的 FN ─┤
        └─ 下游：我依赖的功能
```

**"改了 A 崩了 C"绝大多数是上游方向没遍历到。**

例：改了「基础数据字典」的读取逻辑 → 所有依赖字典的模块都受影响。
如果只往下游遍历（"字典依赖谁"），会得出"什么都没影响"的结论。

## 排除项要写明理由

不是静默丢掉，而是列出来：

```markdown
## 已排除
| FN | 用例 | 排除理由 |
|---|---|---|
| FN-CORE-031 | TC-FN-CORE-031-01~03 | 该 FN 的代码未在本批次 diff 中出现，且依赖图中无路径可达 |
```

**静默排除是这一步最容易出的问题**：范围看起来收窄了、跑得快了，但没人知道漏了什么。

## 依赖图不完整时

遍历完如果发现"某 FN 在上游被改动，但依赖图里没有对应边"，列入**疑似受影响**并标注：

```
## 疑似受影响（依赖图可能不完整）
| FN | 依据 | 建议 |
|---|---|---|
| FN-CORE-052 | 与 FN-CORE-045 共用同一张表的读写 | 建议一并回归；若确认无影响，请补依赖图 |
```

**不要静默忽略，也不要擅自扩大范围。** 摆出来让人决定——同时也是在提示"依赖图该补了"。

## 顺带回填依赖图

本批次新增的 FN 之间的依赖关系，回填到 `.ai/index/依赖关系图.md`。
**只追加，不修改已有关系**——那些关系是历史批次积累的，改它们需要单独确认。

格式：

```markdown
| FN 编号 | 依赖的 FN | 依赖类型 | 说明 |
| FN-CORE-045 | FN-CORE-001 | 数据依赖 | 读取 001 产生的基础数据 |
```

依赖类型取 `数据依赖` / `流程依赖` / `状态依赖`。

## 范围过大时

受影响 FN 超过全部 FN 的 70% 时，提示这是"接近全量回归"——
**但仍原样输出范围，不因为范围大就自行缩小。**

自行缩小范围是最危险的动作：它把"成本问题"变成了"漏测问题"，而后者要到线上才发现。

## 完成后

回写批次状态文件：本步骤置 `done`，登记回归范围文件与哈希。

## 你绝对不要做的事

- 不要在依赖图为空时凭经验圈一个范围
- 不要只遍历下游
- 不要静默排除
- 不要因为范围大就自行缩小
- 不要修改依赖图里已有的关系
- 不要执行 git 操作

## 输出格式

```
代码变更：12 个提交 → 映射到 4 个 FN
  - FN-CORE-045（导出入口）
  - FN-CORE-046（结果下载）
  - FN-CORE-001（基础字典读取）    ← 底层改动，需重点看上游
  - FN-CORE-020（列配置）

依赖图遍历：
  上游（依赖上述 FN 的）：FN-CORE-052、FN-CORE-061、FN-CORE-070
  下游（上述 FN 依赖的）：FN-CORE-001、FN-CORE-010

受影响 FN：共 7 个
回归用例：23 条（占全部 45 条的 51%）

疑似受影响：无
已排除：2 个 FN（无路径可达，理由见文件）
依赖图回填：新增 3 条关系
```
