## 二、两套命名风格（客观并存，不强制统一）

V-IPD 库里存在**两套成熟的命名风格**，分别对应一期与二期，各自有完整规范，按表前缀判定归属。

### 2.1 一期风格（`pp_*` / `iform_*` / `act_*`）

| 维度 | 约定 | 示例 |
|------|------|------|
| 表名 | snake_case，业务前缀 | `pp_project`, `pp_task_assignment`, `iform_auth_res` |
| 字段名 | snake_case **带下划线后缀** | `id_`, `create_by_`, `project_id_`, `deleted_` |
| 主键 | `id_` varchar(64)（雪花/UUID） | |
| 逻辑删除 | `deleted_` varchar(20)，`'N'`=正常 / `'Y'`=已删除 | **查询必须带 `deleted_='N'`** |
| 乐观锁 | `version_` numeric | |
| 审计 | `create_by_`/`create_time_`/`update_by_`/`update_time_` | varchar(64) + timestamp |
| 租户 | `tenant_id_` varchar(64) | |
| 树形 | `first_child_id_` + `next_brother_id_`（链表式） | 不用 `parent_id` |
| 多值字段 | 逗号分隔字符串 | `assignee_ids_`, `approver_ids_`, `informer_ids_` |
| 状态/红绿灯 | `light_` numeric + `light_description_` varchar | |
| 计划字段 | 成对：`start_/finish_`、`actual_start_/actual_finish_`、`baseline_start_/baseline_finish_` | 三套（实际/计划/基线） |
| 进度 | `progress_/planned_progress_/baseline_progress_` | numeric |

### 2.2 二期风格（`extends_*`）

| 维度 | 约定 | 示例 |
|------|------|------|
| 表名 | `extends_<域>_<对象>` snake_case | `extends_car_performance_target_set`, `extends_dvp_process` |
| 字段名 | snake_case **无后缀** | `id`, `create_user_id`, `project_id`, `is_deleted` |
| 主键 | `id` varchar(32)（MyBatis-Plus `assign_id`） | |
| 逻辑删除 | `is_delete` int 或 `is_deleted` smallint，**1=正常，0/2=删除**（注意与常见约定相反） | 以表 COMMENT 为准 |
| 乐观锁 | `lock_version` int（部分表） | |
| 审计 | `create_user_id`/`create_user_name`/`create_time`/`update_user_id`/`update_user_name`/`update_time` | 冗余姓名字段 |
| 来源追溯 | `source_template_*`（set_id/version_id/version_no/snapshot jsonb） | 模板快照 |
| 状态机 | `status` int，各表 COMMENT 写明状态值语义 | 如 1草稿→2目标设定→... |
| 版本化 | 主表 + `_versions` 版本表 + `_version_items` 明细版本表 | 三级版本 |
| 计划/实绩 | 成对：`<node>_plan`/`<node>_actual` | 如 `tg0_data_plan`/`tg0_data_actual` |

### 2.3 选择规则（新表该用哪套？）

| 场景 | 用哪套 |
|------|--------|
| 一期 iform/pp_* 业务（项目/计划/任务/文档/待办） | 一期风格 |
| 二期 extends_* 扩展业务 | 二期风格 |
| 新建二期业务表 | 二期风格（`extends_<域>_<对象>`，字段无下划线后缀） |
| 跨两期的关联字段 | 以**被关联表的风格**为准（如 extends_ 表存 `project_id` 不带下划线，一期 pp_ 表存 `project_id_` 带下划线） |

## 三、字段规范

### 3.1 强制通用字段

| 字段（一期） | 字段（二期） | 类型 | 说明 |
|------|------|------|------|
| `id_` | `id` | varchar(64/32) | 主键 |
| `create_by_` | `create_user_id` + `create_user_name` | varchar(64) | 创建人 |
| `create_time_` | `create_time` | timestamp | 创建时间 |
| `update_by_` | `update_user_id` + `update_user_name` | varchar(64) | 更新人 |
| `update_time_` | `update_time` | timestamp | 更新时间 |
| `deleted_` | `is_delete`/`is_deleted` | — | 逻辑删除（值域见 §2） |

### 3.2 字段命名

- 布尔/标志：一期 `is_xxx_`（如 `is_milestone_`），二期 `is_xxx`（如 `is_deleted`）或 `xxx_flag`
- 日期时间：`xxx_time`（不用 `xxx_date`，统一 timestamp）
- 状态：`status`/`state_`/`state`
- 金额：`xxx_amount` decimal
- 计数：`xxx_count`/`xxx_number`
- 多值：一期 `xxx_ids_` 逗号串；二期 `xxx_id` text（多值场景）

## 四、索引规范

### 4.1 命名（强制）

| 索引类型 | 格式 | 示例 |
|----------|------|------|
| 主键 | `PK_表名` 或 GaussDB 默认 | |
| 唯一 | `UK_表名_字段` | `UK_pp_project_code` |
| 普通 | `IDX_表名_字段` | `IDX_pp_task_project_id` |
| 联合 | `IDX_表名_字段1_字段2` | `IDX_pp_todo_user_id_project_id` |

### 4.2 规范（强制）

- 核心查询字段必须建索引：`project_id_`、`task_id_`、`user_id_`、`code_`、`state_`、`deleted_`
- 联合索引遵循最左前缀
- 大表（>10万行）索引变更走 DBA
- **GaussDB 保留字**（`id`/`status`/`location`/`user`/`group` 等）查询时加双引号

## 五、SQL 编写规范

### 5.1 基本（强制）

- 用 MyBatis/MyBatis-Plus 动态 SQL，禁止字符串拼接
- 关键字大写：`SELECT`/`FROM`/`WHERE`/`AND`/`INSERT`/`UPDATE`/`DELETE`
- GaussDB 字段名建议加双引号防保留字冲突
- 分页：一期用 PageHelper，二期用 MyBatis-Plus 分页插件
- **查询必须带逻辑删除条件**（一期 `deleted_='N'`，二期 `is_delete=1` 或 `is_deleted=1`）

### 5.2 禁止

- 禁止 `SELECT *`，明确列字段
- 禁止循环内执行 SQL（N+1）
- 禁止大事务（>1000 条 DML 拆批）
- 禁止 `INSERT ... ON DUPLICATE KEY UPDATE`（用 MyBatis-Plus `insertOrUpdate`）

### 5.3 参数声明（强制）

MyBatis 共享 SQL 片段的参数必须全量 `@Param` 声明，否则 OGNL `BindingException`：

```java
// 正确
List<Task> listByProject(@Param("projectId") String projectId,
                         @Param("userId") String userId);
```

## 六、DDL 管理

- **无 Flyway/Liquibase**：SQL 文件按日期命名放 `<模块>/src/main/resources/ddl/` 或 `<模块>/ddl/`
- 文件名：`YYYYMMDD[-描述].sql`（如 `20260509-表dvp_template_type增加node_type字段.sql`）
- 多环境执行：手工，**schema 前缀经常写死某环境**，跨环境执行前问 DBA 确认 schema
- 字段变更：必须带 `COMMENT ON COLUMN`（GaussDB comment 是文档来源，一期字段含义全靠 comment 查）
- 回滚脚本：`xxx_rollback.sql`（部分表有）

## 七、GaussDB 特殊规范

- 内核 openGauss，PG 协议兼容，但非完全等价 PG
- 双节点 + `targetServerType=master`（主备自动切换）
- `jsonb` 类型用于快照（二期 `source_template_snapshot` 等）
- `COLLATE "pg_catalog"."default"` 是默认 collation
- `WITH (orientation=ROW)` 行存（默认）
- 保留字双引号：`"id"`、`"status"`、`"location"`、`"user"`、`"group"`
- 字段别名拼写要精确（曾出过 `finished_num` 误写 `finished_um` 的线上事故）

## 八、MyBatis 规范

### 8.1 XML 映射

- 文件名与 Mapper 接口同名：`PpProjectMapper.xml` ↔ `PpProjectMapper.java`
- 一期放 `src/main/resources/mapper/`，自研 `IformMybatisSqlSessionFactoryBean`（JAXB 解析，静默加载——找不到不报错，注意排查）
- 二期放 `src/main/resources/mapper/`，MyBatis-Plus 标准加载

### 8.2 动态 SQL 示例

```xml
<select id="selectByProject" resultMap="BaseResultMap">
    SELECT <include refid="Base_Column_List"/>
    FROM pp_task
    <where>
        <if test="projectId != null">AND project_id_ = #{projectId}</if>
        <if test="deleted != null">AND deleted_ = #{deleted}</if>
    </where>
    ORDER BY order_ ASC
</select>
```
