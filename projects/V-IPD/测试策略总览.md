# 测试策略总览

> 项目：V-IPD
> 最后更新：2026-10-09
> 说明：V-IPD 当前自动化测试覆盖度低（前端 0 单测，后端 target/test-classes 基本空壳，验收报告确认"测试用例仅覆盖 55% 功能项"）。本规范先定分层框架与目标态，给出补齐路径，不照搬玄武的重型守卫测试。

---

## 一、测试分层（目标态）

```
      E2E (Playwright)         ← 最高成本，最少覆盖
    ┌──────────────────────────┐
    │  集成测试 (IT)            │  ← 服务级验证
    ├──────────────────────────┤
    │  功能测试 (FT)            │  ← 接口功能验证
    ├──────────────────────────┤
    │  单元测试 (UT)            │  ← 最低成本，最多覆盖
    └──────────────────────────┘
```

## 二、各层定位与当前现状

### 2.1 单元测试 (UT)

| 维度 | 目标 | 现状 | 差距 |
|------|------|------|------|
| 工具 | 后端 JUnit 5 + Mockito；前端 Vitest/Jest | 后端有 surefire 配置但 target/test-classes 空壳；前端 0 | 全部 |
| 后端覆盖 | 核心 Service 逻辑、Mapper 关键方法 | ≈0 | 关键 Service（项目/计划/任务/待办写入、二期各 service）需补 |
| 前端覆盖 | 关键业务组件 | 0 | 按 xuanwu 模式补充（不强制，按需） |
| 命名 | `{被测类}Test` / `*.spec.js` | — | — |

### 2.2 功能测试 (FT)

| 维度 | 目标 | 现状 |
|------|------|------|
| 工具 | Python requests / Postman / curl | 主要靠人工 + core-test 环境手测 |
| 覆盖 | 所有对外接口 + 核心业务接口 | 验收报告：测试用例 94 条 vs 172 功能项 ≈ 55% |
| 验证 | HTTP 200 + 业务断言 + 数据对账（GaussDB SELECT） | 仅 HTTP 200 |

### 2.3 集成测试 (IT)

| 维度 | 目标 | 现状 |
|------|------|------|
| 服务启动 | 5 一期 + 7 二期 + 前端全部起来 | 本地可启（见 `测试环境与账号管理 V1.0`），dev K8s 内网 IP 不可直连 |
| 跨服务 Feign | integration-layer SDK 调一期 OAuth/组织/表单/消息 | 靠联调 |
| MQ 链路 | 业务事件 → RabbitMQ → 待办同步 → VHome → 飞书 | 靠观察 |
| BPMN 流程 | Activiti 流程实例走通 | 靠手测 |

### 2.4 性能测试 (PT)

| 维度 | 目标 | 现状 |
|------|------|------|
| 关键接口 RT | ≤1000ms @30 并发（验收标准） | 验收 23 接口 50 并发通过 |
| 大数据量导入导出 | 验收标准 15s vs 实测 60s（矛盾，待修） | 矛盾未解决 |
| CPU/内存使用率 | ≤80% | 验收未提供数据 |

### 2.5 持久性测试 (ET)

- 现状：无 7×24 监控数据（验收报告确认）
- 目标：至少跑一次 5min 混合读写 + 30min 读

## 三、补齐路径（推荐顺序）

### 阶段 1：UT 守住核心写入逻辑

V-IPD 没有玄武那种"核心三表写门面"强约束，但有**写入热点**需要守卫：

| 守卫目标 | 价值 | 优先级 |
|---------|------|--------|
| `pp_todo`/`pp_todo_done` 写入（待办同步链路） | 防止业务事件丢失、VHome 同步漏触发 | P0 |
| 二期版本快照写入（`extends_*_versions` + `_version_items`） | 防止快照不一致 | P1 |
| integration-layer Feign 调用契约（OAuth/Org/Form/Message） | 防止两期接口签名漂移 | P1 |
| 逻辑删除条件（一期 `deleted_='N'`、二期 `is_delete=1`） | 防止查到已删除数据 | P1 |

### 阶段 2：FT 覆盖核心业务接口

参照《测试方案-最终版》模式，用 Python requests 在 core-test 环境跑：
- 登录链路（oauth + Redis db3）
- 项目 CRUD + 计划/任务树
- 二期各服务的核心 CRUD + BPMN 审批
- 待办同步 + VHome + 飞书消息

### 阶段 3：IT 端到端联调

本地启 5+7+前端，用真实数据跑核心链路。

## 四、测试数据管理

## 六、质量门禁（目标）

| 检查项 | 要求 | 工具 |
|--------|------|------|
| UT | 核心 Service 0 失败（不强制覆盖率，先守住热点） | JUnit 5 / surefire |
| FT | 核心业务接口全 PASS | Python requests |
| 逻辑删除守卫 | 所有查询带删除条件 | 构建期扫描 |
| integration-layer 契约 | Feign 接口签名变更触发告警 | 契约测试 |
| 验收整改项 | 见《V-IPD平台一期验收评审报告.md》整改清单 | — |

## 七、不引入的东西（与玄武的差异）

| 玄武有 | V-IPD 不引入的原因 |
|--------|-------------------|
| `WorkitemWriteConvergenceGuardTest`（三表写门面） | V-IPD 没有这种强约束写入路径，一期走 iform 动态表单引擎，二期各自治 |
| ES 熔断器 + ES 同步合并器 | V-IPD 的 ES 在 dev 已关闭，生产也非核心读路径 |
| `@ProjectScopedCacheable` 双 Redis 集群隔离 | V-IPD 用单一 Redis db3，无项目级缓存桶设计 |
| XXL-Job + `@XxlJob` 注册 | V-IPD 一期用 iform 自带的 Quartz（`base-quartz`），二期无定时任务框架 |
| 构建期守卫扫描（WorkitemEsSyncCoalescer 等） | 不照搬玄武特有类 |
