## 三、后端行为的承载（无界面）

`FN-TASK-001` / `002` / `003` / `004` / `005` / `017` 是**定时任务与服务端逻辑，没有可交互界面**。
强行给它们造页面就是"造页面凑数"，按 Skill 的要求应该**记明而不是硬造**。

处理方式：在原始任务详情页的「点检任务」页签里加一个**自动生成规则说明块**，
把六条规则逐条列出并挂 `data-fn` 标记，同时用「自动来源」标签区分自动生成的任务。

| FN | 规则要点 | 可观测的界面证据 |
|---|---|---|
| FN-TASK-001 | 扫描未完成任务，按「计划开始 + N × 间隔」判定到期 | 页签中出现新的「自动」来源任务 |
| FN-TASK-002 | 字段继承；**创建人 = 原始任务点检人**（不写「系统」） | 点检任务详情页的创建人显示为「李娜（= 原始任务点检人）」 |
| FN-TASK-003 | 计划开始 = 原计划开始 + 间隔；计划完成 = 计划开始 + 偏移 | 页签的「计划开始 / 计划完成」两列 |
| FN-TASK-004 | 跨度 ≤ 间隔则不生成（⚠️ 口径待 Q-01 固化） | 说明块中显式标注 |
| FN-TASK-005 | 配置缺失时不生成并记日志，不用默认值兜底 | 说明块中显式标注 |
| FN-TASK-017 | 原始任务关闭后停止生成 | 说明块中显式标注 |

> **这也回答了一个容易被问的问题**：「自动生成的规则在原型上怎么看？」
> 答案是——它没有界面，你能看到的是它的结果（页签里不断出现的自动任务）。
> 把这些规则列出来，是为了让业务方能**逐条确认**，而不是只看到一个结果。

## 五、原型不做什么（按 Skill 的边界）

- **不做精细视觉**：配色、图标、动效一律从简，只保证与系统真实主题色一致
- **不写业务逻辑**：全部静态数据，不调用任何真实接口
- **不做响应式适配**
- **不改造基本信息页签与关联任务页签**（PRD §4.8 明确要求保持不变，原型中显示为占位）

> 这些上面花时间是浪费——它们一定会被真正的实现替换掉，而且会拖慢
> 「业务方确认」这个核心目标的达成。

## 六、与外部原型的关系

需求方提供的 `点检任务demo.html` 是**输入材料**，本原型是**在本知识库体系内重新产出的**：

| | 需求方 Demo | 本原型 |
|---|---|---|
| 形态 | HTML 演示 | 可运行原型（单文件，自包含） |
| 与系统的一致性 | 未知 | **按真实主题色与状态枚举构建** |
| `data-fn` 标记 | 无 | **24 个 FN 全覆盖**（供 `04-prd` 遍历与 gate-02 校验） |
| 用途 | 讲清需求意图 | 业务方确认 + 作为 PRD 的事实源 |

**两者不一致时以哪个为准？** PRD §4.1.4 已经给过一个明确判例——
Demo 里点检任务的创建人写的是「系统」，而会议结论是「取原始任务的点检人」，
**以 PRD 为准**。本次沿用这一原则：**落成文字的 PRD 条款优先于 Demo 的视觉呈现。**
