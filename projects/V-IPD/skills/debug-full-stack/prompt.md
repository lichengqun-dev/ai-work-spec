# 指令：V-IPD 前后端联调与问题定位

## 你要做的事

用户说"联调"/"接口不通"/"数据不对"/"要打断点"时，**先定模式，再动手**。本篇讲**组合与排查**，
单个服务的启动细节在对应的启动手册里。

## 第一步：先选联调模式（选错会白折腾）

| 模式 | 起什么 | 何时用 |
|---|---|---|
| A 全本地 | 前端 + 5 一期 + 7 二期 | 要改后端代码、要看本地日志 |
| B 混合 | 前端 + 本地 project + dev OAuth（经代理 `localhost:16200`） | 只想改一期 project 业务，不想起整套 |
| C 前端 + core-test | 只起前端 | 只改前端 |
| D 对账模式 | 不起服务，只连库 | 验证数据 |

**模式 B 有一个前提必须确认**：本地 Redis database = **3**（与 dev K8s ConfigMap 一致），
OAuth 把 token context 写 db3，本地 project 才能从 db3 读到 → 校验通过。**不是 db3 就报 `REQUEST_408`。**

## 第二步：接口不通时，按这个顺序查（不要跳）

1. **请求打到哪了？** 看 `vue.config.js` proxy —— 兜底规则会把未命中本地的请求送去 `core-test`（环境上的**旧代码**）。这是"页面能开、数据不对"最常见的原因
2. **认证过了吗？** token 在 Redis db3；local 必须 `client.gateway.disable: true`，否则报「非法请求」6010101
3. **服务起来了吗？** 看 `Started <XxxApplication> on port(s)`，不是看进程在不在（OOM 的失败形态是进程无声消失）
4. **配置生效了吗？** 改过 yml 就必须同步 `target/classes`
5. **数据对吗？** 连库对账（见下）

**这个顺序是有理由的**：从最外层往最里层查。反过来先查数据，会在一堆正确的东西里找那个错的外层配置。

## 第三步：要断点就先说清怎么断

后端 IDEA 远程 attach（端口自选不冲突，如 cmf 用 5005）；前端走浏览器 devtools 或 `debugger`。
**热改流程**：增量重编译（秒级）→ 先停旧进程再启动。

## 第四步：要验证数据就连库对账

用 psycopg2 连测试库，把接口返回和 `SELECT count(*)` 比对。**逻辑删除条件按期的值域写**
（一期 `deleted_='N'`，二期 `is_delete=1`）——条件写错会让对账结果差一大截，而看起来像"接口漏数据"。

## 你绝对不要做的事

- **不要在用户说"接口不通"时直接改后端代码**——先按第二步定位
- **不要用 core-test 的数据去解释本地行为**——那是环境上的旧代码返回的
- **不要为让请求通而改动 proxy 或关掉 GatewayFilter 之外的校验**
- 不要执行 git 操作

## 输出格式

```
模式：A/B/C/D
启动：<起了哪些> / 前端 9528 ✅
定位结论：
  请求实际打到 → <本地服务 / core-test 兜底>
  认证         → token 在 db3 ✅ / ❌
  服务         → Started ✅ / ❌
  配置         → 已同步 target/classes ✅ / ❌
  数据对账     → 接口 total N vs 库 count N ✅ / ❌

<问题定位：现象 → 根因 → 处理>
```
