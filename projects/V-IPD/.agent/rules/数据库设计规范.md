## STD-PRJ-V-IPD-001 · 表命名按两套风格分，用表前缀判定归属

<!-- meta
tier: resident
scope: 建表、写 SQL、表定位
frozen: false
-->

**规则**：V-IPD 库里**客观并存两套命名风格**，按表前缀判定归属，**不做统一**。
- 一期（`pp_*` / `iform_*` / `act_*`）：snake_case，字段**带下划线后缀**（`id_` / `create_by_` / `project_id_` / `deleted_`）
- 二期（`extends_*`）：`extends_<域>_<对象>`，字段**无后缀**（`id` / `create_user_id` / `project_id` / `is_deleted`）

**新建二期业务表用二期风格**。**跨两期的关联字段以被关联表的风格为准**——`extends_` 表里存 `project_id` 不带下划线，一期 `pp_` 表里存 `project_id_` 带下划线。

**原因**：库共 607 张表（`iform_` 213 / `pp_` 175 / `extends_` 139），两套风格各有完整规范且都已成规模。混用的后果不是报错，而是**字段名对不上导致查不到数据**——写错时 SQL 语法正确、结果为空，看起来像"没有数据"。

## STD-PRJ-V-IPD-002 · 逻辑删除：一期 'N'/'Y'，二期 1=正常、0/2=删除（方向与常见约定相反）

<!-- meta
tier: resident
scope: 所有增删改查
frozen: false
-->

**规则**：查询**必须带逻辑删除条件**，且**两期值域不同、不可互相套用**：
- 一期（`pp_*` / `iform_*`）：`deleted_` varchar，`'N'`=正常 / `'Y'`=已删除 → 查询带 `deleted_='N'`
- 二期（`extends_*`）：`is_delete` int 或 `is_deleted` smallint，**1=正常，0 / 2=删除**

**二期字段名不统一**（`is_delete` 与 `is_deleted` 两种列名并存），**以该表 COMMENT 为准**。

**原因**：取值方向反了**不会报错**，只会让结果悄悄偏掉——要么"已删除的数据被查出来"（数据越权），要么"未删除的数据被过滤掉"（看起来像数据丢了）。两者都要到业务方发现时才暴露。一期 `'N'` 与二期 `1` 都表示"正常"，但**字段名与取值都不同**，跨期抄写必错。

## STD-PRJ-V-IPD-003 · 主键：一期 varchar(64)，二期 varchar(32) assign_id；Java 与接口层一律用 String

<!-- meta
tier: resident
scope: 实体定义、接口出入参、前端取值
frozen: false
-->

**规则**：主键类型按期分：一期 `id_` varchar(64)（雪花/UUID），二期 `id` varchar(32)（MyBatis-Plus `assign_id`）。
**在 Java 与接口层按 `String` 处理，不要用 `Long` 做参数或返回类型。**

**正例**：`@TableId(type = IdType.ASSIGN_ID) private String id;`

**反例**：接口返回 `Long id`，前端 `JSON.parse` 后末位变成 0。

**原因**：雪花 ID 是 19 位十进制数，**超出 JavaScript `Number.MAX_SAFE_INTEGER`（2^53-1，16 位）**。按数值型序列化到前端会静默丢精度——前端拿到的是一个**真实存在但不属于任何记录**的 ID，按它去查返回空，让人以为是数据权限或缓存问题。

## STD-PRJ-V-IPD-009 · 二期 SQL 与 ORM 的项目特有约定

<!-- meta
tier: indexed
scope: 写 Mapper / XML / 分页
frozen: false
-->

**规则**（二期 `extends_*` 专有；基线已覆盖的部分只列引用）：
- 分页用 **MyBatis-Plus 分页插件**，一期是 PageHelper，**不要混用**
- 复杂 SQL 写 XML 放 `src/main/resources/mapper/`，简单 CRUD 用 MP
- **禁止 `INSERT ... ON DUPLICATE KEY UPDATE`**（用 MP 的 `insertOrUpdate`）。`SELECT *`、循环内 SQL、大事务见基线 `STD-BASE-101` 与 `be-springboot2-java8` 包
- **MyBatis 共享 SQL 片段的参数必须全量 `@Param` 声明**，否则 OGNL `BindingException`
- **GaussDB 保留字**（`id` / `status` / `location` / `user` / `group`）查询时加双引号
- **字段别名拼写必须精确**——出过 `finished_num` 误写 `finished_um` 的线上事故

**原因**：这些都是"写错了能跑通但结果不对"的类型。保留字不加引号在 GaussDB 上直接语法错误（这是好消息）；别名拼错则静默返回 null（这是坏消息）。

## STD-PRJ-V-IPD-010 · DDL 变更：无 Flyway，按日期命名，必须带 `COMMENT ON COLUMN`

<!-- meta
tier: resident
scope: 建表、改表、加字段
frozen: false
-->

**规则**：本项目**没有 Flyway / Liquibase**，DDL 由 DBA 手工执行。
- SQL 文件按日期命名放 `<模块>/src/main/resources/ddl/` 或 `<模块>/ddl/`，文件名 `YYYYMMDD[-描述].sql`
- **字段变更必须带 `COMMENT ON COLUMN`**——GaussDB 里 comment **就是文档来源**，一期字段含义全靠它查
- 回滚脚本 `xxx_rollback.sql`（部分表有），见基线 `STD-BASE-311`
- **schema 前缀经常写死某个环境**，跨环境执行前**问 DBA 确认 schema**

**原因**：`COMMENT ON COLUMN` 不是可选项——没有 comment 的表，下一个改它的人只能靠猜字段含义。而"schema 写死某环境"这条最容易在跨环境发布时才暴露。

## STD-PRJ-V-IPD-011 · 字段与通用字段约定（审计字段、乐观锁、时间类型）

<!-- meta
tier: indexed
scope: 建表、实体定义
frozen: false
-->

**规则**：
- **审计字段按期不同**：一期 `create_by_` / `create_time_` / `update_by_` / `update_time_`；二期 `create_user_id` / `create_user_name` / `create_time` / `update_user_id` / `update_user_name` / `update_time`（**冗余存姓名**）
- **乐观锁**：一期 `version_` numeric；二期 `lock_version` int，**只有部分表有——有此字段的表才加 `@Version`**
- **时间字段一律 `timestamp`**，命名用 `xxx_time`，不要 `xxx_date`
- **多值字段**：一期用逗号分隔字符串（`xxx_ids_`），二期用 text

**原因**：二期冗余存姓名是为了列表页免联表，一期没有这个设计。**两期抄错字段名是最常见的混用形态**——字段不存在时会报错（好事），但抄到名字相近的另一个字段上就会静默取错值。

## STD-PRJ-V-IPD-012 · 索引命名格式与必建索引字段

<!-- meta
tier: indexed
scope: 建表、改索引
frozen: false
-->

**规则**：
- 索引命名：唯一 `UK_表名_字段`、普通 `IDX_表名_字段`、联合 `IDX_表名_字段1_字段2`
- **核心查询字段必须建索引**：`project_id_`、`task_id_`、`user_id_`、`code_`、`state_`、`deleted_`
- 联合索引遵循最左前缀
- **大表（> 10 万行）索引变更走 DBA**

**原因**：`deleted_` 也要建索引——它出现在**每一条**查询条件里。基线 `STD-BASE-313` 只讲"高频查询条件必须有索引"，这里补的是本项目的具体字段清单。
