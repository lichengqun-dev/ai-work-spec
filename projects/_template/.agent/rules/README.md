# `.agent/rules/` —— 项目级条目的提炼层

**这个目录装的是「带编号的项目级条目」，它们会进生效快照。**
内容由 `ai-spec-extract` 从项目根的**散文文档**摘录而来——**不要手工新建条目文件**，
手工建的条目没有来源指纹，散文改了不会被发现。

## 一源一文件

散文叫什么，提炼文件就叫什么：

```
projects/<项目码>/
├── 数据库设计规范.md          ← 散文（人读的，随便写）
└── .agent/rules/
    └── 数据库设计规范.md      ← 提炼产物（机器读的，有格式）
```

拆成一个来源一个文件，是为了**改了哪篇散文就只需要重提那一篇**，
以及来源映射一眼可见。

## 文件格式

```markdown
---
source: 数据库设计规范.md                      # 源散文，相对项目目录
source_hash: sha256:8ade6e7316cbe624          # 提炼时源文件的内容哈希
extracted_at: 2026-10-21T10:48:11+08:00
extracted_by: ai-spec-extract
---

# 提炼自 `数据库设计规范.md`

## STD-PRJ-<项目码大写>-001 · <条目标题>

<!-- meta
tier: resident          # resident = 常驻注入；indexed = 按需检索
scope: <触发场景>        # 做什么事的时候会用到这条
frozen: false
-->

<照抄自散文的规则正文>
```

脚本只认 `## STD-<...>` 开头的行作为条目头。frontmatter 与说明文字不会进快照。

## `source_hash` 是这套机制的支点

它回答一个问题：**这条提炼产物，还是源散文的忠实副本吗？**

散文改了而没重新提炼 → `ai-spec-build` 报「源文档已变更」，
并且**把告警写进快照正文顶部**。这一句告警是必须的，因为
「少了一条约束」和「本来就没有这条约束」在快照里长得一模一样——
没有它，散文里新加的规则会静默地不进快照。

**构建不会因此失败**（改文档是常态），但快照会明确标注"项目级约束可能已过期，不要假定它完整"。

## 三条不许做的事

1. **不许手工编辑本目录的文件来改规则。** 改规则是改散文，然后重新提炼。
   手工改会让 `source_hash` 与内容对不上，而构建会照报漂移——等于制造了一个假的告警。
   要手工维护的条目（没有散文来源）请用 `.agent/project.yaml` 的 `project_only`，那条路径不禁手工。
2. **不许改条目的编号。** 编号是追溯锚点，改了历史快照、门禁引用、变更记录全部对不上。
3. **不许在条目正文里"总结"规则。** 正文照抄散文——约束一概括就丢限定条件，
   而丢掉的"除 X 外"、"仅限 Y 场景"恰恰是最要命的部分。判据与正反例见
   `ai-spec-extract` 的 `references/摘录判据与反例.md`。

## 什么时候重新提炼

调用 `ai-spec-extract`。触发时机：

- 构建报「源文档已变更」（快照顶部有告警）
- 新增了项目级散文文档
- 某篇散文有成规模的修改

**源文档哈希没变时它会直接退出**，不会无谓地重新生成——所以不用担心"跑一次就漂一次"。
