# projects —— 项目实例层

> **这是整个知识库中唯一允许出现具体项目名称、模块、表名与业务规则的地方。**

## 边界规则

| 目录 | 允许出现的内容 |
|---|---|
| `00`–`09`、`.ai/` | 只有机制、规范模板、通用工程约束。**不得出现任何具体项目信息** |
| `projects/<项目码>/` | 该项目的全部项目级内容：选包声明、差异、项目特有规范 |

这条边界不是洁癖，它决定了这个知识库能不能被复用到别的团队：

- 共享层一旦混入具体项目信息，其他人读到就会困惑"这是必须遵守的，还是某个项目的特例"
- 共享层一旦引用某个项目的做法，删除该项目时就会留下一堆悬空引用
- 而项目层被清空或替换时，共享层不应受到任何影响——这就是"通用资产"的定义

## 一个项目目录里有什么

```
projects/<项目码>/
├── project.yaml          # 组合声明：技术栈包 + 领域包 + 差异（overrides / project_only）
└── 项目特有规范.md        # 该项目的特有条目（编号前缀 STD-PRJ-<项目码大写>-）
```

**没有共享规范的正文。** 项目 manifest 只写"选了哪些包"和"有哪些差异"，
一旦在 overrides 里粘贴包内规范的内容，这个项目就退化成基线副本，
包更新再也影响不到它——这正是分层设计要解决的问题本身。

## 新增项目

```
1. cp -r _template projects/<项目码>
2. 填 project.yaml（选包 + 差异）
3. python3 00_工作空间配置/skills/ai-spec-build/scripts/spec_build.py --project <项目码>
```

目标耗时 ≤ 30 分钟。超过说明包粒度太细（选项太多）或 manifest 结构太复杂。

## 复用到新团队

清空本目录下除 `_template/` 外的全部内容即可，共享层不需要任何改动。
