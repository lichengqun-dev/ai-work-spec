# projects —— 项目实例层

> **这是整个知识库中唯一允许出现具体项目名称、模块、表名与业务规则的地方。**

## 一、三层结构与权重

```
ai-work-spec/
├── 00_工作空间配置 … 09_资产库/      【用户级】跨项目基线
│   └── standards/ · skills/ · 规范包
└── projects/
    ├── _template/                   新项目的空骨架
    └── <项目码>/                     【项目级】该项目的规范、状态与组合声明
        └── <需求名>/                 【业务级】该需求的全部产出物
```

| 层 | 位置 | 内容 | 权重 |
|---|---|---|---|
| 用户级 | `00`–`09` | 通用规范、技术栈包、机制说明 | 低 |
| 项目级 | `projects/<项目码>/` 根下 | 项目架构、模块、业务模型、测试策略、环境与带编号的项目级约束 | 中 |
| 业务级 | `projects/<项目码>/<需求名>/` | 该需求各阶段的产出物 | **高** |

**内容冲突时：业务级 > 项目级 > 用户级。**

> **`.agent/` 只在项目下，顶层没有。** 它是本知识库的机器状态区，而机器状态天生属于某个项目——
> 放顶层会让"`00`–`09` 是通用资产"这条与它实际装的内容自相矛盾，也会让多个项目
> 共用一个编号总表而撞号。**早期版本在顶层放过一个 `.agent/`，已删除**，不要再新建。
>
> **机制模板住在项目骨架里**：批次状态 Schema 是 `projects/_template/.agent/state/_模板.yaml`，
> 日志格式约定是 `projects/_template/.agent/logs/README.md`。复制 `_template` 就得到
> 一个结构完整的项目目录——模板跟骨架走，比散在别处更容易找。

这条边界不是洁癖，它决定了这个知识库能不能被复用到别的团队：

- 共享层一旦混入具体项目信息，其他人读到就会困惑"这是必须遵守的，还是某个项目的特例"
- 共享层一旦引用某个项目的做法，删除该项目时就会留下一堆悬空引用
- 而项目层被清空或替换时，共享层不应受到任何影响——这就是"通用资产"的定义

## 二、一个项目目录里有什么

```
projects/<项目码>/
├── README.md               项目索引（读什么、怎么定位需求落点）
│
├── 系统架构总览.md          ┐
├── 模块目录.md              │ **散文层**：人读的，描述本项目实际是什么样
├── 核心业务模型.md          │ · 人工维护后复制进来，或 AI 读代码仓梳理产出
├── 数据库设计规范.md        │ · **不遵守编号约定，改动频繁**
├── 后端开发规范.md          │ · 不直接进快照
├── 测试策略总览.md          ┘
├── 环境与账号.md
├── skills/                 项目级 Skill（只对本项目有意义的）
│
├── .agent/                 本项目的机器面（见下）
│   ├── project.yaml        组合声明：选了哪些包 + 有哪些差异
│   ├── rules/              ★ **提炼层**：带编号的项目级条目 —— 进生效快照
│   ├── state/             批次状态 · index/ 编号总表 · memory/ · spec-effective/ · logs/
│   └── …
└── <需求名>/               业务级产出物（见下）
```

**约束和散文分两层，这是刻意的。** 项目根的文档是**人读的散文**——人工维护复制进来，
或 AI 读代码仓梳理总结出来，**不按编号约定写、改动频繁**，这正是它好用的地方。
而生效快照要的是稳定的、可审计的、能追回出处的条目。两者性质不同，硬塞进同一份文件会有两种结局：

| 结局 | 症状 |
|---|---|
| 人烦到不写 | 加一条约束要先想"这算不算条目""编号排到几"，于是干脆不写进文档 |
| 格式偷偷漂掉 | 编号重复、标题符号写错——而**构建不报错**，它只是安静地少算几条 |

**分工是三层的：**

| 层 | 位置 | 谁维护 | 进快照 |
|---|---|---|---|
| 散文 | `projects/<码>/*.md` | 人（或 AI 梳理后给人确认） | ❌ |
| 提炼 | `projects/<码>/.agent/rules/*.md` | `ai-spec-extract` 从散文摘录 | ✅ |
| 快照 | `projects/<码>/.agent/spec-effective/` | `ai-spec-build` 生成 | 生成物 |

**「提炼」是一层派生副本，不是再写一遍规范。** 它**照抄**散文里的规则条文，只做格式转换：
补编号、补 `tier`/`scope`、补来源指纹。**不改词、不合并、不"提炼要点"**——
约束是条文性质的东西，一总结就会丢限定条件，而"除 X 外"、"仅限 Y 场景"恰恰是约束里最要命的部分。

每条提炼文件在 frontmatter 里记着**它摘录自哪个文档、当时那个文档的哈希是多少**。
散文改了而没重新提炼，`ai-spec-build` 会报「源文档已变更」并**把告警写进快照正文顶部**——
因为"少了一条约束"和"本来就没有这条约束"在快照里长得一模一样，只有这行告警能把两者区分开。

### 项目的 `.agent/`

| 目录 | 内容 | 是否入库 |
|---|---|---|
| `.agent/project.yaml` | 组合声明：选了哪些包 + 有哪些差异 + 仓库路径 | ✅ |
| `.agent/rules/` | **带编号的项目级条目**（由散文提炼而来，一源一文件） | ✅（不可再生，散文改了要重新提炼） |
| `.agent/state/` | 批次状态文件——**接手一个批次时的第一个读物** | ✅（追溯链依赖，不可再生） |
| `.agent/index/` | 功能编号总表 · 依赖关系图 · 快车道台账 · 技术债清单 | ✅ |
| `.agent/memory/` | 跨批次沉淀的项目约定 | ✅ |
| `.agent/spec-effective/` | 生效规范快照（生成物） | ❌ 可重建 |
| `.agent/logs/` | 执行日志 | ❌ 可重建 |

**编号总表必须是项目级的**：两个项目都用同一个模块码时，全局共表会撞号，
而"编号一经启用不复用"是追溯链的根基。

### 业务级：一个需求一个目录

```
projects/<项目码>/<需求名>/
├── CLAUDE.md               批次上下文（L3，由 ai-requirement-01-init 生成，随流程回写）
├── 00_批次/ ~ 05_交付/      该需求各阶段的产出物
├── 迭代/                   变更子批次的产出物
└── 原型/                   原型工程，按批次分目录（每批次独立副本）
```

**产出物按需求聚合，而不是按阶段散在全局。** 一个需求的 PRD、设计、测试、交付产物
都在同一个目录下——**事后移交给别人只需给一个目录**，而不是在五个阶段目录里各捞一遍。

各阶段目录的内容：

| 目录 | 内容 |
|---|---|
| `00_批次/` | 批次级材料 |
| `01_需求/` | 需求文档集（原始需求格式化 / 需求功能分析 / 需求问题汇总）、原型规划与映射、PRD |
| `02_设计/` | 架构设计、功能详细设计、数据库设计、接口契约、前端设计、评审记录 |
| `03_实现/` | 工程骨架说明、评审记录、文档同步说明 |
| `04_测试/` | 测试用例、自动化覆盖说明、执行结果、缺陷台账、回归范围、测试报告 |
| `05_交付/` | 上线步骤、发布说明、结项报告 |
| `迭代/` | 影响面分析、增量设计、变更登记（`<批次号>_` 前缀，不是序号） |

**序号固定，不要自造。** 门禁的产出物分类按路径关键词匹配（如「测试」「交付」「设计」），
序号本身不影响匹配，但两套目录共用一个序号会让人分不清某个文件该放哪。

**迭代批次的产出物不覆盖原批次。** 变更走 `<原批次号>-C<n>` 子批次，
原批次产出物保持不可变——否则"上线那一刻的业务规则是什么"就变成不可回答的问题，
而那是排查线上问题时判断"现在的行为对不对"的唯一依据。

## 三、仓库路径字段

**五个字段，`repo` 是兜底。** 项目只有一个仓时只填 `repo`；文档仓 / 原型仓 / 代码仓分开时，
用 `docs_repo` / `prototype_repo` / `code_repo` 分别指定。**代码仓有多个时**（前后端分仓）
用 `code_repos` 列表，与 `code_repo` 二选一。

`docs_repo` 指向**项目的根**（不是某个需求目录）——产出物登记成
`<需求名>/01_需求/PRD.md` 这样的相对路径（含需求名），再拼到 `docs_repo` 上。

**为什么不能混用**：门禁执行器用它们做三件不同的事——`docs_repo` 是**产出物路径的基准**，
`prototype_repo` 是 `data-fr` 覆盖率的**扫描根**，`code_repos` 是提交格式、FR 关联、密钥扫描的**根**。
混用一个字段在双仓库模型下必然撞墙：把 `repo` 指向文档仓则扫不到原型标记，指向原型仓则产出物全部解析不到。

**分仓时要把每个代码仓都列上。** 这三项检查只扫列出来的仓——漏掉的那个仓里的问题
**一句都不会报，且不留痕迹**（不是"报了 0 个问题"，是根本没扫）。执行器的做法是：
只要有一个仓读不到提交历史，`commit-format` 与 `fr-has-commit` 就记 `skip` 而不是 `pass`，
理由与 `skip ≠ pass` 一致——**没读到不等于没有问题**。

> 一个具体后果，值得记住：仓库路径全都没填时，产出物**不是报"不存在"，而是记 `skip`（无法校验）**。
> 「没地方找」和「找了没有」是两件事，执行器不会把它们说成一件事。

## 四、没有共享规范的正文

项目 manifest 只写"选了哪些包"，不写任何规范正文——一旦把包内规范抄进来，
这个项目就退化成包副本，包更新再也影响不到它。

同理，**项目级规范也不要抄基线的内容**：基线已有的，在项目文件里只写引用（条目编号），不写正文。

## 五、新增项目

```
1. cp -r _template projects/<项目码>
2. 填 `.agent/project.yaml`（选包 + 差异 + 仓库路径）
3. 写项目级文档（散文，自由格式，不用管编号）
4. 调用 ai-spec-extract（说"提炼 <项目码> 的约束"即可）把散文摘成 `.agent/rules/` 里的条目
5. 调用 ai-spec-build（说"接入 <项目码>"即可）编译出生效规范快照
```

目标耗时 ≤ 30 分钟。超过说明包粒度太细（选项太多）或 manifest 结构太复杂。

**接入后按需补充**：项目级文档（架构 / 模块 / 模型 / 测试策略 / 环境）。
它们不是接入的硬门槛，但**没有它们，AI 定位需求落点时只能靠猜**。
写完（或改完）要重新调 `ai-spec-extract`，否则新约束不会进快照——
构建会报「源文档已变更」，不会静默放过。

**接入后、跑迭代前还要一件东西**：`projects/<项目码>/.agent/index/依赖关系图.md` 非空
（迭代入口靠它圈定影响范围）。冷启动时它是空的，这是正常状态——
见根 `README.md` 的「迭代路径：开工前的三条前置」。

## 六、复用到新团队

清空本目录下除 `_template/` 外的全部内容即可，共享层不需要任何改动。
