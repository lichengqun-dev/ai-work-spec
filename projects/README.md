# projects —— 项目实例层

> **这是整个知识库中唯一允许出现具体项目名称、模块、表名与业务规则的地方。**

## 边界规则

| 目录 | 允许出现的内容 |
|---|---|
| `00`–`09`、`.ai/` | 只有机制、规范模板、通用工程约束。**不得出现任何具体项目信息** |
| `projects/<项目码>/` | 该项目的全部项目级内容：选包声明、差异、项目特有规范 |

这条边界不是洁癖，它决定了这个知识库能不能被复用到别的团队：

- 共享层一旦混入具体项目信息，其他人读到就会困惑"这是必须遵守的，还是某个项目的特例"
- 共享层一旦引用某个项目的做法，删除该项目时就会留下一堆悬空引用
- 而项目层被清空或替换时，共享层不应受到任何影响——这就是"通用资产"的定义

## 一个项目目录里有什么

```
projects/<项目码>/
├── project.yaml          # 组合声明：仓库路径 + 技术栈包 + 领域包 + 差异
└── 项目特有规范.md        # 该项目的特有条目（编号前缀 STD-PRJ-<项目码大写>-）
```

**仓库路径有四个字段，`repo` 是兜底。** 项目只有一个仓时只填 `repo`；文档仓 / 原型仓 / 代码仓分开时，
用 `docs_repo` / `prototype_repo` / `code_repo` 分别指定。

### 项目文档仓的目录约定（固定）

```
<项目文档仓>/
├── CLAUDE.md             批次上下文（L3，由 ai-requirement-01-init 生成）
└── docs/
    ├── 00_批次/
    ├── 01_需求/           PRD、需求功能分析、原型规划、原型标记补齐说明
    ├── 02_设计/           架构设计、功能详细设计、数据库设计、接口契约、前端设计、评审记录
    ├── 03_实现/           工程骨架说明、评审记录、文档同步说明
    ├── 04_测试/           测试用例、执行结果、缺陷台账、回归范围、测试报告
    └── 05_交付/           上线步骤、发布说明、结项报告
```

**序号固定，不要自造。** 门禁的产出物分类按路径关键词匹配（如「测试」「交付」），
序号本身不影响匹配，但两套目录共用一个序号会让人分不清某个文件该放哪——
演练中 `03_实现` 与 `03_测试` 就撞过。

这不是配置冗余——门禁执行器用它们做三件不同的事：`docs_repo` 是产出物路径的基准，
`prototype_repo` 是 `data-fn` 覆盖率的扫描根，`code_repo` 是提交检查与密钥扫描的根。
混用一个字段，在双仓库模型下必然撞墙（把 `repo` 指向文档仓则扫不到原型标记，
指向原型仓则产出物全部解析不到）。

**没有共享规范的正文。** 项目 manifest 只写"选了哪些包"和"有哪些差异"，
一旦在 overrides 里粘贴包内规范的内容，这个项目就退化成基线副本，
包更新再也影响不到它——这正是分层设计要解决的问题本身。

## 新增项目

```
1. cp -r _template projects/<项目码>
2. 填 project.yaml（选包 + 差异）
3. python3 00_工作空间配置/skills/ai-spec-build/scripts/spec_build.py --project <项目码>
```

目标耗时 ≤ 30 分钟。超过说明包粒度太细（选项太多）或 manifest 结构太复杂。

## 复用到新团队

清空本目录下除 `_template/` 外的全部内容即可，共享层不需要任何改动。
