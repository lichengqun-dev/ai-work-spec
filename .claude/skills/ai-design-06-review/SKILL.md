# ai-design-06-review · 设计评审与契约冻结

## 能力声明

读设计阶段的产出，执行 **gate-03（设计评审 + 契约冻结）**，然后按结果决定下一步；
门禁通过后把接口契约置为冻结态。

**本 Skill 不做检查项判断。** 自动检查交给 `ai-gate-runner`（说"跑 gate-03"即可），人工项原样列给人。
它只负责编排这一步、以及在通过后执行"冻结"这个有副作用的动作。

**不做什么**：不替人判断人工项、不放宽检查项、不修产出物、不豁免、不改门禁定义——见「边界」。

## 何时用 / 何时不用

- **用**：设计段收尾——arch / detail / db / api / frontend-spec 均已产出，要跑 gate-03 并冻结契约时；
  也用于单项重跑（修正某个失败项后重跑 gate-03）
- **不用**：设计产出物本身要修（回到对应的 `ai-design-*` Skill 重做）；
  只想看某个检查项的口径（直接读知识库根下 `07_质量门禁/skills/ai-gate-runner/references/检查项清单.md`）
- 契约已冻结后要改契约：不在本 Skill 做，走变更子批次（`<原批次号>-C<n>`）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 批次状态文件 | `projects/<项目码>/.agent/state/<批次号>.yaml` | 是 | 设计阶段各步骤已 `done` |
| 设计产出物 | 项目文档仓 `<需求名>/02_设计/` | 是 | 已登记到状态文件的 `artifacts` |
| gate-03 定义 | `07_质量门禁/gates/gate-03-*.md` | 是 | 可解析 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 用于确认校验基于哪版规范 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 门禁结果 | 批次状态文件 `gates[]` | 由 `ai-gate-runner` 写入 |
| 评审记录 | 项目文档仓 `<需求名>/02_设计/评审记录.md` | 评审结论、参与人、未通过项与处置 |
| 契约冻结标记 | 批次状态文件 | 记录冻结时间与契约哈希 |

## 前置条件

**hard（不满足则拒绝执行）**

- 批次状态文件存在，设计阶段各步骤（arch / detail / db / api / frontend-spec）均已 `done`
- 设计产出物已登记到状态文件的 `artifacts`
- gate-03 定义可解析
- 生效规范快照存在（用于确认校验基于哪版规范）
- **`ai-gate-runner` 已实现**（`status: implemented`）——未实现时拒绝，**不要手工"模拟"一遍检查**

**soft（不满足则提示，可继续）**

- gate-02 已通过（未通过时评审记录顶部标注「未经上游确认 —— gate-02 未通过」）

## 执行步骤

1. **调用 `ai-gate-runner` 执行 gate-03**（说"跑 gate-03"即可）——本 Skill 不自己做检查项判断
2. **逐条读出执行器输出，不要总结成"评审已完成"**。执行器的输出里有四类信息，每一类都要如实转达：

   | 输出 | 你该做什么 |
   |---|---|
   | `✅ pass` | 无需处理 |
   | `❌ fail` | **原样读出明细**（执行器已给出具体对象，如"缺失 FR-CORE-045"），并给出修正方向 |
   | `⏭️ skip` | 连同"要做什么才能自动校验"一起读出。**`skip` 不是通过** |
   | 人工核对清单 | 原样列出。**不替用户判断这些项过不过** |

3. 按结果分支：

   ```
   failed          → 停止。输出未通过项 + 定位。等修正后重跑。
   pending_manual  → 请用户核对清单后签核，把执行器给出的核对清单与签核方式一并转达
   passed          → 执行契约冻结（见下）
   ```

   **签核必须用真实人名。** 门禁记录的价值在于能回答"谁在什么时候确认的"，
   填 `auto`、`admin` 等于没留痕

4. 门禁结果为 `passed` 后，**执行契约冻结**（见下「契约冻结的实际动作」）
5. 回写批次状态文件

### 契约冻结的实际动作

`passed` 之后不要只说一句"契约已冻结"，要实际做四件事：

1. 计算 `<需求名>/02_设计/接口契约.yaml` 的哈希，写入批次状态文件，附冻结时间
2. 在 `<需求名>/02_设计/评审记录.md` 写：评审结论、参与人、未通过项及其处置（若曾失败过）
3. 更新批次状态文件：`review` 步骤置 `done`
4. 提示用户"需要通知前后端负责人契约已冻结"

**哈希这一步不能省。** 它让"这个批次开发时用的是哪版契约"可被回答。
没有它，契约冻结就只是一句声明，而声明在三个月后无法作为依据。

落到哪的对照：

| 动作 | 落到哪 |
|---|---|
| 记录契约哈希 | 批次状态文件 |
| 记录冻结时间 | 批次状态文件 |
| 记录评审结论与参与人 | `<需求名>/02_设计/评审记录.md` |
| 通知前后端负责人 | 由人执行（本 Skill 只提示） |

**冻结后的变更走变更子批次**（`<原批次号>-C<n>`），原批次产出物保持不可变。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始——单项重跑（修正失败项后重跑 gate-03）是最常见的形态
- soft 不满足时照常产出，并在评审记录顶部标注「未经上游确认 —— gate-02 未通过」
- 批次状态文件不可写（如未接入批次）时：评审记录落到指定路径，**跳过状态回写与契约冻结标记**并在报告中说明
  （哈希与冻结时间无处落账时，只能报告"冻结未登记"，不要口头宣称已冻结）

## 边界（明确不做）

- **不做检查项判断。** 自动项交给执行器；人工项交给人。替人拍板会让门禁失去意义
- **不放宽检查项。** 不因为"这个项目特殊"就跳过某项——那正是门禁失效的方式。用户要求放宽时不要照做，
  解释清楚：
  - 自动检查项不通过 → 修产出物，不是修门禁
  - 人工项拿不准 → 那是需要人判断的，不是"跳过"
  - 确实要带风险上线 → 走豁免：`--waive --by <名字> --reason "<具体原因>" --expires <日期>`。
    **理由要具体**：反例"赶工期"，正例"客户要求当日上线，契约变更待下个批次补"。
    复查日期由执行器校验：必须晚于今天、且在 **90 天**以内——**填很远的日期会被直接拒绝**，那等于没填
- 不修复产出物（发现设计问题应回到对应 Skill 重做）——**不要自己改设计产出物来消除失败项**
- 不豁免。豁免必须由人显式提供批准人与复查日期
- 不改门禁定义、不改状态文件
- **不把 `skip` 说成通过**
- **不在门禁未通过时推进到编码阶段**
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 门禁 `failed` | 停止，输出未通过项与定位；**不尝试绕过** |
| 门禁 `pending_manual` 且人不确认 | 保持 `pending_manual`，不推进 |
| 执行器报"引用了未实现的检查项" | 报错停止——这是门禁定义的问题，需要修定义或补实现，**不要私自从定义里删掉那一项** |
| 契约文件缺失或哈希对不上 | 停止，提示"产出物被外部修改"，由人决定是否重跑上游 |
| 执行器拒绝执行（引用了未实现的检查项、或上一道门禁未通过） | 原样输出原因，提示需先补齐什么。**不要绕过执行器自己判断** |
| 用户要求放宽检查项 | 不照做，按「边界」里的三条解释；确实要放行则走豁免（人名 / 具体原因 / 复查日期） |
