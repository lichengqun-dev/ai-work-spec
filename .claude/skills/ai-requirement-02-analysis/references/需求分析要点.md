# 需求分析要点

> 本文件承载**「为什么」**：需求结构化这一步里那几条纪律的代价，以及"不这么做会怎样"。
> 「做什么」在 `SKILL.md` 的执行步骤里，不重复。

## 一、为什么信息不足时必须停下

**你的默认倾向是补全合理猜测让产出看起来完整。在这个流水线里，这是最贵的错误，因为错误会逐级放大：**

```
需求猜错 → 设计按错的做 → 代码按错的设计写 → 测试按错的设计编用例 → 全部通过 → 上线才发现
```

停下来问，比跑完返工便宜一个数量级。

同理，**异常流程与边界写不出来时，说明需求信息不足——记入待澄清，不要编**。
凭空编一个异常处理方式，比留着空白更糟：它会被当成确定的需求往下实现。

## 二、为什么一个编号只对应一条需求

不要把"导出相关需求"下面再列三条——那样三条都无法被单独追踪。

`REQ` 是追溯链的起点。起点不可编号，后面的 `FN`、`TC`、提交全部失去锚点，
「这个功能是谁提的、做完没有」就无法回答。

另外，**保留原始材料的原话，不要在这一步就"优化表述"**：原话是后续争议时的依据。

## 三、为什么场景归类错了后果很严重

「导出」在**报表场景**下要求格式与完整性，在**数据集成场景**下要求接口稳定与幂等。
同一个词，两个场景下是完全不同的需求。

场景判断错了，后面推导出的功能点与验收标准都会偏。**归类不了时标为"场景待定"，记入问题汇总**——
不要硬塞进最接近的场景。

## 四、编号冲突与废弃为什么不能"就地修一下"

- 编号冲突时**报错退出**，不要自动重新编号——自动重编会让已经写在别处的引用失效。
- 删除的需求条目**保留编号并标记 `[已废弃]`**，不回收：编号一经启用不复用，
  回收会让历史引用指到另一条需求上。
