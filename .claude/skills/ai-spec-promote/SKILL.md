# ai-spec-promote · 规范提升与淘汰候选

## 能力声明

扫描各项目的特有条目，找出**重复出现**的约束，输出「提升为共享包条目」的候选清单，供人确认。

解决的是知识库的**单向膨胀**问题：如果规范只增不减，三年后会变成没人敢改的巨物。
本 Skill 提供反向的流动性——把项目里的共性往上提，把包里的僵尸条目往下删。

**只产出候选，不自动修改任何包或项目文件。** 提升是规范变更，必须由人确认。

**不做什么**：不自动提升、不自动删除任何条目、不判断条目的技术正确性、
不修改 `projects/` 下的任何文件——见「边界」。

## 何时用 / 何时不用

- **用**：**按月执行一次**，或当某个项目的 `project_only` 超过 30 条时触发
  （`ai-spec-build` 会在快照 D 段给出该警告）
- **不用**：
  - 项目根的散文还没被摘成条目时——**不要扫项目根的散文文档**。那里面的约束措辞自由、
    边界模糊，拿它聚类只会得到似是而非的结论。要提也是先让 `ai-spec-extract` 摘成条目再提
  - 项目数不足 2 个时（信息不足，不做聚类）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 全部项目 manifest | `projects/*/.agent/project.yaml` | 是 | 至少 2 个非模板项目 |
| 项目特有条目 | `projects/*/.agent/rules/*.md` + manifest 的 `project_only` | 否 | — |
| 现有包条目 | `09_资产库/规范包/**` | 是 | 用于判断"是否已存在于包中" |
| 规则引用率数据 | `projects/<项目码>/.agent/spec-effective/*.json` | 否 | 用于淘汰分析 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 提升候选清单 | `projects/<项目码>/.agent/index/规范提升候选.md` | Markdown 表格 + 建议归属 |
| 淘汰候选清单 | `projects/<项目码>/.agent/index/规范淘汰候选.md` | Markdown 表格 + 零引用证据 |

`规范提升候选.md`：

```markdown
# 规范提升候选

生成时间：<时间>　｜　扫描项目数：N

## 建议提升（≥3 个项目出现）

| # | 约束内容（决策点） | 出现项目 | 建议归属 | 建议编号 | 置信度 |
|---|---|---|---|---|---|
| 1 | 数据隔离标识必须显式传入 | 项目 A、项目 B、项目 C | domains/platform-base | STD-DOM-PLAT-011 | 高 |

## 已存在于包中（建议改为引用）

| 约束内容 | 已有条目 | 涉及项目 | 处理建议 |
|---|---|---|---|

## 观察中（恰好 2 个项目出现）

| 约束内容 | 出现项目 |
|---|---|
```

`规范淘汰候选.md`：

```markdown
# 规范淘汰候选

生成时间：<时间>　｜　统计来源：projects/<项目码>/.agent/spec-effective/*.json

## 零引用（候选淘汰）

| 条目 ID | 摘要 | 所在包 | 引用项目数 |
|---|---|---|---|

## 被多项目禁用（优先审查）

| 条目 ID | 摘要 | 所在包 | 禁用项目 |
|---|---|---|---|
```

## 前置条件

**hard（不满足则拒绝执行）**

- 至少存在 2 个非 `_template` 的项目目录
- 每个被扫描项目的 `project.yaml` 能通过 YAML 解析
- 若 `09_资产库/规范包/` 不存在 → 拒绝（无法判断"是否已存在于包中"）

**soft**

- 无。本 Skill 的输入全在仓库内，没有"顺序性"前置——任何时刻单独运行都成立

## 执行步骤

1. **收集扫描对象。** 两类来源，都要看：

   1. `projects/*/.agent/project.yaml` 的 `project_only` 列表
   2. `projects/*/.agent/rules/*.md` 里的条目（由散文提炼而来）

   跳过 `_template` 目录。

2. **语义聚类：找出表达同一约束的条目**（措辞不同但含义相同）。

   **判据是语义相同，不是文字相同。** 下面三条属于同一个聚类：

   - 「所有对外接口必须携带 tenant_id」
   - 「查询条件必须带隔离标识，禁止跨租户聚合」
   - 「接口入参必须包含所属组织，用于数据隔离」

   聚类时按「这条约束约束的是什么决策点」分组，而不是按用词。
   分组名用决策点描述，如"数据隔离标识"。

3. **对每个聚类判断：出现在 ≥3 个项目？**（阈值细则见 `references/提升与淘汰判据.md`）

   | 出现项目数 | 处置 |
   |---|---|
   | ≥ 3 个项目 | **建议提升**为共享包条目 |
   | 恰好 2 个项目 | 标记为"观察"，不进候选清单，下次再看 |
   | 1 个项目 | 不处理，这是正常的项目特例 |

   为什么是 3 而不是 2：两个项目共同出现的约束可能只是这两个项目恰好相似
   （同一批人、同一时期、同一客户）。三个项目同时出现，才更可能是团队的共性。

4. **对达阈值的聚类，判断建议归属：**

   | 约束的性质 | 建议归属 | 编号前缀 |
   |---|---|---|
   | 跟具体技术栈有关（框架写法、语言语法） | `09_资产库/规范包/stacks/<对应包>` | 该包的 prefix |
   | 跟业务领域有关（业务规则、领域合规） | `09_资产库/规范包/domains/<对应包>` | `STD-DOM-<领域>-` |
   | 所有项目都适用（流程、编号、文档写法） | 对应业务域的 `standards/` 基线 | `STD-BASE-` |

   **判断有疑问时，标注「建议人工复核」，不要强行归属。** 归错包比不归更糟——
   它会让一个包混入不属于它的约束，后续没人敢动。

5. **生成候选清单**（含建议编号、出现项目、建议归属、理由）——结构见「产出契约」。
   已在包中存在的候选，标记为 "已存在"，建议改为在项目中 disable + 指向已有编号。

6. **反向：淘汰候选。** 从 `projects/<项目码>/.agent/spec-effective/*.json` 统计：
   每条包内条目被多少个项目的生效快照包含（即"被引用"）。

   | 情况 | 处置 |
   |---|---|
   | 被 0 个项目选中，且包内条目连续 3 个月零引用 | 列入淘汰候选 |
   | 被 1 个项目选中 | 不处理 |
   | 被禁用次数 ≥ 2 个项目 | **单独列一类**：这不是"没人用"，而是"多个项目都不适用"——说明该条目可能约束过严或归属错了包 |

   最后那一类最重要：**被多个项目禁用的条目，比零引用的条目更值得审查。**
   它说明这条规则与实际做法脱节。

7. **产出后必须做的事。** **不要只给清单就结束。**

   - 对清单里每一条"建议提升"，补一句人话解释：这条约束现在散在几个项目里，
     各自措辞不同，如果不提升会发生什么（通常是：改一处不改另一处，行为逐渐分叉）
   - 明确告诉用户下一步动作是什么：

     ```
     1. 人工确认候选（建议由知识库 Owner 拍板）
     2. 改包文件：新增条目到对应包，更新 PACK.md 的 files 列表（若新建文件）
     3. 包版本号 +0.1.0（新增条目属次版本变更）
     4. 改各项目 manifest：把原 project_only 条目改为 disable 并指向新编号
     5. 重跑 ai-spec-build --all
     ```

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不自动提升。** 只出候选清单，提升动作由人执行（改包文件 + 改项目 manifest + 重建快照）
- **不自动删除任何条目。** 淘汰同样是人的决策，且淘汰也只是出候选
- 不判断条目的技术正确性——只判断"重复出现的模式"
- 不修改 `projects/` 下的任何文件
- **不要因为"看起来重复"就下结论**——注意区分「同一决策点的相同约束」与「碰巧都用到了某个词」
- 不扫项目根的散文文档（要先经 `ai-spec-extract` 摘成条目）
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 项目数不足 2 个 | 提示信息不足，不做聚类，直接退出 |
| 聚类结果置信度低 | 在候选中标注"建议人工复核"，不做推断 |
| 候选条目已在包中存在 | 标记为 "已存在"，建议改为在项目中 disable + 指向已有编号 |

## 与其他 Skill 的关系

- 上游：`ai-spec-extract`（项目散文先摘成条目）、各项目的 `project_only` 与 `.agent/rules/`
- 下游：`ai-spec-build`——提升后要重建快照；它在 D 段给出的"项目级条目超 30 条"警告是本 Skill 的触发条件
- 同族：`ai-spec-build`（编译规范快照）、`ai-spec-check`（一致性检查）、`ai-spec-mount`（重建挂载层）——
  四个合起来是**知识库自身的治理工具**
