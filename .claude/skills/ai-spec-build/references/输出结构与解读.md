# 输出结构与解读

> 快照 `projects/<项目码>/.agent/spec-effective/<项目码>.md` 分四段，
> **且只装项目级内容**——域级规范（各域 `standards/`、规范包）不在里面，
> 它们到对应阶段按原文读。理解四段的**用途差异**比理解内容更重要。

## 段位速览

| 段 | 内容 | 谁读 | 注入方式 |
|---|---|---|---|
| **A** | 项目级常驻条目 | 每次执行代码生成 / 设计的模型 | 进批次 `CLAUDE.md`，**常驻** |
| **B** | 项目级按需索引 | 执行到具体任务的模型 | 按「触发场景」列定位后读条目原文 |
| **C** | 项目声明：选了哪些包 | 执行到该技术栈阶段的模型 | **指针**：据它去读包原文 |
| **D** | 项目级条目的来源 | 人（审计、判断项目级约束是否过期） | 不注入 |

## A 段：项目级常驻

**这是预算最紧张的一段，硬上限 120 行。** 每条两行：条目 ID + 标题，以及规则首句。

**判据是「不看这条会不会做错」**，不是「这条重不重要」。举例：

- ✅ 符合：「二期逻辑删除 1=正常、0/2=删除（方向与常见约定相反）」——不看就会查错数据
- ❌ 不符合：「变量命名用驼峰」——不看也基本不会错，且 lint 能兜住

**A 段条目过多（超过 ~35 条）是设计信号**：`tier: resident` 被滥用了。
要么收紧判据，要么把条目挪回它真正所属的文档——项目级条目跟着项目散文走，一个主题一份。

## B 段：项目级按需索引

一张表：条目 ID、摘要、来源文件、触发场景。**表里没有正文**，只有定位信息。

模型执行到具体任务时（如"写 Mapper"）按「触发场景」列找到相关条目，
再回 `.agent/rules/` 的提炼文件读原文。

**隐含要求**：条目的 `scope` 必须写清触发场景。写"后端"这种过宽的词会让索引失去检索价值。

## C 段：项目声明

**这一段的用途是「指路」，不是「给规则」。** 它列出本项目在每个维度选了哪个包，
以及「什么时候去读它」。

域级规范不编译进快照的代价就是这一段：模型必须知道**该去读哪一份原文**。
表里的「什么时候去读它」列给的就是阶段判据（如"写 SQL、建表改表、做数据库设计时"）。

包原文位置：知识库根下 `09_资产库/规范包/stacks/<包>/` 与 `.../domains/<包>/`。

## D 段：项目级条目的来源

列出每个提炼文件（`.agent/rules/*.md`）、它有多少条、提炼自哪份散文、**源文档是否已变更**。

**这是判断"项目级约束还算不算数"的唯一入口。** 提炼产物是散文的派生副本：
散文改了而没重新提炼，快照里的条目就是旧的——而且不报错。
`source_hash` 是它的保质期，D 段的状态列会写「⚠️ 源文档已变更，待重新提炼」。

处理方式：调用 `ai-spec-extract` 重新提炼，然后重跑 `ai-spec-build`。
**不要手工去改 `.agent/rules/` 里的文件**——那会让来源指纹对不上，等于制造一个假告警。

## 机读版 JSON

`<项目码>.json` 顶部有 `"scope": "project-only"`，含逐条完整信息
（`id` / `title` / `origin_file` / `tier` / `scope`）。用途：断链检测、覆盖率统计、给其他工具消费。

**判据**：JSON 里出现 `STD-BASE-*` 或包前缀（如 `STD-GAUSS-*`）的条目就是**异常**——
那说明快照被重新编译成了全量合并。`ai-spec-check` 会查这一条。

## 执行日志

`projects/<项目码>/.agent/logs/spec-build.jsonl` 每次构建追加一行：

```json
{"at": "2026-10-22T16:23:28+08:00", "project": "<项目码>", "entries": 29,
 "manifest_hash": "sha256:2a504cb2b06fc8ce", "snapshot_hash": "sha256:44cf64812b5756e6"}
```

`manifest_hash` 是**组合声明指纹**（只含 `stacks`/`domains`/`project_only`，与规范无关的改动不会让它变），
`snapshot_hash` 是**内容指纹**。

两个哈希是**可审计性的关键**：批次状态文件记录 `snapshot_hash` 后，
就能精确回答"这个批次开发时用的是哪版规范"。

`snapshot_hash` 变了说明规范内容变了——如果这个变化发生在批次进行中且没人察觉，
就是一个值得追查的信号。
