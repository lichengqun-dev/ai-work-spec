# 机制退役说明

> 这份文件回答一个问题：**哪些机制被刻意删掉了，为什么。**
> 留着它，是因为"删掉的东西"最容易在半年后被人当成"忘了做"而重新加回来——
> 那时又会带上一整套没人用的字段与校验。

## 1. 为什么退役

快照曾经装**全部层级**的规范（团队基线 + 技术栈包 + 领域包 + 项目层），
于是必须回答一个问题：**两个包的规则打架怎么办**。
`overrides`（覆盖 / 禁用 / 追加）、`frozen`（不可覆盖）、同层冲突仲裁，
三者都是为这个问题服务的。

现在快照**只装项目级内容**：域级规范（各域 `standards/`、`09_资产库/规范包/`）
到对应阶段按原文读取，**不参与编译**，也就不会与谁合并——冲突自然不存在。

**合并不是被简化了，而是不再需要了。**

## 2. 退役清单

| 机制 | 曾经的用途 | 现在怎么办 |
|---|---|---|
| `overrides`（append / disable / override） | 项目层改写包或基线条目 | 项目要偏离某条域级规范 → **在项目散文里写清「本项目用 X 不用 Y」**，由 `ai-spec-extract` 摘成项目级条目 |
| `frozen: true` | 拒绝项目层的任何修改 | 没有覆盖机制了，拦截无从谈起。要强调「这条不可协商」→ **在规范正文里写一行话**（`03_编码开发/standards/提交信息与分支规范.md` 的 `STD-BASE-005` 就是这么写的） |
| 同层冲突自动仲裁 + `domains` 优先级 | 两个领域包对同一决策点给出不同答案 | 这是**内容问题**，交给评审。manifest 里的 `domains` 仍按顺序声明（它决定阶段加载顺序），但**不再用于自动裁决** |
| `conflicts_with` 声明 | 让构建器知道哪两条条目冲突 | 删掉。语义矛盾靠评审发现，不靠机器声明 |
| `<!-- meta -->` 块（域级） | 承载 tier / scope / frozen / conflicts_with | 域级回归「原文」：四个字段的机器语义全部消失。「为什么」用正文里的文字表达 |
| `disable` 的 `expires` / `approved_by` | 防止"临时禁用变永久遗忘" | 机制没了，**但那条洞见还在**——见下 |

## 3. 仍然成立的三条洞见

**① 静默的选择会产生隐性债务。**

以前它用来论证"同层冲突必须报错而不是随便挑一个"。现在没有自动裁决了，
但同一道理用在更上游：**如果一个偏离域级规范的决定没有写进项目散文、没有被提炼成项目级条目，
它就是一次静默选择**——三个月后没人能解释当初为什么这么定。

**② "临时"必须有到期条件。**

以前它用来论证 `disable` 要带 `expires`。现在没有 disable 了，
但项目散文里写「暂不遵守 X」时，**照样要写清截止条件**，否则它和永久例外没有区别。

**③ 为了让构建通过而放宽校验，是这条链路里最贵的错误。**

构建失败一次，损失是几分钟；校验被放宽一次，损失是"以后再也没人相信快照"。

## 4. 构建失败时的排查顺序

```
1. 看清失败信息里的条目 ID / 包名 / 文件路径（脚本会打印这些）
2. 判断类型：
   - 配置写错（包不存在、版本不匹配、文件路径不存在）→ 改 manifest 或包
   - 项目级条目前缀不符 / 编号重复 → 确认是不是写错了文件；
     编号一经启用不复用，改编号等于断掉所有引用
3. 修完重跑。不要用 --check 当"跳过校验"用（它只是不写文件，校验照跑）
```

**绝对不要做的三件事**：改脚本放宽校验、删掉报错的条目、把失败当成"环境问题"重试。
