# ai-spec-mount · Skill 挂载层

## 能力声明

把知识库里的全部 Skill **挂载**到 `.claude/skills/`，让它们能被 Claude 的 skill 发现机制看到。

同时可**校验**挂载层是否与真实定义同步——不同步就是问题，不是"下次再说"。

这是纯脚本 Skill，**不调用模型**。

**为什么需要这一层**：知识库里的 Skill 原本只是 Markdown 文件，**没有被 Claude 的 skill 机制发现**。
使用者必须知道路径、手动让 AI 去读——这正是"上手难度高"的全部来源。
Claude 靠 `.claude/skills/<name>/SKILL.md` 的 frontmatter（`name` + `description`）决定
「什么时候该用哪个 skill」，所以要让这些 Skill 真正可用，必须把它们挂到那个位置。

**为什么是生成而不是手写**：挂载层只是**指针**，真实定义仍在各域的 `skills/<name>/` 目录里。
手写会产生 N 份需要同步的副本，**而副本一定会与真实定义分叉**——这个仓库里已经反复出现过这类问题
（README 里的条目数、域 README 里的路径、Skill 状态描述，全部是同一个病）。
所以挂载层是生成的，`description` 从真实定义里抽取。

**不做什么**：不改 Skill 的真实定义；不手改挂载层；不判断 Skill 的内容好坏——见「边界」。

## 何时用 / 何时不用

- **用**：
  - 新增、重命名、删除任何 Skill 后
  - 改了任何 Skill 的 `description` 后（**这是最容易忘、后果最隐蔽的一种**——
    挂载层的 `description` 决定模型何时选它，过期就等于按错误的条件选 Skill）
  - 改了 Skill 的目录位置后
  - `ai-spec-check` 报出"挂载层不同步"时
  - 发版前
- **不用**：要改的是 Skill 的正文内容（改真实定义，不是改挂载层）；判断 Skill 写得对不对
  （那是 `ai-spec-check` 与人的事）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 全部 Skill 真实定义 | `<域>/skills/*/SKILL.md` | 是 | 每个都须有 `name` 与 `description` |
| 仓库根目录 | 由 `CLAUDE.md` + `09_资产库/` 自动定位 | 是 | 两者都存在；否则拒绝执行 |

**`description` 是硬要求。** 缺它的 Skill 会被跳过并警告——那不是"少挂一个"，
而是这个 Skill 永远不会被任何会话看到。

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 挂载层 | `.claude/skills/<name>/SKILL.md` | 生成物，含 `name` + `description` + 指向真实定义的路径 |
| 同步性校验结果 | 输出给调用者 | 一致 / 列出不一致项 |

**挂载层要入库。** 它是 Claude 能否发现这些 Skill 的前提，不是本地产物。
（`.gitignore` 里对此有显式说明，不要把它忽略掉。）

**重建是"先清空 `.claude/skills/` 再重新生成"，不是增量更新。**
所以：**任何手工放进 `.claude/skills/` 的东西都会消失。** 这是刻意的——
增量更新会留下"真实定义已删但挂载层还在"的孤儿，而孤儿挂载会让 Claude 调用一个不存在的 Skill。

## 前置条件

**hard（不满足则拒绝执行）**

- 仓库根可定位
- 至少存在 1 个带 `name` + `description` 的 `SKILL.md`

**soft**

- 无。本 Skill 的输入全在仓库内，没有"顺序性"前置——任何时刻单独运行都成立

## 执行步骤

1. **先判断用户要的是重建还是校验**——这两件事后果不同：

   | 用户说 | 动作 | 会不会写文件 |
   |---|---|---|
   | "挂载层过期了""刚加了 Skill""重建一下""Claude 看不到某个 Skill" | **重建** | 会——清空并重新生成 `.claude/skills/` |
   | "检查一下挂载层""是不是同步的""发版前过一遍" | **校验** | 不会，只报不改 |

   **分不清就问。** 重建会清空目录，不该在用户只想要个答案时发生。

2. **执行本 Skill 的实现脚本**（**知识库根下** `00_工作空间配置/scripts/build_claude_skills.py`）。
   两个动作都由这一个脚本完成，参数见脚本 docstring。**不需要向用户展示参数**——
   调用本 Skill 的意图本身已经足够。

3. **逐条读出脚本输出，不要总结成"已完成"。**

4. **重建成功**：脚本报 `✅ 已生成 N 个 skill 挂载到 .claude/skills/`。
   —— 把 N 念出来，并与"知识库里的 Skill 总数"对照。**N 变小了就是出事了**，
   多半是某个 Skill 缺 `description` 被跳过了。

5. **校验一致**：脚本报 `✅ 挂载层与真实定义一致（N 个 Skill）`。
   —— 顺手提一句：`.claude/skills/` 是生成物，改动后要入库。

6. **有警告或不同步**：**原样转达全部内容**，然后按「失败处理」表给处理建议。

## 独立执行

纯脚本 Skill，不依赖批次状态：**任何时刻都可单独运行**。
最安全的单独执行形态是**只校验不写文件**——它只报不改，任何仓库状态下都不会改动任何东西。

## 边界（明确不做）

- **不改 Skill 的真实定义。** 只读 `<域>/skills/<name>/`，只写 `.claude/skills/`
- **不手改挂载层。** 它是生成物；改它等于制造一份会在下次重建时消失的副本
- **不要在重建前不确认。** 重建会清空整个目录——任何手工放进去的东西都会消失
- **不要为了让校验通过而只改挂载层。** 那正好制造了这个 Skill 要防的那种分叉
- **不要把 `description` 写成"做什么"的功能描述。** 它是给 Claude 判断**何时触发**用的，
  要写"什么时候该用它"（如"新增、重命名、删除 Skill 之后使用"），而不是"本 Skill 重建挂载层"
- 不判断 Skill 的**内容**好坏。那是 `ai-spec-check` 与人的事
- 不执行 git 操作

## 失败处理

| 脚本输出 | 含义 | 处理 |
|---|---|---|
| `缺 name 或 description，跳过` | 该 Skill 不会被任何会话发现 | 去它的真实 `SKILL.md` 补 frontmatter。**`description` 不是可选项**——它是 Claude 决定"什么时候用哪个 skill"的唯一依据 |
| `挂载层缺失` | 该 Skill 没被挂上 | 重建即可。若重建后仍缺失，说明它的 frontmatter 有问题 |
| `description 与真实定义不一致` | 挂载层过期 | 重建。**这才是这个 Skill 存在的主要理由**——过期的 `description` 会让模型按错误的触发条件选 Skill，而它不会报错，只会静默选错 |
| `挂载层存在但知识库里已无此 Skill` | 孤儿挂载 | **先确认那个 Skill 是真的被删了，还是被移动/改名了。** 前者重建清掉即可；后者要先找回真实定义，否则挂载层会指向不存在的东西 |
| 校验发现不同步 | 哪些缺挂载、哪些 `description` 过期、哪些是孤儿 | 列出不一致项，退出码 1 |

## 输出格式

执行完用下面结构回复（保持简短）：

```
动作：<重建 / 校验>
结果：<N 个 Skill 已挂载 / 挂载层与真实定义一致 / N 处不同步>

<如有警告或不同步，原样列出>

<提示：.claude/skills/ 是生成物，改动后需入库>
```
