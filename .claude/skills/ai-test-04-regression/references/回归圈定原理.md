# 回归圈定原理

> 本文件回答「为什么这么做」「每一跳断了会怎样」。**范围怎么算、产出什么格式在 `SKILL.md` 里**，本文件不重复规则。

## 一、为什么这一步值得单独做一个 Skill

回归测试的传统做法只有两种，都不好：

| 做法 | 问题 |
|---|---|
| 全量回归 | 慢。改动一行也要跑完全部用例，团队会开始跳过回归 |
| 凭经验选 | 漏。"我觉得这块不影响"——直到线上出问题 |

本 Skill 把它变成**图的遍历**：从代码变更出发，沿依赖关系走一遍，得出范围。
比全量快，比经验准，而且**范围是怎么来的可以复核**——这是最关键的一点。

## 二、走这条链，每一跳断了都会退化成"凭经验"

```
代码 diff
  → 提交信息里的 FR 编号
    → 依赖关系图双向遍历
      → 受影响 FR 集合
        → 每个 FR 挂载的 TC 集合
          → 回归范围
```

| 断点 | 后果 |
|---|---|
| 提交信息没带 FR | 无法映射，只能按文件路径猜 |
| 依赖图为空 | 无法遍历，只能全量或凭经验 |
| 用例没挂 FR | 圈出 FR 也找不到对应用例 |

遇到断点**拒绝执行并说明**，不要猜一个范围。猜出来的范围看起来合理，但没人能复核它。

## 三、双向遍历，尤其是上游

```
        ┌─ 上游：依赖我的功能  ← 最容易漏
我改的 FR ─┤
        └─ 下游：我依赖的功能
```

只往下游走（"我改的 FR 依赖谁"）会漏掉**上游**：改了底层能力，所有依赖它的功能都受影响。

| 方向 | 含义 | 漏掉的后果 |
|---|---|---|
| 下游 | 我依赖的功能 | 我改了它，被改的功能需回归 |
| **上游** | 依赖我的功能 | **我改了底层，上层全部受影响——这是最容易漏的方向** |

**"改了 A 崩了 C"绝大多数是上游方向没遍历到。**

例：改了「基础数据字典」的读取逻辑 → 所有依赖字典的模块都受影响。
如果只往下游遍历（"字典依赖谁"），会得出"什么都没影响"的结论。

## 四、这套机制的天花板由依赖图决定

**依赖图不完整，回归范围就一定不准**——而且是偏向"漏"的方向（因为没边就没路径）。
所以每次发现"疑似受影响但图上无路径"，都应该回填依赖图，而不是记一笔就算了。

本目录值得沉淀的内容：依赖类型判定参考（数据依赖 / 流程依赖 / 状态依赖 怎么区分）、
历次"改了 A 崩了 C"的案例（**特别是依赖图没覆盖到的那类**）、回归范围与执行时长的权衡经验。
