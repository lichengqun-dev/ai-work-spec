# ai-test-05-report · 测试报告与上线建议

## 能力声明

汇总测试执行结果，产出**测试报告**与**上线建议**。

**报告的价值在于"让人据此做决定"，而不是"看起来完成度很高"。** 一份把遗留风险写在角落的报告，
比一份分节漂亮但没人看的报告有用得多。**结论必须在第一屏**——读者（往往是没时间细看的人）
会直接看结论和通过率，然后决定上线。

**不做什么**：不修缺陷、不补测、不美化数据、不做上线部署、
不判定"这个缺陷不重要"——见「边界」。

## 何时用 / 何时不用

- **用**：执行结果与缺陷台账已产出，要给出测试结论与上线建议时（测试收尾）
- **不用**：修缺陷（开发职责）；补测（回到 `ai-test-03-execute`）；上线部署（`ai-iteration-04-release` 或运维职责）
- **存在未关闭 P0/P1 时仍走本 Skill**：正常产出报告，但上线建议必须是"不建议上线"

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 执行结果 | `ai-test-03-execute` 产出 | 是 | 含每条的结论 |
| 缺陷台账 | `ai-test-03-execute` 产出 | 是 | 表头固定（见 `ai-test-03-execute`） |
| 回归范围 | `ai-test-04-regression` 产出 | 是 | 受影响 FN 与用例清单 |
| 测试用例 | `ai-test-01-cases` 产出 | 是 | 用于计算总数与执行率 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 测试报告 | 项目文档仓 `<需求名>/04_测试/测试报告.md` | **含「用例执行率」字段**（见下） |

**报告必须包含可被机械解析的执行率**，两种写法任选，**字段名不能改**：

```markdown
用例执行率：100%
```

或

```markdown
| 项 | 值 |
|---|---|
| 用例执行率 | 100% |
```

gate-05 的 `testcase-executed` 检查项按这两种形式解析。**改字段名它会报"无法解析"**——
那个告警是对的：**"用例都跑完了吗"这件事必须能被机械判定**，否则只能靠人说，而人说的会被打折。

产出结构：

```markdown
# 测试报告

## 一、结论
**不建议上线。** 依据：存在 1 个未关闭 P0 缺陷（导出产生错误行数），
且 3 条核心路径用例因第三方沙箱不可用而未执行。

## 二、执行概览
## 三、缺陷汇总
## 四、遗留风险
## 五、回归覆盖情况
## 六、附录（明细）
```

**最容易犯的错是把遗留风险写在最后。** 一份把风险埋在附录里的报告，
读者会直接看结论和通过率，然后决定上线。

缺陷汇总要把未关闭项顶到前面：

```markdown
## 三、缺陷汇总

| 级别 | 总数 | 已关闭 | 未关闭 |
|---|---|---|---|
| P0 | 1 | 0 | **1** |
| P1 | 1 | 1 | 0 |
| P2 | 2 | 1 | 1 |
| P3 | 0 | 0 | 0 |

**未关闭的阻塞项**
- BUG-PROJ-20261020-001-001（P0）导出产生错误行数 —— 负责人张三，预计 10-21 修复
```

## 前置条件

**hard（不满足则拒绝执行）**

- 执行结果与缺陷台账已产出（台账表头符合约定，否则不自行猜测列含义）
- 用例总数可确定（用例文件存在且编号可解析）
- 回归范围已产出（报告的「回归覆盖情况」节依赖它）

**soft**

- 无。上游产出物/编号不可解析时一律报告并停止，不自行估算数字

## 执行步骤

1. 统计：用例总数、已执行、通过、失败、**用例执行率**
2. 缺陷汇总：按级别统计，列出**未关闭的 P0/P1**
3. 回归覆盖情况：回归范围内的用例是否全部执行
4. **明确列出遗留风险**：未执行的用例、未修复的缺陷、覆盖不到的路径
5. 给出上线建议，并说明依据
6. 回写批次状态文件：本步骤置 `done`，登记测试报告与哈希

### 上线建议必须带条件

| 结论 | 条件 |
|---|---|
| **建议上线** | 执行率 100%，无未关闭 P0/P1，遗留风险已列明且可接受 |
| **有条件上线** | 存在遗留项，但影响可控——**必须写明具体条件与后续动作** |
| **不建议上线** | 有未关闭 P0/P1，或执行率不足且缺口涉及核心路径 |

**"有条件上线"最容易写虚。** 反例："建议在注意风险的前提下上线"——这句话没有任何信息量。
正例："建议上线，条件：P2 缺陷 3 条转入下批次（已登记到快车道台账），需在发布说明中标注；
受限的 3 条第三方沙箱用例在沙箱恢复后 24 小时内补测。"

不写条件的"有条件上线"等于"上线"。**条件要能被验收：谁、在什么时候、做什么。**

### 存在未关闭的 P0/P1 时

**正常产出报告**，但上线建议必须是"不建议上线"，并列出未关闭项。

不要因为"负责人说今天能修好"就写成"建议上线"。修好了再跑一次门禁，
这份报告的价值恰恰在于它记录的是**当时的事实**。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不修缺陷**（开发职责）
- 不补测（回到 `ai-test-03-execute`）
- **不美化数据**：执行率是 93% 就写 93%
- 不做上线部署（那是 `ai-iteration-04-release` 或运维职责）
- 不判定"这个缺陷不重要"——那是定级阶段的结论，不是报告阶段的
- 不要美化执行率或通过率
- 不要把遗留风险埋在报告末尾
- 不要写没有具体条件的"有条件上线"
- 不要在存在未关闭 P0/P1 时给"建议上线"
- **不要改「用例执行率」字段名**
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 用例总数无法确定 | 报告并停止，回到 `ai-test-01-cases` 补编号 |
| 缺陷台账表头不符 | 报告并停止——不自行猜测列含义 |
| 存在未关闭 P0/P1 | **正常产出报告**，但上线建议必须是"不建议上线"，并列出未关闭项 |
| 执行率不足且缺口涉及核心路径 | 同上，明确写进遗留风险 |
