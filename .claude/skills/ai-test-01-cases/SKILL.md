# ai-test-01-cases · 测试用例生成

## 能力声明

从 **PRD + 接口契约 + 功能详细设计**三者生成测试用例，编号挂载到 `FR`。

三份输入缺一不可：PRD 提供业务场景与验收标准、契约提供参数组合与错误码、详细设计提供异常分支。
只从其中一份生成，会漏掉另外两个维度的问题。**三份都读，然后交叉推导**——只从 PRD 生成会得到一堆"能跑通就行"的用例。

**不做什么**：不写自动化脚本（那是 `ai-test-02-automation`）、不执行用例（`ai-test-03-execute`）、
不修实现代码、不设计性能测试方案——见「边界」。

## 何时用 / 何时不用

- **用**：进入测试阶段，要把 PRD、冻结契约、功能详细设计三者落成用例集时
- **不用**：写接口自动化脚本（`ai-test-02-automation`）；执行用例（`ai-test-03-execute`）；
  设计性能测试方案（另一类工作，不在本 Skill 内）
- **用例与实现不符时仍走本 Skill**：先确认是用例错了还是实现错了，不要直接改用例迁就实现

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| PRD | `ai-requirement-04-prd` 产出 | 是 | 每个功能有 `FR` 编号与验收要点 |
| 接口契约 | `ai-design-04-api` 产出 | 是 | 冻结态；每 operation 带 `x-fr-id` 与错误码 |
| 功能详细设计 | `ai-design-02-detail` 产出 | 是 | 每 FR 一节，含异常分支与边界 |
| 原型工程 | `ai-requirement-03-prototype` 产出 | 否 | 用于 UI 路径类用例 |
| 测试用例设计规范 | 知识库根下 `04_测试验证/standards/测试用例设计规范.md` | 是 | 编号挂载规则、优先级 |
| 缺陷分级标准 | 知识库根下 `04_测试验证/standards/缺陷分级标准.md` | 是 | 用于标注用例严重程度 |

三份必需输入各自提供什么、只读它一份会漏什么：

| 输入 | 提供什么 | 只读它一份会漏什么 |
|---|---|---|
| PRD | 业务场景、验收要点 | 漏掉参数组合与错误码 |
| 接口契约 | 参数定义、错误码、必填性 | 漏掉业务规则与异常流程 |
| 功能详细设计 | 异常分支、边界条件、状态流转 | 漏掉参数边界与接口层错误 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 测试用例 | 项目文档仓 `<需求名>/04_测试/测试用例.md` | **编号格式 `TC-<FN编号>-<两位序号>`** |
| 用例登记 | `projects/<项目码>/.agent/index/功能编号总表.md` 功能点段的「覆盖用例」列 | 回填 `TC` 编号 |

产出结构——每条用例的三个要素：

```markdown
### TC-FR-CORE-045-01 正常导出

**前置**：存在 100 条未归档数据，当前用户有导出权限
**步骤**：
1. 打开列表页
2. 点击导出
3. 等待完成

**预期**：下载到 xlsx 文件；行数 = 100；列与页面列表一致；耗时 ≤ 30 秒
```

**编号必须挂载到 `FR`**，写法固定：

```
TC-FR-CORE-045-01      ✅
TC-001                 ❌
导出测试1               ❌
```

格式 `TC-<FN编号>-<两位序号>`，两位序号在同一 FR 下递增。

**预期结果必须可判定。** 反例：「页面正常显示」「导出成功」——
不可判定的预期结果使用例执行变成主观判断，不同人执行结果不同，也无法自动化。

## 前置条件

**hard（不满足则拒绝执行）**

- PRD、接口契约、功能详细设计三份必需输入均已产出（每 FR 有 `FR` 编号与验收要点）
- 契约处于**冻结态，且哈希与记录一致**
- 功能详细设计中每个 FR 都有异常分支章节（缺失时拒绝——异常分支是用例设计的主要输入）

**soft（不满足则提示，可继续）**

- gate-04 已通过（未通过时产出物标注「未经上游确认 —— gate-04 未通过」）
- 原型工程已产出（缺则 UI 路径类用例可能不全，产出物标注）

## 执行步骤

1. 取本批次范围内全部 `FR`
2. **每个 FR 至少一条用例**（gate-05 的 `fr-has-testcase` 是 BLOCK 级）
3. 按三个来源分别推导：

   | 来源 | 推导什么 |
   |---|---|
   | PRD 验收要点 | 正常路径与验收判定 |
   | 契约 | 参数组合、边界值、**每个错误码一条** |
   | 详细设计的异常分支 | 状态冲突、并发冲突、权限不足、数据为空、数据量上限 |

   契约里声明了 403/409 却没有对应用例，等于声明了不测。

4. 编号 `TC-<FN编号>-<两位序号>`，两位序号在同一 FR 下递增
5. 每条用例写清：前置条件、步骤、**可判定的预期结果**
6. 覆盖检查（产出后自查三条，见下）
7. 回填 `projects/<项目码>/.agent/index/功能编号总表.md` 功能点段的「覆盖用例」列
8. 回写批次状态文件：本步骤置 `done`，登记 `<需求名>/04_测试/测试用例.md` 与哈希

### 覆盖检查

- 每个 FR 都有用例吗？（gate-05 的 BLOCK 项）
- 契约里每个错误码都有对应用例吗？
- 详细设计里每条异常分支都有对应用例吗？

**第三条最容易漏。** 详细设计写了 5 条异常分支，用例里只覆盖了 2 条——这是"覆盖率高但漏测多"的典型形态。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不写自动化脚本**（那是 `ai-test-02-automation`）
- 不执行用例（`ai-test-03-execute`）
- 不修实现代码。用例与实现不符时**先确认是用例错了还是实现错了**，不要直接改用例迁就实现
- 不设计性能测试方案（那是另一类工作）
- 不要写不挂载 FR 的游离编号
- 不要写不可判定的预期结果
- 不要只从 PRD 生成（会漏参数与错误码维度）
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 某 FR 的详细设计缺异常分支章节 | **拒绝执行**，回到 `ai-design-02-detail` 补齐——凭空想象异常分支会漏掉真实的分支 |
| 某 FR 找不到对应接口 | 列出——**通常意味着设计阶段漏了接口，或该 FR 不需要接口但设计没说清** |
| 验收要点不可判定 | 列出并记入待澄清，**不自行编造判定标准** |
| 契约哈希不一致 | 停止，报告契约被改动过 |
| 用例与实现不符 | 先确认是**用例错了**还是**实现错了**，报告并停止，由人判断——不要直接改用例迁就实现；改用例迁就实现等于用手中的笔把缺陷擦掉 |

## 输出格式

```
FR 范围：3 个（FR-CORE-045 / 046 / 047）
新增用例：18 条

覆盖分布：
- 正常路径：3 条
- 契约错误码：6 条（403 / 409 / 400 各 2 条）
- 异常分支：7 条（状态冲突 3 / 并发 2 / 数据为空 2）
- 边界值：2 条（数据量上限、时间范围）

未覆盖：
- FR-CORE-047 的「导出格式异常」分支——详细设计未写明该分支的预期行为，已记入待澄清

待确认：无
```
