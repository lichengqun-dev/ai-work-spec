# ai-daily-03-techdebt · 技术债识别与排期建议

## 能力声明

从**快车道台账、故障复盘、缺陷台账**中识别技术债，输出带依据的排期建议。

**核心纪律：技术债必须有数据依据。** "我觉得这块代码有点乱"排不进任何计划——
"这块一个月被改了 7 次"才能。

**不做什么**：不给没有数据依据的债项、不排期不分配资源、**不自动重构**、不评价代码风格——见「边界」。

## 何时用 / 何时不用

- **用**：按月执行，从运行数据里识别技术债并给出带依据的排期建议
- **不用**：快车道台账为空——没有数据就没有依据，**拒绝执行**
- **不用**：评价代码风格（那是 lint 的事）；实施重构（那是排期后的常规开发流程）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 快车道台账 | `projects/<项目码>/.agent/index/快车道台账.md` | 是 | 含时间、FN、改动摘要 |
| 故障案例库 | `09_资产库/故障案例库/线上问题复盘.md` | 否 | 存在则纳入分析 |
| 缺陷台账 | 项目文档仓 | 否 | 存在则纳入分析 |
| 依赖关系图 | `projects/<项目码>/.agent/index/依赖关系图.md` | 否 | 用于判断影响面 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 技术债清单 | `projects/<项目码>/.agent/index/技术债清单.md` | 每项含：位置、依据（数据）、影响面、建议处置、优先级 |

产出结构——清单的每一项：

```markdown
## 技术债清单

### TD-001 导出模块（FN-CORE-045）

**依据**
- 快车道台账：近 30 天改动 7 次（2026-09-21 ~ 2026-10-20）
- 故障复盘：1 次（INC-20261020-003，缓存失效链路）
- 依赖关系图：被 3 个 FN 依赖

**问题判断**：导出能力在持续叠加（分组维度、格式、结果列），每次改动都是打补丁式扩展，
原始设计的「单一导出任务」模型已不适用。

**影响面**：中等——3 个下游 FN，但均为主流程。

**建议处置**：重构为可扩展的导出任务模型；建议在下次迭代清出独立批次。

**优先级**：高（改动频率 + 故障均集中于此）

---

### TD-002 …（未达到阈值的候选不列入）
```

产出结构——样本不足时的标注（**标注比不标注好，不标注比乱给结论好**）：

```
⚠️ 样本说明：台账覆盖 12 天，样本不足。以下结论仅供参考，
建议积累到 4 周后重新分析。
```

## 前置条件

**hard（不满足则拒绝执行）**

- 快车道台账存在且有数据（**空台账时拒绝**——没有数据就没有依据，见失败处理）

**soft（不满足则提示，可继续）**

- 台账覆盖时间足够（建议 ≥4 周；数据太少时结论不可靠）
  → 不满足时照常产出，并在清单顶部标注「未经上游确认 —— 台账覆盖不足 4 周，样本不足，结论仅供参考」

## 执行步骤

1. 统计快车道台账：按 FN 聚合改动次数
2. 统计故障复盘与缺陷台账：按模块聚合
3. 结合依赖关系图判断影响面
4. 对每个候选债项**列出数据依据**（具体数字，不是形容）
5. 给出建议处置与优先级；**交叉最有价值**——既是高频改动、又被广泛依赖、又反复出问题 → 优先级最高
6. 写入 `projects/<项目码>/.agent/index/技术债清单.md`，并输出摘要
   （本次新增几项、优先级分布、相比上次的变化）

### 识别依据（必须来自数据，不来自感觉）

| 信号 | 数据来源 | 说明 |
|---|---|---|
| **高频改动** | 快车道台账 | 同一 FN 在 N 天内被改 ≥M 次 → 该处设计可能不适用 |
| **反复出问题** | 故障复盘 | 同一模块 N 次故障 → 结构性问题而非偶发 |
| **缺陷集中** | 缺陷台账 | 同一模块缺陷占比显著高于其他 |
| **影响面大** | 依赖关系图 | 被很多 FN 依赖的模块，改动风险高 |
| **热修遗留** | 故障复盘 | 热修往往只止血，遗留了长期方案 |

示例阈值（**可按项目调，但要有阈值**）：同一 FN 30 天内改动 ≥5 次；同一模块 60 天内故障 ≥2 次；
某模块缺陷占比 > 全部模块的 25%；被 ≥10 个 FN 依赖且处于高频改动区。

没有阈值的"高频"和"集中"都是主观判断。正反例与阈值调参口径见 `references/技术债识别要点.md`。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始（它的输入是运行数据，不是流程产出物）
- soft 不满足时照常产出，并在清单顶部标注「未经上游确认 —— 台账覆盖不足 4 周，样本不足，结论仅供参考」
- 批次状态文件不可写（本 Skill 不属任何批次）时：清单照常写入 `projects/<项目码>/.agent/index/技术债清单.md`，
  跳过状态回写并在报告中说明

## 边界（明确不做）

- **不给没有数据依据的债项。** "代码可读性差"不是债项，除非能给出具体证据
- 不排期、不分配资源（那是人的决策）
- **不自动重构**（本 Skill 只识别与建议）
- 不评价代码风格——风格问题应由 lint 解决，不占用技术债额度
- 不要凭代码阅读给出"技术债清单"（那是代码评审的结论，不是技术债分析的结论，可信度差一个量级）
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 快车道台账为空 | **拒绝执行**，说明无数据依据；建议先运行一段时间台账再分析 |
| 台账覆盖时间 < 4 周 | 产出结果但**明确标注"样本不足，结论仅供参考"** |
| 某项只有感觉没有数据 | **不列入清单**——列进去会让整份清单的可信度下降 |

## 输出格式

```
分析周期：2026-09-21 ~ 2026-10-20（30 天）
输入：快车道台账 42 条、故障复盘 2 条、缺陷台账 31 条

新增债项：3 项
  TD-001 导出模块        优先级 高（改动 7 次 + 1 次故障 + 被 3 个 FN 依赖）
  TD-002 列配置服务      优先级 中（改动 5 次，但无故障、影响面小）
  TD-003 上传路径        优先级 中（缺陷占比 34%）

未列入：4 个候选未达阈值（列出但不建议排期）
样本说明：台账覆盖 30 天，样本充分
```
