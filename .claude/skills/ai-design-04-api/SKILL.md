# ai-design-04-api · 接口契约设计

## 能力声明

依据功能详细设计与数据库设计产出**接口契约（OpenAPI）**，并在 gate-03 通过后进入冻结态。
每个 operation 带 `x-fr-id` 与 4xx/5xx 响应，字段类型与数据库设计一致。

**契约是前后端并行开发的唯一依据。** 契约不冻结，并行开发必然在联调时返工——而联调返工是代价最高的一类
返工，因为它同时占用前后端两个人的时间。

**不做什么**：不实现接口、不做接口性能设计、不定义内部方法签名、冻结后不修改——见「边界」。

## 何时用 / 何时不用

- **用**：功能详细设计与数据库设计均已产出，要把跨进程/跨前后端的调用定成契约时
- **不用**：只是实现接口（那是编码阶段的事）；只是做接口压测与性能调优（那是另一回事）
- **契约已冻结后需要变更**：不要用本 Skill 直接改产出物——停止并说明需开变更子批次（`<原批次号>-C<n>`），
  原批次产出物保持不可变。见「边界」与「失败处理」

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 功能详细设计 | `ai-design-02-detail` 产出 | 是 | 每 FR 一节 |

| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 接口设计规范（`STD-BASE-32x`）从这里读 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 接口契约 | 项目文档仓 `<需求名>/02_设计/接口契约.yaml` | OpenAPI 3，**每个 operation 带 `x-fr-id` 与 4xx/5xx 响应** |
| 接口登记 | `projects/<项目码>/.agent/index/功能编号总表.md` 接口段 | `API-<模块码>-<3位>` + 所属 FR + 契约版本 |

产出结构（一个 operation 的最小形态）：

```yaml
paths:
  /api/v1/export:
    post:
      operationId: exportList
      x-fr-id: FR-CORE-045          # ← 必须有
      summary: 列表导出
      responses:
        "200":
          description: 导出成功
        "403":
          description: 无权限
          content: { application/json: { schema: { $ref: '#/components/schemas/Error' } } }
        "409":
          description: 数据状态冲突
```

## 前置条件

**hard（不满足则拒绝执行）**

- 功能详细设计已产出（每 FR 一节）
- 数据库设计已产出（字段类型要对齐，缺了就没有对齐的基准）
- 功能详细设计中涉及外部交互的 FR 全部已列出（**漏一个就等于漏一个接口**）
- 契约尚未冻结（**已冻结则拒绝改写**——冻结后变更必须走变更子批次）

**soft**

- 无。上列各条都是硬依赖，没有"顺序性"前置——hard 全满足即可单独跑

## 执行步骤

1. 从功能详细设计的时序中提取**接口边界**（哪些调用跨进程/跨前后端）
2. 向编号总表申请 `API-<模块码>-<3位>` 编号
3. 逐个产出 operation，**必须包含**：
   - `x-fr-id`：该接口服务的 `FR` 编号（gate-03 的 `api-has-fn`，**BLOCK**）
   - `responses` 中至少一个 4xx/5xx（gate-03 的 `api-error-codes`，**WARN**）
   - 完整的请求/响应 schema，字段类型与数据库设计一致
4. 校验契约结构（gate-03 的 `openapi-valid`，**BLOCK**）：`openapi` 版本字段、`info.title`、`paths` 齐全；
   路径以 `/` 开头；每个 operation 有 `responses`
5. 登记接口到编号总表：`API` 编号、路径、所属 FR、契约版本
6. 回写批次状态文件：本步骤置 `done`，登记契约文件与哈希

### 三个必须写进契约的字段

**一、`x-fr-id`：每个 operation 必须能追溯到 FR。** 检查项 `api-has-fn`（BLOCK）：没有这个字段，
且 operation 描述里也找不到 FR 编号时，报孤儿接口。**孤儿接口往往意味着需求分析漏了东西，
或设计时凭空加了一个。** 两种情况都值得停下来看。

**二、`responses` 里的 4xx/5xx。** 检查项 `api-error-codes`（WARN）：只有 200 的接口，前端无法给出准确提示，
只能显示"系统错误"；测试也无法针对性地设计异常用例。**错误码是契约里信息密度最高的部分**，别只写一个通用的 500。

**三、结构完整性。** 见执行步骤第 4 条。完整规范校验建议在 CI 中追加：
`npx @redocly/cli lint <需求名>/02_设计/接口契约.yaml`

### 字段类型必须与数据库设计一致

契约里的字段类型、长度、可空性，要和 `数据库设计.md` 对齐。不一致时**以数据库设计为准并报告冲突**，
不要自行取舍——自行取舍的结果是前端按契约写、后端按库表写，联调时才发现。

### 契约冻结的语义

契约在本 Skill 产出，**在 gate-03 通过后**进入冻结态。冻结动作由 `ai-design-06-review` 在门禁通过后记录。

冻结意味着：**此后任何变更都需要通知前后端双方，并重跑受影响的下游步骤。**
这个设计的价值是：你永远能回答"联调那一刻的契约是什么样"。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始（如只补一个接口的错误响应）
- 本 Skill 无 soft 前置，因此不存在"未经上游确认"的标注场景
- 批次状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不实现接口**（那是编码阶段的事）
- 不做接口性能设计（压测是另一回事）
- **不定义内部方法签名**——契约只描述**跨边界**的调用。把它们写进来会让契约变成一份会随时过期的
  代码副本，而契约的价值恰恰在于稳定
- **冻结后不修改。** 变更走变更子批次并通知前后端负责人——**不要偷偷改**
- 不省略 `x-fr-id` 与错误响应（那会让门禁失败，且失败是对的）
- 不降低校验标准来让契约通过
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 某接口无法追溯到 FR | 拒绝完成并列出——**孤儿接口往往意味着需求分析漏了东西，或设计时凭空加了一个** |
| 字段类型与数据库设计冲突 | 以数据库设计为准并报告冲突，不自行取舍 |
| 契约无法通过结构校验 | 修正后重跑，不降低校验标准 |
| 已冻结契约需变更 | 停止，说明需开变更子批次（`<原批次号>-C<n>`），并通知前后端负责人 |
