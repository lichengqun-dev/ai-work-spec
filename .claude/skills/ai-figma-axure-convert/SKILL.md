# ai-figma-axure-convert · 设计稿转原型

## 能力声明

把外部设计稿（Figma / Axure 导出物）转成**与 `ai-requirement-03-prototype` 同构的原型产出**，
并补齐 `data-fr` 标记。

**"同构"是硬要求**：`ai-requirement-04-prd` 靠遍历原型的 `data-fr` 标记生成 PRD。
两条路径（自画原型 / 外部设计稿）的产出格式必须一致，否则 04-prd 只认其中一条。

**唯一的目标是信息结构与交互路径可验证，不是像素级复刻**（理由见 `references/设计稿转换要点.md`）。

**不做什么**：不做像素级复刻、不产出 PRD、不修改 `ai-requirement-03-prototype` 的产出——见「边界」。

## 何时用 / 何时不用

- **用**：用户提供了设计稿导出物（Figma JSON / Axure HTML 导出 / 切图 + 标注），要从设计稿产出原型时
- **不用**：没有设计稿、要从需求从零规划原型 → `ai-requirement-03-prototype`；
  原型已存在、要写 PRD → `ai-requirement-04-prd`
- 本 Skill 与 `ai-requirement-03-prototype` 是**并列关系**：一个从需求画原型，一个从设计稿转原型，
  两者产出的格式必须同构

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 设计稿导出物 | 用户提供 | 是 | Figma JSON / Axure HTML 导出 / 切图 + 标注，可解析 |
| 需求功能分析 | `ai-requirement-02-analysis` 产出 | 是 | 每个功能有 `FR` 编号——**用于补齐标记** |
| 原型工程仓 | `ai-requirement-01-init` 产出 | 是 | 目标落点 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 目标前端技术栈从这里读 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 原型页面 | 原型工程仓 | **与 `ai-requirement-03-prototype` 同构**：可运行、每个可交互元素带 `data-fr` |
| 标记补齐说明 | 项目文档仓 `<需求名>/01_需求/原型标记补齐说明.md` | 哪些元素无法映射到 FR、需人工确认 |
| 原型规划（补充） | 项目文档仓 `<需求名>/01_需求/原型规划.md` | 与 03-prototype 合并——页面清单与 `PAGE` 编号 |

标记补齐说明的产出结构：

```markdown
# 原型标记补齐说明

## 一、页面清单
| PAGE 编号 | 页面 | data-fr 标记数 |

## 二、待人工确认
| 元素 | 位置 | 为什么无法归属到 FR |

## 三、冲突提示
| 设计稿有、需求功能分析没有的功能 | 是需求遗漏还是设计稿版本较旧 |
```

## 前置条件

**hard（不满足则拒绝执行）**

- 需求功能分析已产出，且每个功能有 `FR` 编号（无编号则拒绝——没有编号就无从补标记）
- **格式基准可读**：`ai-requirement-03-prototype` 的 `SKILL.md` 与产出契约存在——同构是硬要求，
  读不到基准就无从对齐，不要凭印象造一套格式
- 生效快照中 `fe` 维度的规范包存在（技术栈未知时拒绝，不要自己选一套）

**soft（不满足则提示，可继续）**

- `ai-requirement-03-prototype` 尚未产出过任何原型：本 Skill 照常产出，格式一律以它的产出契约为基准，
  产出物标注「未经上游确认 —— 尚无 03-prototype 产出可对齐」

## 执行步骤

1. **先读格式基准**：读 `ai-requirement-03-prototype` 的产出契约，以它为格式基准，不新造一套目录风格
2. 解析设计稿，提取页面结构与可交互元素
3. 按生效快照的前端技术栈生成原型代码（**不自行选型**）
4. **补齐 `data-fr` 标记**：对照需求功能分析，为每个可交互元素标注它服务的 `FR`
5. 无法确定归属的元素 → 列入「待人工确认」清单，**不猜**
6. 设计稿里有需求功能分析中没有的功能 → 停止并报告，不自行取舍（见「失败处理」）
7. 申请 `PAGE` 编号并补进原型规划
8. 自检同构性（见下），**任一项不满足就报告**
9. 回写批次状态文件：本步骤置 `done`，登记原型工程路径、页面清单与哈希
10. 输出标记补齐说明（含待人工确认清单）

### 同构性自检（产出后必做）

| 项 | 要求 |
|---|---|
| 可运行 | 能启动、主流程能走通 |
| `data-fr` 标记 | 每个可交互元素带，且取值是合法 `FR` 编号 |
| 目录结构 | 与 03-prototype 的产出同构（不新造一套目录风格） |
| 页面清单 | 已在 `原型规划.md` 中登记 `PAGE` 编号 |

**任一项不满足就报告，不要"先这样，反正能看"** —— 04-prd 是按格式解析的，
格式不一致的后果是 PRD 生成不出来，而那时已经过了原型确认这道门禁，返工要从头来。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始（本 Skill 与 03-prototype 并列，天然可单独调用）
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：产出物落到指定路径，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不做像素级复刻**。目标是**信息结构与交互路径**可验证，不是美术还原——
  配色、圆角、动效的实现成本高且一定会被真实实现替换
- 不产出 PRD（那是 `ai-requirement-04-prd`）
- **不猜测 `data-fr` 归属**。无法确定的元素一律列入待确认清单
- 不在设计稿与需求冲突时自行取舍
- **不自行选择前端技术栈**（从生效规范快照读）
- 不修改 `ai-requirement-03-prototype` 的产出
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 设计稿无法解析 | 说明需要哪种导出格式，停止 |
| 元素无法映射到任何 `FR` | 列入待确认清单；**若整个页面都映射不上，说明需求分析漏了这一块**——回去补 |
| 设计稿与需求功能分析冲突（稿里有需求没有的功能） | **停止并报告**。这可能是需求遗漏，也可能是设计稿画多了 / 画的是旧版本——两种都要人判断，不要自行取舍 |
| 目标技术栈不明确 | 提示先运行 `ai-spec-build`，中止 |
| 产出无法与 03-prototype 同构 | 报告差异点，不要强行交付 |

## 输出格式

执行完用下面结构回复：

```
设计稿：Figma 导出（3 个页面）
目标技术栈：fe-vue3-elementplus（来自生效快照）

产出页面：3 个
  PAGE-CORE-001 列表页    data-fr 标记 7 处
  PAGE-CORE-002 详情页    data-fr 标记 4 处
  PAGE-CORE-003 设置页    data-fr 标记 2 处

同构性自检：✅ 可运行 · ✅ 标记合法 · ✅ 目录同构 · ✅ 已登记 PAGE 编号

待人工确认：
  - 设置页「高级选项」折叠区，无对应 FR —— 需求功能分析中未列出
  - 列表页「批量操作」按钮，可能对应 FR-CORE-047（未确认）

冲突提示：
  - 设计稿含「报表订阅」入口，需求功能分析中无此项 —— 是需求遗漏还是设计稿版本较旧？
```
