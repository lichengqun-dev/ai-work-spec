# 设计稿转换要点

> 本文件承载**「为什么」**：从设计稿转原型时那几件"不这么做就会出事"的事，以及各自的代价。
> 「做什么」在 `SKILL.md` 的执行步骤里，不重复。

## 一、为什么不做像素级复刻

**不是像素级复刻。** 配色、圆角、阴影、动效的实现成本高，而且一定会被真实实现替换掉——
在原型阶段做它们是纯浪费。

判断标准只有一条：**业务方能否通过它确认「这就是我要的」**。

## 二、为什么必须与 `ai-requirement-03-prototype` 同构

这条比"好看"重要得多。`ai-requirement-04-prd` 靠遍历原型的 `data-fr` 标记生成 PRD：

```
04-prd 读原型 → 提取 data-fr → 逐个 FR 生成 PRD 章节
```

**两条路径（自画原型 / 外部设计稿）的产出必须格式一致**，否则 04-prd 只认其中一条。

格式不一致的后果不是"不好看"，而是 **PRD 生成不出来**——而那时已经过了原型确认这道门禁，返工要从头来。
所以动手前先读 `ai-requirement-03-prototype` 的产出契约，以它为格式基准。

## 三、为什么 `data-fr` 不能猜

设计稿里没有功能编号信息，要对照 `需求功能分析.md` 补齐：

```
设计稿元素                            → 需求功能分析
「导出」按钮                          → FR-CORE-045（列表页导出）
「筛选」下拉                          → FR-CORE-046（按分组筛选）
右上角「设置」图标                    → ❓ 需求功能分析里没有对应项
```

最后一类**列入「待人工确认」清单，不要猜**。

猜错的标记会让 04-prd 生成错误的功能章节，而错误会被下游一路放大：
需求错 → 设计错 → 代码错 → 测试按错的设计编用例且全部通过。

## 四、设计稿与需求冲突时为什么停下

设计稿里出现了需求功能分析中没有的功能时，**两种情况都有可能**：

| 可能 | 该谁处理 |
|---|---|
| 需求分析漏了这一块 | 回 `ai-requirement-02-analysis` 补 |
| 设计稿画多了 / 画的是旧版本 | 找设计方确认 |

**不要自行取舍。** 自行取舍的结果是原型里有一个"没人认领"的功能页，
而它会一路走到 PRD、设计、代码——直到有人问"这个功能谁提的"。
