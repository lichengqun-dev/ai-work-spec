# 检查项清单

> 执行器实现的全部检查项。**门禁定义里的 `auto:<id>` 必须在这里有对应实现**，
> 否则执行器会拒绝执行整道门禁。

核对方式：调用 `ai-gate-runner`，让它列出检查项库与实现状态（它会标出哪些被门禁引用、哪些没有）。

## 一、批次状态与产出物

| 检查项 ID | 校验什么 | 结果语义 |
|---|---|---|
| `state-steps-final` | `steps` 全部为 `done`/`skipped`/`failed`，且 `current_step` 在 `steps` 中 | 缺 `steps` 段 → fail；有步骤未终态 → fail |
| `artifacts-exist` | `artifacts` 中每个文件存在，且 `hash` 与登记值一致 | 缺文件 → fail；哈希不一致 → fail（说明产出物在确认后被改过） |

**为什么查哈希**：哈希不一致意味着"这个批次的产出物在确认之后被人改过"。此时归档会让追溯链记录一个不准确的状态。

## 二、追溯链（编号相关）

| 检查项 ID | 校验什么 | 数据来源 |
|---|---|---|
| `orphan-fr-no-req` | 功能编号总表「功能点」段每一行的「来源 REQ」列非空 | `projects/<项目码>/.agent/index/功能编号总表.md` |
| `no-orphan-ids` | 总表中登记的每个 FR 至少被一份产出物引用 | 总表 + 批次产出物 |
| `fr-coverage-design` | 范围内每个 FR 都出现在设计类产出物中 | 批次产出物 |
| `fr-design-section` | 范围内每个 FR 在设计文档中有**专属小节**（标题或 `§` 引用） | 批次产出物 |
| `fr-has-testcase` | 范围内每个 FR 有 `TC-FR-…-NN` 挂载 | 批次产出物 |
| `fr-has-commit` | 范围内每个 FR 在提交信息中出现 | 项目仓 git log |

**原型侧的两个（数据源是原型工程仓，不是文档仓）：**

| 检查项 ID | 校验什么 | 数据来源 |
|---|---|---|
| `data-fr-markers` | 原型工程中是否存在可统计的 `data-fr` 标记 | `prototype_repo` |
| `fr-coverage-prototype` | 范围内每个 FR 都有对应的原型元素 | `prototype_repo` + 批次产出物 |

**`fr-coverage-prototype` 有一条防"空集假通过"的守卫**：扫到 0 个 FR 时**判 `skip` 而不是 `pass`**。
理由很直接——"一个 FR 都没找到"和"所有 FR 都被覆盖了"在代码里长得几乎一样，
而前者恰恰是最该报出来的情况。同一族的编号检查目前还没有这条守卫，是本文件**已知的薄弱处**（见 §十二）。

**「范围」怎么定义**：本批次产出物中出现的 FR 编号，排除 `功能编号总表` 本身。这样不需要额外配置，范围随产出物自然确定。

**为什么 `fr-coverage-design` 和 `fr-design-section` 分两级**：前者是下限（契约、数据库设计里提到该 FR 也算），后者才是「有对应设计章节」的字面含义。后者定为 WARN，因为文档命名习惯千差万别，误报不该阻断交付。

## 三、接口契约

| 检查项 ID | 校验什么 |
|---|---|
| `api-has-fn` | 契约中每个 operation 能追溯到 FR（`x-fr-id` 字段；找不到字段时退一步：operation 描述或整份契约中出现 `FR-` 即算通过） |
| `api-error-codes` | 每个 operation 定义了至少一个 4xx/5xx 响应（或声明 `x-error-codes`） |
| `openapi-valid` | 契约结构：有 `openapi`/`swagger` 字段、`info.title`、`paths`；路径以 `/` 开头；每个 operation 有 `responses` |

**限制**：`openapi-valid` 只做结构校验，不是完整的规范校验器。完整校验建议在 CI 中追加：

```bash
npx @redocly/cli lint <需求名>/02_设计/接口契约.yaml
```

## 四、数据库设计

| 检查项 ID | 校验什么 |
|---|---|
| `ddl-rollback` | 数据库设计产出物中同时存在 DDL（`CREATE TABLE` / `ALTER TABLE`）与回滚方案（`回滚` / `ROLLBACK` / `rollback.sql`） |
| `db-field-comments` | `CREATE TABLE` 内每个字段带 `COMMENT`，或存在 `COMMENT ON COLUMN`（达梦写法） |

**为什么回滚是 BLOCK**：上线出问题时没有时间现场推导回滚语句。回滚脚本必须在变更前写好（符合 `STD-BASE-311`）。

## 五、代码与提交

| 检查项 ID | 校验什么 |
|---|---|
| `commit-format` | 最近 30 个提交（**跳过合并提交**）符合 `<type>(<scope>): <subject>`，且 subject 或 body 含 FR 编号 |
| `secrets-externalized` | 代码仓配置类文件中无硬编码凭据（**跳过构建产物目录**） |

**为什么跳过合并提交**：合并提交是 Git 自动生成的（`Merge branch 'x' into 'release'`），
人**不可能**给它写 type/scope 和 FR。不跳过它们，这项检查会对所有走合并流
（GitLab MR / GitHub PR）的仓库全红——而团队唯一能做的"修复"就是把这道门禁关掉。
排除合并提交不影响追溯：**真正带 FR 的是被合并的那些业务提交**，它们仍在历史里。

**为什么跳过构建产物目录**：`target/`、`node_modules/`、`dist/` 等里面是**源文件的副本**。
扫它们会让同一处问题被重复计数——真实案例：某项目密钥扫描报了 134 处，
其中近半来自 `target/classes/` 下的 `application.yml` 副本。**重复计数把清单变长，而长清单没人会读完。**

**密钥扫描的白名单**：`${...}`、`<...>`、`xxx`、`your…`、`example`、`placeholder`、`****`、`change_me`、含"见配置"/"环境变量"字样的值会被跳过——它们不是真实凭据。扫描范围排除 `test/sample/example/readme` 路径。

**已知取舍**：这是窄口径扫描，宁可漏报也不误报。误报会让团队学会忽略这条检查，那比漏报更糟。

## 六、需求与交付文档

| 检查项 ID | 校验什么 |
|---|---|
| `req-acceptance-quantified` | 需求类产出物的「验收」章节含可判定要素（数字 / 阈值 / 状态码 / 强制词） |
| `decision-recorded` | 设计类产出物中至少出现一个 `DEC-` 编号 |
| `rollout-plan-present` | 交付类产出物存在且含回滚方案 |

`req-acceptance-quantified` 是启发式检查（找数字与强制词），所以定为 WARN——它可能漏判，但不该阻断。

## 七、测试与缺陷（依赖产出物格式约定）

| 检查项 ID | 校验什么 | 数据来源与格式约定 |
|---|---|---|
| `testcase-executed` | 用例执行率是否 100% | 测试报告中的「用例执行率」字段，两种写法见 `ai-test-05-report` |
| `p0p1-closed` | 是否存在未关闭的 P0/P1 | 缺陷台账的表头 `\| 编号 \| 级别 \| 描述 \| 状态 \| 发现时间 \| 负责人 \|` |
| `regression-scoped` | 是否有回归范围产出物且其中含 FR | **路径**含「回归」的产出物，且正文含 FR 编号 |

**这类检查项有一个共同特征：它们的准确性取决于产出物的格式约定。**
字段名或表头一改，检查项只会报 `skip`/`无法解析`——于是"用例都跑完了吗""P0/P1 都关闭了吗"
又回到了"靠人说"的状态。所以格式约定写在各 Skill 的产出契约里，且标注了"不可改"。

**判定细节**：
- `testcase-executed`：找不到字段记 `skip`（不是 `pass`）；找到但无法解析记 `fail`；
  执行率 < 100% 记 `fail`，并在明细里带上"未执行 N 条"（若报告中有该信息）
- `p0p1-closed`：表头缺「级别」或「状态」列记 `skip`（**不猜列含义**，猜错会把"有未关闭的 P0"误报成通过）；
  状态取值中「已关闭 / 已转待办 / 已验证」算已关闭

## 八、`external` —— 不在执行器职责内的检查项

检查项的结果有**四种**，`external` 与 `skip` 的区别是整个机制的关键：

| 结果 | 含义 | 材料能补吗 | 能否签核 |
|---|---|---|---|
| `pass` | 自动校验通过 | — | — |
| `fail` | 自动校验不通过（可定位） | — | 修好重跑 |
| `skip` | **缺校验材料** | **能**——补了执行器就能自动校验 | **不能**（BLOCK 级）。签核的前提是「有人核对过了」，材料不存在时无从核对 |
| `external` | **不归它查** | **不能**——补材料没用 | **能**，但**必须附证据**（`--evidence`） |

**当前四个 `external` 项：**

| 检查项 | 为什么不在执行器职责内 | 人要做什么 |
|---|---|---|
| `lint-passthrough` | 静态检查要按项目自己的配置执行。执行器不跑任意命令、不假设项目的构建工具 | 在项目仓跑 lint，把结果写进评审记录，签核时用 `--evidence` 指出它记在哪 |
| `unit-coverage-report` | 覆盖率报告由项目侧构建工具生成，格式因工具而异，无稳定约定可解析 | 生成报告、核对核心模块分支覆盖，签核时用 `--evidence` 说明报告在哪、结论是什么 |
| `fr-coverage-prototype` | **原型由需求方外部提供**时，本项目不存在带 `data-fr` 标记的原型工程，执行器无从扫描 | 人工核对「每个 FR 在原型里都有对应交互」，签核时用 `--evidence` 给出原型链接 / 文件名 |
| `data-fr-markers` | 同上 | 同上 |

**为什么必须有 `external` 这个状态。** 没有它时，这四项只能挂 `skip`；而其中 `lint-passthrough` 与
`fr-coverage-prototype` 都是 **BLOCK 级**，BLOCK 级 skip 拒绝签核 —— 于是两道门禁**结构上永远无法 `passed`**：

| 项 | 卡住的门禁 | 后果 |
|---|---|---|
| `lint-passthrough` | gate-04 | 每次都必须走 `--waive`，**豁免从"例外通道"变成"常规通道"** |
| `fr-coverage-prototype` / `data-fr-markers` | gate-02 | gate-02 是 `waivable: no`——**连豁免都不许，整条流程卡死在原型确认** |

后者更严重。**「原型由需求方外部提供」是合法情形**（存量系统的功能增强、客户已给精确原型），
但知识库原先的模型假设"每个批次都由 `ai-requirement-03-prototype` 产出原型"，没考虑这一种。
补材料也补不出来——那不是"暂时缺"，是"这份材料在本项目里不会存在"。

**为什么 `external` 允许签核、`skip` 不允许。** 判据是「这件事有没有人的判断可依赖」：

- `skip`：材料根本不存在 → 没有人核对过任何东西 → 签核下去，记录显示"已通过"，而它什么都没查
- `external`：人**可以**真的去跑 lint、看覆盖率报告、核对原型覆盖 → 判断有依据 → 签核成立，但要把依据写下来

**所以 `external` 项的签核强制要求 `--evidence`。** 不要求的话，"我跑过 lint 了""原型确认过了"就是
无成本的口头话，这条门禁会退回成走过场——和它没实现时一样没用，只是更隐蔽。

**还有一项有条件 `skip`：** 密钥扫描（主条目见 §五）在项目仓未挂载时记 `skip`——
它属于「缺材料」那一类，补上仓库路径执行器就能自动校验。

## 九、仓库路径字段（多仓分离）

manifest 有五个路径字段，`repo` 是兜底：

| 字段 | 谁在用 |
|---|---|
| 字段 `repo` | 兜底：未填下面几项时，都用它 |
| 字段 `docs_repo` | **产出物路径基准**（`artifacts` 的解析根） |
| 字段 `prototype_repo` | **原型相关检查项的扫描根**（`fr-coverage-prototype`、`data-fr-markers`） |
| 字段 `code_repo` / `code_repos` | **提交与密钥扫描的根**（`commit-format`、`fr-has-commit`、`secrets-externalized`）。单仓用前者，多仓用后者（列表） |

**为什么要分开**：这几类仓的角色不同。早期版本只有一个 `repo`，在双仓库模型（文档仓 + 独立原型工程仓）下
必然撞墙——把 `repo` 指向文档仓，原型覆盖率就扫不到 `data-fr`；指向原型仓，产出物路径又全部解析不到。
更隐蔽的是：指错之后 `fr-coverage-prototype` 可能变成**假通过**（扫到 0 个 FR 却判成功）。

### 多代码仓（`code_repos`）

**前后端分仓是常态，一个 `code_repo` 装不下。** 用列表声明全部代码仓：

```yaml
code_repos:
  - /path/to/backend
  - /path/to/frontend
```

每条检查项对这两个仓的处理不同，这是刻意的：

| 检查项 | 多仓行为 |
|---|---|
| `commit-format` | **逐仓统计**，报告带仓名前缀（`[后端仓] a1b2c3d 「…」格式不符`）。两个仓的提交规范往往本来就不同，混在一起报数让人无法定位 |
| `fr-has-commit` | **合并检索**。一个 FR 的实现可能跨前后端，只要在**任一**仓的提交里出现即算关联 |
| `secrets-externalized` | 扫描全部仓，结果里的相对路径**带仓名前缀**——否则两个仓里的同名文件分不清是哪个 |

**只要有一个仓读不到提交历史，`commit-format` 与 `fr-has-commit` 就记 `skip` 而不是 `pass`。**
这是 `skip ≠ pass` 的直接应用：这两项的结论是**全量判断**，少读一个仓就等于少判一个仓，
而"我只检查了一部分"和"我检查完了没问题"必须能被区分开。
漏掉一个仓的后果不是"报了 0 个问题"，是**根本没扫、也不留痕迹**。

## 十、签核的边界：什么能签、什么不能

签核（`--confirm`）的前提只有一句：**有人核对过了**。所以判据是「有没有人的判断可依赖」，
而不是「这一项是不是自动校验的」。

| 情形 | 能不能签核 | 为什么 |
|---|---|---|
| 自动项 `pass` | 不需要签核 | — |
| 自动项 `fail` | 不能 | 先修好 |
| `人` 标注的项 | **能**，须给真实姓名 | 项本身就是要人判断 |
| `external` 项 | **能**，且**必须给 `--evidence`** | 人能真的去跑 lint、看覆盖率报告；但依据必须写下来 |
| `skip` 项（材料不存在） | **不能**（BLOCK 级会被拒） | 没有人核对过任何东西 |
| `skip` 项（材料存在但执行器不开箱） | 见下 | 这类现在归 `external`，不再是 skip |

**BLOCK 级 `skip` 会被执行器拒绝签核**，两条出路：补齐材料后重跑，或走 `--waive`。
这条规则是 2026-10-20 一次端到端演练后补上的：演练中 gate-04 在**零提交**下、
gate-05 在**零用例执行**下被签核通过——「提交带 FR」「用例跑完了吗」「P0/P1 关闭了吗」三件最想守住的事，
证据全是空的。门禁自己反复讲的「skip ≠ pass」，在机制上被抵消了。

**注意上表第一行与倒数第二行的区别。** 早期实现把"东西在、只是执行器不开箱"（静态检查、覆盖率报告）
也记成 `skip`，于是它们被那条 BLOCK 规则一起挡在签核之外——**gate-04 因此永远无法通过**。
2026-10-20 引入 `external` 把这两类分开后，gate-04 才回到"可签核"，同时证据要求反而更严了（必须有 `--evidence`）。

## 十一、跳过与兜底的边界

有些检查项**刻意没有实现**，而是留给人工，因为它们需要判断力：

- 「业务目标明确」「干系人已确认」——需求准入的本质是人的决策
- 「技术方案符合分层架构规范」——需要读懂方案，不是匹配关键词
- 「是否引入新的中间件」——关键词命中"新增依赖"会产生大量误报
- 「无 N+1 查询」「事务内是否发起远程调用」——需要读代码逻辑

把这些做成 auto 会得到两种坏结果之一：**误报阻断交付**（团队会关掉门禁），
或**开一个宽松到永远通过的口子**（等于没有检查）。两者都比老实留给人更糟。

## 十二、已知薄弱处

**这份清单与执行器必须一一对应。** 对不上的后果是：清单说"查过了"，而执行器其实没查。

`ai-spec-check` 会做**双向差集**（"实现有清单缺"与"清单有实现无"两边都查），
所以这一节只需记录**检查器查不到的**限制。

### 空集假通过（2026-10-20 已修，但规律要记住）

**在"什么都没找到"的情况下判 `pass`，是本执行器最危险的一类 bug。**

两个数一对比就看出来了：
- "扫到 0 个对象，所以全部都达标" —— 逻辑上成立，语义上是灾难
- 而"扫到 0 个对象"本身，恰恰是最该被报出来的情况

已修的三处：`fr-coverage-prototype`（0 个 FR → skip）、`orphan-fr-no-req`（占位行 → skip）、
`no-orphan-ids`（同上）。

`orphan-fr-no-req` 这处值得记住，因为它**坏得很隐蔽**：占位行 `_示例_ FR-XXX-001` 会被算进
"有 N 行功能点"，却在校验时被 `FR_RE.fullmatch` 跳过。于是"有行、但一行都没验"报成了
"N 行功能点均有来源 REQ"。**计数与校验用了两套口径**，这是这类 bug 的共同形态。

**新增检查项时先问一句**：如果它要扫的对象一个都没有，我返回的是什么？
若答案是 `pass`，那多半就是下一个空集假通过。

### 其他已知限制

- **豁免的"到期自动复查"未实现。** 复查日期会被写入 `waivers` 段，但没有任何代码在到期时提醒。
  现阶段豁免的复查靠人记。
- **没有保留验证夹具。** 拦截行为在开发期用夹具逐条验证过，但仓库内没有这些夹具，
  该结论目前不可复核。要让它可信，需要把夹具入库并纳入常规验证。
