# ai-requirement-03-prototype · 原型设计

## 能力声明

依据需求功能分析产出**原型规划**与**可运行的原型工程**，页面上每个可交互元素带功能编号标记。

原型是 PRD 的**事实源**——PRD 是原型的文字化，不是原型是 PRD 的配图。
这个顺序反过来，能消除大量"文档说 A、原型是 B"的扯皮。

**不做什么**：不做视觉设计、不写业务逻辑、不产出 PRD——见「边界」。

## 何时用 / 何时不用

- **用**：需求功能分析已产出（每个功能有 `FN` 编号），要规划页面清单并产出可运行的原型工程时
- **不用**：已有 Figma / Axure 设计稿 → `ai-figma-axure-convert`（产出格式必须与本 Skill 同构）；
  原型已产出、要写 PRD → `ai-requirement-04-prd`；要实现真实的业务逻辑 → 编码域

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 需求功能分析 | `ai-requirement-02-analysis` 产出 | 是 | 每个功能有 `FN` 编号 |
| 批次上下文（L3 CLAUDE.md） | 文档仓 | 是 | 存在 |
| 前端技术栈包 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 用于确认目标技术栈与组件约定 |
| 原型工程仓 | `ai-requirement-01-init` 产出 | 是 | 存在且可运行 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 原型规划 | 文档仓 `<需求名>/01_需求/原型规划.md` | 页面清单 + `PAGE` 编号 + 页面与 FN 的映射 |
| 原型工程页面 | 原型工程仓 | 每个可交互元素带 `data-fn="FN-XXX-000"` |
| 原型与功能映射表 | 文档仓 `<需求名>/01_需求/原型与功能映射.md` | `PAGE` → `FN` 对照 |

产出结构：

```markdown
# 原型规划

## 一、页面清单
| PAGE 编号 | 页面名称 | 承载的 FN | 复用 / 迁移自 |

## 二、页面与功能映射
| PAGE 编号 | FN 编号 | 说明 |
```

**每个可交互元素必须带 `data-fn` 标记**：

```html
<button data-fn="FN-CORE-045" class="btn-primary">导出</button>
```

这不是给浏览器看的，是给 `ai-requirement-04-prd` 看的——PRD 靠遍历这些标记来生成功能章节。
**没有标记，PRD 就生成不出来，整个"读原型生成 PRD"的机制失效。**

## 前置条件

**hard（不满足则拒绝执行）**

- 需求功能分析已产出，每个功能有 `FN` 编号（没有 `FN` 就没有 `data-fn` 的取值域）
- 原型工程仓存在且可运行（目标落点；未建时先走 `ai-requirement-01-init`）
- 生效规范快照能读出目标前端技术栈（读不出时提示先运行 `ai-spec-build`，**不要自行选一个技术栈**）

**soft（不满足则提示，可继续）**

- 批次上下文（L3 CLAUDE.md）缺失：提示先执行 `ai-requirement-01-init`，
  照常产出并在产出物顶部标注「未经上游确认 —— 批次上下文缺失」
- gate-01 需求准入尚未通过 / 尚未运行：照常产出，产出物标注「未经上游确认 —— gate-01 未通过」
- 组件清单为空骨架 / 无可复用组件：**跳过"先匹配"**，直接按需求规划页面，并在报告中说明

## 执行步骤

**执行顺序（顺序很重要）：先匹配 → 再迁移 → 后调整 → 完整性检查 → 验证修复**

1. 读需求功能分析，规划页面清单，申请 `PAGE` 编号
2. **先匹配**：查知识库根下 `09_资产库/组件库/前端组件清单.md`，看已有组件能否覆盖需求。
   **不要一上来就画新页面**——项目里大概率已经有 80% 相似的页面或组件
3. **再迁移**：基于最接近的已有页面改造，而不是从零构造；迁移时保留原有的布局骨架与交互模式
4. **后调整**：按需求功能分析调整字段、交互、流程
5. **完整性检查**：每个 `FN` 是否都有页面承载？每个页面是否有明确的 `FN` 归属？
   字段与需求功能分析是否一致？不满足的项记入问题汇总，不要强行造页面凑数
6. 生成原型代码，**为每个可交互元素加 `data-fn` 标记**
7. **验证修复**：启动原型工程确认能跑通，主流程要能完整走完
8. 每批次使用**独立的原型副本**，不覆盖历史批次的原型
9. 回写状态文件：`prototype` 步骤置 `done`，登记 `原型规划.md`、原型工程路径、`PAGE` 编号

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始（补一个页面、重出一版原型都成立）
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（如未接入批次）时：原型副本与规划文档落到指定路径
  （副本目录自定，但要在报告中写明），跳过状态回写并在报告中说明

## 边界（明确不做）

- 不做视觉设计（配色、图标、精细排版）——原型验证的是**信息结构与交互路径**，不是美术
- 不写业务逻辑（原型用静态数据即可）；**不在原型里实现真实接口调用**
- 不做响应式适配（除非需求明确要求）
- 不产出 PRD（那是 `ai-requirement-04-prd` 的职责）
- 不修改需求功能分析（发现的矛盾记入问题汇总，由人在别处解决）
- **不要自行选择前端技术栈**（从生效规范快照读）
- 不要因为"这样更好看"而偏离目标技术栈的组件体系
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 某 FN 无法映射到页面 | 记录到问题汇总，不强行造页面 |
| 原型工程无法启动 | 报告错误但保留已生成代码，由人排查环境问题 |
| 目标技术栈不明确 | 提示先运行 `ai-spec-build`；**不要自行选一个技术栈** |
| 历史批次原型已存在 | 新建本批次独立副本，不覆盖 |
