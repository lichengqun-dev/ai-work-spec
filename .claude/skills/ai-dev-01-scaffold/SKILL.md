# ai-dev-01-scaffold · 工程骨架

## 能力声明

依据架构设计产出**工程骨架**：模块划分、目录结构、构建配置、依赖声明。

**不实现任何业务逻辑。** 骨架的价值是让后续每个 FR 的实现有明确的落点，而不是把代码写一半。

**不做什么**：不建表、不写 Mapper、不实现接口、不升级既有工程的技术栈——见「边界」。

## 何时用 / 何时不用

- **用**：契约冻结后，把架构设计的模块划分落成工程结构时——新工程从零搭，既有工程增量补模块
- **不用**：只是往既有模块里加一个类（直接走 `ai-dev-02-backend` / `ai-dev-03-frontend`）；
  技术栈升级（走独立批次评估，不走本 Skill）
- **既有工程非空**：仍走本 Skill，但走增量分支——只补缺失的模块

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 架构设计 | `ai-design-01-arch` 产出 | 是 | 含模块划分与依赖方向 |
| 接口契约 | `ai-design-04-api` 产出 | 是 | **必须处于冻结态** |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 目录组织、分层、构建配置从这里读 |
| 既有工程 | 项目仓 | 否 | 增量开发时读取，**不得重建既有结构** |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 工程骨架 | 项目代码仓 | 目录、模块、构建配置、依赖声明 |
| 骨架说明 | 项目文档仓 `<需求名>/03_实现/工程骨架说明.md` | 模块职责与目录对应关系 |

工程骨架的产出结构：

```
<项目代码仓>/
├── <模块 1>/
├── <模块 2>/
└── <构建配置>
```

骨架说明里给出**模块 ↔ 目录 ↔ 职责**的对应表。下游的 backend / frontend Skill 靠它决定代码该落在哪，
**没有这张表，不同的人会把同一个功能放进不同的模块**。

## 前置条件

**hard（不满足则拒绝执行）**

- 架构设计已产出（含模块划分与依赖方向）
- **接口契约已产出且处于冻结态**——契约未定就搭骨架，模块划分大概率要返工
- 生效快照中对应维度的规范包存在（目录组织、分层、构建配置从它读）
- 目标代码仓存在且可写（骨架要落到那里）

**soft（不满足则提示，可继续）**

- gate-03 设计评审已通过（未通过时产出物标注"未经评审"）

## 执行步骤

1. 读架构设计的模块划分，映射成目录 / 模块结构
2. 按生效快照的目录组织规范创建骨架（**不自行发明目录风格**）。
   快照没规定时**遵循既有工程的风格**——在骨架说明里记录你观察到的相对一致的约定
3. 声明依赖：只引入架构设计明确需要的依赖，**不"顺便"加常用库**
4. 配置构建：版本号、编译目标等从快照读——最易出问题的是**编译目标**与 **API 命名空间**两处
5. 产出骨架说明（模块 ↔ 目录 ↔ 职责）
6. 目标工程非空时走**增量分支**：只补缺失的模块，不重建既有结构
7. 回写批次状态文件：本步骤置 `done`，登记 `<需求名>/03_实现/工程骨架说明.md` 与哈希

### 测试框架要特别处理

测试框架属于架构设计应当明确的内容，**不是"可选的常用库"**。架构设计里没提时**停下询问**，不要跳过——
`ai-dev-04-unittest` 的前置条件要求项目仓有可运行的测试命令；
骨架阶段漏掉它，单元测试那一步就没法执行。
（这不是把责任推给下游，而是这一步就该问清楚。）

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— <哪一条没满足>」
- 批次状态文件不可写（未接入批次）时：产出物落到指定路径、跳过状态回写并在报告中说明

## 边界（明确不做）

- **不实现任何业务逻辑**——可以有目录、模块声明、构建配置、空的核心类（启动类、配置类），
  但**不应该**有任何业务方法，哪怕"顺手实现一下最简单的那个 FR"
- 不建表、不写 Mapper、不实现接口
- **不引入架构设计未提及的依赖**——不要"顺便"加上常用的工具库、日志库
- **不升级既有工程的技术栈**——增量开发时"顺手升个版本"是事故高发区；版本由生效快照锁定
- 不改既有模块的目录结构；**不以"统一风格"为名重构既有目录结构**
- 不执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 契约未冻结 | 拒绝执行，提示先完成 `ai-design-06-review` |
| 架构设计的模块与既有工程冲突 | 输出冲突点，交人决策，**不自行取舍** |
| 需要引入规范包未覆盖的依赖 | 停止并说明——**新增依赖需要先确认它是否在规范覆盖范围内**，否则后续无约束可依；设计里没提到但确实需要的，先问，不要自己加 |
| 架构设计未提及测试框架 | **停下询问**，不要跳过（`ai-dev-04-unittest` 依赖项目仓有可运行的测试命令） |
| 既有工程已有不同的目录风格 | 遵循既有风格并在骨架说明中记录，**不以"规范"为名重构既有结构** |
