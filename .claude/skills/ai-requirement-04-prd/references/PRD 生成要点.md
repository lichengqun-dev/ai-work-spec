# PRD 生成要点

> 本文件承载**「为什么」**：读原型生成 PRD 时那几件"不这么做就会出事"的事，以及各自的代价。
> 「做什么」在 `SKILL.md` 的执行步骤里，不重复。

## 一、为什么必须"从原型生成"，而不是"照需求再写一遍"

**原型是事实源，PRD 是原型的文字化。**

不要从需求功能分析"重新写一遍需求"——那样会写出一份**与原型不一致**的文档。
正确做法是遍历原型，把页面上实际存在的东西描述出来。

顺序绝不能反过来（先写 PRD 再画原型）。反过来必然产生"文档说 A、原型是 B"的扯皮，
而且没人能判定哪个对。

## 二、待确认事项为什么只能原样带入

`需求问题汇总.md` 里的未解决问题，**原样列进 PRD 的「待确认事项」节**。

**不要自行填补，也不要删掉它们。** 一份"看起来很完整"的 PRD 比一份明确写着
"这里还没确定"的 PRD 危险得多——前者会让人以为都想清楚了。

## 三、PRD 与原型不一致时为什么以原型为准

因为原型是**业务方确认过的**那份东西（gate-02 确认的是原型，不是文字）。
以原型为准，并把不一致处单独列出供人复核——复核的是"原型本身是不是要改"，那是 03 的事。

## 四、验收要点为什么不能写"显示正常"

**验收要点必须是可客观判定的标准**（`STD-BASE-204`）。
"显示正常""体验友好"这类表述无法判定，等于把"测试通过"这道门禁的判定依据抽掉了，
最终只能由人凭感觉说"可以了"，争议时无法仲裁。

## 五、某个 `FN` 在原型中体现不清，为什么不能跳过

跳过它，等于这个功能在 PRD 里**没有位置**：没有章节、没有验收要点，也没有"这里还没确定"的记录。
下一段流程只会看到一份结构完整的 PRD，看不出少了一块。

正确做法是**列出来让人确认**——列出来只是多一行字，跳过却是把一个已知的空白变成不可见。
