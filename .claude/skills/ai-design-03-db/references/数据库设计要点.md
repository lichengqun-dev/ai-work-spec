# 数据库设计要点

> 本文件承载**「为什么」**：回滚脚本与索引设计里那些"不这么做就会出事"的理由与正反例。
> 「做什么」在 `SKILL.md` 的执行步骤里，不重复。

## 回滚脚本不是"反过来写一遍"

真正要写的时候会发现有些变更**不可逆**：

| 变更 | 能否回滚 |
|---|---|
| 建表 | 能（DROP） |
| 加列（可空 / 有默认值） | 能（DROP COLUMN） |
| 加索引 | 能 |
| 删列 | **不能**——数据没了 |
| 改类型（缩小精度） | **不能**——截断的数据恢复不了 |
| 加非空列且无默认值 | 不能直接回滚（已回填的数据无法区分） |

遇到不可逆变更，**不要写一句假的"反向 SQL"糊过去**。明确标注「不可逆变更」并说明后果
（比如"执行后 3 个月内的历史数据无法恢复"），交由人确认。
**一个假装可回滚的脚本比没有回滚脚本更危险**——它会让审批的人以为退路已经准备好了。

## 索引设计：写清它覆盖的是哪个查询场景

为每个索引写清它覆盖的是哪个查询场景，而不是罗列字段：

- ❌ `IDX_STATUS (status)`
- ✅ `IDX_STATUS_CREATE_TIME (status, create_time)` —— 覆盖列表页「按状态筛选 + 按创建时间倒序」，避免排序回表

没有对应查询场景的索引不要建。索引是写入放大，建了不用的索引是纯成本。

## 字段注释为什么是硬要求

字段含义只存在于开发者记忆中时，人一换就成了**不可知数据**：没人敢改、没人敢删、
AI 也拿不到上下文（注释是 AI 生成代码与 SQL 时最关键的输入）。所以枚举型字段必须在注释里写明取值。
