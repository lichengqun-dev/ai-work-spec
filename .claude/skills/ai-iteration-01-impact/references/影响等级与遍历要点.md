# 影响等级与遍历要点 · ai-iteration-01-impact

> 本文件收纳"为什么这么判"的论证与正反例。**判据本身在 `SKILL.md` 的「影响等级的判定」与「执行步骤」**，
> 这里只回答"为什么定成这样"。判定等级、圈定范围、或复盘"等级判低了"时读。

## 为什么这一步值得用最强的模型

它判断错的代价是**线上故障**（回归不足）或**无谓返工**（过度设计）。
而且它判断错的后果会向下传递：等级定错了，后面的路径、范围、回归全都跟着错。

其余环节可以省，这一步不要省。

## 走这条链

```
新需求
  → 映射到已有的 FN（改行为 / 加字段 / 改交互）
    → 依赖关系图双向遍历
      → 受影响 FN 集合
        → 展开到接口 / 数据表 / 测试用例
          → 影响等级 + 建议路径
```

## 为什么"涉及表结构即为大"

表结构变更的影响面超出本项目范围：

| 影响 | 说明 |
|---|---|
| 数据迁移 | 存量数据如何转换，能否回滚 |
| 历史兼容 | 旧版本代码/接口读到新结构会怎样 |
| 回归范围 | 所有读写该表的 FN 都受影响，通常是一大片 |

把它当成"中"或"小"，是迭代流程里最容易出问题的一类低估——而且后果在回归阶段才暴露。

## 为什么必须双向遍历

```
        ┌─ 上游：依赖它的功能  ← 最容易漏
改动的 FN ─┤
        └─ 下游：它依赖的功能
```

改了底层能力 → 上层全部受影响。"改了 A 崩了 C"绝大多数是上游没遍历到。

## 为什么必须列出「不受影响的部分」

这不是凑字数。它有两个作用：

1. **防止设计蔓延**——本批次只碰 2 个模块，就不要顺手把另外 5 个模块也重新设计一遍
2. **让人能复核范围**——列出来了，别人才能说"不对，X 也受影响"

反过来，如果你列不出"不受影响的部分"，说明你对系统结构的理解还不够，应该先去读架构设计。

## 为什么"大"不能降成"中"

涉及数据模型或对外契约的变更，需要走完整的设计评审与契约冻结流程——
因为受影响的不只是本项目：契约变更影响前端与外部调用方，表结构变更影响存量数据。

把"大"降成"中"，等于跳过了 `02` 域的契约冻结，而前端可能已经按旧契约写完代码了。

## 需求映射不到已有 FN 时怎么分流

**不要默认按迭代处理。** 先确认：

- 改的是已有功能的行为 → 迭代（走变更子批次）
- 加一个原来不存在的能力 → **新建**（走 `01_需求设计` 的完整流程）

判断不了就问用户。走错流程的代价比多问一句大得多。

## 依赖关系图为空时为什么只能拒绝

**不要凭经验圈一个范围。** 拿出两条路让用户选：

1. 先补维护依赖关系图（可以从代码的模块依赖、接口调用关系、表读写关系反推，不必全量，够遍历即可）
2. 由人显式圈定影响范围，并在分析文件中标注"范围由人指定，非图遍历得出"

**"非图遍历得出"这个标注很重要**——它说明这份范围的可复核性低一档，回归时该更保守。

无图只能做全量回归或凭经验选，而两者都不该由 Skill 默默决定：让它猜一个范围然后看起来跑完了，
比让它停下来危险得多。
