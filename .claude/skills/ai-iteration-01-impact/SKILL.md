# ai-iteration-01-impact · 变更影响面分析

## 能力声明

输入一个新需求，输出**变更影响面**：受影响的 `FR`、接口、数据表、测试用例范围，以及影响等级。

**这是迭代流程的枢纽。** 它决定后面要不要重跑设计、回归测哪些、走哪条路径。
这一步做好了，迭代成本可控；做不好，团队要么过度设计（小改动走全流程），要么回归不足（改了 A 崩了 C）。

**不做什么**：不做设计（`ai-iteration-02-delta-spec`）、不决定要不要做（那是需求方的判断）、
不执行改动、不跑回归——见「边界」。

## 何时用 / 何时不用

- **用**：已有系统接到新需求（改行为 / 加字段 / 改交互），要圈定影响范围并定级时
- **不用**：全新功能——走新建流程（`01_需求设计`），不走迭代流程
- **不用**：已明确是小改动、要按快车道处理时（走 `ai-daily-01-fastlane` 的准入判定）
- **不用**：只是问问题、不产生任何改动（走 `ai-daily-04-qa`）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 迭代需求 | 用户提供 | 是 | 能判断出它改的是哪个已有功能 |
| 依赖关系图 | `projects/<项目码>/.agent/index/依赖关系图.md` | 是 | 非空；**为空时拒绝** |
| 功能编号总表 | `projects/<项目码>/.agent/index/功能编号总表.md` | 是 | 含已有 FR、接口、表 |
| 已归档批次产出物 | 项目文档仓 | 是 | 基线设计的来源 |
| 生效规范快照 | `projects/<项目码>/.agent/spec-effective/<项目码>.md` | 是 | 判断改动是否触及技术栈约束 |

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 影响面分析 | 项目文档仓 `<需求名>/迭代/<批次号>_影响面分析.md` | 受影响清单 + 影响等级 + 建议路径 |

**本 Skill 负责创建 `<需求名>/迭代/` 目录（若不存在）。** 它是迭代路径的第一步，
而 `ai-requirement-01-init` 只建 `<需求名>/00_批次` ~ `<需求名>/05_交付`（那是新建路径的骨架，
接入已上线项目时不会跑它）。同域后续 Skill（`02-delta-spec`、`03-change-control`）
都往这个目录写，谁先跑谁建——但**明确由本 Skill 承担**，避免"都以为对方会建"。

产出物里必须能被复核的四个量：**涉及几个 FR、几个接口、几张表、多少条测试用例**。

## 前置条件

**hard（不满足则拒绝执行）**

- **目标项目已接入**：`projects/<项目码>/.agent/project.yaml` 存在，且仓库路径填的是真实值（不是 `<占位>`）
- **依赖关系图非空**（`projects/<项目码>/.agent/index/依赖关系图.md`）——无图无法遍历，只能靠猜
- **已有基线**：该功能至少有一个**已归档批次**（全新功能应走新建流程，不走迭代流程）
- **能确定改动针对的是哪个已有 `FR`**（确定不了时向用户澄清，**不猜**）

**soft（不满足则提示，可继续）**

- 无。本 Skill 是迭代路径的第一步，没有"顺序性"前置——上面四条缺任何一条都是**做不了**，
  不是"没轮到"

## 执行步骤

1. 把需求映射到已有的 `FR`（可能涉及多个：改行为 / 加字段 / 改交互）
2. 从这些 FR 出发，按依赖关系图**双向遍历**，得到受影响 FR 集合
3. 展开到三类影响面：
   - **接口**：哪些 `API` 的请求/响应需要改
   - **数据表**：哪些 `TBL` 需要加列/改类型（**涉及表结构即为"大"**）
   - **测试用例**：受影响的 `TC` 集合（供回归使用）
4. 判定影响等级，给出建议路径。**判据必须量化**：涉及几个 FR、几个接口、几张表
5. 列出**不受影响的部分**（防止设计蔓延，也让人能复核范围）
6. 回写批次状态文件：本步骤置 `done`，登记影响面分析文件、影响等级与建议路径

### 影响等级的判定（决定后续走哪条路）

| 等级 | 判据 | 后续路径 |
|---|---|---|
| **小** | 单个页面或单个接口；不涉及数据模型；不涉及对外契约 | 快速通道（`ai-daily-01-fastlane`） |
| **中** | 跨模块，但不改架构与数据模型 | 增量设计 → 增量开发 → 回归 |
| **大** | 触及架构、数据模型，或对外契约 | **转完整流程**，回到 `02_概要详细设计` |

**不要写"这个改动不大"这种话。** 判据要能被别人复核——那个判断在赶工时永远倾向于"不大"。

### 双向遍历：上游最容易漏

改了底层能力 → 上层全部受影响。"改了 A 崩了 C"绝大多数是**上游**没遍历到。
遍历的两种方向、以及为什么"不受影响的部分"必须显式列出，见 `references/影响等级与遍历要点.md`。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- 本 Skill 没有 soft 前置——不存在"没轮到"的情形
- 批次状态文件不可写（如未接入批次、或范围由人工圈定的例外情形）时：
  产出物落到 `<需求名>/迭代/<批次号>_影响面分析.md`，跳过状态回写并在报告中说明

## 边界（明确不做）

- **不做设计**（那是 `ai-iteration-02-delta-spec`）
- **不决定要不要做**——那是需求方的判断
- 不执行改动、不跑回归
- 不改依赖关系图里已有的关系
- 不要在没有依赖图时凭经验圈范围
- 不要只遍历下游
- 不要把涉及表结构的改动判成"中"或"小"
- 不要把"大"降级成"中"来省流程
- 不要在需求映射不到 FR 时默认按迭代处理
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 依赖关系图为空 | **拒绝执行**，说明无图只能猜范围。给出两条路：① 先补维护依赖关系图（可从代码的模块依赖、接口调用关系、表读写关系反推，不必全量，够遍历即可）；② 由人显式圈定影响范围，**并在分析文件中标注"范围由人指定，非图遍历得出"**——该标注说明可复核性低一档，回归时该更保守 |
| 需求映射不到已有 FR | 澄清：这是改已有功能（迭代），还是加新功能（新建）？**不默认按迭代处理** |
| 判定为"大"（触及数据模型或契约） | **明确输出"建议转完整流程"**，不要为了省事降到"中" |
| 需求描述本身不清晰 | 输出待澄清清单，中止 |

## 输出格式

```
需求：给列表页的导出增加「按分组维度筛选」

映射到的已有 FR：
  - FR-CORE-045（导出入口）—— 改行为
  - FR-CORE-020（列配置）—— 加字段

依赖图遍历（双向）：
  上游（依赖上述 FR 的）：FR-CORE-052 列表页、FR-CORE-061 报表
  下游：FR-CORE-010 权限校验

受影响清单：
  接口：API-CORE-008（请求体加 groupId）、API-CORE-021（列配置）
  数据表：无变更
  测试用例：11 条

影响等级：中
  判据：跨 4 个 FR、2 个接口；未涉及数据模型与对外契约
  建议路径：增量设计 → 增量开发 → 回归

不受影响：门户首页、消息中心、审批流（无路径可达）

待澄清：无
```
