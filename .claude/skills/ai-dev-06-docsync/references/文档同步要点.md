# 文档同步要点

> 本文件承载**「为什么」**：这道工序为什么不能省、哪些变更必须停下、以及最重要的那条红线。
> 「做什么」在 `SKILL.md` 的执行步骤与边界里，不重复。

## 一、这件事为什么不能省

知识库死掉的方式几乎总是同一个：**文档只在开始时写一次，之后代码改了文档没改。**

两周后，有人照着文档做，发现跟实际不符；再两周后，没人再看文档。
于是维护文档的成本还在，价值已经归零。

**这道工序就是防止这件事。** 它很枯燥，但它是知识库"可信"的唯一保证。

## 二、判断变更是否影响文档

对每处代码变更问一句：**行为变了吗？**

| 变更性质 | 例子 | 改文档吗 |
|---|---|---|
| 纯重构 | 提取方法、重命名变量、调整类结构 | ❌ 不改 |
| 格式 / 风格 | 格式化、import 顺序 | ❌ 不改 |
| 性能优化（行为不变） | 加缓存但结果一致 | ❌ 不改 |
| **行为变了** | 异常处理方式改了、边界条件改了、新增了分支 | ✅ 更新功能详细设计对应章节 |
| **契约变了** | 新增 / 修改接口字段 | ⛔ **停止** |
| **表结构变了** | 加列、改类型 | ⛔ **停止** |

## 三、契约与表结构变更必须停下

这两种变更的影响面超出本项目：

| 变更 | 谁受影响 |
|---|---|
| 契约变更 | 前端、测试脚本、外部调用方 |
| 表结构变更 | 数据迁移、回滚方案、历史数据兼容 |

**文档同步是单向的"代码 → 文档"回流。** 契约与表结构变更需要的是
"多方确认 → 变更 → 全员同步"，走变更子批次（`<原批次号>-C<n>`）。

把后者塞进文档同步，等于绕过了变更流程——而绕过的那一次，
恰恰是前端已经按旧契约写完代码的那一次。

发现这类变更时：停止，明确告知用户需要开变更子批次并通知前后端负责人。

## 四、最重要的红线：不要让文档迎合实现

有一种情况必须区分清楚：

| 情况 | 特征 | 处理 |
|---|---|---|
| 设计过时了 | 设计写的是旧做法，实现按新共识走了 | ✅ 更新文档 |
| **实现偏离了设计** | 设计是对的，实现做错了 | ⛔ **停止并报告** |

第二种情况下改文档，等于**把缺陷洗成了设计**——它从此消失，再也没人会发现。
而且下一次有人照着"更新后"的文档做，会重复同一个错误。

判断不了时**问用户**：这个改动是有意为之，还是实现走偏了？

## 五、为什么只改受影响的章节

不要"顺便优化措辞"。文档同步的 diff 应该能一眼看出"哪些行为变了"——
如果 diff 里混着大量措辞调整，评审者无法判断这次同步到底改了什么实质内容。
