# ai-iteration-04-release · 发布说明与上线步骤

## 能力声明

产出**发布说明**与**上线步骤（含回滚方案）**，并对齐版本号。

**回滚方案与上线步骤一同产出，不是可选项。** gate-05 的 `rollout-plan-present` 是 BLOCK 级检查项。

**不做什么**：不执行部署、不修改缺陷状态、不判断"能不能上线"（那是 gate-05 的事）、
不做上线后的验证——见「边界」。

## 何时用 / 何时不用

- **用**：测试报告已产出、准备上线，要组织上线步骤 + 回滚方案 + 发布说明 + 版本号时
- **不用**：判断"能不能上线"——那是 gate-05 在本 Skill **之后**做的事
- **不用**：执行部署（运维 / 发布的职责）；上线后的验证（回归，属 `ai-test-03-execute`）

## 输入契约

| 输入 | 来源 | 必需 | 校验规则 |
|---|---|---|---|
| 测试报告 | `ai-test-05-report` 产出 | 是 | 含上线建议 |
| 变更登记 | `ai-iteration-03-change-control` 产出 | 是（迭代路径） | 含变更项与基线 |
| 数据库设计 | 本批次产出物 | 否 | 含 DDL 与回滚脚本时用于组织上线顺序 |

**注意：本 Skill 不依赖 `ai-archive-01-close`。** 归档在本流程里是**本 Skill 之后**的一步
（第 23 步 vs 第 22 步），把它当上游会形成环。FR 清单从 `projects/<项目码>/.agent/index/功能编号总表.md` 读即可。

## 产出契约

| 产出 | 路径 | 格式 |
|---|---|---|
| 上线步骤 | 项目文档仓 `<需求名>/05_交付/上线步骤.md` | 步骤 + **回滚方案** |
| 发布说明 | 项目文档仓 `<需求名>/05_交付/发布说明.md` | 面向使用方的变更说明 |
| 版本号 | 项目代码仓 | 按项目版本约定更新 |

产出结构——上线步骤：

```markdown
# 上线步骤

## 一、前置检查
- [ ] 数据库备份已完成
- [ ] 回滚脚本已验证可用

## 二、执行步骤

| # | 步骤 | 执行人 | 预计耗时 | 可逆 |
|---|---|---|---|---|
| 1 | 执行 DDL（TBL_APP_EXPORT 建表） | DBA | 1 min | 是 |
| 2 | 发布后端服务 v1.2.0 | 运维 | 5 min | 是 |
| 3 | 发布前端资源 v1.2.0 | 运维 | 3 min | 是 |
| 4 | 执行数据清洗脚本 | DBA | 10 min | **否** |

## 三、回滚方案
| 步骤 | 回滚操作 | 耗时 | 备注 |
|---|---|---|---|
| 1 | DROP TABLE TBL_APP_EXPORT | 1 min | — |
| 2 | 回滚到 v1.1.9 | 5 min | — |
| 3 | 回滚前端资源 | 3 min | — |
| 4 | **无** | — | 数据已被覆盖，需从步骤 0 的备份恢复 |
```

产出结构——发布说明（**读者是使用方，不是开发者**）：

```markdown
# 发布说明 v1.2.0

## 新增
- 列表页支持按分组维度导出

## 行为变化
- 导出结果新增「分组」列（**兼容性影响**：依赖固定列序的下游脚本需调整）

## 注意事项
- 单次导出上限 1 万条（超出会分片下载）

## 已知限制
- 3 条用例因第三方沙箱不可用未执行，恢复后 24 小时内补测
- P2 缺陷 1 条转入下批次：导出文件名为英文
```

**遗留风险必须写，且不弱化。** 发布说明是使用方唯一的知情渠道，
把风险藏着，等于让他们在不知情的情况下承担后果。

## 前置条件

**hard（不满足则拒绝执行）**

- 测试报告已产出，且上线建议不是"不建议上线"
- 有 DDL 变更时，其回滚脚本已存在（`ai-design-03-db` 产出）

**soft（不满足则提示，可继续）**

- 迭代路径下变更登记已产出（新建路径本项不适用）。缺失时照常产出，
  并在产出物顶部标注「未经上游确认 —— 迭代路径缺变更登记」

**这里刻意*不*要求「gate-05 已通过」。** 本 Skill 的产出正是 gate-05 第 4 项
`rollout-plan-present`（BLOCK）的校验对象——要求 gate-05 先通过会形成死锁：
门禁要的文件，只有"门禁已通过"才能产出。

「不带着未关闭的 P0/P1 上线」这条约束**由 gate-05 在本 Skill 之后强制执行**，不靠前置条件。
顺序是：`test-report` → **`release`（产出方案）** → **gate-05（校验方案 + 测试结论）** → 真正上线 → `archive`。

## 执行步骤

1. 读测试报告的上线建议与遗留风险，**原样带入发布说明**（不美化）
2. 组织上线步骤，按依赖排序：
   - DDL 与数据迁移在前，服务发布在后
   - 多个服务时标注发布顺序
   - 标注**不可逆步骤**（如删列、数据清洗）
3. 产出回滚方案：对应每一步的反向操作
4. 产出发布说明：面向使用方的变更描述（做了什么、有什么影响、需要注意什么）
5. 版本号按项目约定更新
6. 回写批次状态文件：本步骤置 `done`，登记上线步骤、发布说明与哈希

### 产出物必须落在「交付」路径下

gate-05 的 `rollout-plan-present` 是 BLOCK 级，它**按路径关键词**找交付类产出物：
`<需求名>/05_交付/上线步骤.md`、`<需求名>/05_交付/发布说明.md`。

放在别的目录（如 `<需求名>/04_测试/`）会让检查项报"没有交付类产出物"。
**那个告警是对的**——上线方案放在测试目录下，发布时没人会去那里找。

### 不可逆步骤：标注，不要假装能回滚

处理方式，按优先级：

1. **前置备份**——能备份的先备份，并把恢复步骤写进方案
2. **明确标注**——在表格的「可逆」列标"否"，并说明"执行后 X 不可恢复"
3. **写 `无`，不要写假的反向 SQL**

写一句 `-- 反向：ALTER TABLE ...` 看起来能回滚、实则无效，会让人在有退路的心态下执行不可逆操作。
**一个假装可回滚的方案比明说"回不去"危险得多。** 哪些变更不可逆、为什么，见 `references/上线方案要点.md`。

## 独立执行

- **hard 全满足即可单独运行**，不必从流程第一步开始
- soft 不满足时照常产出，并在产出物顶部标注「未经上游确认 —— 迭代路径缺变更登记」，
  状态记 `partial`
- 批次状态文件不可写（如未接入批次）时：产出物落到 `<需求名>/05_交付/`，
  跳过状态回写并在报告中说明

## 边界（明确不做）

- **不执行部署**。只产出方案，执行是运维/发布的职责
- 不修改缺陷状态（那是 `ai-test-03-execute`）
- 不美化遗留风险（测试报告里写了什么就带什么）
- 不做上线后的验证（那是回归验证，属 `ai-test-03-execute`）
- 不要**自己去判断**能不能上线——那是 gate-05 的事，你只把方案写出来
- 不要把上线方案放在非「交付」路径下
- **不要为不可逆步骤写假的反向 SQL**
- 不要在发布说明里省略或弱化遗留风险
- 不要自行假定多服务的发布顺序
- 不要执行 git 操作

## 失败处理

| 失败情形 | 处理 |
|---|---|
| 测试报告缺失 | **拒绝执行**，提示先跑 `ai-test-05-report` |
| 存在不可逆步骤 | 明确标注「不可逆」并说明后果，**不写假的反向操作** |
| DDL 缺回滚脚本 | 拒绝执行，回到 `ai-design-03-db` 补齐 |
| 测试报告建议"不建议上线" | 拒绝组织上线，输出报告中列出的未关闭项 |
| 多服务发布顺序不明确 | 停下询问，**不自行假定顺序** |

## 与其他 Skill 的关系

- 上游：`ai-test-05-report`（必备）、`ai-iteration-03-change-control`（迭代路径）
- **下游不是归档，而是门禁**：本 Skill 产出 gate-05 要校验的上线方案（`rollout-plan-present`，BLOCK）。
  归档（`ai-archive-01-close`）在 gate-05 通过、真正上线之后
- 再下游：执行部署（人工 / 运维）→ `ai-archive-01-close`
- 门禁：`rollout-plan-present`（BLOCK，按「交付」路径产出物 + 回滚方案解析）
