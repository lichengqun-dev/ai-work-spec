# 指令：架构设计与技术选型

## 开始前

读三个东西：PRD、生效规范快照（`projects/<项目码>/.agent/spec-effective/<项目码>.md`）、现有系统结构（增量开发时）。

**技术栈从快照读，不要自己选。** 快照里没有的技术，说明它不在本项目的规范覆盖范围内——
此时应停止并说明，而不是"先用着"。用了没有规范包覆盖的技术，等于后续所有产出都失去约束依据。

## 产出结构

```markdown
# 架构设计

## 一、非功能需求
| 类别 | 要求 | 依据 |
| 性能 | 列表页 P95 ≤ 800ms（1 万条） | PRD 非功能需求章节 |

## 二、模块划分
| 模块 | 职责 | 依赖 |
|---|---|---|

## 三、依赖方向
（依赖关系图或矩阵；标注禁止的依赖方向）

## 四、决策记录
### DEC-XXX-001 <决策标题>
**决策**：……
**被否决的选项**：……（及为什么不选）
**理由**：……
**影响范围**：……
```

## 这一阶段最容易出错的三件事

**一、把"选型"当成"列出技术"。**
`**被否决的选项**` 这一项不能省。半年后有人问"为什么不用 X"，答案在这里；没有它，那次决策就是不可复核的，也就没人敢改。

**二、非功能需求缺失时自行假定量级。**
"预计日均几万条"和"预计日均几百万条"对应完全不同的架构。写下假定量级看起来让方案完整了，实际是把错误藏进了地基——返工成本最高的一类错误。**写不出量级就记入待澄清，不要假定。**

**三、让架构跟着功能走。**
本批次只涉及 3 个模块，就不要顺手把另外 5 个模块也重新设计一遍。在设计方案里明确写出**不涉及哪些模块**，这个清单的价值是防止设计蔓延。

## 决策记录的编号与检查

决策编号 `DEC-<模块码>-<3位>`，向 `projects/<项目码>/.agent/index/功能编号总表.md` 申请（或按项目约定登记）。

**gate-03 会校验设计类产出物中至少存在一个 `DEC` 编号**（检查项 `decision-recorded`，WARN 级）。
这不是格式要求——没有决策记录，架构文档就只是一份结论，无法回答"为什么是这样"。

## 完成后

回写批次状态文件：把本步骤置 `done`，在 `artifacts` 中登记 `<需求名>/02_设计/架构设计.md` 及其哈希。

## 你绝对不要做的事

- **不要做技术选型。** 技术栈由快照决定；确需调整则停止并说明，走知识库流程
- 不要设计表结构、接口、页面（那是 03/04/05 的职责）
- 不要假定非功能需求的量级
- 不要执行 git 操作
