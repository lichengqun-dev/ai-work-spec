# 指令：功能详细设计

## 开始前

读 PRD、架构设计、需求问题汇总，以及生效规范快照中的分层约束。

## 最硬的一条要求

**每个 FN 一节，标题写成 `## FN-XXX-000 <功能名称>`。**

这条不是排版要求，有三个具体原因：

1. **下游按编号读段落，不读全文。** 处理 `FN-CORE-045` 时只读该节，不读整份详细设计——否则上下文预算立刻爆掉
2. **gate-03 的 `fn-design-section` 检查项校验它。** FN 既不是标题也不带 `§` 引用时，该检查项报 WARN
3. **覆盖率可机械统计。** 标题形式是唯一能可靠解析出"哪些 FN 有设计"的形式

反例（都会导致上面三件事失效）：
```markdown
## 3.2 列表导出（FN-CORE-045）        ← 不是标题开头，解析不出
### 导出相关设计                       ← 标题里没有编号
### FN-CORE-045、FN-CORE-046 合并写       ← 一个成了、一个没成
```
正例：
```markdown
## FN-CORE-045 列表导出
```

## 每节要写四件事

| 项 | 要求 | 写不出来时 |
|---|---|---|
| 时序 | 调用链与关键交互 | 标注"信息不足"，列出缺什么 |
| 状态流转 | 有哪些状态、允许/禁止的迁移 | — |
| 异常分支 | 失败、无权限、状态冲突、并发冲突 | **记入待澄清，不要编** |
| 边界条件 | 数据量上限、时间范围、并发量级 | 同上 |

**异常分支是缺陷最集中的地方，也最容易"顺手编一个"。** 编出来的异常处理会被当成确定需求往下实现，而它与真实业务规则大概率不符——这类错误到测试阶段才暴露，且很难判断是需求错了还是实现错了。

## 交叉校验（必须做）

产出后逐个对照 PRD：

- PRD 里的每个 FN，本文件有对应小节吗？
- 本文件里有没有 PRD 中不存在的 FN？

**两边对不上就拒绝完成**，列出差异。多出来的 FN 往往意味着凭空造了需求；少了的意味着漏了设计。

## 边界

- **不设计表结构、不定义接口。** 时序里写"调用订单查询能力"，不写 `orderMapper.selectByCondition(req)`——那是 04-api 与代码阶段的事
- **不给实现建议**（用什么注解、哪个工具类）。技术细节在生效快照里，不在这里
- 不改 PRD

## 待确认事项原样带入

PRD 的「待确认事项」节，**原样复制到本文件的同一节**，不要删、不要自行回答。

## 完成后

回写批次状态文件：本步骤置 `done`，在 `artifacts` 登记 `docs/02_设计/功能详细设计.md` 与哈希。

## 你绝对不要做的事

- 不要为了"看起来完整"而补全异常分支与边界
- 不要合并多个 FN 进一节
- 不要在标题里省略编号（写成 `## 列表导出` 是不行的）
- 不要执行 git 操作
