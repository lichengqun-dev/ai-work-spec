# 指令：接口契约设计

## 开始前

读功能详细设计、数据库设计、编号总表。技术栈细节从生效快照读。

## 三个必须写进契约的字段

gate-03 有三个自动检查项直接校验契约，**不满足就是构建失败**：

### 1. `x-fn-id` —— 每个 operation 必须能追溯到 FN

```yaml
paths:
  /api/v1/export:
    post:
      operationId: exportList
      x-fn-id: FN-CORE-045          # ← 必须有
      summary: 列表导出
```

检查项 `api-has-fn`（BLOCK）：没有这个字段，且 operation 描述里也找不到 FN 编号时，报孤儿接口。

**孤儿接口往往意味着需求分析漏了东西，或设计时凭空加了一个。** 两种情况都值得停下来看。

### 2. `responses` 里的 4xx/5xx —— 每个 operation 必须有错误响应

```yaml
      responses:
        "200":
          description: 导出成功
        "403":
          description: 无权限
          content: { application/json: { schema: { $ref: '#/components/schemas/Error' } } }
        "409":
          description: 数据状态冲突
```

检查项 `api-error-codes`（WARN）：只有 200 的接口，前端无法给出准确提示，只能显示"系统错误"；
测试也无法针对性地设计异常用例。

**错误码是契约里信息密度最高的部分。** 别只写一个通用的 500。

### 3. 结构完整性

检查项 `openapi-valid`（BLOCK）：`openapi` 版本字段、`info.title`、`paths` 齐全；
路径以 `/` 开头；每个 operation 有 `responses`。

完整规范校验建议在 CI 中追加：`npx @redocly/cli lint <需求名>/02_设计/接口契约.yaml`

## 字段类型必须与数据库设计一致

契约里的字段类型、长度、可空性，要和 `数据库设计.md` 对齐。不一致时**以数据库设计为准并报告冲突**，
不要自行取舍——自行取舍的结果是前端按契约写、后端按库表写，联调时才发现。

## 契约冻结的语义

契约在本步骤产出，**在 gate-03 通过后冻结**。

冻结意味着：**此后任何变更都需要通知前后端双方，并重跑受影响的下游步骤。**

冻结后的修改不在这里做——要走变更子批次（`<原批次号>-C<n>`），原批次产出物保持不可变。
这个设计的价值是：你永远能回答"联调那一刻的契约是什么样"。

**如果发现契约需要变更，不要偷偷改。** 明确告诉用户：这需要开变更子批次并通知前端负责人。

## 只描述跨边界的调用

契约里只放**跨进程/跨前后端**的接口。内部方法签名不属于契约——把它们写进来会让契约变成
一份会随时过期的代码副本，而契约的价值恰恰在于稳定。

## 完成后

1. 回写批次状态文件：本步骤置 `done`，登记契约文件与哈希
2. 在 `projects/<项目码>/.agent/index/功能编号总表.md` 的接口段登记：`API` 编号、路径、所属 FN、契约版本

## 你绝对不要做的事

- 不要省略 `x-fn-id` 与错误响应——这会让门禁失败，且失败是对的
- 不要把内部方法签名写进契约
- **不要在冻结后直接改契约**
- 不要实现接口
- 不要执行 git 操作
