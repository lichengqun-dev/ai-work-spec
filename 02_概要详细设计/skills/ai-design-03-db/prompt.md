# 指令：数据库设计

## 开始前

读功能详细设计、架构设计、生效规范快照中 `db` 维度的规范包（本仓库默认 `db-dm8`）。

**没有 `db` 规范包就停下。** 达梦 DM8 的方言与 MySQL 有实质差异（CLOB 读取、空串与 NULL 不等价、
`CONCAT` 只接受两参数、模式名大小写敏感）——套用 MySQL 习惯会写出**能编译但语义错误**的 SQL。

## 产出结构与两份硬性要求

```markdown
# 数据库设计

## 一、表结构

### TBL_XXX_MAIN
| 字段 | 类型 | 允许空 | 默认 | 说明 |

```sql
CREATE TABLE TBL_XXX_MAIN (
  id BIGINT COMMENT '主键',
  status INT COMMENT '状态：1-草稿 2-已提交 3-已归档'
);
```

## 二、索引
| 索引 | 字段 | 覆盖的查询场景 |

## 三、回滚脚本
```sql
DROP TABLE TBL_XXX_MAIN;
```

## 四、迁移顺序
```

**要求一：每个字段必须有注释，枚举型写明取值。**
gate-03 的 `db-field-comments` 会校验（WARN）。这不是格式洁癖——字段含义只存在于开发者记忆中时，
人一换就成了不可知数据；而且注释是 AI 生成代码与 SQL 时最关键的上下文来源。

**要求二：DDL 与回滚脚本成对产出。**
gate-03 的 `ddl-rollback` 是 **BLOCK** 级：有 DDL 但没回滚方案，门禁不通过。

## 回滚脚本不是"反过来写一遍"

真正要写的时候会发现有些变更**不可逆**：

| 变更 | 能否回滚 |
|---|---|
| 建表 | 能（DROP） |
| 加列（可空 / 有默认值） | 能（DROP COLUMN） |
| 加索引 | 能 |
| 删列 | **不能**——数据没了 |
| 改类型（缩小精度） | **不能**——截断的数据恢复不了 |
| 加非空列且无默认值 | 不能直接回滚（已回填的数据无法区分） |

遇到不可逆变更，**不要写一句假的"反向 SQL"糊过去**。明确标注「不可逆变更」并说明后果
（比如"执行后 3 个月内的历史数据无法恢复"），交由人确认。**一个假装可回滚的脚本比没有回滚脚本更危险。**

## 索引设计

为每个索引写清它覆盖的是哪个查询场景，而不是罗列字段：

- ❌ `IDX_STATUS (status)`
- ✅ `IDX_STATUS_CREATE_TIME (status, create_time)` —— 覆盖列表页「按状态筛选 + 按创建时间倒序」，避免排序回表

没有对应查询场景的索引不要建。索引是写入放大，建了不用的索引是纯成本。

## 涉及已有表的变更

**必须走变更子批次**（`STD-BASE-601`），不得直接改写已归档的设计文档。
原批次产出物不可变，是为了回答"上线那一刻的业务规则是什么"。

## 你绝对不要做的事

- 不要写 Mapper / SQL 查询逻辑（编码阶段的事）
- 不要写没有查询场景对应的索引
- **不要为了通过门禁而补一个假的回滚脚本**
- 不要在有破坏性变更时默默继续
- 不要执行 git 操作
