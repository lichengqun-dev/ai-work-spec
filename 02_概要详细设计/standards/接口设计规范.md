# 接口设计规范

## STD-BASE-321 · 接口必须定义错误码

<!-- meta
tier: resident
scope: 接口契约
frozen: false
-->

**规则**：每个接口必须定义完整的错误码集合（业务错误 + 参数错误 + 权限错误），错误码需在契约中列出，不得只返回通用的 500。

**正例**：契约中明确列出 40001 参数非法 / 40301 无权限 / 40901 状态冲突

**反例**：接口只返回 `{code: 500, msg: '系统错误'}`

**原因**：前端无法据此给出准确提示，只能显示「系统错误」；测试也无法针对性地设计异常用例。错误码是接口契约中信息密度最高的部分。

---

## STD-BASE-322 · 契约冻结后变更必须走变更流程

<!-- meta
tier: resident
scope: 接口契约
frozen: false
-->

**规则**：接口契约一旦在设计评审时冻结，任何变更必须开变更子批次并通知前后端负责人，不得单方面修改。

**正例**：契约变更 → 开 `-C1` 子批次 → 通知前端 → 更新双方

**反例**：后端开发时觉得字段名不合适「顺手改一下」

**原因**：契约是前后端并行开发的唯一依据。契约一改，前端基于旧契约写的所有代码都要返工，而这类返工通常在联调时才被发现，代价最高。

---

## STD-BASE-323 · 列表接口必须分页且设上限

<!-- meta
tier: indexed
scope: 接口设计
frozen: false
-->

**规则**：返回集合的接口必须支持分页，且分页大小由服务端设上限，不信任前端传值。

**正例**：请求含 `pageNum` / `pageSize`，服务端 `pageSize` 上限 200

**反例**：接口一次返回全部数据，靠前端截断

**原因**：全量返回在数据量增长后会导致接口超时与内存溢出，且这个改动**无法在客户端不知情的情况下做**，将来补分页会变成破坏性变更。
