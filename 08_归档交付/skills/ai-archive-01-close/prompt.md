# 指令：批次结项与归档

## 先跑门禁，不手工判断

```bash
S=07_质量门禁/skills/ai-gate-runner/scripts/gate_run.py
python3 $S --project <项目码> --batch <批次号> --gate gate-06
```

自动检查项交给执行器；**人工项原样列出，不替人判断**；结果 `failed` 就停下。

## 断链检测：五类都要查

这是本 Skill 的核心动作。**不要在门禁通过后跳过它**——门禁的 `fn-has-commit` 在项目仓不是 git 仓库时只能记 `skip`，那时断链数在门禁视图里显示为 0，而实际上只是"没查"。

| 类型 | 判据 | 级别 |
|---|---|---|
| 无 REQ 来源的 FN | 总表「来源 REQ」列为空 | **BLOCK** |
| 无设计章节的 FN | 该 FN 未出现在设计类产出物中 | **BLOCK** |
| 无测试用例覆盖的 FN | 该 FN 没有挂载的 `TC` | **BLOCK** |
| 无对应提交的 FN | 该 FN 未出现在任何提交信息中 | WARN |
| 孤儿编号 | 总表有登记但无任何产出物引用 | WARN |

**BLOCK 类非 0 → 拒绝归档。WARN 类非 0 → 归档，但写进结项报告的「遗留问题」节。**

分级的理由：前两类是"东西缺了"，后两类是"没能证明它在"。
后者可能是环境问题（没接 git、产出物命名不同），前者不是。

## 断链了不要"顺手补上"

补链意味着补文档或补用例——**那是人的工作**。

脚本能做的只是把断链指出来并定位到具体对象：

```
❌ FN-CORE-047 没有挂载用例
   定位：功能详细设计 §FN-CORE-047 存在，但测试用例文件中无 TC-FN-CORE-047-*
   → 需补充用例，或确认该 FN 是否应被拆掉
```

**"补上一条用例让它通过"是最坏的处置**——它把一次真实的覆盖缺口变成了记录上的一个数字。

## 回填总表的三列

本 Skill 负责填这三列，此前它们的负责人没有定义：

| 列 | 填什么 | 来源 |
|---|---|---|
| 覆盖用例 | `TC-FN-XXX-000-NN` | 测试用例文件 |
| 提交 | commit hash 或 PR 号 | 代码仓 git log（按 FN 编号反查） |
| 批次 | 本批次号 | 当前批次 |

**只填真实值。** 查不到的留空并在结项报告的遗留问题里写明——**不要填"待补"这种占位**，
它会让人以为之后有人会补。

## 结项报告：遗留问题节最重要

报告的价值不在于证明批次完成，而在于**告诉下个接手的人当时有哪些已知但没解决的事**。

```markdown
## 六、遗留问题与技术债

| # | 问题 | 影响 | 处置计划 | 负责人 |
|---|---|---|---|---|
| 1 | 3 条用例因第三方沙箱不可用未执行 | FN-CORE-047 的对接受阻未验证 | 沙箱恢复后 24 小时内补测 | 张三 |
| 2 | FN-CORE-046 无提交关联（项目仓未接 git） | 无法回答该功能由哪次提交上线 | 接入 git 后重跑 gate-06 | 李四 |
```

**不要把遗留问题写得含糊。** "部分功能待完善"没有任何信息量；
"3 条用例未执行、涉及 FN-CORE-047、原因是沙箱不可用"才能被处置。

## 归档后状态文件只读

置 `archived: true` 并记录时间。此后任何修改请求都应被拒绝。

**已归档的状态文件不得删除**——追溯链依赖它。这是全局红线之一。

## 提示提升候选

归档时若本批次产生了项目特有条目，提示运行 `ai-spec-promote` 分析是否达到提升阈值
（同一条约束出现在 ≥3 个项目 → 建议提升为共享包条目）。

## 完成后

1. 结项报告写入 `docs/05_交付/结项报告.md`
2. 总表回填完毕
3. 状态文件 `archived: true`
4. 输出摘要

## 你绝对不要做的事

- **不要补链**（补文档、补用例）来让断链归零
- **不要在 BLOCK 类断链未清零时归档**
- 不要在门禁 `failed` 时继续
- 不要手工改产出物来满足哈希校验
- **不要删除已归档的状态文件**
- 不要在总表里填"待补"这类占位
- 不要执行 git 操作
