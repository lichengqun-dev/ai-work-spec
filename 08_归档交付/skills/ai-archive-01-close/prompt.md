# 指令：批次结项与归档

> ⚠️ **本 Skill 尚未实现（P2 阶段交付）。** 收到调用请求时明确告知用户未实现，
> **不得假装执行**。当前请按 `08_归档交付/templates/批次结项报告模板.md` 人工结项。

## 实现时应遵循的约束

### 1. 断链检测是本 Skill 的核心，不是附加项

五类断链必须全部检查并输出明细（见 `00_工作空间配置/命名与编号规范.md` 第 9 节）：
无 REQ 来源的 FN / 无设计章节的 FN / 无测试用例覆盖的 FN / 无对应提交的 FN / 孤儿编号。

**断链非 0 时不能"顺手补上"。** 补链意味着补文档或补用例，那是人的工作。
脚本能做的只是把断链指出来并定位到具体对象。

### 2. 产出物哈希校验

状态文件 `artifacts` 段记录了每个产出物的哈希。结项时要逐个核对：

| 情况 | 处理 |
|---|---|
| 哈希一致 | 通过 |
| 哈希不一致 | **拒绝归档**，提示"产出物被外部修改"，由人决定是否重跑上游 |
| 文件缺失 | 拒绝归档，指出缺哪个 |

哈希不一致意味着"这个批次的产出物在确认之后被人改过"——此时归档会让追溯链记录一个不准确的状态。

### 3. 归档后状态文件只读

置 `archived: true` 并记录归档时间。此后任何修改请求都应被拒绝。

**已归档的状态文件不得删除**——追溯链依赖它。这是全局红线之一。

### 4. 不生成"漂亮"的结项报告

结项报告要如实反映遗留问题、豁免记录、断链情况。**不要把遗留问题写得含糊**——
报告的价值在于让半年后的人知道当时有哪些没做完的事，而不是让当下看起来完美。

### 5. 提示提升候选

归档时若本批次产生了"项目特有条目"，提示运行 `ai-spec-promote` 分析是否达到提升阈值。

## 你绝对不要做的事

- 不要在未实现时假装执行
- 不要自动补链（补文档、补用例）
- 不要在断链非 0 时静默归档
- 不要删除任何已归档的状态文件
- 不要执行 git 操作
